** OPEN #483 Build and install til natively on a Windows host (make, make install)

Filed while planning [[./472.org][#472]] and [[./473.org][#473]]: the question was whether a
Windows-installed til exists to compare against the Linux and macOS ones.
It does not yet. Read from the source at master 9a71a09; nothing here was
run on Windows.

*** What does not work

- ~make~, and therefore ~make install~: the Makefile sets ~HOST_OS~ for
  ~Linux~ and ~Darwin~ only and stops any other host with "unsupported
  build host ...: til builds on Linux and macOS". The bootstrap
  (~til_boot~ from ~boot/~, the vendored libffi and nng, ~bin/make~) never
  starts.
- The only Windows compiler is ~bin/til.exe~ cross-built on Linux
  (~make build_win_host~) and handed to the Windows runner as an artifact.
  There it interprets, translates, and builds and runs small programs with
  the native gcc. It has never built ~src/til.til~ there, and no step runs
  ~til.exe install~.

*** What exists but has never executed on Windows

- ~src/self/install.til~: ~default_install_prefix~ returns
  ~C:/Program Files/til~ on a Windows host, and the support tree copies
  ~.dll~ twins instead of ~.so~. ~make.til::run_install~ ->
  ~copy_compiler_install~ uses it, with ~TIL~ spelled ~bin/til~ (no
  ~.exe~).
- ~codegen/ext.c~ has Win32 branches for ~copy_file~ / ~copy_tree~ /
  ~mkdir_p~; ~install.til::drop_shared_write~ returns early on Windows.
- ~test/install.til~ (install under ~tmp/~, then compile and run a program
  with the installed compiler from another directory) runs in the Linux
  and macOS suites only.

*** Known requirements

- Installing the compiler copies the HOST target's vendored archives and
  their loadable twins (libffi, raylib, tinyfiledialogs, secp256k1 under
  ~build-windows-x64~). Today only the Linux cross build produces them;
  the runner receives the raylib, tinyfd and secp256k1 ones as artifacts
  and no libffi.
- ~C:/Program Files~ needs elevation. Tests stay unprivileged: they
  install with ~--prefix~ under the checkout's ~tmp/~.
- Drive letters and backslashes reach the source path the compiler bakes
  into ~__LOC__~ and private C names. What is baked is #472's source
  identity decision; this issue only has to deliver a working install.

*** Steps

1. With the imported ~til.exe~ on the Windows runner:
   ~til.exe install --prefix=tmp/install_test~ for a program, then the
   compiler support install; fix what fails.
2. ~til.exe build src/til.til~ with the native gcc against the
   windows-x64 libffi and nng, then the same from the committed ~boot/~ C
   without an imported compiler.
3. Makefile and ~make.til~ accept a Windows host (the MSYS/MinGW ~uname~
   spellings, ~.exe~ names, host target ~windows-x64~), so ~make~ and
   ~make install~ work.
4. ~test/install.til~ on Windows in CI, then the suite subset that needs
   no POSIX-only tool (#473 step C4).

*** Progress

The goal, decided 2026-11-15: plain ~make~ and ~make install~ work on
Windows like on the other hosts, from an MSYS2 MinGW shell, with nothing
special for the user. Remote sessions have no Windows host, so CI's
~windows-x64-native~ job is the test bench: each merge shows how far the
native build gets, and the next commit fixes that.

  - [X] The Makefile's bootstrap seam accepts an MSYS2 MinGW host
    (~MINGW*~ / ~MSYS*~ ~uname -s~): gcc, the Windows link flags of every
    til program (~-Wl,--export-all-symbols -lpsapi~), and ~.exe~ names
    for ~bin/til_boot~ and ~bin/make~.
  - [X] make.til names the compilers it builds with the host's suffix
    (~EXE~ from ~host_os()~): a Windows til checks files through Win32,
    which does not add ~.exe~ the way an MSYS2 shell does.
  - [X] CI ~windows-x64-native~: pacman's MinGW gcc and cmake, ~make~,
    ~make install~ into ~C:/Program Files/til~, then the installed til
    interprets and runs a program from outside the checkout. In bring-up:
    ~continue-on-error~ and no cancel step until it passes once.
  - [X] First run (3105): the Makefile bootstrap worked on Windows --
    libffi configured and built, bin/til_boot.exe linked, bin/make.exe
    built and started ~all~ -- and stopped at ~make -C tmp/raylib-... clean~,
    which ran bin/make.exe itself: CreateProcess searches the running
    program's directory before PATH.
  - [X] Second round: make.til names GNU make ~mingw32-make~ on a Windows
    host (pacman ~mingw-w64-x86_64-make~) and passes raylib
    ~PLATFORM_SHELL=sh~; the host C compiler is ~gcc~; the windows-x64
    MinGW tools lose their cross prefix on that host; its interpreter
    twins are DLLs made by ~build_win_twin~ (libffi's too); host cmake
    builds use the "MSYS Makefiles" generator, since cmake would pick
    Visual Studio and "MinGW Makefiles" refuses sh on PATH.
  - [X] Checked under wine, without Windows' gcc: the compiler support
    install (~install_compiler_support~, its Win32 copies) fills
    ~<prefix>/lib/til~ with every windows-x64 archive and DLL twin, and the
    installed til.exe, run from outside the checkout, finds that tree and
    interprets a program.
  - [X] Run 3108: raylib (mingw32-make) and tinyfd built; nng stopped on
    ~implicit declaration of function 'timespec_get'~ -- an error since
    gcc 14, a warning in the cross gcc. nng requires the universal C
    runtime (its CMakeLists rejects "the legacy MinGW environments"), and
    MINGW64's gcc links msvcrt. Decided: the Windows build shell is MSYS2
    UCRT64 (pacman's ~mingw-w64-ucrt-x86_64-~ gcc, make and cmake). A UCRT
    host's nng twin does not import timespec_get from til.exe, which
    defines it only for msvcrt.
  - [X] Run 3110: MSYS2's ~uname -s~ is ~MINGW64_NT-...~ in the UCRT64
    shell too, so a check on the shell's name rejected the right shell.
    The Makefile now asks the compiler: on an MSYS2 host it requires the
    gcc on PATH to define ~_UCRT~, and otherwise stops naming UCRT64 and
    its gcc package. Both branches checked with ~make -n~ and a stand-in
    gcc.
  - [X] Why runs 3105-3110 were cancelled: the first round made make.til's
    ~TIL~ a computed constant (~format("bin/til", EXE)~), and
    ~Command(name = TIL)~ moved it into the goal list, which freed it; the
    Linux ~windows-x64 host~ job's ~make build_win_host win_server~ then
    ran a garbage program name and cancelled the run. The garbager's #415
    rule skipped constants on the assumption that they are literals.
    d226262 made make.til clone ~TIL~, ~ASAN~ and ~DEBUG~ there; the rule
    now rejects moving a computed constant out ("pass X.clone()").
  - [ ] Fix what the next runs report, until the job passes; then make it
    blocking like the others and document the Windows build (MSYS2
    UCRT64, the three pacman packages) beside the Linux and macOS ones.
