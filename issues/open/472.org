** OPEN #472 Deterministic builds independent of build host

*** Goal

CURRENT PLAN AND DECISIONS: the last section, "Plan to close". Where an
earlier section differs from it, that section wins; the earlier ones are
kept as the record of how the plan was reached.

A til build is a function of its inputs (source tree, target, flags), not
of the machine it ran on. Start with lexing through the pre-codegen boundary,
then establish reproducible emitted source and binaries under explicit input
contracts. Fix nondeterminism in the compiler/build pipeline at its source.

[[./473.org][#473]] separately owns cross-platform CI coverage, native/cross execution,
artifact collection and the eventual equality gates. Its functional CI work
can proceed now. Each equality gate depends on the relevant milestone here,
not on this entire issue being closed. This issue owns the frontend observation
contract and determinism regressions; #473 integrates them across producers.

[[./474.org][#474]] records eventual replacement of interpretation by native JITs and,
much later, removal of the GCC/Clang requirement. The determinism contract
applies to either compile-time execution engine. It must be established now,
not deferred until the JIT or native-backend migration; JIT host execution
still must not substitute host facts for the selected target's facts.

Today no CI job compares these outputs across hosts. The closest is
~self_translate~, which compares the compiler's generated C and forward
header with the local bootstrap output (or two local translations in the
explicit-width suite). Cross jobs check execution or file format instead.

*** Three levels, in order

1. *Lexing through the pre-codegen boundary.* First establish identical
   tokens, parsed program and prepared, typed/lowered program for identical
   source bytes, logical module identities, explicit target/backend and
   compile-time inputs. Stop before invoking a backend. Compare program
   structure and codegen-relevant facts, not raw heap addresses, padding or
   host interpreter storage. This is the FIRST milestone; choosing FASM or
   changing GCC/Clang flags cannot repair differences introduced here.
2. *The translator's output.* ~til translate~ for a target (the .c and
   _forward.h for C targets, .HC for TempleOS, .fasm for FASM, ...)
   is produced by til alone, so it must be byte-identical across hosts
   for the same source/compiler revision, target and configuration,
   independently of the host's C toolchain. This is entirely til's
   responsibility, after the frontend gate. Run it on every host for every
   supported target/backend, including all emitted companion files. Java
   files are currently generated library bindings, not a JVM Target entry.
3. *The binaries.* A compiled artifact also depends on the C toolchain
   and the sysroot. Two hosts can only agree when they use the same
   compiler version, linker, headers and libraries for that target. On
   macOS the native jobs use Apple's clang and ld, while the linux cross
   job uses upstream clang, lld and the vendored SDK-less headers
   (vendor/macos), so those two will not produce the same bytes and
   should not be expected to. The binary level therefore compares only
   hosts that use the SAME pinned toolchain for a target, and the issue
   should record which pairs those are.

*** Build contract

- Fix source and bootstrap revisions, dependency versions, target
  OS/architecture/ABI, CPU baseline, USize width, optimization and sanitizer
  settings. For binary comparisons, pin compatible host-native editions of
  the same compiler, linker and archive tools, plus the target sysroot/SDK
  and deployment target.
- Compare the same build stage and artifact set. Different targets, USize
  widths or other configurations are separate groups, not expected to hash
  alike. Include generated source, compiler binaries and runtime/core
  libraries explicitly in the comparison inventory.
- Define the boundary for packaging and signing. If signed or timestamped
  distribution wrappers cannot be reproduced, compare the exact pre-signing
  payload and state that boundary; do not silently strip or rewrite
  differing outputs just to make their hashes match.

*** Sources of nondeterminism to audit and remove

- Absolute paths. ~__LOC__~ strings and debug info carry the path the
  sources were read from; an installed til bakes its install path into
  libtilcore (see CLAUDE.md, "Compiler versions, installs, and shared
  core"). Builds from different checkout paths differ for that reason
  alone. Candidates: -ffile-prefix-map / -fdebug-prefix-map, or emitting
  repo-relative locations. C compiler prefix maps do not necessarily rewrite
  paths already emitted as til string literals; check the translator output
  as well as debug information. Decide explicitly how reproducibility and
  useful diagnostic paths coexist before changing location semantics or
  installation layout.
- Archive metadata. Non-deterministic archive modes can record timestamps,
  uids and modes; ensure deterministic mode (~ar D~ / ~-D~ where supported)
  wherever til or make.til builds an archive. Do not assume the same default
  for every implementation of ~ar rcs~.
- Locale, directory traversal and archive member ordering, generated code
  ordering, embedded dates and accidental host CPU detection.
- Build ids and linker-chosen identifiers (--build-id, Mach-O LC_UUID).
- Code signatures (Mach-O ad-hoc signing by lld or codesign) -- check
  whether they are stable for identical input.
- Vendored libraries (libffi, nng, raylib, secp256k1, ...) built by
  their own build systems, which may embed paths or dates; either pin
  their flags or exclude them from the comparison and say so.

**** Frontend pipeline and evidence

- *Lexing*: ~src/self/lexer.til::tokenize~ walks source bytes and emits
  token kind, start/length and line/column. Character classification uses
  explicit ASCII comparisons rather than locale-sensitive ctype calls.
  Compare source bytes as inputs and numeric token fields, never a raw
  ~Token~ memory image (start/length use the compiler's USize).
- *Parsing/loading*: ~parser.til::parse~ and ~loader.til::load_program~
  produce the canonical imported ASTs. Import discovery follows source
  child order and records dependencies before importers; it is not a
  directory scan. Modes/core/user imports all participate. ~SymbolPool~
  assigns IDs in intern order; its hash buckets are lookup storage.
- *Initialization/typing*: ~loader.til::type_program_errors~ resolves
  target aliases, expands namespace imports/lazy calls, initializes units,
  performs recursive type sweeps, instantiates generics, lowers constructs
  and validates ownership-related facts. Compile-time evaluation occurs
  during these passes, not just in one final constfolder pass.
- *Final preparation*: ~finish_init_and_type_program~ runs ownership
  destruction insertion and clears evaluation state. ~finish_prepare_program~
  calls ~constfolder_imported~, validates the entry point and scavenges.
  The shared boundary is the return from ~prepare_program~, before
  ~cmd_translate~ / ~builder.til::translate_ast~ dispatches to a backend.
  Backend configuration already affects preparation (~cptr32~, MLIR's ABI
  settings, etc.); compare a fixed backend as well as a fixed target.
- *Ordering already present*: core Map/Set use ordered storage, and #101
  moved synthesized-name counters into Context/per-definition scopes.
  Preserve these instead of assuming every map needs sorting. Audit any
  pointer-keyed analysis state and hash-table iteration for observable
  order; a pointer used solely for identity is not itself a determinism bug.
- *Confirmed host-layout dependency*: ~context.til::size_intrinsics_emit_sizeof~
  checks target widths/compression AGAINST the running compiler's layout.
  ~constfolder_classify_stmt~ uses that result to decide whether size
  methods/~dyn_size_of~ fold. The same target can therefore receive different
  lowered expressions from compact and native-layout compiler binaries.
  ~src/tests.til~ explicitly accommodates that difference in ~self_translate~.
  It is a frontend issue before any C optimization is considered.
- *Target-layout groundwork*: ~typer.til::target_value_size_align~ computes
  target facts separately from ~ctx.struct_layouts~ (host evaluation
  buffers); generator evaluation also has ~target_size_queries~. Reuse that
  separation, but audit coverage before applying it universally: the helper
  is not automatically a complete model of compressed pointers, SIMD,
  external C layouts and every backend ABI.
- *Paths already affect semantics*: ~context.til::display_path~ makes paths
  under cwd relative but leaves outside paths absolute. Private declaration
  identities are path-mangled in ~initer.til::init_private_names~. The typer
  resolves ~__LOC__~ to string literals. Stable logical source identity must
  be addressed before codegen, including installed core/std and Windows
  spelling. Do not hide those differences by scrubbing emitted output.
- *Compile-time external inputs*: macros may perform effects, as documented
  in ~constfolder.til::try_eval_call~. ~src/til.til~ itself executes git at
  compile time for VERSION/COMPILER_REVISION. Pin full revision and short
  revision spelling, source/support trees and the declared external inputs.
  Arbitrary time/environment/command-dependent macros cannot be promised
  host-independent results without controlling those inputs or changing
  their language contract. The latter needs a separate explicit decision.
- *Numerical audit*: folded F32/F64 values use host parsing/formatting
  (~strtof~, ~strtod~, ~snprintf~ in ~src/self/codegen/ext.c~), and evaluation
  can call host external functions. Round-trip formatting is not proof of
  cross-libc identical spelling or arithmetic. Test signed zero, subnormals,
  rounding boundaries and nonfinite values where supported; distinguish
  representation differences from differing values. These are audit risks,
  not measured regressions in this inventory.

**** Why the size-folding divergence is not fixed in this commit

The prepared AST serves two consumers with different layouts. Generated
~size~ bodies hold the HOST literal (~initer.til~ gen_*_size_method_for_stmt
from ~ctx.struct_layouts~), and the compile-time interpreter runs them for
host storage: core Vec/Array/Map/Set/mem and std ~hashmap~/~hashset~ compute
host buffer offsets with ~T.size()~. Folding size queries to target values in
the AST would corrupt compile-time storage on a cross-layout host (why #309
left them unfolded); folding host values bakes wrong results (above). Neither
choice can be made per unit: ~src/std/hashmap.til~ uses ~K.size()~ for
storage outside core, and user code may too.

SUPERSEDED by decision 1 in "Plan to close": the roles are still split, but
~size()~ keeps the storage meaning and the new name (~size_for_target()~)
goes on the target value, so no core/std call site changes.

Proposed design (needs approval: it changes core/std APIs and folding):
separate the two roles at the source. Containers' byte arithmetic calls a
dedicated storage-size query; the interpreter answers it from the host layout,
codegen emits the target size, and the constfolder never folds it. Value
queries (~X.size()~, ~dyn_size_of~) fold to the audited target model on every
host, staying unfolded only when the model has no answer (a target fact).
Generated size bodies stop carrying a host literal; every backend emits size
methods from the target model. A compile-time evaluation that feeds a target
size into host byte arithmetic must be diagnosed, as generator preparation
already does (~comptime_check_storage_domains~). Costs: ~90 core/std call
sites, interpreter/constfolder/C/HolyC/MLIR/FASM changes, boot churn, and one
dispatch per interpreted storage query (to be measured).

**** Remaining limitations

- The direct and indirect size divergences above remain; the self_translate
  accommodation in ~src/tests.til~ (check_usize64) stays.
- Compile-time evaluation during typing (macros, generators) is outside the
  above design's constfolder pass and needs the same role split.
- Path identity/~__LOC__~, effectful macros, compiler revision queries and
  floating-point folding are untouched.

**** Decisions (all taken; 2 by default, as no change)

1. Size methods (steps F1 and F3). DECIDED. The principle: a regular user
   writes ~size()~ once and it is right on every target, without knowing
   the target or the compactness; choosing those belongs to whoever builds
   the program. Only code that reasons about the build target on purpose
   uses the second method, which says so in its name.
   - ~size()~ keeps its meaning: the size in the program that EXECUTES the
     call. At compile time that is the compiler's own memory, so containers
     and the lowerings that pass ~T.size()~ to ~swap_bytes~ and
     ~KwargsMap.set~ stay correct, and no core/std call site changes.
   - A new ~size_for_target()~: the size in the program being BUILT. It is
     generated by the same generator under the same rule as ~size~ (skipped
     when the type defines it), with a literal body computed by til from
     the target's layout instead of the compiler's. If a type defines its
     own ~size~ and no ~size_for_target~, the generated one forwards to it.
     Core writes it by hand next to ~size~ for the primitives and ~Bool~.
     At runtime the two always agree. It takes no target or Context
     argument: the compiler knows what it is building for.
   - No ~sizeof~ for values, for either method: til computes every layout.
     Both end up folded in emitted code. ~size_for_target()~ can be folded
     at any time; ~size()~ only once compile-time evaluation is over (F1b),
     and then to the same target number.
     The C compiler is kept only as a CHECK: a static assert per emitted
     type that its ~sizeof~ equals til's number, so a wrong layout
     computation is a compile error instead of corrupted memory.
   - Only compile-time code that needs the built program's size uses the
     new method: generator conditions and macros (today
     ~if T.size() == expected~ in ~test/first_class.til~). That is a
     spelling change in such conditions, including users'. The generator
     frame's special mode and its storage diagnostics go away.
   - Known limits, stated once: a fold that passes through a container at
     compile time is not baked (F2), for good; and a macro that uses plain
     ~size()~ as a value on a cross-layout build still bakes the
     compiler's size, caught for the repository by the two-compiler-layout
     comparison rows.
2. Source identity (step F4). DECIDED BY DEFAULT: leave it. Jorge can pick
   another option later; nothing else in the plan depends on it.
   The question is what gets baked into a BUILT PROGRAM (~__LOC__~,
   ~__FILE__~, cast locations, private C names) for a file of the
   compiler's own ~src/core~, ~src/std~, ~src/modes~. Today it is the path
   as loaded: ~./src/core/...~ in the repository, the absolute install path
   for an installed compiler. Compiler error messages are not part of this:
   they show the real path in every option, so an editor's jump-to-error
   keeps working.
   - Leave it (the default), and state the contract: comparisons use the
     in-repository compiler run from the checkout root. Every CI producer
     already does that, so they bake the same ~./src/core/...~ wherever the
     checkout lives (the Windows ~til.exe~ spelling still has to be
     checked). No work now. Known leftover: an installed compiler produces
     different bytes from the in-repository one, and from one installed
     under another prefix.
   - Always ~./src/core/...~, whatever the install root. Nothing changes in
     the repository; an installed compiler on any OS produces the same
     bytes; an installed user sees a relative-looking path in a runtime
     panic that is not under their directory.
   - Always ~core/...~, ~std/...~, ~modes/...~, the import spelling. Same
     bytes everywhere; every private C name of core changes (a large
     ~boot/~ diff, Two-pass) and expected files are regenerated.
   - Keep baking the real path and run CI from compilers installed at one
     fixed prefix. Windows and TempleOS have their own paths and can never
     match, and a user who installs elsewhere gets different bytes.
   No prefix-map flag is proposed in any of them.
3. Observation surface (step O1). DECIDED: a phase selector on the
   EXISTING ~til ast~ command (~tokens~, ~parsed~, ~typed~, ~owned~,
   ~prepared~) that streams field-tagged records to stdout. Who writes: the
   compiler, on request. Who reads: the test harness and #473's collector;
   nothing loads it back and nothing is cached. This replaces the earlier
   ~test/frontend_determinism.til~ driver proposal. ~cmd_ast~ as it stands
   is only the entry point: it returns after parsing, prints user units
   only, and its printer omits types, signatures and ownership, so the
   phases after parsing and the serializer are new work (O1, O2).
4. Decided in #473: hash-list artifacts between jobs, the collector, and
   one pinned clang per target on every producer (its decision 4), which
   is what makes binary hashes comparable at all.

for values. Two commits.

How it works today, read from ~initer.til~ and the backends: the
generated body is ~return N~ with N from ~ctx.struct_layouts~, the RUNNING
compiler's layout (~compute_struct_layout~ / ~compute_enum_layout~: own

~return sizeof(X)~, ~Dynamic~ spelled ~void *~ (#394). Primitives and
~Bool~ are hand-written literals in core (~U8.size()~ is ~return 1~), a

- F1a, check first, no behavior change (Two-pass: the compiler's own C
  gains the asserts). The C backend emits, for every struct and enum it

**** O2: the record contract, as built

Written out at the top of ~src/self/observer.til~. In short:
- First line: phase, compiler revision, target, backend, mode, the
  requested width, ~cptr32~, CPU profile, compile mode. From ~typed~ on a
  second line with what the typer settled: USize and UPtr primitive,
  ~cptr32~, 64-bit scalar alignment, SIMD width.
- Per unit in load order (~lp.unit_paths()~, core first): its path, then
  every node in pre-order with depth, kind, line:col, resolved type and
  every field of its payload struct. Declarations that hang off a node
  (parameters, captures, struct fields, namespace members, enum variants)
  are records of their own, followed by their default value's nodes.
  Symbols are written by name; text is quoted with unambiguous escapes.
- After ~prepared~: the target size and alignment of every struct and
  enum left, the foldable classification, the throw registries, and one
  record for the intern order (count and hash of every spelling).
- Left out, each with its reason there: ~ctx.struct_layouts~, the
  evaluation heap, scopes and caches, addresses and capacities,
  ~FunctionDef.namespace_decl~ (a pointer the interpreter caches; it
  dangles after the scavenger), the index maps (written as member names),
  the body of a generated ~size()~, and the body of a generated ~hash()~
  before ~prepared~. Not written, against the plan's wording: the
  ~builder_*~ inventories. They do not exist until a backend runs; they
  are derived inside it from the records above, and level 2 compares what
  comes out.
- Completeness: ~NodeType~, ~Literal~ and ~Type~ are switched over with
  no default arm. For the payload structs, ~test/observe_fields.til~
  compares each struct's fields, as reflection lists them, with the keys
  its writer function names; exclusions are by name with the reason.
  Removing one field from a writer fails it, naming the field.

*** The toolchain rule (decided by Jorge, 2026-11-14)

READ THIS before any binary comparison work (L3b onward, #473 C4/C7). It
replaces every earlier "one clang / LLVM 18 for everything" in this file
and in #473; those passages are marked as superseded where they stand.

- Each TARGET has ONE toolchain: compiler, linker, archiver, headers and
  libraries or sysroot, at one exact version, with the flags til passes.
- Every producer that builds that target -- natively or cross, whatever
  its host -- uses that target's toolchain. That is the whole
  requirement: the producers of ONE target agree.
- Different targets may use different toolchains, for every producer:
  gcc for linux-x64 and clang for macos-arm64 is fine, as long as every
  host that builds linux-x64 uses the same gcc and every host that builds
  macos-arm64 the same clang. Nothing has to match ACROSS targets.
- clang is not required. It is convenient where several hosts build a
  target, because one clang binary builds for every target (one pinned
  download per host), while gcc needs its own cross build per (host,
  target) pair.
- A target with a single producer is not compared ("not compared", never
  "equal"). A comparison needs a second producer with the same toolchain.
- The producer records its toolchain identity for each target next to
  the hashes; one whose identity differs from the target's is reported as
  a failure, not compared (#473 C7).
- A host's own native build of its own target is one of that target's
  producers and uses the target's toolchain too, so "the native suite
  tests what is compared" holds (#473 decision 4).
- C remains the main path (with LLVM through the MLIR backend) and a
  translation target for good, for compatibility and testing (Jorge,
  2026-11-14). Any compiler a user picks can build the generated C, at
  their own risk; only the target's toolchain is inside the guarantees.
