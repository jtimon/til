   Dozens of functions across the compiler dispatch on a single subject
   with a linear run of ~if~ statements, one per value, when a ~switch~
   says the same thing in fewer lines and compiles better. The archetype
   is ~binop_method~ (src/self/parser.til:1850): sixteen consecutive
   ~if tt.is(TokenType.X) { return "..." }~ lines that are literally a
   switch written out by hand.

   #+begin_src til
   // src/self/parser.til:1850, today
   priv binop_method := func(tt: TokenType) returns Str {
       if tt.is(TokenType.Star)      { return "mul" }
       if tt.is(TokenType.Slash)     { return "div" }
       // ... 14 more ...
       UNREACHABLE()
       return ""
   }

   // what it should be
   priv binop_method := func(tt: TokenType) returns Str {
       switch tt {
       case TokenType.Star:    return "mul"
       case TokenType.Slash:   return "div"
       // ... 14 more ...
       case: UNREACHABLE()
       }
       return ""
   }
   #+end_src

*** Why switch, not just "it looks nicer"

   - *Enum / integer / char subjects emit a real C switch.* Since #254 /
     #276 a switch whose scrutinee is an enum, integer or char and whose
     cases are bare constants stays a ~Switch~/~Case~ node all the way to
     the backend (~switch_is_clike~, src/self/desugarer.til:3095), so the
     C compiler gets a jump table instead of N sequential tag compares.
     An if-chain over the same values never gets that.
   - *Enum switches are exhaustiveness-checked.* ~infer_clike_switch~
     (src/self/typer.til:7779) reports missing variants and rejects a
     redundant ~case:~. An if-chain silently falls through to whatever
     comes after the last ~if~, which is how a missing ~F32~ arm in
     ~elem_size_for_type~ once shipped as a wrong stride (see the comment
     still sitting at src/self/interpreter.til:541).
   - *~Str~ subjects lose nothing and gain later.* A string switch still
     lowers to the same ~Str_eq~ if/elif chain today, so converting is
     free; when [[./278.org][#278]] lands a smarter string dispatch, every
     converted site gets it automatically, while every remaining hand-written
     if-chain stays O(N) forever.

*** What the language does and does not support

   Checked against ~parse_case_head~ (src/self/parser.til:2285): a case
   takes exactly ONE pattern plus an optional ~if~ guard. There is no
   multi-pattern case (~case "a", "b":~) and no fallthrough. So an
   ~.or()~-joined condition -- ~c.eq("char").or(c.eq("signed char"))~ --
   becomes two cases with the same one-line body. That is fine and still
   shorter than the ~if~ form; adding multi-pattern cases is a separate
   language question and is NOT part of this issue.

   Also note that ~switch_is_clike~ only accepts bare constant patterns.
   A case pattern that is a runtime call (the ~enum_variant_tag(def, "I16")~
   chains below) parses and type-checks fine but falls back to the
   if/elif desugar -- readability win only, no jump table.

*** Scope and staging

   Not one commit. One file (or one function group) per commit, each
   verified with the full suite, so a regression bisects to a small diff.
   Pure refactor: no behaviour change, no new helpers, no new dispatch
   tables, no reordering of arms that could change which one wins when a
   subject matches two conditions (check the ~.or()~ groups before
   splitting them).

   Two conversions need care rather than a mechanical rewrite:

   - ~parse_statement_body~: the arms are not all bare tag tests. The
     ~KwTest~ arm peeks at the following token and falls through to
     ~parse_expression~ when it does not match, and the ~StringTok /
     Number / KwTrue / ... / KwMatch~ group shares one body. Both are
     expressible (guard-free early ~return~ inside the case, repeated
     cases for the shared group), but a blind rewrite will change which
     statements reach the fallthrough at the end.
   - ~constfolder.til:99~: the arms ~continue~ the enclosing ~while~. C
     ~continue~ is not captured by ~switch~ (~switch_is_clike~ says so
     explicitly), so this is safe -- but a ~break~ in a converted case
     would NOT be, and the chain must not grow one.
