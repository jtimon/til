** WIP #408 tilminal: terminal emulator for standalone use and tiled

Develop [[file:../../examples/tilminal.til][examples/tilminal.til]] into a terminal emulator that can
run standalone and serve as the terminal component of
[[./83.org][#83 tiled]]. Tiled combines an Emacs-like integrated environment with
i3-style tiling; it should include tilminal rather than implement a
second terminal emulator.

*** Current state

The first terminal milestone is implemented in the approved example
modules: ~terminal_text~, ~terminal_model~, ~terminal_session~ (til/C),
and ~terminal_view~ under ~examples/lib/~. The GUI now hosts a
persistent shell through a PTY/ConPTY session rather than running and
capturing a new ~sh -lc~ command for each line. An optional command
runs once; the final screen and exit status remain visible. Escape
belongs to the child, while window close tears down the session.

The model handles incremental UTF-8, Unicode 17 scalar widths,
combining/wide cells, cursor/wrap state, scrolling regions, ANSI/VT
editing and rendition, DEC graphics, keypad modes, and terminal-query
replies. The view renders a supplied pane; it owns no window/event
loop. The session owns native resources and bounded output pumping.
~send~ reports false when child exit races input, separately from an
OS error. Windows uses independent read, write, and exit/teardown
workers so final ConPTY frames can be drained while close is pending.

*** Startup and build corrections

- Launching from ~bin/~ reproduced an immediate exit after window
  creation: ~terminal font not found: img/DejaVuSans.ttf~. Tilminal now
  locates the existing font through the runtime's executable-root
  resolver, without changing the shell's working directory. The GUI
  smoke test launches from ~bin/~, and the interactive Xvfb checks
  passed from that directory as well.
- Parallel builds could overwrite the shared ~gen/c/user_0.o~ before
  another program linked it. ~compile_c~ now names each bridge object
  after its generated C basename, matching its program-specific forward
  header. ~test/terminal_session.til~ forces the interleaving by building
  B after compiling A's bridge but before linking A. The old compiler
  deterministically failed with ~linked another program's bridge~;
  the repaired compiler passes. No timing-dependent race is needed to
  exercise the regression.
- The full ~make clean && make test~ run with both corrections passed
  496/496, including the normal parallel build tests.

*** Terminal foundation

- Persistent shell and child-process session through a PTY on POSIX;
  use the corresponding ConPTY facilities for Windows support.
- Event-driven input/output so running programs do not block the GUI.
- Terminal screen grid, cursor state, escape-sequence parsing, text
  attributes, scrolling, and resize propagation.
- Keyboard input forwarding and UTF-8 rendering with cell-width
  accounting, rather than treating every byte as a display column.
- Keep terminal/session behavior reusable by tiled's panes as well
  as the standalone window. Concrete interfaces and file layout are
  implementation decisions to discuss when work starts.

*** General inline graphics

Investigate support for application-supplied inline graphics, so any
program can display a logo or icon without requiring the user to
install and select that application's font. Applications should be
able to query support, transmit the image, and place it in a defined
number of terminal cells, retaining textual output on unsupported
terminals. This is a general terminal capability, not a special case
for til or ~til repl~.

Evaluate existing protocols, particularly kitty's graphics protocol,
before designing a new one. Older downloadable-character protocols
are another reference. Image placement is not the same as a Unicode
text glyph: specify cursor behavior, redraws, scrolling, resizing,
copy/selection semantics, and resource lifetime. Check how capability
queries and image data behave through SSH and terminal multiplexers.
This is a design goal to investigate, not a selected new protocol.

If terminals share such a capability, programs can supply their own
graphics to the actual renderer instead of guessing whether a local
font installation will be used by it.

*** Related example feature

[[./159.org][#159]] covers drawing the til logo in tilminal's own prompt using
the existing logo font directly. That small GUI feature does not
require the full terminal foundation or a graphics protocol. The
decision there to keep ordinary ~til repl~ prompts textual remains
in place; this issue explores the more general terminal facility.

*** Design review against master d72865e0d

This is a source/protocol review, not a working terminal implementation
or a claim of tested interoperability. Recommended direction: first
establish a reusable terminal session and screen model, then implement
an existing graphics protocol. Kitty graphics is the strongest match
among the protocols reviewed for queryable, reusable inline images.

**** Existing code and reuse boundaries

- ~src/std/sys.til~'s ~Cmd~ provides argv, environment, cwd, process
  start, and exit-status handling. Its capture mode uses spool files
  for reading completed output; it exposes neither a PTY nor an
  interactive stdin stream. Replacing ~run_cmd~ with ~Cmd.capture~
  would not turn tilminal into a terminal.
- ~src/self/repl_editor.til~ and the ~repl_term_*~ C functions operate
  on the application's existing terminal. Their input decoder turns
  terminal key sequences into editor actions; a terminal emulator
  instead parses child output into screen operations and encodes GUI
  keys into child input. Reuse the testing ideas, not the editor's
  one-line/history model as the emulator's screen.
- ~test/repl_pty.til~ obtains its PTY through the external ~script~
  command. ~test/repl_wincon.til~ and ~test/wincon.c~ test a real
  Windows console through console APIs, not ConPTY. Both provide
  useful application scenarios, but neither supplies a reusable
  terminal-host transport or proves ConPTY behavior.

**** Session, screen, and view responsibilities

Keep these responsibilities separate, with one independent instance
per pane; this describes boundaries, not new public API signatures:

- Platform session: own the child and terminal handles; read/write
  bytes, propagate size, report exit/EOF/errors, and finish teardown.
  Child exit and draining its remaining output are distinct events.
- Terminal model: incremental UTF-8 and escape parsing, cell contents
  and attributes, cursor and wrap state, scroll regions, primary and
  alternate screens, and outgoing terminal-query responses. Retain
  incomplete sequences between reads; reads are not lines or frames.
- Raylib view: render cells in a supplied pane rectangle, determine
  rows/columns from cell metrics, and translate focused input. Window
  creation and the main event loop belong to the standalone/tiled
  host, so embedding does not open another window or event loop.

The shell or child application owns its prompt, line editing, echo,
and history. The current fixed ~$ ~ input bar and Enter-to-run logic
are not appropriate inside an emulated terminal. Tilminal should not
inspect child text to recognize or replace a til prompt. The direct
GUI logo in #159 remains distinct from application-supplied graphics.

**** Platform transport findings

POSIX: allocate a PTY, create a child session with its slave as the
controlling terminal and stdin/stdout/stderr, then execute the shell.
The parent owns the master. Use nonblocking I/O with queued partial
writes and bounded per-frame processing so a busy child cannot starve
the GUI. Resize through ~TIOCSWINSZ~; let the tty's line discipline
deliver Ctrl-C/Ctrl-Z to the foreground job rather than manually
signalling the shell for every key. Close unused descriptors, report
spawn failures, and reap the child. ~posix_openpt~/~grantpt~/~unlockpt~
are a candidate allocation route; check Linux/macOS details before
choosing the C boundary.

Windows: create the pipe pair and ~CreatePseudoConsole~ first, then
attach the child through ~STARTUPINFOEX~ and
~PROC_THREAD_ATTRIBUTE_PSEUDOCONSOLE~. The terminal host consumes the
UTF-8/VT output stream and sends encoded input; existing console API
clients can run behind ConPTY. Use ~ResizePseudoConsole~ for size.
Microsoft recommends separate servicing threads for synchronous input
and output channels to avoid deadlock. Those workers must communicate
with the GUI through owned queues, not mutate the screen or call
raylib. Keep draining output during ~ClosePseudoConsole~; closing can
emit a final frame. Native Windows execution is needed to verify this
path, including whether the chosen graphics sequences survive ConPTY.

**** Screen and input requirements

The first end-to-end milestone should support a persistent shell and
unmodified ~til repl~: CR/LF, backspace, tabs, cursor movement, erase
line/display, wrapping, scrolling, basic SGR attributes, key forwarding,
resizing, and process lifecycle. Follow with alternate-screen and
scroll-region behavior required by full-screen terminal applications.
Choose and test a terminal compatibility baseline before advertising
a ~TERM~ value; do not claim xterm compatibility from a few CSI codes.

Cell width is not UTF-8 byte count. Preserve wide-character continuation
cells and combining text, with incremental decoding across reads.
Character coverage and Unicode width/shaping policy need an explicit
implementation decision; raylib text drawing alone does not define
terminal layout. Unknown terminal sequences must be consumed according
to parser rules without leaking their payload as printable text, while
broken internal invariants and platform failures remain explicit errors.

Escape must reach the child instead of triggering raylib's default
window-close key. Existing startup command behavior, shell selection,
window-close behavior, and host shortcuts need an explicit UX decision
before replacing the current command runner. These are not changes
implemented or finalized by this review.

**** Graphics protocol comparison

- Kitty graphics: application-supplied pixels, a real query action
  (~a=q~), image/placement IDs, deletion, and sizing in cells (~c~, ~r~).
  Direct base64 transmission (~t=d~) works without a shared filesystem,
  making it suitable for SSH when the transport passes the sequences.
  The protocol specifies chunks no larger than 4096 encoded bytes.
  Prefer this route over terminal-name or installed-font detection.
- iTerm2 OSC 1337 images: also transfers base64 image contents and
  accepts cell dimensions; multipart transfers and feature reporting
  are documented. It is another viable existing protocol, but kitty's
  explicit image/placement lifecycle is a better starting point for
  reused prompt icons. The current iTerm2 documentation also reports
  support for kitty graphics, so the choice need not be kitty-only.
- DEC DECDLD/DRCS: downloads bitmap character sets and selects them
  through terminal character-set state. This is closer to a literal
  custom glyph, but involves legacy charset selection and limited
  font buffers rather than ordinary Unicode text or a TTF upload.
  It is not the recommended first route for general inline graphics.

For kitty detection, the specification recommends a tiny image query
followed by primary device attributes (~CSI c~). A graphics response
establishes support; a device-attributes response without the earlier
graphics response establishes non-support under the protocol's reply
ordering. An application still needs a deadline for terminals or
intermediaries that do not reply, and must distinguish replies from
keyboard input. This solves capability detection for this protocol,
not arbitrary font selection in a terminal.

A one-cell placement is possible with ~c=1,r=1~. Default image placement
moves the cursor down as well as right; a same-line prompt needs
~C=1~ and explicit cursor management, or the protocol's Unicode
placeholder mechanism. Images have no inherent copied-text meaning.
Unicode placeholders (~U+10EEEE~ plus attributes/combining markers)
can make images follow text redraws, but require the corresponding
Unicode cell model and protocol support; they are not plain font glyphs.
Treat placeholder support as a separate capability to verify, not an
automatic consequence of basic image support.

Before implementing the graphics milestone, define the supported
protocol subset and responses for unsupported requests. Static inline
transfer, query, placement/replacement, and deletion are the candidate
first subset. Specify image lifetime on scroll, erase, resize, alternate
screen, and reset, plus storage bounds and cleanup. Multiplexer support
requires end-to-end checks: direct transmission avoids remote paths,
but does not guarantee that tmux or another intermediary forwards the
commands and replies. Animation and file/shared-memory transfer are
not prerequisites for a one-cell icon.

**** Verification and next implementation boundary

- Headless model tests: feed identical bytes whole and split at every
  boundary; compare cells, cursor, modes, and generated replies. Cover
  narrow grids, pending wrap, wide/combining text, scrolling, erase,
  and primary/alternate screen restoration.
- Transport tests: interactive child behavior, persistent cwd/env,
  foreground-job interruption, resize observation, partial I/O, final
  output before exit, and teardown. Exercise native POSIX and Windows
  hosts; the current REPL console tests are not substitutes for ConPTY.
- GUI milestone: shell plus unmodified ~til repl~, repeated editing,
  Escape forwarding, resizing, and a child producing continuous output
  while the window remains responsive. Verify instance isolation for
  eventual tiled panes.
- Graphics milestone: use an independent application speaking the
  selected protocol; test support/unsupported responses, one-cell
  placement without cursor drift, reuse/delete, scrolling, and a
  remote session. Record multiplexer and ConPTY results separately.

The next implementation proposal should pin down the platform bridge
and reusable example-module layout, the initial terminal compatibility
and Unicode scope, and the command-runner UX transition. Any new API,
file layout, dependency, or installed terminfo entry needs approval
before creation. No such surface is introduced by this review.

*** Implementation proposal against master 24b032796 (approved)

Deliver a standalone terminal that runs a persistent shell and
unmodified ~til repl~, with the same terminal instances usable later
inside tiled. The proposal below names the new source surfaces and UX
changes for approval; it does not create them. Kitty graphics remains
the next milestone after the terminal foundation, not part of the
initial terminal implementation.

**** Proposed source layout and ownership

- ~examples/lib/terminal_model.til~: pure til parser and screen state.
  Owns cells, cursor, modes, scroll regions, and pending replies.
  Used by the view, headless tests, and eventually tiled.
- ~examples/lib/terminal_text.til~: UTF-8 decoding and cell-width
  classification shared by the parser and renderer. Keep pinned
  Unicode 17 width/combining range data here as source with attribution
  and provenance, rather than depending on host locale or font advance.
- ~examples/lib/terminal_session.til~: til ownership wrapper for a
  child terminal session. Imports its example-local C bridge with
  ~link_c~; used by tilminal, transport tests, and eventually tiled.
- ~examples/lib/terminal_session.c~: POSIX PTY and Windows ConPTY
  handles, process creation, I/O queues, resize, and teardown. Follow
  the existing ~test/wincon.c~ example-local bridge pattern rather than
  adding terminal-host primitives to the compiler's ~src/c/ext.c~.
- ~examples/lib/terminal_view.til~: raylib cell rendering and input
  encoding, taking a pane rectangle and focus state. Imports model
  and session code, but does not create a window or own an event loop.
- ~test/terminal_model.til~: headless parser, text-width, screen, and
  input-encoding cases.
- ~test/terminal_session.til~ and ~test/terminal_session_child.til~:
  transport driver and deterministic child for real-terminal tests.
  The driver launches the child in each supported host's PTY/ConPTY.

These would be ordinary maintained source files, compiled through
the existing example/test build paths. The Unicode ranges are an
explicit versioned copy of upstream Unicode data, read by tilminal's
width classifier; maintainers update them deliberately alongside tests,
not through a build-time download or a generated cache. The existing
byte-oriented Str operations and raylib glyph advances do not supply
portable terminal cell widths. This adds a small Unicode-data
maintenance obligation in exchange for reproducible behavior across
POSIX and Windows; it does not promise complete Unicode text shaping.

Update ~examples/tilminal.til~ to compose these modules and register
the tests through the existing ~src/tests.til~ machinery. OS calls
and the already-vendored raylib supply the native functionality; no
new third-party runtime library is proposed. Binaries and generated C
use the existing ~bin/~, ~gen/~, and ~tmp/~ conventions. No new
installed font, terminfo file, manifest, or CLI configuration is needed
for this first milestone. No new public stdlib API is proposed.

**** Proposed module contracts

~TerminalSession~ is an owning, non-clonable session handle. Its til
interface has the following operations; the C bridge should accept
scalar arguments and strings rather than duplicate Vec/enum layouts:

- ~new~ and ~arg~ construct an argv-based child command, following
  Cmd's ownership pattern. Arguments are appended before starting.
- ~start(columns, rows)~ creates the terminal and child exactly once.
- ~send(bytes)~ queues input without blocking the GUI.
- ~pump~ services available work and returns output bytes. Empty
  output is a legitimate no-data-yet state, not EOF. A distinct session
  state reports running, draining, and exited-with-status; platform
  errors are reported with their operation and OS error.
- ~resize(columns, rows)~ updates the child terminal size.
- ~close~ performs explicit orderly teardown; destruction also releases
  the owned session. No global singleton terminal state is permitted.

~TerminalScreen~ owns the cell grid and incremental parser. Its
interface is ~new(columns, rows)~, ~feed(bytes)~, ~resize~, and
~take_replies~. The host queues those replies to the session in parser
order. A cell owns its text, rendition, and span (single, double, or
wide-character continuation). The cursor position and pending-wrap
state are separate. Consumers read the grid; only model operations
change terminal state.

The view exposes a per-frame update and draw operation over an
instance plus a supplied rectangle/focus state. Update computes resize,
queues focused keyboard input, pumps session output into the model,
and returns parser replies to the session. Draw has no process I/O.
Keep key-to-terminal-byte encoding testable without opening a window.
Tiled can run these same operations once per pane, assigning focus and
geometry itself.

**** Initial compatibility and text scope

Use the existing ~vt100~ terminal profile on POSIX, after tests verify
the advertised terminfo operations. Implement its cursor addressing,
tabs, erase/insert/delete operations as advertised, SGR rendition,
scroll regions, save/restore cursor, application cursor/keypad modes,
DEC special graphics, and device/status replies. Add the output
sequences exercised by ConPTY to the shared model. Do not advertise
an xterm/kitty terminal profile or graphics support at this stage.

Decode UTF-8 incrementally. For the first text implementation, use
Unicode scalar cell widths: wide/fullwidth characters span two cells,
combining marks attach to the preceding base, and ambiguous-width
characters use one cell. Retain the actual text for future selection.
Malformed UTF-8 produces a visible replacement character, as an
explicit input-decoding policy. Width is independent of font coverage:
a missing rendered glyph retains the source character's cell span.
Emoji ZWJ ligatures, bidi layout, and full grapheme shaping are later
text work, not claimed by this initial scalar-width profile.

Draw from the existing bundled font at fixed cell positions; do not
measure a whole proportional string and call its advance a column.
Load the glyphs needed by received text without interpreting font
availability as a terminal capability. Grid resize initially preserves
row contents with clipping/padding rather than reflowing paragraphs.
Retain the visible screen and scroll within it; scrollback navigation,
selection/clipboard, and alternate-screen applications are later
milestones. This first acceptance target is shell/REPL interaction.

**** Proposed standalone startup and keyboard behavior

- With no command, POSIX starts the executable named by the existing
  ~SHELL~ environment variable interactively (~/bin/sh~ when unset).
  Windows starts ~COMSPEC~ (the system command processor when unset).
  This reads conventional OS settings; it adds no til-specific setting.
- Preserve the current optional command-string argument as a one-shot
  shell command, now attached to the terminal: POSIX shell ~-c~,
  Windows command processor ~/C~. Its completion leaves the final
  screen and exit status visible; it does not silently start a second
  shell. Cwd and environment are inherited at startup.
- Remove tilminal's private input bar, echo, ~help~, and ~clear~
  dispatch. Editing and history belong to the shell or foreground application.
  Enter sends Return immediately; printable text, Backspace, Tab,
  arrows, Home/End/Delete, modifiers, and control keys are encoded for
  the child using the current terminal modes.
- Escape goes to the child; disable raylib's Escape-to-close default.
  Window-manager close ends the standalone session. Do not add another
  tilminal shortcut or a keybinding configuration surface in this slice.
- On normal child exit keep the final screen, with exit status in
  host-owned window chrome rather than injected into the child's grid.
  On window close tear down the session and reap/join its resources.

POSIX should use ~posix_openpt~/~grantpt~/~unlockpt~ with child
session/controlling-terminal setup and nonblocking parent I/O. Windows
uses ~CreatePseudoConsole~, ~CreateProcessW~ with the pseudoconsole
attribute, and dedicated input/output servicing behind the same til
contract. Only the UI thread accesses raylib and TerminalScreen.
Partial writes remain queued; EOF, child exit, and OS errors are
distinct. Limit per-frame work so continuous child output leaves the
host responsive, with backpressure rather than discarded bytes.

**** Acceptance and delivery

Implement and test the pure text/model layer first, then the native
session adapters, then wire the existing GUI to both. This is a work
order within #408, not new tracking issues or a requirement to split
the final change into separate commits.

The milestone is ready when a persistent shell retains ~cd~ and
environment changes; unmodified ~til repl~ supports editing/history,
Ctrl-L and resize; control keys reach the foreground job; final output
is drained; and closing the host releases its children/handles. Check
chunk-split parsing, Unicode spans, narrow grids, tab/erase/wrap,
reply ordering, argv with spaces, start failure, and two independent
session/model instances. Verify the native Windows path rather than
equating cross-compilation or Wine with ConPTY conformance.

Run the existing full suite as well as the new focused tests. Record
native GUI/ConPTY checks separately from headless test results. Keep
#408 open: tiled integration, broader terminal compatibility, and the
graphics protocol remain subsequent work. Approval is requested for
the named source files, example-level contracts, Unicode-data copy,
initial compatibility scope, and standalone UX transition above.
