** OPEN #201 More built-in error types and safe_* methods

*** Current status (2026-10-31, master 9ab5f052b)

   The original checklist below predates substantial implementation. Keep
   this issue open for the remaining access/parse and arithmetic work, not
   for methods that already exist.

   Implemented in [[file:../../src/core/numbers.til][src/core/numbers.til]]:
   - ~safe_add~, ~safe_sub~, and ~safe_mul~ on ~U8~, ~U16~, ~U32~,
     ~U64~, ~I16~, ~I32~, and ~I64~. They share ~IntegerOverflow~
     with a ~msg: Str~ field; the error-name choice is no longer open.
   - ~F32.safe_div~ and ~F64.safe_div~, as well as ~I64.safe_div~,
     throw ~DivideByZero~ with a message and caller location.
   - [[file:../../test/errors.til][test/errors.til]] already covers F32 safe division and checked
     integer arithmetic, including overflow/underflow catches and messages.

   Remaining work from the original proposal:
   - ~I8~ checked arithmetic is not present in ~numbers.til~; audit its
     current representation before extending the numeric family.
   - [[file:../../src/core/str.til][Str.get]] still panics on an invalid byte index, and ~Str.to_i64~
     still panics on invalid/out-of-range input. The throwing byte-access
     API and optional throwing parse API remain design/implementation work.
   - [[file:../../src/core/tuple.til][Tuple.get]] and [[file:../../src/core/vec.til][Vec.pop]] still have panic-based failure paths.
     Re-inventory current container methods before applying the old list:
     [[file:../../src/core/map.til][Map(K, V).get]] already throws ~KeyNotFound~, and the old
     ~HashMap~ / ~DynHashMap~ / ~DynVec~ names are not a current API map.

   This is a source/test review, not a fresh execution of those tests.

*** Historical proposal (superseded where noted above)

   Follow-up to [[../fixed/198.org][#198]]: extend the catalogue of
   built-in error types and the safe_* method variants that throw
   them. [[../fixed/198.org][#198]] shipped only ~DivideByZero~ +
   ~I64.safe_div~ as a proof of concept. Two further error types
   have landed since on the container side: ~Vec.get~ throws
   ~OutOfBounds~ (empty struct, drives the ~a[b]~ subscript
   desugar), and ~Map.get~ throws ~KeyNotFound~ (likewise). Both
   are name-only types -- the rstil-style ~msg: Str~ form noted
   below was not adopted for them; the file:line:col is recovered
   from the bang's panic shim instead.

   The container accessors are now complete: ~Array.get~ also throws
   ~OutOfBounds~, and ~Vec.set~ / ~Array.set~ throw ~OutOfBounds~ too
   -- shipped with [[../fixed/225.org][#225]], driving the ~a[b]~ read
   and ~a[b] = c~ write subscript desugars.

   Wanted (mirror rstil's ~src/core/~):

   - ~I64.safe_add~ / ~safe_sub~ / ~safe_mul~ throwing
     ~I64_Overflow~ with a ~msg: Str~ field, plus the equivalent
     on ~I32~, ~U32~, ~U64~, ~U8~, ~I16~, ~I8~. ~I64_Overflow~
     should be a single type used by all integer widths (or one
     per width -- decide once and document). Note: the ~I8~ variant
     is now mechanically unblocked -- issue #176's follow-up landed
     ~Type.I8~ as a first-class primitive with arithmetic methods,
     so ~I8.safe_add~ et al. drop in alongside the rest.
   - ~F32.safe_div~ throwing ~DivideByZero~ (reuse the existing
     type).
   - ~Str.get_byte_safe(self, i: USize) returns I8 throws OutOfBounds~
     -- the last container accessor still missing a throwing variant
     (~Vec.get~, ~Map.get~, ~Array.get~ already throw). Reuse the
     existing ~OutOfBounds~ for consistency.
   - Optional: ~Str.parse_i64~ throwing ~ParseError~ for the
     fallible-parse pattern.
   - Migrate the methods that still ~panic~ on a bad index / empty
     receiver / missing key to THROW the existing error types instead
     -- no new type, the same panic->throw move #225 did for ~get~ /
     ~set~. Callers that don't catch keep today's behavior with ~!~;
     the gain is catchability.
     - ~OutOfBounds~: ~Tuple.get~; ~Vec.pop~ (empty) / ~take_prefix~ /
       ~push_take~; ~DynVec.pop~ / ~take_prefix~ / ~push_take~.
     - ~KeyNotFound~: ~HashMap.get~ and ~DynHashMap.get~ (~Map.get~
       already throws it).
     ~Str.get~'s byte-index OOB is the ~Str.get_byte_safe~ item above
     -- decide there between making ~Str.get~ itself throw vs adding
     the safe_ variant. Stays ~panic~ (programmer error, not OOB): the
     ~new()~ precondition checks (key_type required, must implement
     hash / cmp). ~Str.to_i64~ on empty / invalid input is the
     ~ParseError~ item, not OOB.

   For each new built-in error type, add a corresponding regression
   in ~test/errors.til~ that exercises a successful return and
   a catch on the throw path.

   *** Things to check while adding these

   - Cross-file resolution: ~throws_names_global~ already
     accumulates across files but each built-in error type wants
     a single Decl somewhere in ~src/core/~ (don't duplicate the
     struct).
   - ASAN: ~_err_<T>~ slots must be cleaned up when ~T~ owns a
     heap string. Verify with ~make test~ once
     ~ErrorWithMessage~-style types have an init that allocates.

   *** Why low priority

   [[../fixed/198.org][#198]] already covers the user-facing
   semantics for any new error type -- adding one is a roughly
   ten-line change per built-in. The lift here is in agreeing on
   the names / shapes and writing the tests, not the lowering.

   *** Recipe

   [[../../doc/concepts/throws.org][doc/concepts/throws.org]] has a worked example
   ("Adding a new built-in error type") that walks through the
   ~DivideByZero~ / ~I64.safe_div~ pattern. Each new safe_* in this
   issue is a copy of that recipe with a different error type and
   arithmetic body.
