** OPEN #473 Expand native and cross-platform CI, then enforce per-target reproducibility

CURRENT PLAN AND DECISIONS: the last section, "Plan to close". Where an
earlier section differs from it, that section wins; the earlier ones are
kept as the record of how the plan was reached.

Each supported host should test its own native build and build programs for
the other supported targets. Execute cross-built artifacts on the target or
an emulator where available. A collecting job checks completeness and, as
determinism is established, that corresponding outputs for each target hash
identically regardless of producer host.

This is a separate CI improvement issue. [[./472.org][#472]] owns deterministic
compilation, starting with lexing through the pre-codegen boundary. Only the
corresponding equality gates depend on its milestones; native tests, functional
cross-build coverage, artifact delivery and toolchain research can proceed now.
Do not put a blanket "blocked by #472" dependency on this issue.

*** Dependency map

| Work | Prerequisite |
|------+--------------|
| Inventory actual host/target/backend/width coverage and costs | None from #472 |
| Native self-builds/tests and functional cross-build/run coverage | Host/target support and tools, not deterministic bytes |
| Required-artifact checks, collection, diagnostics and hashes | A declared expected producer set; no equality promise needed |
| Research/pin comparable toolchains, sysroots and dependency builds | Can start independently of #472 |
| Cross-host frontend-state equality | #472's approved complete observation contract and fixes for that comparison group |
| Generated-source equality | #472's frontend-first milestone and emission determinism for that group |
| Binary equality | Reproducible upstream stages plus matched assembler/C toolchain, runtime, sysroot and packaging inputs |

Matching hashes in an exploratory run are evidence for that run, not proof
that a whole platform is reproducible. Native/cross execution checks remain
blocking independently of equality checks. Enable each equality group when
its prerequisites are met; do not wait for every target or all of #472.

**** Decisions (all four are taken)

1. Collector job (step C3). DECIDED: one new job, proposed name ~collect~,
   on ~ubuntu-latest~, that ~needs~ every producer and consumer it reports
   on, runs with a status condition that survives upstream failure, and
   fails when a required result or file is missing. It writes only to the
   job log and the job summary.
2. Comparison artifacts (step C5 on). DECIDED: hash lists only. Each
   producer uploads one small text artifact per level, named by producer,
   with lines of "sha256, level, target, backend, width, case, item". For
   translator output and binaries the item is the file; for #472's frontend
   records it is the checkpoint and unit, so a mismatch still names the
   first phase and file that differ and is reproduced locally from there.
   Who writes: the producer step. Who reads: the collector, in the same
   run. Nothing persists beyond the run's artifact retention and nothing in
   the repository reads them. This adds artifacts; it changes no existing
   one. Uploading the differing files themselves for a small corpus is
   the next step only if hashes prove insufficient to diagnose.
3. Collector logic. DECIDED: a til program (proposed
   ~examples/ci_collect.til~, beside ~examples/issues.til~ and
   ~examples/merge_commit.til~), so the suite runs it against fixture
   directories under ~tmp/~ and the injected failures of the handoff's
   matrix become ordinary tests. The collector job builds ~bin/til~ first.
4. What each environment builds and runs. DECIDED.
   - Every environment tests its own native build.
   - It cross-compiles so the collector can compare hashes, and the goal
     is that a cross-built binary has the SAME hash as the natively built
     one. til only writes the C (or MLIR); the bytes come from the C
     compiler and linker, and two different compilers never agree. So
     for each target, every producer uses the same toolchain at the same
     pinned version with the same headers and libraries. CORRECTED
     2026-11-14 (Jorge): that toolchain is chosen PER TARGET and need not
     be clang, nor be the same for different targets; see "The toolchain
     rule" at the end of #472. The text here first said "clang is used
     everywhere ... LLVM 18 is the proposed pin", which is superseded.
   - For the reasoning "the native tests cover the cross build" to hold,
     the binaries the native suite runs must come from that same clang.
     til's default C compiler therefore becomes clang on every host, one
     target at a time (step C4). Apple's own compiler cannot run on Linux,
     so for macOS targets the shared one is the open-source clang on the
     Mac too; the GUI examples that need Apple's SDK frameworks keep
     Apple's toolchain and stay outside the comparison.
   - "Build on one OS, run it on another" goes away target by target, as
     soon as that target's cross and native hashes match. The
     Linux-to-Windows pair also needs [[./483.org][#483]], because today the only
     Windows compiler is the cross-built ~til.exe~.
   - Unchanged: targets that are run under an emulator or in a VM (riscv64,
     x86, arm32, riscv32 under qemu, wasm32 under node, TempleOS in its
     guest). The compiler does not run on those systems, only its output
     does, and that is how they are tested today.

**** The program

*** The toolchain rule (decided by Jorge, 2026-11-14)

Decision 4 as corrected: each target has one toolchain, chosen per target
(not necessarily clang, and not necessarily the same for two targets),
and every producer of that target uses it, at the same version, with the
same headers and libraries. The full rule, why clang is merely
convenient, and the table of what each target's producers use today are
in #472, "The toolchain rule". C4 therefore proceeds target by target:
pick the target's toolchain, give each of its producers that toolchain,
then compare. The Ubuntu packages, a pinned download or a vendored tree
are all acceptable ways to supply it; each download is its own commit.
