** OPEN #290 Tooling gap: no regex / text-processing library for source-rewriting tasks

*** Summary

The remaining gap is a regular-expression API and reusable higher-level
text-processing helpers, not an inability to rewrite files in til. Current
Str and File APIs already support ordinary scan/replace/write tools.
The original trigger was the gte/lte/lt/gt -> >= / <= / < / > sweep across
src/ (the inverse of how the parser desugars the operators): doing it
safely needs balanced-paren matching plus string/comment skipping plus
cross-line chain detection, which a one-line sed cannot express, so it was
done with a throwaway Python script instead of a checked-in til tool.

*** Current inventory (2026-10-31, master 9ab5f052b)

- [[file:../../src/core/str.til][Str]] already supplies ~split~, ~trim~, ~find~, ~rfind~, and
  ~replace~. ~replace~ replaces all occurrences; a second API named
  ~replace_all~ is not needed merely to obtain that behavior.
- [[file:../../src/std/file.til][File]] supplies ~readfile~, ~writefile~, and ~appendfile~.
  Whole-file line processing can use ~readfile(...).split("\n")~ and
  ordinary loops; this is distinct from a streaming line iterator.
- The same file supplies directory iteration through ~Dir~ and the
  ~cdir_*~ primitives, plus ~File.is_dir~ / ~File.is_file~. Directory
  enumeration does not require a shell. Glob-pattern matching is a
  separate feature, not a prerequisite for enumerating files.

*** Remaining scope to evaluate

- A regex engine: compile + match + capture groups + replace. Even a small
  backtracking matcher over Str would cover most tooling needs.
- Additional scanning conveniences such as index-of-from, find-all, and
  character-class predicates, after checking the existing Str methods.
- Reusable streaming/line-rewrite helpers where whole-file splitting and
  ordinary loops are insufficient; basic file rewriting already works.
- Glob-pattern matching over the existing directory iterator.

*** Note: til already has a better lever than regex for til sources

Source rewrites that must respect nesting/precedence (like the comparison
sweep) are really AST transforms, and til already lexes and parses itself
(src/self/lexer.til, src/self/parser.til). Exposing the lexer/parser as a
reusable library plus an unparse/format-back step would let refactors run as
typed AST passes -- safer than regex for structured edits. Regex is still
the right tool for unstructured text (logs, docs, csv), which is what this
issue is mainly about.

*** Why low priority

Nice-to-have developer tooling, not a compiler-correctness gap. Filed so the
"had to drop to sed/python" friction is tracked rather than forgotten. Pick
the smallest useful missing slice first (for example a regex matcher)
when someone wants to write the next source sweep in til, reusing the
existing string and file APIs.
