** WIP #463 Call til from the JVM and BEAM through generated bindings

Make til libraries usable from the JVM (Java and every JVM language, Android
included) and from BEAM
(Erlang, Elixir) the way Python already uses them: a native ~mode lib~
library plus generated bindings, without translating til to those VMs. The
managed backends are cancelled (JVM #375, BEAM #374): til's raw-memory and
ownership model maps down to machine targets and fights managed VMs, while a
binding keeps til native and lets each VM keep what it is good at.

*** The bridge each VM needs

Python's bindings use ~ctypes~: plain source that loads the library at run
time, nothing compiled. Neither VM has a portable equivalent:

- JVM: JNI is the bridge that works on desktop JVMs and Android alike (the
  JDK's FFM, ~java.lang.foreign~, is desktop-only; ART has none). JNI needs a
  small C bridge compiled against ~jni.h~, which only a JDK or the Android
  NDK provides. The generated side is plain Java, which every JVM language
  (Kotlin, Scala, Clojure, ...) calls natively, so no language gets wrappers
  of its own ([[../cancelled/454.org][#454]], cancelled).
- BEAM: NIFs (native implemented functions), a C bridge compiled against
  ERTS's ~erl_nif.h~ and loaded by an Erlang module. NIFs run on scheduler
  threads, so long calls must be marked dirty or yield, and a crash takes
  the VM down -- the bindings must say which calls are safe to call
  directly.

Til already emits C, so the bridge itself can be generated C compiled into
the library (or beside it). Generating its sources needs no JDK or OTP;
compiling it does.

*** Scope

  - Reuse the library's exported interface and native ABI as the single
    source of truth, as the Python bindings do; no hand-maintained
    declarations per language.
  - Specify, per VM: numeric widths (unsigned types included), strings,
    aggregates, enums, borrowed and mutable references, owned results and
    explicit release, callbacks, and throws. Reject unsupported signatures
    with diagnostics rather than changing their semantics.
  - Keep generating binding sources separate from compiling the bridge, so a
    default build never needs a JDK, the NDK or OTP.

*** Decisions needing approval before implementation

  Generated file names and layout, package/module naming, which builds
  generate which bindings by default, how the bridge is compiled and where
  the result is installed, and the tools each step requires.

*** Progress

  - JNI, first slice (scalars of every width, Bool, Str, throws): every
    ~mode lib~ build writes ~gen/til/java/til/<pkg>/<Cls>.java~ and
    ~gen/til/<name>_jni.c~ (layout and bridge command in doc/ffi.org,
    "Calling a library from the JVM"). Unbound signatures are listed in the
    class as ~// <name>: not bound: <reason>~. ~test/jni.til~ checks the
    generated text in the suite; a Java caller ran through a JDK on demand
    (now in the suite, below).
  - JNI, second slice: public structs as AutoCloseable handle classes
    (owned results, borrowed / ~mut~ / ~own~ parameters, inline scalar and
    Str field accessors, a default constructor from literal defaults),
    public globals and namespace data (getters, setters when ~mut~, borrowed
    handles for struct globals), and the cage ABI (~TIL_CPTR32~, now the
    default) in the bridge. The JDK run also drove
    library_namespace_a, the library the Python binding test checks, which
    completes the first JVM acceptance item.
  - JNI, third slice: enums (tags, payload getters, variant constructors),
    ~mut~ scalar / Str / Vec(Str) parameters as one-element arrays,
    ~returns ref~, ~own~ and ~ref~ fields, Vec(Str) as String[], function
    aliases, default constructors through nested constructor calls and own
    boxes, and FuncSigs as Java functional interfaces (callbacks through a
    TilClosure over a JNI global reference). The JDK run also reran
    both callers with ~--asan~ libraries and bridges, so the cage's leak
    report covers every bridge path. What stays unbound is listed in
    doc/ffi.org and in each generated class.
  - The JVM checks run in ~make test~, like the Python ones: the ~jni~ test
    (jni_lib) and library_namespace (library_namespace_a, beside its Python
    check), each with a Linux ASAN leak run. A JDK is an optional
    dependency: ~make test NO_JVM=1~ (~bin/tests --no-jvm~) skips the JDK
    runs on hosts without one.
  - Open: whether ~til build~ should compile the bridge, Java packaging (a
    jar), Android packaging (#462); then the BEAM half (NIFs).

*** Acceptance

  - [X] A JVM caller (desktop) loads a til ~mode lib~ library through the
    generated JNI bridge and exercises values, ownership/release and errors
    against the same interface the Python bindings test.
  - [ ] An Erlang caller does the same through a generated NIF module,
    including a long-running call that does not block a scheduler.
  - [ ] Unsupported signatures produce actionable diagnostics; existing
    Python/C/til bindings keep working.
