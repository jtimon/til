** OPEN #329 Add borrowed Slice(T) views and slicing

   Add a typed, non-owning view over a contiguous run of elements. A slice
   owns neither its backing allocation nor its elements; it carries a data
   pointer and a length, supports checked indexing/iteration, and can view an
   ~Array(T)~, ~Vec(T)~, or another ~Slice(T)~ without copying.

   This is the first of the slice issues: [[./330.org][#330]] (bracket type
   sugar), [[./478.org][#478]] (Str views as a typed slice) and
   [[./243.org][#243]] (value literals) all build on it.

   Works today as a plain core-library type:

   - Representation. #321 made a no-default ~ref~ field required at
     construction and left null only in the raw quarantine. ~ref data : U8~
     is a raw-buffer label, so ~data~ may be null exactly when ~count~ is 0
     (a slice of a lazy-empty Vec; ~Slice(T)(data = 0, count = 0)~ compiles).
     That settles the "reconcile the empty slice with #321" item.
   - Generic type through ~struct<T: Type> { ... }~, the same generator path
     as Array/Vec.
   - Checked ~s[i]~, ~for x : T in s~ (the ~len~ / ~unsafe_get~ lowering),
     nested slicing, a slice as a parameter, as a struct field with no
     default (#242), and returned from a function that borrows a parameter.
   - The auto-generated clone/delete: a ~ref~ field is copied as a pointer
     and never freed (doc/concepts/ownership.org, "Fields").
   - Owner lifetime. The typer's carried-borrow summaries
     (~ref_return_carried_params~ / ~ref_return_into_params~, #351/#357)
     see that the returned struct carries a borrow of the parameter, and the
     garbager's ~collect_call_ref_return_edges~ keeps the owner alive
     through the slice, through a slice of the slice, and through a clone of
     it. A temporary source (~of_vec(make(), 0, 2)~) is hoisted and kept
     alive as well. All ASAN-clean. This answers "specify how the garbager
     extends an owner's last use through every live slice": it already does.
   - Rejected today, by existing diagnostics:
     - returning a slice of a local: "cannot return a borrow of local
       'local' inside 'ProtoSlice__Str': the local dies with this call"
       (~check_carried_borrow_of_local_return~);
     - the same through a wrapping struct ("inside 'Holder'");
     - reassigning the owner while the slice is used later: "cannot reassign
       'values' while 'view' still borrows its storage";
     - ~own values.delete()~ followed by a use of the slice: "use of
       'values' after ownership transfer".

   Holes found (ASAN use-after-poison compiled; garbage bytes or silence
   interpreted). None is specific to slices:

   - H1, inner-scope escape through an owned deposit. A slice of a
     block-local pushed with ~own~ into a ~Vec(ProtoSlice(Str))~ declared
     outside the block is accepted, and the Vec reads freed memory after the
     block. Str views have ~check_view_escapes~ for exactly this (#456) and
     ~Vec(ref T)~ has the deposit lifetime checks; a struct that CARRIES a
     ref field and is deposited by value has neither.
   - H2, owner mutation. ~values.push(...)~ while a slice is still used
     later reallocates under it. The same hole exists without any slice:
     ~ref first : Str = values[0]~, then ~values.push(own ...)~, then
     ~println(first)~ compiles today and reads freed memory. ~Vec.get~'s doc
     comment says the reference is "valid until the next mutation"; nothing
     enforces that.
   - H3, write permission. ~ref mut x : I64 = view[1]~ followed by ~x = 20~
     writes through a slice of an immutable Vec. This is the access-path
     enforcement #490 / #491 still have pending, not a slice rule.

*** Decisions still needed

   Decided 2026-11-15: slicing is spelled ~a[low..high]~ (see "Approved
   type and slicing syntax").

   Decided 2026-11-15: Slice has a ~new~. A struct with ~new~ in its
   namespace cannot be built with the field literal outside that namespace
   (#99, ~infer_struct_constructor_fcall_impl~: "struct 'X' has a new()
   constructor; use X.new(...) instead"), and that is wanted here: without
   it ~Slice(Str)(data = 0, count = 1000)~ compiles and forges a view with
   no owner. More constructors may exist under their own names; ~new~ is
   the one that disables the literal. ~new~ itself calls the literal, and
   every other constructor reuses ~new~ rather than repeating it. (The
   typer would allow the literal anywhere inside Slice's own namespace --
   the rule compares the active type name, as ~Vec.with_capacity~ and
   ~Range.clone~ rely on -- so "only ~new~ spells the literal" is this
   type's convention, giving one place where the fields are set. Outside
   the namespace, ~Vec.slice~ / ~Array.slice~ have no choice.)

   Proposed shape, following core: ~new~ takes what the type cannot do
   without (~Range.new(start, end)~, ~Array.new(cap)~,
   ~Expr.new(data, line, col)~; ~Vec.new()~ takes nothing because nothing
   is mandatory), further constructors are named (~with_capacity~,
   ~from_hex~, ~from_c_str~), and a view or conversion is a method on its
   source that calls the other type's constructor (~Array.to_vec~ calls
   ~Vec(T).with_capacity~; ~Str.substr~). So: ~Slice(T).new(data, count)~,
   called by ~Vec.slice~ / ~Array.slice~, which live outside Slice's
   namespace and therefore cannot use the literal either. Checked with the
   prototype: with a ~new~ the literal is rejected, and a function outside
   the namespace that builds the slice through such a constructor from
   ~ptr_add(v.data, ...)~ still gets the "cannot return a borrow of local"
   and "cannot reassign ... while ... still borrows" diagnostics and is
   ASAN-clean.

   Still open:

   - Mutability for the first cut. Recommended: read-only slices (no ~set~,
     ~get~ / ~unsafe_get~ return ~ref T~), with writable slices decided
     together with #490 / #491 once access-path enforcement exists; until
     then H3 applies to slices exactly as it applies to ~Vec.get~.
   - The H2 rule. Recommended: reject passing an owner as a ~mut~ argument
     or receiver while a borrow INTO its storage (an element ref or a slice)
     has a later use, the same shape as today's reassignment diagnostic.
     That is conservative (~v.set~ does not reallocate), so its first step
     is to count what it flags in src/ and test/ before it becomes an error.
   - Method names for the open-bound forms, since the sugar must not
     evaluate the receiver twice to ask for its length. Proposed:
     ~slice(low, high)~, ~slice_from(low)~ and ~as_slice()~, with ~a[..high]~
     lowering to ~a.slice(0, high)~.

*** Prototype

   Kept here so the status above can be re-checked; it was a file under
   tmp/ and is not committed anywhere.

   #+begin_src til
   ProtoSlice := struct<T: Type> {
       ref data : U8
       const count : USize = 0
   namespace:
       len := func(self: ProtoSlice(T)) returns USize { return self.count }
       unsafe_get := func(self: ProtoSlice(T), i: USize) returns ref T {
           return ptr_add(self.data, i.to_uptr().mul(T.size().to_uptr()))
       }
       get := func(self: ProtoSlice(T), shallow i: USize) returns ref T throws OutOfBounds {
           if i < self.count { return self.unsafe_get(i) }
           throw OutOfBounds()
       }
       of_vec := func(v: Vec(T), lo: USize, hi: USize) returns ProtoSlice(T) throws OutOfBounds {
           if lo.lte(hi).and(hi.lte(v.count)) {
               return ProtoSlice(T)(data = ptr_add(v.data, lo.to_uptr().mul(T.size().to_uptr())), count = hi.sub(lo))
           }
           throw OutOfBounds()
       }
       slice := func(self: ProtoSlice(T), lo: USize, hi: USize) returns ProtoSlice(T) throws OutOfBounds {
           if lo.lte(hi).and(hi.lte(self.count)) {
               return ProtoSlice(T)(data = ptr_add(self.data, lo.to_uptr().mul(T.size().to_uptr())), count = hi.sub(lo))
           }
           throw OutOfBounds()
       }
   }

   // H1: accepted today, reads freed memory.
   h1 := proc() {
       mut views := Vec(ProtoSlice(Str)).new()
       {
           base := vec(Str, format("a", "1"), format("b", "2"))
           views.push(own ProtoSlice(Str).of_vec(base, 0, 2)!)
       }
       println(views[0][0])
   }

   // H2: accepted today, reads freed memory.
   h2 := proc() {
       mut values := vec(Str, format("a", "1"), format("b", "2"))
       view := ProtoSlice(Str).of_vec(values, 0, 2)!
       values.push(own format("c", "3"))
       println(view[0])
   }
   #+end_src

*** Verified language precedents

   Checked 2026-07-27. Jai has no public official specification, so its
   entries below come from current beta-community documentation and are
   labelled accordingly; Odin, Go, and Zig references are official.

   - Odin: [[https://odin-lang.org/docs/overview/#slices][official overview]].
     ~[]T~ is a slice; ~a[low:high]~ creates a half-open view. Fixed arrays use
     ~[N]T~ and dynamic arrays use ~[dynamic]T~.
   - Go: [[https://go.dev/ref/spec#Slice_types][official specification]].
     ~[]T~ is a slice descriptor sharing an underlying array;
     ~a[low:high]~ is half-open. Arrays use ~[N]T~.
   - Zig: [[https://ziglang.org/documentation/master/#Slices][official language
     reference]]. ~[]T~ is a slice and ~a[low..high]~ is half-open; arrays use
     ~[N]T~.
   - Jai: [[https://raw.githubusercontent.com/wiki/Jai-Community/Jai-Community-Library/Getting-Started.md][beta-community wiki]].
     ~[]T~ is an "array view", while ~[..]T~ is the resizable/dynamic array.
     Static and dynamic arrays convert to views when passed to a view
     parameter. A current beta-user [[https://sjoerdev.github.io/posts/jai-guide/#arrays--lists][guide]]
     reports the same three type spellings, but public material is not an
     authoritative Jai language specification.

   Thus ~[..]Str~ is not the slice spelling in either Jai or Odin. In Jai it
   is the growable array (the analogue of til's ~Vec(Str)~); Odin spells that
   type ~[dynamic]Str~. Both reserve ~[]Str~ for the borrowed view.

*** Approved type and slicing syntax

   Use ~[]T~ in type positions. Both Jai and Odin use this spelling for
   borrowed views. Keep ~Slice(T)~ as the canonical semantic type name:

   #+begin_src til
   consume := func(items: []Str) {
       for item : Str in items { println(item) }
   }

   Holder := struct {
       // A field declaration specifies the type only. Its backing view is
       // supplied by Holder(...) rather than forced into a field default.
       names : []Str
   }

   names := array(Str, "a", "b", "c")
   holder := Holder(names = names[0..2])
   #+end_src

   Slicing uses til's own half-open range spelling (Candidate A below).
   Approved by the human on 2026-11-15, after reading the same program in
   both spellings: it is consistent with the range syntax of for loops and
   lets the parser reuse the range code. Candidate B is kept as the
   rejected alternative.

   *Candidate A -- til-native / Zig-style range (APPROVED):*

   #+begin_src til
   middle : []Str = names[1..3]  // indices 1 and 2; high bound excluded
   prefix : []Str = names[..3]
   suffix : []Str = names[1..]
   all    : []Str = names[..]
   #+end_src

   Til already uses half-open ~lo..hi~ ranges, and today's subscript parser
   already parses ~names[lo..hi]~ as ~names.get(Range.new(lo, hi))!~
   (nothing writes that today, and no type has a ~get~ taking a Range).
   Open bounds are new parser cases; see the Plan's step 5.

   *Candidate B -- Odin / Go colon range (rejected):*

   #+begin_src til
   middle : []Str = names[1:3]
   prefix : []Str = names[:3]
   suffix : []Str = names[1:]
   all    : []Str = names[:]
   #+end_src

   This copies Odin/Go directly and visually separates indexing from til's
   value-level ~Range~, but colon is not currently an expression operator and
   needs dedicated parsing inside brackets.

   Public Jai sources reliably confirm the ~[]T~ type but not one official
   slicing-operator spelling. One current beta-user guide shows
   ~value[low..high]~; treat that as supporting evidence only, not authority.

*** Semantics

   A first cut should define the following contract before adding sugar:

   - ~Slice(T)~ stores a non-owning pointer plus ~count: USize~. It has no
     capacity and never reallocates.
   - ~len~, ~unsafe_get~, checked ~get~, and checked ~set~ mirror ~Array(T)~ /
     ~Vec(T)~. Iteration therefore works through the existing ~len~ /
     ~unsafe_get~ lowering.
   - ~slice(low, high)~ uses half-open bounds and throws ~OutOfBounds~ unless
     ~low <= high <= len~. The subscript sugar uses ~!~, matching today's
     checked ~a[i]~ behavior; callers that want propagation can call
     ~a.slice(low, high)?~ explicitly.
   - Slicing a slice composes offsets without allocating.
   - Copy/clone copies only the descriptor. Delete never destroys elements or
     backing storage; it only releases a heap wrapper when the representation
     actually allocated one.
   - Mutability must be explicit. Decide whether all slices permit element
     writes (matching current Array/Vec refs), or whether the type system needs
     separate read-only and mutable views before accepting ~view[i] = value~.
     Since this was written, #490 / #491 defined independent slot and
     referent permissions (~returns ref T~ read-only, ~returns ref mut T~
     writable); see "Decisions still needed".
   - An empty slice is a real expected state: ~data~ is a ~ref ... : U8~
     raw-buffer label, null exactly when ~count~ is 0 (settled by #321, see
     "Current status").

*** Borrow and lifetime rules

   The backing owner must outlive every slice. At minimum diagnose these
   cases at the source:

   #+begin_src til
   bad := func() returns []Str {
       local := array(Str, "a", "b")
       return local[..]             // must not return a view of dead storage
   }

   mut values := vec(Str, "a", "b")
   view := values[..]
   values.push(own "c")             // may realloc and invalidate view
   println(view[0])                  // must not silently use a dangling view
   #+end_src

   Prefer a loud compile-time lifetime error. If the current ownership model
   cannot prove the needed lifetime yet, restrict the first implementation to
   scopes/calls it can prove; do not silently copy into an owning Array/Vec or
   continue with a potentially dangling pointer.

   Expected valid sources include globals, a caller-owned parameter whose
   view does not escape it, and a local Array/Vec used while that owner remains
   live and un-reallocated. The garbager already extends an owner's last use
   through every live slice (the carried-borrow edges; see "Current
   status"). Of the two examples above, the first is rejected today; the
   second is hole H2.

*** Implementation outline (original, superseded by "Plan" above)

   Kept for the record. Items 1, 2 and 5 are the Plan's steps 1, 4 and 5.
   Item 3's first half ("a Slice borrows its source") needs no work: the
   carried-borrow summaries already provide it. Its second half is H2.

   1. Add canonical ~Slice(T)~ storage and methods in core, using the same
      generic type-generation path as Array/Vec.
   2. Add explicit ~slice(low, high)~ constructors on Array, Vec, and Slice;
      prove checked indexing, mutation policy, clone/delete, and for-in before
      parser sugar.
   3. Teach ownership/liveness analysis that a Slice borrows its source and
      that Vec capacity-changing operations invalidate outstanding views.
   4. Extend ~parse_type_ref~ for the approved ~[]T~ spelling. Once one range
      candidate is approved, extend the postfix subscript parser for those
      forms.
   5. Lower all sugar to the explicit Slice methods before interpreter/builder
      stages; neither backend should need syntax-specific handling.
   6. Document FFI layout only after deciding whether Slice is guaranteed to
      be exactly ~(data, count)~ and how empty slices are represented. Under
      the default ~--usize=32~ the prototype is a native pointer plus a
      32-bit count; whether stored references stay native-width is #313's
      open question.

*** Acceptance

   - Explicit ~Slice(T)~ construction and ~[]T~ annotations work for locals,
     parameters, returns, and fields without requiring field defaults.
   - Array, Vec, and Slice sources produce zero-copy subviews with checked
     half-open bounds.
   - Indexing, assignment under the approved mutability rule, nested slicing,
     and for-in work in interpret and compile modes.
   - Slice clone/delete never clone or destroy backing elements.
   - Escaping a dead owner and using a view across a Vec reallocation are
     rejected, with regression tests naming the violated lifetime.
   - Tests cover empty/full/prefix/middle/suffix views, low > high, high > len,
     aggregates with owned elements, and source destruction ordering.

   The ~[]T~ type spelling and the ~a[low..high]~ slicing spelling are both
   settled. What remains open is listed under "Decisions still needed".
