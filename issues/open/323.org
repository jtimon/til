** WIP #323 Try HashMap instead of Map for the hot lookup-only tables in src/self, one candidate per commit

til's core Map is two sorted parallel Vecs with a binary-search probe:
O(log n) Str_cmp calls per lookup, ordered iteration, and a win on
small tables. std's HashMap is separate chaining over dense parallel
arrays: ~1 compare per lookup, insertion-ordered iteration, and a win
on big ones.

*** READ #214 FIRST -- it already ran this experiment and said no

#214 ("Unordered HashMap for big tables where key order does not
matter") profiled the self-host compiler at 21153c7 and concluded the
migration was empirically NOT worth it. Its finding: the only Map hot
enough to matter was the typer's root TypeScope.bindings (~170
entries), and a drop-in swap would REGRESS, because HashMap.new
pre-allocates 16 buckets while a TypeScope is created per
function/block -- construction cost swamps the per-lookup saving.

#214 also left a re-check recipe and three go/no-go criteria. A
migration is worth attempting only when ALL THREE hold:

  a. the candidate appears near the top by INCLUSIVE (total_ms) time,
  b. the implied typical-N is well above the crossover (call it 32),
  c. the container is CONSTRUCTED RARELY -- once per build or per
     pass, not once per function/block.

Criterion (c) is the one that kills most candidates, and it is why
this issue's first draft was wrong: it ranked TypeScope.struct_defs /
func_defs top on call count alone, but those are FIELDS OF TypeScope,
constructed per scope exactly like bindings. Same for the
interpreter's Scope.heap_bindings.

Worse, the gap has WIDENED since #214 measured: master f671bb1 made
empty Vecs cost zero mallocs, so an empty core Map is now free, while
HashMap.new still eagerly pushes 16 bucket entries. Every per-scope
candidate is further behind than it was.

*** Measurements

Profile, post-#307 (`bin/til run examples/profile.til test/maps.til
<N>`; self_ms from an instrumented --prof build, which inflates small
hot functions -- treat CALL COUNTS as the signal):

  Map__Str_Dynamic_get       2883715 calls    287.9 self_ms
  Map__Str_TypeBinding_get    834825 calls    184.7 self_ms
  Map__Str_U32_get            208616 calls     56.5 self_ms
  Map__Str_U32_has            202657 calls     55.7 self_ms
  Map__Str_HeapBinding_get    192487 calls     58.0 self_ms
  Str_cmp                   10041303 calls    567.6 self_ms

Str_cmp is the top self-time row and the Map binary searches are its
dominant caller (~log2(n) compares per probe). Str.cmp is already one
memcmp over the common prefix and Str.eq early-outs on length and
same-buffer, so the residual is CALL COUNT times per-call overhead,
not byte scanning -- fewer compares per probe is the lever.

Microbench (`bin/til run examples/bench_hashmap.til`), Str keys:

  | N       | Map has/get | HashMap has/get | Map ins | HashMap ins |
  |---------+-------------+-----------------+---------+-------------|
  |   1,000 |   0 / 0 ms  |    0 / 0 ms     |    0 ms |       0 ms  |
  |  10,000 |   2 / 4 ms  |    1 / 2 ms     |    5 ms |       4 ms  |
  | 100,000 |  35 / 43 ms |   17 / 24 ms    |  217 ms |      78 ms  |

HashMap roughly halves lookup at 100K and crushes Map on Str insert
(the sorted-array memmove). But that table could not answer either
criterion: its smallest size, 1,000, already reads 0ms while the
compiler's hot tables are ~170 entries, and it never measured
construction. Both gaps are now filled (see Progress).

Criterion (b) -- per-lookup cost, 2,000,000 Str lookups per row so the
rows are comparable:

  | N    | Map   | HashMap |
  |------+-------+---------|
  |   16 | 149ms |   168ms |
  |   32 | 181ms |   173ms |
  |   64 | 202ms |   174ms |
  |  128 | 247ms |   190ms |
  |  256 | 278ms |   184ms |
  | 1024 | 459ms |   197ms |

The crossover sits at N ~= 32, exactly where #214 guessed it. At the
compiler's ~170 entries HashMap wins lookup by roughly 1.3x -- real,
but not the 2x the 100K row suggests.

Criterion (c) -- build and drop 200,000 tables (the per-scope
pattern), I64 keys to keep Str allocation out of the number:

  | entries | Map   | HashMap |
  |---------+-------+---------|
  |       0 |  16ms |   147ms |
  |       4 |  77ms |   311ms |
  |      16 | 308ms |  1228ms |

An EMPTY HashMap cost 9x an empty Map to build (0.74us vs 0.08us
each). That was the eager 16-bucket allocation, and it was decisive:
at ~28ns saved per lookup (the N=128 row), one extra construction
needed ~23 lookups against that table just to break even. A root scope
answering millions of lookups clears that easily; a per-function scope
answering a handful never does -- which was exactly #214's verdict,
with numbers behind it rather than reasoning.

*** After lazy buckets (below), the same rows re-measured

  | entries | Map   | HashMap before | HashMap after |
  |---------+-------+----------------+---------------|
  |       0 |  14ms |          147ms |          27ms |
  |       4 |  67ms |          311ms |         321ms |
  |      16 | 262ms |         1228ms |         987ms |

(Absolute times drift a few percent between runs -- the Map column
moved too -- so compare within a row, not across runs.)

Empty construction drops 5x and the Map:HashMap ratio goes from 9.2x
to 1.9x. Recomputing the break-even from the same run: an extra
construction now costs (27-14)ms/200K = ~65ns, and the N=128 lookup
rows save (154-111)ms/2M = ~21ns per lookup, so a table needs about
THREE lookups to pay for itself instead of twenty-three.

That is the number that re-opens the per-scope candidates. Tables
built per function/block are mostly empty or near-empty and answer a
handful of lookups each -- at 3 they are plausible, at 23 they were
not. The entries=4 and entries=16 rows are unchanged, as expected:
a table that inserts seeds its buckets anyway, so lazy buckets buy
nothing there. The win is exactly and only in the empty case, which is
the common one for scopes.

*** Correctness gate for every candidate: is the map ITERATED?

Map iterates in KEY order; HashMap iterates in INSERTION order. Any
table whose iteration order is observable cannot be swapped without
first making the consumer order-independent. Grep for `.keys` /
`.values` / `for k, v in <map>` on the specific field, do not assume.
Iteration-order sensitivity in this compiler has already produced real
bugs (the #307 hardening fixes, the ns-constant ordering work).

*** The #214 emit blocker: VERIFIED GONE, no fix needed

#214 warned of a latent emit bug: a struct namespace data decl
(`mut HashMap.hasher : HashFn = fnv1a`) reaching the generated forward
header as a plain `void * HashMap_hasher;` instead of `extern ...`, so
the first src/self file to import hashmap would fail to link with
"multiple definition of HashMap_hasher".

Checked directly and it does NOT reproduce. Method matters here,
because the obvious check is vacuous: adding `import("../std/hashmap")`
to src/self/context.til builds fine but emits NOTHING -- the scavenger
prunes the unused import. Adding a HashMap-typed Context FIELD emits
the type but still not the hasher, because nothing calls `set`, so
`hash_key` (the only reader of `HashMap(K, V).hasher`) is pruned too.
Only a probe that actually inserts pulls the symbol in.

With such a probe (a Context field defaulted from a func that does one
`set`), the self-host build compiles and links clean, `bin/til` runs
the suite, and the symbol appears exactly once:

  gen/til/til.c:  TilClosure * HashMap__Str_U32_hasher;   <- definition
  gen/til/til.c:  HashMap__Str_U32_hasher = (void *)&fnv1a__til_closure;
  gen/til/til_forward.h:  (absent)                        <- no dup decl

The templated HashMap monomorphizes per specialization
(HashMap__Str_U32_hasher, not HashMap_hasher), and the forward header
does not declare namespace data decls at all any more, so there is
nothing to collide. Whatever fixed it (#236's neighbourhood, or the
template/emit work since 21153c7), no `header_extern` plumbing is
needed. Probe reverted; nothing from this check is committed.

*** HANDOFF: the remaining steps are TIMING work -- run them locally

Everything measurable without a stopwatch is done (see Progress). What
is left is candidate swaps whose whole point is a before/after number,
and the remote sandbox is not a trustworthy stopwatch: absolute times
drifted several percent between runs of an unchanged binary. A local
session should take these.

**** Ground rules for the measurements

- Compare WITHIN one run, never across runs. Every table in this issue
  follows that rule; the Map column is re-measured alongside the
  HashMap column each time precisely so drift cancels.
- Build before measuring, and remember `bin/til` goes stale whenever
  master moves: a stale compiler produced a phantom
  "Map__Str_USize vs Map__Str_U32" type error here once. `make` first.
- Bench:      bin/til run examples/bench_hashmap.til
- Profile:    bin/til run examples/profile.til test/maps.til 60
  (the profile harness builds bin/til_prof itself, ~100s, then runs
  instrumented; self_ms is inflated for small hot functions, so read
  CALL COUNTS and inclusive total_ms, per #214 step 3.)
- Local-session conventions from CLAUDE.md apply: dedicated worktree,
  `systemd-run --user --scope -p MemoryMax=64G make clean && make test`,
  commit in the worktree, do NOT push.

**** Decision rule per candidate

Keep the swap only if the profile row for that table improves AND the
suite wall-clock does not regress. A neutral or worse result is a
RESULT: record the numbers here and revert the swap. If two candidates
in a row measure neutral, stop and close the issue with the numbers --
that is #214's answer confirmed, and it is a perfectly good outcome.

**** Mechanical notes that will save time

- Ergonomics are already equal: since step 1, HashMap supports
  `m[k]` (bang-subscript), `m.get(k)? catch`, `for k, v in m`,
  clear/clone/remove -- verified. A swap is a one-line type change at
  the field plus whatever the compiler then complains about.
- WATCH THE USize WIDTH ALIAS. A `Map(Str, USize)` field and a
  `Map(Str, USize)` *parameter* monomorphize to different names
  (Map__Str_U32 vs Map__Str_USize) and the typer rejects the mismatch.
  This already bit twice (StructDef.field_name_at's comment, and
  ns_const_eval_order, which had to return Vec(I64) instead of
  Vec(USize)). Candidate 4 is a Map(Str, USize) -- expect it there.
- A probe that "verifies" something by importing hashmap into
  src/self is usually VACUOUS: the scavenger prunes an unused import,
  and even a HashMap-typed field does not emit `hash_key` unless
  something calls `set`. Make the probe insert.

*** Candidates, with their gates already checked

Two claims in this issue's earlier drafts were WRONG and are corrected
below -- re-verify with the greps rather than trusting prose.

1. ctx.interp_type_defs -- Map(Str, Dynamic), src/self/context.til:666.
   ONE instance, on the Context: passes criterion (c) outright, which
   is why it is first.
   Writes: initer.til:88, initer.til:554. Read: interpreter.til:325
   (lookup_interp_type_def).
   ITERATED -- correcting the earlier "never iterated" claim:
   interpreter.til:60, `stable_type_name`, walks the keys to find the
   one equal to `name` and returns a REF to the stored key (callers
   need a stable Str address, and Map.get hands back the value, not
   the key). Order-INDEPENDENT: keys are unique, so exactly one entry
   matches and iteration order cannot change the answer. Safe to swap;
   the scan works the same over HashMap's dense keys Vec.

2. TypeScope.struct_defs and TypeScope.func_defs -- Map(Str, Dynamic),
   src/self/context.til:104-105. The 2.9M-get row, the hottest tables
   in the compiler. NOT iterated anywhere (grep confirms zero
   `.keys` / `.values` / `for .. in` sites). Per-scope, so this was
   disqualified by criterion (c) until lazy buckets landed; at the new
   ~3-lookup break-even it is the most interesting candidate in the
   issue. Note both fields live on the same struct, so they can be
   swapped independently or together -- try struct_defs alone first,
   it carries the get_struct traffic.

3. Scope.heap_bindings (interpreter) -- 192K gets. CORRECTION: the
   earlier draft said "iterated once, at teardown". It is iterated in
   SIX places, and three of them are a real hazard:
   - interpreter.til:4006, 4036 -- teardown drops; order = free order,
     independent.
   - interpreter.til:4062 -- closure_env_clone copies every binding;
     per-binding independent.
   - interpreter.til:2607, 3384, 6437 -- these walk
     ctx.ns_fields.heap_bindings looking for an entry whose func_def
     POINTER matches, then use the key `qn` to build a name. If two
     qualified names ever share one func_def, FIRST MATCH WINS and
     which one is first changes with iteration order. That is a
     behaviour change waiting to happen, not just a golden churn.
   Also note ns_fields is a Scope too, so swapping the field type
   changes the namespace table and the per-call scopes together.

4. TypeScope.bindings -- 835K gets, iterated in SEVEN places
   (garbager.til:981; typer.til:3521, 3551, 3579, 5141, 5150, 5248),
   and collect_scope_locals' order is pinned by
   test/gc_audit.expected. Swapping reorders that golden and can
   reorder diagnostics. #214's original rejection; stays last
   regardless of what 1-3 measure.

5. StructDef.fields_index / ns_index -- Map(Str, USize), ~410K
   get+has, but tiny tables (a handful of members each), so criterion
   (b) fails outright: expected LOSS. Worth at most one confirming
   measurement, and see the USize width-alias note above.

*** Process

Land one candidate per commit so each can be merged (or dropped) on
its own measured result. Each commit states, in its message, the
before/after rows from
`bin/til run examples/profile.til test/maps.til <N>` for the table it
touched plus the wall-clock of the run, so a swap that does not pay
can be identified and reverted without unpicking the others. A
candidate that measures neutral or worse is a RESULT, not a failure:
record it here and move on -- as #214 did, which is why this issue
exists in a useful form at all.

If the measurements repeat #214's verdict, the right outcome is to
close this issue with the numbers and leave core Map in place, not to
grind through the deferred list.
