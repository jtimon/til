** WIP #462 Android through the C backend and the NDK

Run til programs on Android by compiling the C backend's output with the
Android NDK, instead of translating til to a managed language (the JVM
backend, #375, is cancelled). Android has supported native code for years:
the NDK's clang builds C for the device CPUs, an app packages the result as
a ~.so~, and ~NativeActivity~ (with the NDK's ~android_native_app_glue~)
lets an app be written entirely in C -- Android supplies the small Java
shell that loads the library and forwards window, input and lifecycle
events. Many games ship this way.

*** What C can and cannot reach

- Directly, through NDK headers: OpenGL ES / Vulkan, audio (AAudio), input,
  sensors, assets, logging, and libc/POSIX through bionic.
- Only through JNI: standard UI widgets, permission dialogs, intents,
  notifications and most of the Android SDK, which are Java APIs.
- An app still needs a manifest and an APK built and signed by the Android
  tools.

So the natural first apps draw their own UI (raylib-style, GL), and anything
needing the Java SDK goes through generated JNI calls later
([[../fixed/463.org][#463]]).

The other direction matters as much: an ordinary Java or Kotlin app using a
til ~mode lib~ library through the binding #463 generates (a Java class
over a JNI bridge). JNI is the only bridge needed for that -- Android has no
FFM, and a JNA-like shim was cancelled (#477): it would still need a native
build per ABI. What is missing is building the library and its bridge with
the NDK.

*** Android lifecycle fixes found by the demo

Both fixes are in ~vendor/raylib/src/platforms/rcore_android.c~:

  - Back delivered ~APP_CMD_DESTROY~, but ~PollInputEvents~ set
    ~shouldClose~ and then entered another blocking ~ALooper_pollOnce~
    because the activity was paused. Android's UI thread waited for the
    native thread to exit, and the next launch timed out. Break out of
    polling on destruction so the application can run ~CloseWindow~ and
    return from its native entry point. The same reproducer then exits
    and relaunches instead of hanging.
  - ~APP_CMD_TERM_WINDOW~ had detached the GL context and destroyed the
    window surface. Once the loop could exit, ~CloseWindow~ tried to
    unload GL resources without a current context (confirmed by libEGL's
    error). Request a config supporting window and pbuffer surfaces, and
    on destruction bind a 1x1 pbuffer when the window surface is gone.
    Cleanup then runs with the preserved context; ~ClosePlatform~ destroys
    the pbuffer and context normally. Creation/binding failures are fatal,
    not silently ignored. The GL-without-context error disappears.

Manual regression sequence on the installed, rebuilt APK: launch; Home;
wait three seconds for surface destruction; relaunch; Back; wait two
seconds; relaunch; repeat Back/relaunch. Check both log markers and the

*** Toolchain direction (agreed 2026-11-11)

Do not vendor the NDK: it is 1-2 GB and Google distributes it under the
Android SDK license. Instead vendor only what the host's own clang needs to
target Android, the way vendor/macos/ lets the host clang build for macOS
without an SDK (issue #25): upstream clang already knows the Android
triples (~--target=aarch64-linux-android28~), it only lacks a sysroot.
Everything in that sysroot is open source (bionic and the Linux UAPI
headers from AOSP: BSD / Apache-2.0; compiler-rt from LLVM: Apache-2.0
with the LLVM exception), so the subset can be redistributed with its
notices, as vendor/macos/README.org does for Zig's darwin headers.

The NDK is still the SOURCE of that subset and the reference to compare
against: a session with an NDK installed extracts it once (and on
upgrades), and CI can cross-check a vendored build against the NDK the
GitHub Ubuntu runners preinstall (~$ANDROID_NDK_LATEST_HOME~).

Development needs a device or emulator to run on, which the remote
sessions do not have (no NDK, no SDK, and dl.google.com is not reachable
from them). So the remote session prepares and documents; the
implementation is done by a local session with the Android SDK installed
(adb, an emulator or a phone), and CI runs it afterwards.

*** Preparation notes (remote session, 2026-11-11)

What the vendored sysroot must hold, per ABI (arm64-v8a first; x86_64 for
the emulator; armeabi-v7a later) and for the one minimum API level:

  - ~sysroot/usr/include~: the bionic C headers and the Linux UAPI headers,
    plus ~usr/include/<triple>/~ (~asm/~ and friends). Not libc++.
  - ~sysroot/usr/lib/<triple>/<api>/~: the linker stubs ~libc.so~,
    ~libm.so~, ~libdl.so~, ~liblog.so~ (stage 2 adds ~libandroid.so~,
    ~libEGL.so~, ~libGLESv3.so~), and the startup objects
    ~crtbegin_dynamic.o~, ~crtend_android.o~, ~crtbegin_so.o~,
    ~crtend_so.o~.
  - ~libclang_rt.builtins-<arch>-android.a~ (and ~libunwind.a~ if the clang
    driver asks for it): the host clang's resource directory has builtins
    for the host only. Needed at least for 128-bit ~long double~ math, which
    is the ~long double~ of arm64 and x86_64 Android.
  - Measure the size of the subset before vendoring it; headers dominate.

What ~src/self/codegen/ext.c~ and the targets need (Android defines
~__linux__~, so every Linux branch applies unless guarded with
~__ANDROID__~):

  - ~spawn_cmd~ starts ~"/bin/sh"~, which Android does not have; its shell
    is ~/system/bin/sh~. (The ~Cmd~ family uses ~posix_spawnp~ with a PATH
    search and is fine.)
  - ~posix_spawn~ / ~posix_spawnp~ exist from API 28 only. ext.c uses them
    for every child process, so API 28 (Android 9) is the natural minimum.
    ELF TLS (~__thread~, used only by the ~--prof~ profiler) needs API 29;
    below that clang emits emulated TLS on its own.
  - ~target_system_libs~ links ~-ldl -lrt -lm -lpthread~ on Linux; bionic
    has no ~librt~ or ~libpthread~ (both are in ~libc~), so Android links
    ~-ldl -lm~ (plus ~-llog~ if the runtime logs through logcat).
  - ~current_rss_bytes~ walks ~/proc~ and calls ~kcmp~. Verify permissions
    under ~adb shell~ rather than assuming Linux behavior. An APP process
    also runs under Android's seccomp filter, where a blocked syscall can
    kill the process. Audit the real call paths and test app execution
    separately; shell success is not proof of sandbox compatibility.
  - ~RTLD_DEFAULT~: bionic defines it (0 on 64-bit, ~0xffffffff~ on
    32-bit), so ext.c's fallback definition never applies; matters only for
    armeabi-v7a.
  - Link with ~-Wl,-z,max-page-size=16384~: Android 15 devices can use 16 KB
    pages, and Google Play requires 16 KB-aligned native libraries for apps
    subject to its 16 KB requirement. This flag alone is not proof:
    inspect every packaged native dependency and APK zip alignment, and
    audit the cage/allocator and runtime page-size assumptions.
  - Vendored libraries: compiled til programs do not reference libffi (see
    the CI comments on the cross jobs), so stage 1 needs only ext.c and core.
    raylib supports Android (~PLATFORM_ANDROID~) for stage 2; nng, secp256k1
    and tinyfiledialogs are out of scope until a program needs them.

For stage 3 (a til library in a Java/Kotlin app), the generated class's
loader (~emit_jni_native_loader~ in src/self/codegen/c_codegen.til) must
recognise Android: there ~os.name~ is ~"Linux"~, so today it would look for
~native/linux-arm64/~ in the jar -- glibc natives a merged server jar may
carry, which fail to load on bionic -- instead of loading from the APK's
~jniLibs/<abi>/~. Detect Android (~java.vm.name~ is ~"Dalvik"~ on ART) and
name the target ~android-<arch>~; with no such directory in the jar the
class already falls back to ~System.loadLibrary~, which is how Android
loads ~jniLibs/~.

*** Decisions needing approval before implementation

  - APPROVED (2026-11-11): the targets ~android-arm64~ and ~android-x64~
    first (~android-arm32~ later), in ~src/self/targets.til~.
  - APPROVED (2026-11-11): minimum API level 28 (Android 9, 2018), the
    first with ~posix_spawn~, which ext.c uses for every child process.
    About 97% of Play devices in October 2026; Samsung: Galaxy S8 / Note 8
    and later. It is a floor, not a limit: the same build runs on every
    newer Android, and APIs newer than 28 are reached by run-time lookup
    or an API-level check. Lowering it later is additive: re-extract the
    sysroot for the lower level (a lower level's stubs run on newer
    devices), add a fork/exec spawn path for bionic below 28, and add
    ~android-arm32~ for the 32-bit phones of that era.
  - The "roof" is not a fixed limit. The newest API a til program can call
    is that of the vendored headers, so extract them from the newest NDK
    (API 36-37 in late 2026) and re-vendor to raise it. An APK's
    ~targetSdkVersion~ (the newest Android it declares tested, which Google
    Play requires to be recent) is a stage 2 manifest choice, separate from
    both.
  - APPROVED (2026-11-11): the vendored sysroot lives in ~vendor/android/~
    (one sysroot for the minimum API level), found as targets.til finds
    vendor/macos/, with no environment variable. Neither it nor the NDK is
    needed by a default build or ~make test~.
  - The APK packaging route (the SDK's ~aapt2~ / ~zipalign~ / ~apksigner~
    directly, or Gradle) and where generated manifests and APKs live.
  - For stage 3: whether ~--jni~ for an Android target produces an AAR, a
    ~jniLibs/~ tree, or only the ~.so~ files for the app's own build.
  - Whether an emulator-based check runs anywhere automated (CI only, or
    opt-in locally).
