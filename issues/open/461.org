** OPEN #461 Simplify borrow-aware last-use destruction and reduce analysis cost

Revisit how much lifetime protection til should provide around non-owning
references and automatic last-use destruction. The reference-rebinding work
in #453 (merged as ~7a7ce5a51~) prompted a reported performance regression and
this policy question: should using a ref keep its owner alive, or should the
programmer be responsible for keeping the owner live?

~ref~ does not own its pointee. ~mut~ permits mutation; it does not transfer
ownership. Extending an owner's lifetime because a reference is used later
is an additional analysis policy, not a consequence of reference ownership.

*** Motivating case

  Schematic source, with ~borrow~ returning a reference to its argument:

  #+begin_src til
  a := first.clone()
  b := second.clone()
  ref mut alias := borrow(a)
  ref source := borrow(b)
  alias = source
  println(alias.text)
  #+end_src

  After rebinding, ~alias~ points at ~b~. Neither reference owns ~b~.
  Borrow-aware analysis retains ~b~ through the print. A simpler last-use
  policy could destroy ~b~ after its last direct use, making the later
  reference use a programmer error. In this example, writing ~println(b.text)~
  directly makes the owner's use explicit. Accessors, containers and conditional
  reference selection make less obvious versions of the same question.

*** Separate the decisions

  Preserve the two reference-operation fixes from #453:

  - Rebinding retargets the reference rather than overwriting its old pointee.
  - Rebinding a non-owning reference does not destroy its old pointee.

  Evaluate lifetime extension separately. Removing it changes when owned
  values and their resources are destroyed and which programs are valid; it
  is a language-policy change, not merely a faster implementation. The current
  analysis is not a complete dangling-reference proof, especially across raw
  pointers, Dynamic, explicit frees and FFI.

*** Investigation and possible simplifications

  - [ ] Measure the regression against the parent of ~7a7ce5a51~, using the
    same builds, inputs and compiler settings. Record time, peak memory and
    profiles; the dominant cost has not yet been established.
  - [ ] Profile the new scoped reference-loan walk, string-keyed maps/vectors,
    scope-name cloning and reach propagation. Check for repeated traversal of
    nested bodies already processed by the destruction pass.
  - [ ] Inventory existing borrow-driven lifetime extensions, not just the
    rebinding additions, and identify tests/programs that rely on them.
  - [ ] Decide whether programmers should keep owners live explicitly, whether
    provably unsafe uses should be rejected, or whether the current extension
    policy should remain. Document the intended destruction timing and the
    responsibility for dangling references before changing behavior.
  - [ ] If retaining protection, investigate narrower analysis, reuse of
    existing binding/fact identities, and avoiding new graph work in bodies
    without relevant rebindings. Compare measured improvements rather than
    assuming a particular data structure is the bottleneck.
  - [ ] If simplifying the policy, remove the corresponding analysis and
    revise lifetime-dependent tests/documentation while preserving rebinding
    semantics, destructor correctness and interpreter/C/FASM agreement.

  Relevant starting points: ~collect_reference_loans~,
  ~reference_storage_sources~ and ~propagate_borrow_edges~ in
  ~src/self/garbager.til~; reference-assignment provenance/lifetime checks in
  ~src/self/typer.til~; ~test/reference_rebinding.til~ and its negative fixtures.
  This issue does not authorize a new flag, opt-in mode or alternate analysis
  path; settle the language policy and improve the existing path.
