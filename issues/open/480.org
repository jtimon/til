** OPEN #480 A mut local holding a capture-free func is lifted to a top-level function

Found while binding ~mut~ closure parameters for the JVM (#463). The
initer's nested-definition lifting (~init_is_lift_target~ in
src/self/initer.til, issue #93) lifts every capture-free ~func~ declared in
a function body to a top-level ~<parent>_<name>~ function, ~mut~ locals
included. A ~mut~ local is a variable that starts out holding the function,
not a definition: once lifted it has no storage, so it cannot be reassigned
or passed to a ~mut~ parameter.

#+begin_src til
mode cli

Fn := func(I64) returns I64

swap := func(mut f: Fn, k: I64) {
    kk := k
    f = func(x: I64) returns I64 [own kk] { return x * kk }
}

main := proc() {
    mut f : Fn = func(x: I64) returns I64 { return x + 1 }
    swap(f, 3)
    println(f(5).to_str())
}
#+end_src

Compiled, the call passes ~&&main_f__til_closure~ (the address of the
lifted function's static closure, taken twice) and the C compile fails
(~label 'main_f__til_closure' used but not defined~).

Not lifting ~mut~ locals is not enough on its own: with that change the
interpreter reports ~f is undefined~ and the compiler panics with ~unwrap of
a None Option~ (context.til), so the capture-free ~func~ value held by a
plain local is unsupported further down as well (typer, interpreter and C
codegen). A capturing ~func~ is never lifted and already works as a ~mut~
local.

Workaround today: hold the closure in a struct field and pass the field
(~swap(h.f, 3)~), as ~test_mut_closure_param_assigned~ in
test/closures_compile_escape.til does.
