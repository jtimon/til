** WIP #415 Own-consuming reassignment double-deletes; audit cleanup masking

*** Required ownership behavior

Passing ~own value~ transfers responsibility for that value to the callee.
The callee destroys it or transfers it onward. In ~value = replace(own value)~,
the caller owns the returned replacement, but must not also destroy the old
value already consumed by the RHS. ASAP destruction must make that decision
at the ownership/cleanup source, not compensate with an idempotent destructor.

*** Reproducer

#+begin_src til
mode test

runtime_text := proc() returns Str {
    noop_proc()
    mut text := Str.with_capacity(8)
    text.push_str("head")
    return text
}

replace_text := proc(own text: Str) returns Str {
    assert_eq(USize, text.len(), 4)
    return runtime_text()
}

test_own_consuming_self_reassignment := test() {
    mut text := runtime_text()
    text = replace_text(own text)
    assert_eq(USize, text.len(), 4)
}
#+end_src

Run interpreted and compiled with ~til test --asan~. During the CFG-fact
optimization, an equivalent ownership_shapes test passed interpreted execution
but failed compiled ASAN execution with ~attempting double-free~. The same
failure reproduced with the unmodified master compiler, before the optimization.

Reconfirmed on top of master ~a581330e7~ with the exact source above:

bin/til test --asan -o tmp/own_reassignment_415 \
    -c tmp/own_reassignment_415.c tmp/own_reassignment_415.til

=== compile + run ===

  Str_delete -> test_own_consuming_self_reassignment
freed by:
  Str_delete -> replace_text -> test_own_consuming_self_reassignment

The generated C showed the duplicate ownership obligation explicitly:

#+begin_src c
static Str replace_text(Str *text) {
    /* argument use */
    Str_delete(text, 0);                 /* callee owns the old payload */
    return runtime_text();
}

static void test_own_consuming_self_reassignment(void) {
    Str text = runtime_text();
    {
        Str new_value = replace_text(&text);
        Str_delete(&text, 0);            /* wrong: old payload consumed */
        text = new_value;
    }
    /* later use and legitimate destruction of the replacement */
}
#+end_src

*** Reproducer: transfer in an earlier statement

Found 2026-10-09 while burning down the #375 JVM corpus. The same mistake
when the ~own~ transfer and the reassignment are separate statements: the
garbager still deletes the old value before rebinding, although
~push(own pt)~ already moved it into the Vec.

#+begin_src til
mode cli

P := struct {
    name := "p"
}

runtime_text := proc() returns Str {
    noop_proc()
    mut text := Str.with_capacity(8)
    text.push_str("first")
    return text
}

main := proc() {
    mut v := Vec(P).new()
    mut pt := P(name = runtime_text())
    v.push(own pt)
    pt = P(name = "second")
    println(v[0].name, " ", pt.name)
}
#+end_src

Expected ~first second~. Checked on top of master ~f4b028f~: ~til run~
aborts with ~free(): double free detected in tcache 2~, ~til run --asan~
reports the use, and ~til interpret~ panics on the delete itself:

#+begin_example
ERROR: AddressSanitizer: heap-use-after-free
    #1 Str_clone
    #2 main                      /* reading v[0].name */
freed by thread T0 here:
    #1 Str_delete
    #2 P_delete
    #3 main                      /* the P_delete(&pt, 0) below */

./src/self/interpreter.til:3070:38: panic: argument from moved binding: pt
#+end_example

#+begin_src c
Vec__P_push(&v, &pt);    /* pt's bytes, incl. name's buffer, now in v */

*** Cleanup paths and masking audit

Not all frees are protected by null checks or followed by pointer clearing.
~src/core/str.til~'s ~Str.delete~ frees ~self.c_str~ when ~cap < CAP_VIEW~
without a null guard or post-free zeroing. Its CAP_VIEW/CAP_LIT tests enforce
borrowed/static ownership; they do not make a repeated owning delete valid.
~free~ in ~src/core/mem.til~ is the external free operation. Libc ~free(NULL)~
is a no-op, but freeing the same non-null allocation twice is invalid.

The interpreter tracks actual transfers: ~scope_move_bound_raw~ clears the
source binding's pointer and sets ~moved_out~, and storage teardown checks that
state. Some other cleanup paths contain null checks or clear slots, including
generated own-field destructors and raw interpreter storage cleanup. Audit
their contracts rather than assuming they are all necessary or all defensive.

*** Scope / acceptance criteria

- [X] Fix the garbager's assignment/replacement cleanup decision so an RHS
  ownership transfer of the old target suppresses its caller-side destruction.
  Inspect ~insert_assign_delete~, ~flag_outer_assign_rebinds~, and the emitted
  ~save_old_delete~ path. Preserve destruction when the RHS only borrows the
  old value or consumes a different value.
- [ ] Cover body locals, outer-scope/global targets, captures and field/payload
  replacement paths where the same ownership mistake can occur. Keep the
  returned replacement's ownership and subsequent cleanup correct.
- [X] Inventory null guards, post-free clearing, moved-source zeroing and
  repeated-cleanup/default-return paths in generated and hand-written
  destructors, interpreter storage teardown, and backend cleanup adapters.
- [X] Remove checks/zeroing whose purpose is to silently absorb a cleanup
  that ownership analysis should not emit. Fix the ownership/lifecycle cause;
  do not replace the duplicate delete with another null check or skip guard.
- [X] Retain only genuine optional/empty/moved-state handling required by a
  documented contract (for example a lazy-empty container, None, or transfer
  metadata). Unexpected repeated owning destruction must fail at its source,
  not silently become a no-op. Audit and explain each retained case.
- [X] Add heap-backed ASAN regressions for self-consuming reassignment and
  surrounding control-flow shapes, in interpreted and compiled modes. Verify
  the emitted cleanup counts and real destructor side effects, so nulling or
  literal/view sentinels cannot conceal a duplicate owning cleanup.
- [X] Run the full required clean suite. The existing passing suite lacked
  this self-consuming reassignment shape; passing counts alone did not prove
  its ownership handoff correct.

*** Progress

2026-10-09, the decision fix. Every reassignment of a local is now
settled against the garbager's own ownership dataflow -- the CFG
solve the exit deletes already used, which spans the nested bodies of
a view -- instead of being decided by RHS shape alone:

- ~gc_flow_assign_verdicts~ gives each Assign to a binding, root or
  nested, its entry state. Its old value is CONSUMED when an own
  transfer moved it on every path in (Moved), or when the Assign's own
  RHS transfers it (~x = f(own x)~). A consumed root Assign gets no
  delete from ~insert_assign_delete~ and no ~save_old_delete~; a nested
  one has the ~save_old_delete~ that ~flag_outer_assign_rebinds~ set in
  the nested pass cleared by the owning view's pass
  (~gc_clear_consumed_assigns~; the walk is post-order, so the owner
  runs last and is the one that sees the paths).
- Mixed at a reassignment (moved on some paths only) is the exit's
  conditional-transfer problem moved earlier: the sink grafts the delete
  onto the owning paths of the transferring compound
  (~gc_mixing_transfer_index~), leaving the binding uniformly Moved
  there. This runs before the ~own_transfer~ gate, which
  ~check_use_after_own_transfer~ clears exactly when a reassignment
  re-owns the binding. A Mixed reassignment left after the sink panics,
  unless the unit is already rejected (#365's "transferred inside a
  loop" is that shape).
- Interpreter: an Assign whose ~save_old_delete~ names a moved-out
  binding used to skip the delete silently
  (~scope_drop_existing_heap_slot~ returns on ~moved_out~ for its other
  caller, a rebind); the Assign site now panics on it.

Regressions in test/ownership_shapes.til, both backends and ASAN: seven
shapes (RHS consumes; earlier statement consumes; one branch consumes;
nested RHS consumes the outer binding; nested consume-then-reassign;
consume then nested reassign on every branch; loop consume-and-reassign)
with a heap-backed Str (~own415_reassign_after_consume_str~) and with a
struct whose ~delete~ counts (~own415_reassign_after_consume_counted~),
so a duplicate or missing cleanup is a wrong count even where a literal
sentinel hides it from ASAN. Master's compiler fails them (interpreter
panic on the moved binding; ASAN use-after-free / double free).

2026-10-09, captures, payloads and globals. Probed every remaining
target kind on master ~6fab8c5e~, heap-backed Str, both backends + ASAN:

- Payloads: closed at the source already. ~own p~ on a switch payload
  binding is "cannot pass ref variable to 'own' parameter".
- Captures of a deferred closure (Body value, capturing func): both
  backends ACCEPTED ~own x~ and broke on every shape -- self-consuming
  reassignment, consume-then-reassign, consume-only -- for Ref captures
  (~[mut x]~) and own captures (~[own mut x]~) alike: heap corruption
  interpreted, uncompilable C compiled (~own_value_arg_has_outer_ptr~
  unboxed the env slot as an owned outer pointer). Root cause was the
  typer, not the backends: a Ref capture borrows the frame's binding
  exactly as a ~mut~ parameter borrows the caller's, and a ~mut~
  parameter cannot be passed ~own~ at all. An own capture belongs to
  the env, which the next call reads and the drop deletes -- the reason
  a re-callable (FnMut) closure cannot move out of a capture in Rust.
  ~check_own_captures~ (typer.til) now rejects it for both kinds; inline
  capture blocks stay legal (they run once, inside the enclosing view's
  dataflow). Typer errors: test/typer_errors.til ~terr415_closures~,
  needle "cannot pass capture" (3).
- Globals rebound from inside a function: ~g = f(own g)~ deleted the old
  value the callee had just released (interpreter: the moved-binding
  assert; compiled: double free). No view's dataflow spans a function
  body from the global's owner, so ~flag_outer_assign_rebinds~ now lets
  the assign's own RHS transfer decide: a rebind whose RHS consumes its
  target sets no ~save_old_delete~. Regression:
  ~own415_global_self_reassignment~ (test/ownership_shapes.til; master's
  compiler panics on it).

Still open:

- Globals consumed in an EARLIER statement of a function, then
  reassigned (~sink(own g); g = new~): still the moved-binding assert
  interpreted and a double free compiled. Needs the dataflow run for
  the global in the function's root view (entry owned), plus a rule for
  a function that moves a global out without re-establishing it.
- Fields: ~own s.f~ is accepted and never tracked. ~s.f = f(own s.f)~,
  ~push(own s.f); s.f = ...~, and a bare ~push(own s.f)~ with no
  reassignment all double free -- the FieldAssign old-value delete
  (desugarer ~field_assign_needs_delete~, type-driven only) and the
  owner's exit delete both free the moved field. Plain rejection is not
  possible: ~own self.data~ to free/realloc and destructor field
  consumption are legitimate. Needs a semantics decision (track the
  moved field as a place that must be re-established before the owner
  is used or leaves scope, or reject outside those contexts).
2026-10-09, the masking audit. Method: remove each guard and run the
suite; a crash means it was control flow, nothing crashing means it
stays gone. Two-pass, 511/511 with every removal below in.

Removed:

- Generated struct destructors (initer.til): every own field's delete
  was wrapped in ~if self.f.to_ptr().is_null().not()~, "moved-out
  sources are zeroed". Removing it failed exactly three tests (REPL,
  interp_session, the installed TilVm host) with one source:
  ~interp_program_to_heap~ moved its own LoadedProgram out with
  memcpy + ~memset(lp, 0, ...)~ and let the garbager delete the zeroed
  husk. It now moves with ~adopt~, the primitive mem.til documents as
  the replacement for that hand-written blanking, so no delete is
  scheduled at all.
- ~Expr.delete~ (core/ast.til): ~if to_ptr(self).is_null() { return }~,
  "a fold helper returns NULL"; never reached.
- ~LoadedProgram.delete~ (loader.til): the null-self and null-unit
  early returns -- the other half of the blanking above.
- Interpreter teardown, twelve null early-returns:
  enum_payload_deep_free, heap_drop_enum, heap_drop_struct,
  heap_drop_by_type, free_tuple_data, free_container_data,
  free_dyn_vec_buffer, free_dyn_array_buffer, free_dyn_set_buffer,
  scope_drop_existing_heap_slot (after its ~moved_out~ check, so dead),
  free_owned_struct_slot, free_owned_enum_slot. For the container
  helpers a lazy-empty NULL buffer is still safe by construction: its
  count is zero and EvalHeap.heap_free is plain free.
- Three ~if x.is_null().not() { free(own x) }~ in interpreter teardown:
  free(NULL) is already a no-op.

Retained, each a documented contract:

- InternedTypes' ~pointee.is_null()~ (context.til): its slots are NULL
  until first interned.
- Interpreter clone helpers' null source buffer (a lazy-empty
  container clones to a lazy-empty one), and the lookups marked
  ~// REM: nullable scope ARG~.
- Container zeroed-slot drains: ~adopt_from~ / ~push_take~ blank the
  source slot as the documented count==0/data==NULL convention, and
  the JVM runtime's ~deleteStrAt~ null-slot return is that convention's
  JVM model (its ~deleteStr~ already throws on a double delete).
- The interpreter's ~moved_out~ binding state (transfer metadata), and
  the lazy-empty resets after freeing a container's storage
  (scope_pool_drain, scope recycling, session teardown).
