** WIP #151 TempleOS target

:DEPENDENCIES: [[../fixed/12.org][#12]]

  Add a TempleOS target. This is not part of the hosted 32-bit target
  work anymore: TempleOS is a separate toolchain, runtime, filesystem,
  graphics, and testing environment.

  The old broad 32-bit scope was split:

  - Hosted 32-bit Linux/Windows targets are tracked in [[./232.org][#232]].
  - Browser WASM is tracked in [[./228.org][#228]].

*** Scope

  - Emit or translate til programs to HolyC or another TempleOS-native
    representation.
  - Replace POSIX/Windows runtime assumptions with TempleOS primitives.
  - Implement ~mode gui~ on TempleOS using native graphics rather than
    raylib.
  - Define a QEMU-based test loop using a TempleOS VM image.

*** Notes

  TempleOS has no normal C compiler path comparable to the Linux,
  Windows, or browser targets. Treat it as deferred platform work, not
  as one more clang cross target.

*** Direction

  Translation stays on the Linux host: Linux til loads, types, lowers,
  and emits a HolyC source file. TempleOS receives only that generated
  source plus its TempleOS-native runtime support, then its own compiler
  compiles and executes the program. A host-side HolyC implementation is
  not the acceptance environment.

  Share the frontend and semantic analyses, not the textual emitter. HolyC
  receives the same typed, lowered, ownership-annotated, constant-folded, and
  scavenged AST as C. It should also reuse target-width resolution, callable
  and type queries, definition dependency ordering, and core-operation
  classification where those describe til semantics rather than C spelling.

  Keep textual emission in a dedicated ~holyc_codegen.til~ backend, following
  the builder boundary already used by the JVM backend. The regular C emitter
  assumes libc headers and ~ext.h~, typedefs/unions, the C pointer ABI, GNU
  statement expressions, compound literals, ternaries, attributes, libc
  allocation/memory/output, C entrypoints, libffi, and C-specific helper
  reachability. Passing a dialect flag through those paths would spread
  backend conditionals across the most ownership- and evaluation-order-
  sensitive parts of ~c_codegen.til~. A ~HolyCEmitState~ should instead own
  HolyC feature requirements and runtime-helper reachability; do not put a
  dialect flag in the frontend ~Context~.

  Extract target-neutral pieces from the C backend only when HolyC needs them.
  In particular, separate scope-pointer refresh and symbol registration from
  the C-only emit inventory, and separate aggregate dependency ordering from
  C struct/union syntax. Preserve the same logical til object and ownership
  model where TempleOS can implement it, but use TempleOS-native runtime
  functions and ABI decisions at the external boundary.

  TempleOS is x86-64-only with 64-bit pointers. The current
  ~TempleosX86~ target is excluded from ~target_is_32bit~, so UPtr is U64.
  The project-wide USize default can remain U32 independently of UPtr.

*** Incremental plan

  - [X] Extract C emission, C ABI bindings, and C-only emit reachability
    from ~builder.til~ into ~c_codegen.til~. Builder retains paths,
    commands, compilation, install, run, test, and documentation.
  - [X] Route the existing TempleOS target to a HolyC dialect in the
    C-family codegen and emit a HolyC source path on Linux. Unsupported
    AST/runtime features must fail explicitly rather than emit C or skip
    work silently.
  - [X] Emit and run ~examples/hello_script.til~ first. Lower its literal
    print to TempleOS HolyC and use a final top-level call as the guest
    entrypoint; do not require ~src/til.til~, mode gui, libffi, or the
    POSIX C runtime.
  - [X] Add scalar locals, arithmetic/core_func lowering, direct calls,
    conditionals, and loops, then grow a named TempleOS example corpus one
    passing example at a time.
  - [X] Move the existing HolyC emitter from ~c_codegen.til~ to
    ~holyc_codegen.til~ without changing output. Add ~HolyCEmitState~ and
    replace helper-name searches with explicit feature recording. Split out
    only the target-neutral preparation analyses HolyC actually consumes.
  - [X] Make the scalar subset honest before broadening it: either implement
    or explicitly reject narrow-integer truncation/sign behavior, shifts,
    ~continue~, F64, nested calls, and every other currently untested emitted
    form. Add TempleOS guest coverage for widths, overflow, div/mod by zero,
    Bool, and nested calls.
  - [ ] Walk all user units and support direct calls across imports. Keep
    backend-specific support roots separate from the C ~ext.c~ roots and its
    C-only emit reachability inventory.
  - [ ] Define and pin the HolyC ABI/runtime contract: UPtr/USize widths,
    value versus pointer parameters and returns, null-deref/panic behavior,
    and TempleOS wrappers for ~MAlloc~, ~CAlloc~, ~Free~, raw memory, and raw
    output.
  - [ ] Implement the general til ~Str~ representation in HolyC: literals,
    clone/delete, views, mutation, integer conversion, and native output.
    Keep the current lowered-~println~ scaffold optimization only until real
    ~Array(Str)~ execution can replace it.
  - [ ] Add aggregates and enums using shared dependency ordering but HolyC
    ~class~ syntax. Add field access/assignment, constructors, tags, payloads,
    and switches using statement-level temporaries rather than C statement
    expressions or compound literals.
  - [ ] Add lifecycle operations and collections incrementally: clone/delete/
    equality first, then Array and Vec, then Map/Set as the guest corpus
    requires them.
  - [ ] Add TempleOS-native filesystem, timing, task, and other ~ext_func~
    primitives individually. Keep host ~link_c~, include flags, generic
    libffi, and unavailable primitives as explicit errors.
  - [ ] Add function addresses, indirect calls, closures, ~dyn_fn~,
    reflection, and callable cleanup only after the scalar and aggregate ABI
    is stable; these need a HolyC-specific callable representation.
  - [ ] Integrate the pinned QEMU copy/inject/~Once.HC~/~ExeFile2~ loop with
    ~build~, ~run~, and CI. Require both host golden output and TempleOS
    compile/run success for every accepted feature.
  - [ ] Add mode gui last, using TempleOS graphics rather than raylib.

  The first HolyC slice emits the lowered literal-only form of
  ~examples/hello_script.til~ as ~gen/til/hello_script.HC~. TempleOS 5.03
  compiled and ran it with ~ExeFile2~ under QEMU TCG, reported
  ~TILTEST:PASS~ over ~isa-debugcon~, and exited through ~isa-debug-exit~.
  ~build~ and ~run~ still fail explicitly until that guest path is
  integrated.

  The second slice emits ~examples/fizzbuzz.til~, including scalar locals,
  I64 arithmetic/comparisons, mutation, conditionals, loops, literal output,
  and ~I64.to_str()~ output. TempleOS 5.03 compiled and ran that generated
  file under QEMU TCG and reported ~TILTEST:PASS~. User-defined direct calls
  were the remaining part of this incremental-plan item.

  The third slice emits ~examples/templeos_calls.til~ with scalar parameters,
  return values, forward declarations, function definitions, and direct calls.
  TempleOS 5.03 compiled and ran it under QEMU TCG and reported
  ~TILTEST:PASS~.

  The fourth slice moves all HolyC textual emission into
  ~src/self/holyc_codegen.til~. The builder dispatches directly to that
  backend, and ~HolyCEmitState~ records user functions and I64 div/mod helper
  requirements instead of searching generated text. All HolyC goldens remain
  byte-identical. The current subset consumes no C-only preparation analysis,
  so none was extracted prematurely; shared analyses will move only when a
  HolyC feature needs them.

  The fifth slice makes the scalar subset match TempleOS register semantics.
  Narrow arithmetic explicitly wraps and sign-extends instead of relying on
  HolyC local declarations to truncate; C-style prototypes become HolyC
  ~extern~ declarations; unsupported ~continue~ and F64 fail explicitly.
  ~examples/templeos_scalars.til~ covers every integer width, signed and
  unsigned overflow, shifts, Bool, div/mod by zero and nonzero divisors,
  comparisons, bitwise operations, and nested calls. TempleOS 5.03 compiled
  and ran the generated file under QEMU TCG and reported ~TILTEST:PASS~.

*** QEMU validation

  Use a pinned, FAT32-installed TempleOS disk image. For each local or CI
  run, copy the image, inject the Linux-generated HolyC file and a fixed
  ~C:/Home/Once.HC~ harness, then boot that copy under qemu-system-x86_64.
  ~Once.HC~ runs automatically in the first user task; it should compile
  and execute the generated file with ~ExeFile2~, catch exceptions, write
  a PASS/FAIL result file, report the same token over COM1, and exit QEMU
  through ~isa-debug-exit~. The host requires the guest exit status and
  result token to agree and applies a hard timeout.

  This runs the generated program directly on TempleOS in both local and
  CI testing. QEMU uses TCG in CI, legacy PC/IDE hardware, one CPU, and at
  least 512 MiB RAM; KVM is an optional local acceleration only.
