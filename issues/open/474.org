** OPEN #474 Replace AST interpretation with native JIT execution

Long-term direction: replace the tree-walking interpreter with native JIT
execution, rather than retaining interpretation as the permanent execution
engine alongside an optional accelerator. Use FASM as a basis for hosted
native JIT work, TempleOS's HolyC compiler for the TempleOS JIT, and eventually
develop our own reduced MLIR-style JIT appropriate to til's needs.

Eventually retire GCC/Clang from the required build/execution toolchain too.
That is a distant goal, not an immediate backend switch or permission to
remove today's working compiler, interpreter or C conformance reference.
JIT replacement and eliminating the C toolchain are separate milestones.

*** Scope and existing dependencies

Source inspection updated at master ~ae1daf9eb~:

- ~src/self/interpreter.til~ supplies ordinary interpretation, persistent
  sessions, native-call dispatch and embedded execution. ~src/std/tilvm.til~
  exposes loading, initialization, typed callback lookup and VM/code lifetime
  contracts to applications; replacing the engine must account for them.
- The interpreter also executes macros/generators and constant evaluation
  during initialization/typing and folding. A replacement is not complete
  when ~interpret hello_script.til~ works: compiler self-hosting needs its
  own compile-time execution to keep working throughout the migration.
- The REPL needs persistent globals, incremental definitions, imports,
  diagnostics and recoverable errors. Shared ownership/throwing semantics,
  retained callables and foreign callbacks must work in the same process.
- [[./453.org][#453]] currently emits standalone Linux-x64 FASM executables. Its
  callable support is useful groundwork, but it is not an in-process JIT.
  The TempleOS native compiler/FASM host bootstrap is tracked in [[./151.org][#151]].
- [[./317.org][#317]] is the current MLIR backend. Its build path invokes LLVM 18
  command-line tools and Clang, and compiles C runtime code. Fully direct
  programs now omit C-core compilation/linking; remaining emitted bridge
  references still pull in C-core. This is progress toward direct core emission,
  not an in-process or self-contained JIT, nor removal of the C toolchain.
- [[./490.org][#490]] and [[./491.org][#491]] separate ownership, reference-slot mutability and
  referent permission. The current guides are [[file:../../doc/concepts/ownership.org][ownership.org]] and
  [[file:../../doc/concepts/qualifiers.org][qualifiers.org]]. Native execution must preserve their source contracts and
  migration status, not infer them from a pointer-shaped ABI.

**** What is actually x86-only?

- JIT describes when/where native code is compiled and executed, not an ISA.
  An ARM64 or RISC-V host can have a native JIT with its own code generator,
  calling convention and code-memory implementation.
- Vendored FASM 1 encodes x86/x86-64 instructions, including 16-/32-/64-bit
  code and binary/PE/COFF/ELF formats; see ~vendor/fasm/FASM.TXT~. Multiple
  formats/host frontends do not make its instruction encoder cross-ISA.
- til currently emits Linux x86-64 ELF executables, with a private internal
  ABI and Linux syscall runtime. ~--usize=32~ changes til's scalar/container
  layout but leaves 64-bit native pointers and x86-64 instructions. It is not
  a 32-bit x86 execution mode. Reusing this emitter initially gives a Linux
  x64 JIT; neither Windows x64 nor ARM64 is already supported by that fact.
  FASM native own-pointer fields and a compact C host's compressed own fields
  differ even at the same USize. Passing aggregate buffers between them needs
  an explicit layout/allocator contract; the first scalar entry avoids this.
- The separate [[https://github.com/tgrysztar/fasmg/tree/e888130a6a3d5b4c38fb965e6b94ebbc01dd703d][fasmg reference]] defines instruction sets with macros, rather
  than built-in CPU opcodes. Its [[https://github.com/tgrysztar/fasmg/blob/e888130a6a3d5b4c38fb965e6b94ebbc01dd703d/core/docs/fasmg.txt][overview]] describes this distinction; its
  [[https://github.com/tgrysztar/fasmg/blob/e888130a6a3d5b4c38fb965e6b94ebbc01dd703d/packages/aarch64/hello_linux.asm][AArch64 Linux example]] emits ~EM_AARCH64~ ELF with an AArch64 instruction
  package. Those target encoders do not prove an ARM-native assembler host:
  the [[https://github.com/tgrysztar/fasmg/blob/e888130a6a3d5b4c38fb965e6b94ebbc01dd703d/core/readme.txt][distributed core frontends]] are x86. Switching assemblers alone would
  not port til's x86 instructions, private ABI, syscalls or host bridge.
- Stock TempleOS and its native HolyC compiler target x86-64. HolyC's JIT and
  AOT share native compilation machinery; this is not an AST interpreter or
  evidence of tracing/tiered compilation. Its [[https://github.com/cia-foundation/TempleOS/blob/c26482bb6ad3f80106d28504ec5db3c6a360732c/Doc/HolyC.DD][HolyC documentation]] specifies F64
  but no F32; til's HolyC backend must preserve til's separate F32 contract
  itself.

**** Lessons to carry into til

- Treat a session as compiler state plus symbols, globals, owned code and
  callbacks. Distinguish short-lived command code from persistent definitions
  and from captured/returned code references. A command's successful return is
  not sufficient permission to unload everything compiled for it.
- Publish callable addresses only after emission, fixups and host code-memory
  finalization succeed. Preserve debug/source associations. Define redefinition,
  initialization and failure recovery rather than silently leaving partial
  session state. TempleOS's code is a reference, not proof of those til rules.
- Plan branch/address reach explicitly. TempleOS puts code in the low 2 GiB
  within one shared address map; hosted Linux libraries, ASLR and separately
  mapped modules need not lie within rel32 reach. A bounded loader must check
  displacement ranges or use an agreed indirection strategy.
- Do not copy TempleOS's ring-0/executable-heap assumptions into hosted til.
  Hosted code needs an OS-owned mapping/protection/release boundary, writable
  relocation before executable publication, and any target-required instruction
  cache synchronization. Keep mutable data and immutable executable code apart.
- HolyC callable addresses are not til callable descriptors. til's private
  aggregate/address/capture ABI needs an explicit host adapter; task-level
  cleanup does not replace til's ownership or retained-callback contracts.
- The four-word FASM callable descriptor and its owned capture block do not
  acquire ownership of the module containing their code. A later retained
  callable must keep a valid code/session borrow, as TilVmCallback does for its
  VM; cloning captures must not silently retain or outlive that separate owner.
  Preserve the existing lifetime policy rather than adding reference counting.
- Reuse lowering and semantic tests, not just an emitter's text output.
  Standalone startup/~rt_exit~ and fatal runtime services cannot be imported
  blindly into a recoverable REPL/embedding process. Staged native compile-time
  execution must also preserve #472's host-versus-target distinction.

The first scalar-I64 milestone below is already supported by the standalone
emitter's language subset. Completing I64/U64 SIMD, vector casts or every
runtime service first would not establish the missing load/call/lifetime
boundary. Keep that first proof bounded, then extend runtime/ownership/session
coverage using measured costs. The proposed artifact/bridge contract below
still requires its explicit implementation approval; this research does not
select a new assembler dependency or implement a loader.

*** Execution-engine direction

**** FASM-based hosted JIT

- Reuse the prepared program, shared lowering and FASM backend/runtime
  semantics. Add callable native code loading, symbol resolution/relocation,
  host memory/execution support and diagnostics around the assembler.
  Producing and spawning an ELF executable is not in-process JIT execution.
- Define the ABI for values, aggregate results, ownership, closures/captures,
  throwing calls, globals and native services before exposing entry points.
  Code must remain alive while callbacks/closures or executing frames use it;
  session teardown/redefinition must not invalidate live code or captured data.
- Preserve independent reference permissions in prepared signatures, adapters
  and future native/TilVm schemas, as specified below. A matching register or
  pointer layout is not sufficient evidence of a compatible callable contract.
- FASM 1 is an x86 assembler, not a portable machine-code backend. Initial
  work can target Linux x64, but other host architectures need their own
  native code-generation strategy before their interpreter can be retired.

**** TempleOS JIT through HolyC

- Generate HolyC through the existing backend and ask the native HolyC
  compiler to compile callable functions/modules in the running session.
  Bridge its entry/callable conventions to til's values and lifetime rules.
  This route uses TempleOS's native compiler, not GCC/Clang or hosted LLVM.
- Preserve session state, initialization ordering, callbacks and error
  recovery; loading generated source once is not by itself REPL/VM parity.
- Keep this distinct from porting FASM to TempleOS. HolyC is the planned
  TempleOS JIT engine; a TempleOS-hosted FASM primarily enables the separate
  Linux-x64 cross-build path initially. Native til self-building remains
  the first compiler-host milestone, not dependent on completing this issue.

**** Our own reduced MLIR-style JIT

- Define the minimum typed intermediate operations, lowering and native
  execution machinery til actually needs, informed by #317 and the shared
  backend/runtime work in [[./383.org][#383]]. The goal is our own reduced system,
  not an implicit requirement to host the full LLVM/MLIR/Clang distribution.
- Decide explicitly whether that becomes a til-specific implementation or
  uses selected upstream components, and how it relates to FASM assembly.
  The exact IR, dependency selection and public interfaces are not chosen by
  this issue. Do not add a parallel semantic definition or persistent IR
  format/cache merely to start experimenting.
- Account for verification, optimization, target lowering, instruction
  selection/register allocation where needed, relocation, code memory and
  runtime integration. A smaller system reduces dependency scope but moves
  that maintenance and portability work into til; it is not a free replacement
  for the functionality currently supplied by LLVM.

- [ ] Inventory interpreter consumers: CLI, REPL, TilVm, macros/generators,
  constant evaluation, reflection, foreign calls and retained callbacks.
  Define the first callable-code/ABI/lifetime slice before implementing it.
- [ ] Establish a small FASM-backed native JIT using shared-source tests and
  the current interpreter/C backend as differential references. Unsupported
  operations must be identified explicitly during the transition, not hidden
  behind a permanent silent interpreter fallback.
- [ ] Establish the HolyC-backed TempleOS JIT with native guest execution,
  session-state and callback/lifetime checks. Coordinate the required host
  runtime services and frontend execution with #151.
- [ ] Cover incremental loading/redefinition, globals and initialization,
  ownership/destruction, exceptions, callback ABI and session teardown.
  Preserve existing public behavior unless a specific change is approved;
  integrate #490/#491's permission contracts without claiming their remaining
  accessor/path/schema migration is already complete.
- [ ] Move compile-time evaluation to the new engine while keeping the
  bootstrap viable. A JIT needing the fully prepared whole program cannot
  be the only mechanism used to prepare that same program: support the
  necessary staged evaluation of already-resolved functions and generators.
  Follow ~doc/self.org~ for preparation/use migrations rather than breaking
  the seed compiler mid-transition.
- [ ] Preserve [[./472.org][#472]]'s frontend determinism contract. Compile-time JIT code
  runs on the host, while queried layout/semantics belong to the selected
  target. Code addresses, host widths and floating-point behavior must not
  leak into persistent program results. Replacing interpretation alone does
  not make constant evaluation deterministic.
- [ ] Measure cold compilation plus execution, repeated calls, REPL latency,
  compiler self-build/constant-folding time, memory and teardown. JIT startup
  can cost more than interpreting tiny one-shot operations; tune based on
  those measurements without weakening the eventual replacement goal.
- [ ] Implement the agreed reduced MLIR-style JIT scope, with shared semantics
  and cross-target coverage. Retire AST interpretation only after its required
  consumers and supported host platforms have native-engine coverage.
- [ ] Eventually remove GCC/Clang as required tools once self-building,
  runtime services, supported targets, native library/foreign integration,
  diagnostics and testing have replacement paths. Resolve the remaining
  C/vendor dependency build strategy explicitly; do not claim independence
  while JIT/AOT runtime or library builds still invoke a C compiler.

The bootstrap interpreter and C backend remain transition references until
their replacements meet these gates. FASM/AOT completion does not require
this entire issue; #472's initial frontend work and [[./473.org][#473]]'s functional
CI improvements can proceed independently. New APIs, generated artifacts,
dependencies, install surfaces or persistent caches require their concrete
design approval before implementation.

  Reuse them behind a suitable module wrapper; do not copy the expression

  the caller, is an adequate initial JIT; embedding the assembler itself is
  a later startup-cost optimization.
- ~test/fasm_native.til~ already compares interpretation/C/FASM using shared
  inputs, checks runtime arithmetic was not folded away and covers both USize
  widths. Reuse that style. These process-execution tests do not already
  validate in-process entry, register preservation or code lifetime.

**** Proposed first output/entry contract -- approve before implementing

Use FASM's existing ELF64 relocatable-object support, rather than inventing a
raw-code container. Proposed test artifacts are
~tmp/fasm_jit/module.fasm~ and ~tmp/fasm_jit/module.o~: the til emitter writes
the former, the existing assembler writes the latter, and a test-only loader
reads the object and maps its callable code. Each run regenerates them; they
are not installed, cached or loaded as compiler source state. The existing
AOT ELF executable includes startup/exit machinery and has no suitable
callable-module contract, which is why it is insufficient.

Propose ~test/fasm_jit.til~ as the driver, an internal callable-emission entry
reusing the current emitter, and a narrow host bridge for code memory and
typed calls in the existing runtime boundary. No public JIT CLI flag or TilVm
API is selected by this plan. Before implementation, agree the exact helper
signatures, ownership and artifact contract in plain chat. Standard ELF avoids
a proprietary format, but a bounded object loader/relocator is real new code
to maintain; this proposal does not assume a new libelf/LLVM dependency.

Initial logical function contract: two I64 inputs and an I64 result, no
captures, global initialization, allocation, external calls, exceptions or
aggregate values. Include arithmetic using the runtime inputs, a conditional
and a direct call to another supported scalar function. Verify it is not
reduced to a precomputed result. Select and retain this function as an explicit
compilation root before scavenging; do not depend on an uncalled function
surviving an executable's main-root reachability pass.

**** Ownership and reference permissions at the native boundary

Follow the current ownership/qualifier guides linked above; the machine ABI
does not replace their contracts:

- ~arg: T~ borrows by default; ~own arg: T~ consumes ownership. Eligible
  primitive arguments/results auto-shallow in ordinary functions, so the first
  two-I64/value-result function needs no explicit ~shallow~. Mut/own parameters,
  borrowed-result functions and fixed ext/core boundaries retain their own
  pointer/value conventions; use shared ABI analysis rather than this shorthand.
- ~returns T~ produces a result owned by the caller, while ~returns ref T~
  and ~returns ref mut T~ borrow. A non-ref aggregate result may use caller
  frame storage and still own heap-backed contents. Preserve its cleanup and
  outer-storage metadata: ownership alone does not imply a heap box/free.
- Stored-reference slot permission and referent permission are independent.
  ~const ref mut value : T~ has a fixed slot and writable referent;
  ~mut ref value : T~ has a replaceable slot and read-only referent. For fields
  the replaceable-slot form is simply ~ref value : T~. Borrowed parameters use
  ~arg : T~/~mut arg : T~, not a stored-local slot qualifier.
- Under the #490/#491 contract, ~returns ref T~ grants read-only access and
  ~returns ref mut T~ grants writable access; the caller chooses its receiving
  slot's mutability. A caller may restrict a writable result to read-only with
  the same borrow ABI, but cannot upgrade a read-only result. No owned-return
  ~mut~ qualifier or new getter API is selected by this JIT plan.
- Current parsing/AST, generic identities/substitution, callable-result
  compatibility, typed dynamic lookup and Til-library bindings preserve/check
  the new permissions. Full source-path/writable-alias enforcement, plain-ref
  defaults migration, collection accessors, reflection/native schemas and the
  C-header translator are still pending. Existing accepted legacy programs
  do not prove those future checks. Preserve current checks now and integrate
  each approved migration; do not enforce a different JIT-only language.
- Identical pointer shapes do not make read-only/writable or borrowed/owned
  callable contracts interchangeable. Retain the prepared signature metadata
  through direct/indirect calls and adapters; diagnose unsupported native
  callable transfers instead of executing an incompatible descriptor. #370's
  reported interpreted-native-host dispatch crash remains separate from its
  validated compiled-host/guest paths and from the permission migration.
- Slot/referent mutability neither transfers ownership nor retains a VM or
  code module. Owning/cloning a carrier or capture does not acquire the owners
  of its borrowed fields. Keep borrowed owners/code alive through every use,
  and preserve callback-before-VM destruction and active-call retirement rules.

These are integration requirements as the JIT grows beyond the initial scalar
entry, not a requirement to finish the entire #490/#491 migration before
proving in-process scalar execution. The first entry has no borrowed result,
capture, retained callback or cross-layout aggregate.

**** Entry ABI and module lifetime

- Export one internal entry symbol (proposed ~til_jit_entry~) whose external
  convention is exactly SysV ~I64(I64, I64)~: RDI/RSI inputs, RAX result,
  normal stack alignment and preservation of callee-saved registers. Generate
  an adapter to the actual prepared til function ABI, including address slots
  when required by the shared analysis. No hidden closure environment is part
  of this first entry. Do not cast a raw address to til's managed callable
  descriptor representation.
- Call through a host bridge with that exact signature. The initial driver
  and host bridge may still be built using today's C toolchain; the generated
  function itself must be assembled by FASM. This is not GCC/Clang retirement.
- Let one owner hold the mapped region, symbol/entry metadata and any memory
  needed through invocation. Calls borrow the owner synchronously; no callback
  or executable pointer escapes it in this slice. Its destructor releases the
  mapping after the final use, including failure cleanup. A private teardown
  helper follows the File/TilVm pattern; ordinary callers need no manual free
  or new public close API. Do not deliberately call freed code as a lifetime
  test.
- Code allocation uses native addresses, not compressed til-own-pointer slots.
  Write/relocate while writable, make code executable before publishing the
  entry, then keep it immutable during calls. Propagate mapping/protection/
  unmapping failures explicitly. Keep any later writable data distinct from
  executable code. The API must make ownership and lengths explicit.

**** Loading, relocation and runtime symbols

- Inspect objects actually emitted by the small corpus before choosing the
  relocation subset. Read ELF class/machine/type, sections, symbols and the
  designated entry; reject unsupported required sections/relocations and
  unresolved symbols. Check referenced offsets and sizes before mapping or
  patching. Do not silently skip relocations or reinterpret an executable as
  a relocatable module.
- Map at an ordinary allocator-selected address. For each supported
  relocation, honor its addend, field width and signed range; a relative call
  is not repaired by truncating an arbitrary 64-bit address to 32 bits.
  If the first same-section scalar functions need no relocations, document
  that deliberately narrow contract rather than claiming a general loader.
- The first slice has NO external runtime symbols. Reject any unexpected
  dependency, including ~rt_exit~ or allocation helpers; never include the
  entire process runtime just to make unresolved names disappear.
- Next, add a deliberately chosen host callback/runtime function with an
  explicit typed resolver and a tested relocation/indirection strategy. Account
  for code/data sections and branch reach before extending to strings, globals
  and closures. No dynamic symbol-name fallback to unrelated process exports.
  Recoverable errors and panic behavior must be defined before importing
  runtime routines that currently terminate a standalone process.

**** Concrete verification

| Check | Required evidence |
|-------+-------------------|
| Runtime input changes | Multiple input pairs produce correct distinct I64 results without recompiling |
| Differential behavior | Interpreter, C, standalone FASM and in-process JIT agree on the same logical functions/inputs |
| Widths and signed arithmetic | Both driver USize layouts work; negative values, boundaries and defined wrapping agree |
| Direct calls and branches | Untaken/taken branches and a reachable helper execute as emitted code |
| Entry ABI | Stack alignment and callee-saved registers survive calls; argument/result transport matches the declared bridge |
| Actual in-process execution | The driver reads full return values and continues after the call; no subprocess exit-code substitute |
| Independent modules | Two live modules with the same entry spelling keep separate code/owners; freeing one does not invalidate the other |
| Failure paths | Missing entry, unresolved symbol, unsupported relocation and assembler failure report the actual error and clean owned resources |
| Repeated lifetime | Repeated compile/load/call/release cycles release mappings; validate without invoking a dangling entry |

Keep fixtures under repository ~tmp/~ and make execution synchronous. Add
focused ABI/lifetime checks to the native driver and preserve existing AOT
tests. ASAN can check the driver/host bridge but does not instrument emitted
assembly; do not describe it as coverage of generated machine-code memory
accesses. Follow the required full/two-pass verification before committing.

**** Cost measurements before optimizing

Measure source preparation, assembly emission, assembler subprocess, object
load/relocation/protection, first call, repeated-call total and teardown
separately. Compare cold prepare-plus-execute and warm repeated execution
against the interpreter; report ordinary AOT execution separately from its
build cost. Use runtime-varying inputs and consume results so optimization
cannot remove the work. Report memory/code size too. Tiny function tests
establish correctness, not a representative compiler speedup; add a realistic
repeated computation after the ABI/lifetime slice passes. No persistent code
cache or timing-based fallback is selected here.

**** Bootstrap and later integration

The first JIT runs AFTER ordinary preparation, which still uses the existing
interpreter for macros/generators/folding. It makes no attempt to replace that
evaluator in the same commit. Later, inventory each compile-time entry and
compile only sufficiently resolved dependency closures: requesting a fully
prepared program from the evaluator needed to prepare it would be a cycle.
Keep host execution ABI and target semantic/layout queries separate, following

owned values/closures and session lifetime, then REPL/TilVm and compile-time
