** OPEN #275 Interpreter manufactures double-ownership at construction; should only interpret the AST's delete/free

The interpreter's recurring leak / UAF / double-free class (the
make_str_value, StructInstance_clone and enum-payload bugs chased across
2026-06) is not a set of independent leaks. They are all symptoms of one
design fault: the interpreter keeps a runtime value representation (~Value~
over ~StructInstance~ / ~EnumInstance~ with raw ~Dynamic~ data buffers) that
DIVERGES from the single-owner, typed program the garbager compiled, and it
COMPOSES aggregates by ~memcpy~-ing sub-value bytes -- which duplicates owned
pointers and forces a manual-memory layer that then fights the
garbager-inserted deletes.

This is the #272 principle stated as a concrete root cause: memory management
is the garbager's job. The interpreter should do exactly two things with
memory -- interpret the ~delete~/~free~ calls the garbager already placed in
the AST, and free its OWN bookkeeping (the malloc'd ~Cell~/~Binding~/~Scope~).
It should never manufacture double-ownership, and it should never compensate
with manual reclamation.

*** STATUS 2026-08: the mechanism below is HISTORICAL

The code this issue described no longer exists. Verified against the tree
at the time of writing:

  - ~Value~ / ~StructInstance~ / ~EnumInstance~, ~shallow_copy_value~,
    ~val_enum_flat~ and ~src/self/dispatch.til~ are all gone. The
    interpreter binds through ~HeapBinding~ (interpreter.til) over typed
    raw blocks, with ~Scope.heap_bindings~ holding the metadata.
  - ~scope_free~ has no ~deep~ flag: its signature is
    ~scope_free := func(own s: Scope)~ and it reclaims the binding maps,
    not program payloads.
  - The ~is_str~ cache is gone; the surviving ~is_str~ is a ~FieldLayout~
    fast-path stamped by the initer.
  - ~check_move_managed_dest~ retired with the raw byte-move (see the note
    at typer.til's move handling).

The double-ownership itself was probed and did not reproduce: building an
enum payload and a struct field from owned locals, plus ~test/enums.til~,
run clean under ASAN with leak detection on.

Two concrete slices HAVE landed since:

  - The raw-allocation half of "reclaim only your own bookkeeping":
    ~scope_drop_owned_bindings~ / ~scope_free~ skip ~is_raw_alloc~
    bindings, because a #302 raw allocation binds the BLOCK as its datum
    and the compiled backend never auto-frees one. Freeing it at teardown
    manufactured a second owner and double-freed whatever an alias had
    already released through the AST's ~free~.
  - ~write_field~'s pointer-field arm stores the source ADDRESS for a
    concrete pointer (it used to write NULL unless the source was
    Dynamic).

*** What is actually left

Items 1-3 have all LANDED, and so has the dyn_call shortcut (0). What
remains is 0b: one teardown gap, reproduced and narrowed but not fixed.

  0. (DONE) ~dyn_call~ dispatches ~delete~ now; the shortcut and its
     hand-rolled reclamation are gone.

  0b. (DONE) Session teardown ran a script-scope binding's destructor a
     SECOND time. The cause was not the missing moved-out mark this text
     first blamed: the garbager already puts ~Vec.delete(v, false)~ in the
     AST for a script global -- drop the innards, leave the box, the same
     shape the compiled backend emits -- and ~scope_drop_owned_bindings~
     then called ~heap_drop_by_type~ over the same value, freeing the
     container's buffer twice. ~HeapBinding.payload_released~ records that
     an interpreted ~delete~ already ran against a named binding, and
     teardown reclaims only its own slot for those. Teardown still drops
     bindings the AST never deleted: removing the drop outright leaked
     9559 bytes across 698 allocations.

  0c. Historical note -- item 0 as originally written:
     ~interpreter.til~'s
     ~if method == "delete"~ arm calls ~heap_drop_by_type~ +
     ~EvalHeap.heap_free~ directly instead of dispatching to the type's
     own ~delete~, so a user-defined ~delete~ with any behaviour beyond
     releasing fields does not run on that path -- a divergence from the
     compiled backend, and the last piece of "interpret the AST's
     delete/free, do not reimplement it". Found by carrying out this
     issue's own TODO; not yet fixed.

  1. DONE. Step 3 below -- typer enforcement. ~check_memcpy_managed_src~
     rejects a ~memcpy~ whose source names a binding of a type with a
     ~delete~, looking through the ~to_ptr(x)~ laundering this issue
     recorded. It fires only over TYPED sources, exactly as predicted: a
     ~Dynamic~ source still erases the owned pointer, so ~heap_clone~'s
     own ~memcpy(dst_data, data, sz)~ over a ~Dynamic~ parameter stays
     invisible to it. Three exemptions, each a real move rather than a
     duplication: an ~own~ source binding (core's ~adopt~), the typer's
     own ~_steal_~ move-out temps (the same prefix the #321 own-a-ref
     exemption already recognises), and everything without a ~delete~.
     The ban then found three hand-rolled ~memcpy~+~memset~ pairs that
     already had a primitive -- ~intern_type_box~, the FFI-entry
     registration, and ~test/templ_vec.til~'s clone -- all now spelled
     with core's ~adopt_from~, which is the manual island shrinking.
  2. (DONE 2026-08) The #245 / #239 workaround is gone. ~stable_type_name~
     is deleted and the three clone sites pass the Declaration's own name
     straight through: the memcpy-duplication that made an owned name
     double-free no longer exists, so the borrow no longer needs
     canonicalising to program-lifetime storage -- and the linear scan over
     ~interp_type_defs~ it did on every nested clone goes with it. Full
     suite green, ASAN included.
  3. DONE in ee4f8fc7 (the #357 family commit): a by-value scalar passed
     to a pointer position (~ptr_add(q, 1)~ on a ~q : U8~ param) is now a

     in argument one, answered from ~TypeBinding.is_raw_alloc~.

*** The original mechanism, kept for the record

~Token.Name("hello")~ in interpret mode, as the code stood in 2026-06:

  1. ~enum_method_dispatch~ (dispatch.til) evals the arg -> a
     ~Value.Struct(Str)~ that OWNS a heap ~c_str~ (call it A). The garbager
     tracks this Value; its ~Value.delete~ would free A.
  2. It drops to raw pointers: ~pdata = to_ptr(payload.data)~ -- a ~Dynamic~.
  3. ~val_enum_flat~ (interpreter.til) does
     ~memcpy(enum_buf + ENUM_PAYLOAD_OFFSET, pdata, 16)~ -- copies the whole
     Str struct bytes, i.e. the c_str pointer A, into the enum's calloc'd
     buffer.

After step 3, A had TWO owners: the tracked source Value and the raw enum
buffer. til's model (ownership.org) is owned XOR borrowed -- there are NO
shared pointers -- so this was a flat violation, created by copying an owned
pointer's bits without a transfer. The code papered over it by setting
~payload.borrowed = true~ to forge a move, then bolted on manual frees.

The TYPE ERASURE point still stands and still explains item 1 above: the
duplication went through ~to_ptr(...) -> Dynamic -> memcpy~, and once a
value is a ~Dynamic~ the typer sees ~memcpy(Dynamic, Dynamic, n)~ with no
idea those bytes contain an owned ~c_str~.

*** The fix (original plan; step 3 is what remains)

  1. Construct interpreter aggregates with a real MOVE rather than a
     ~memcpy~ duplication. Moot as written -- those construction sites are
     gone -- except that ~write_field~ still clones for inline aggregate
     fields, which is a copy by design for a borrowed source.
  2. Then DELETE the manual layer. Done: no ~deep~ flag, no
     StructInstance/EnumInstance payload frees, no ~is_str~ cache.
  3. Typer enforcement, so double-ownership is forbidden in the first
     place: extend the ban on ~move()~ onto a managed dest with its dual --
     forbid copying a managed aggregate's bytes. This can only fire over
     TYPED pointers. STILL OPEN, and it is the gate on #245/#239.

*** Relation to #272

This is #272 step 3 stated as its root: the interpreter's manual-memory island
is not just "where leaks hide", it is where the interpreter actively
MANUFACTURES the double-ownership that the rest of #272's whack-a-mole then
patches. The enum-payload c_str ownership fix on this branch is one such patch
-- it makes the symptom green for ~1% but adds to the manual layer this issue
says to remove. The principled fix (move at construction + delete the manual
layer + typer enforcement) subsumes it.

    StructInstance.struct_name / EnumInstance.enum_name. Both shipped the
