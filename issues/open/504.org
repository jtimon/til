** WIP #504 Linux targets: the host's C library leaks into the binary (header paths in debug info today, more with other hosts)

Split from [[./472.org][#472]] (Jorge, 2026-11-16): which model to follow
is undecided, so it gets its own issue. #472 and #473 cannot finish for
the Linux targets until this is settled, because the collector compares
whole binaries.

*** The problem

til's generated C and ~ext.c~ include the system's C headers
(~stdio.h~, ~stdint.h~, the ~bits/~, ~sys/~ and ~linux/~ headers), and a
Linux build links the system's start files and C library. Everything
else til links is vendored (libffi, nng, secp256k1, raylib,
tinyfiledialogs, the X11 headers, ~vendor/macos~, the Android sysroot,
emscripten, fasm). glibc is the one part of a Linux build the repository
takes from the host.

What that costs today, measured in CI runs 3115 and 3117 (Ubuntu 24.04
on both hosts, gcc 13.3.0, glibc 2.39): for linux-arm64 built natively
on an arm64 host and cross-built on an x64 host, and for linux-x64 the
other way round, code and data are the same bytes; only the debug
information differs (~.debug_info~, ~.debug_line~, ~.debug_line_str~),
and the build id computed over it. DWARF records the directory of every
file that went into the program, and Debian installs the same headers in
two places:

| | native gcc | Debian cross gcc |
|-+------------+------------------|
| C library headers | ~/usr/include~ | ~/usr/aarch64-linux-gnu/include~ |
| per-architecture headers (~bits/~, ~sys/~, ...) | ~/usr/include/aarch64-linux-gnu/...~ | ~/usr/aarch64-linux-gnu/include/...~ |
| the compiler's own headers | ~/usr/lib/gcc/aarch64-linux-gnu/13/include~ | ~/usr/lib/gcc-cross/aarch64-linux-gnu/13/include~ |

(The cross column was read from a til built here; the native column is
Debian's layout, not read from a runner.) til's own source paths are
relative and already equal.

Switching the Linux targets to clang does not change this by itself:
clang 18.1.3 here, building for linux-arm64 on x64, records
~/usr/bin/../lib/gcc-cross/aarch64-linux-gnu/13/../../../../aarch64-linux-gnu/include/bits~,
the same cross layout.

What it would cost with hosts that are NOT the same distribution release:
the C library "standard" is the interface, not the files. Header macros
and inline functions become code, each libc function a program uses is
bound to a symbol version (~memcpy@GLIBC_2.14~, recorded in ~.dynsym~,
which also fixes the oldest glibc the program runs on), and the start
files (~crt1.o~ and friends) are linked into every executable. Two hosts
with different glibc versions would differ in code and symbols, not only
in paths.

*** What other languages do

- Rust: no C header takes part in compiling Rust code (its ~libc~ crate
  declares the C functions by hand; from memory, not from the searches
  below), so no header directory reaches the debug information. Where
  its own paths would differ per machine it rewrites them: the standard
  library's sources are recorded as ~/rustc/<commit hash>/library/...~ on
  every host, and Cargo's ~trim-paths~ / ~--remap-path-prefix~ do the same
  for user code. Linker and C library still come from the system, and
  Rust does not promise the same binary from every host (its own
  reproducibility test notes executables are not reproducible on
  non-Linux targets).
- Go: no C library and no C compiler by default; its own compiler and
  linker, talking to the kernel directly. Since Go 1.21 the toolchain is
  byte-identical whichever host builds it, cross-compiled or not, and
  user programs too with ~-trimpath~. With cgo (the host's C compiler and
  library) Go gives no such guarantee.
- Zig: bundles the C library headers for every target inside the
  compiler, including one set of glibc headers that stands for any
  supported glibc version, plus a symbol list per version, so every host
  reads the same headers from the compiler's own directory. No statement
  was found that its output is byte-identical from any host.

*** The options for til

til generates C that includes the system headers, so it stands where Go
stands with cgo. Each option changes the compile commands til emits or
adds a tree, so each needs Jorge's yes.

1. Rewrite the recorded paths (Rust's way). til passes
   ~-ffile-prefix-map~ options when it drives a Debian cross gcc, mapping
   the cross directories to the native ones. One map is not enough: the
   native layout keeps ~bits/~, ~sys/~, ~gnu/~, ~asm/~ under a
   per-architecture directory, so it takes one map per such directory,
   plus one for the compiler's own include directory. No download; the
   debugger still finds the headers on a native system. Tied to Debian's
   layout, and it only fixes paths: it does nothing for hosts with
   another glibc version.
2. A view of the host's own headers. til or ~bin/make~ builds a directory
   with one fixed layout (say ~tmp/sysroot-<target>/~) of links to
   whatever the host has installed, and points the compiler only there
   (~-nostdinc~ plus ~-isystem~ per directory). The compiler records the
   path it opened, so every host writes the same strings. No download; a
   new generated directory and new flags. Paths only, like option 1.
3. Bundle the C library (Zig's way, and what ~vendor/macos~ already is
   for the mac targets): a pinned glibc's headers, start files and
   libraries per Linux target, vendored or a pinned download, used by the
   native build too. Removes the dependence on the host's glibc version
   altogether, and that version becomes the minimum users need to run
   til. A new vendored tree; the largest change. clang would make this
   easier (one binary, ~--target~ and ~--sysroot~), gcc takes ~--sysroot~
   too.
4. Do not include system headers at all (Go's way, Rust's for headers):
   declare what the generated C needs from the C library in til's own
   headers. Removes the header paths and the inline code; start files and
   symbol versions remain the host's unless combined with option 3.
5. No ~-g~ for the binaries compared. They match, but that til carries no
   debug information; not what users get.

*** Decided (Jorge, 2026-11-20): bundle the C library, from Bootlin, for all six targets

Option 3: the same binaries from everywhere is the requirement, and it
is the only option that gives a host without glibc (a Mac, Windows) a C
library at all, or two Linux hosts with different glibc versions the
same one. Source: the target side of Bootlin's prebuilt toolchains
(toolchains.bootlin.com), which CI already downloads for riscv32, for
all six Linux targets.

**** The version: glibc 2.34

The oldest glibc Bootlin has for all six, its 2021.11 series:

| target | Bootlin directory | release | tuple | gcc (start files, libgcc) |
|--------+-------------------+---------+-------+---------------------------|
| linux-x64 | x86-64 | stable-2021.11-5 | x86_64-buildroot-linux-gnu | 10.3.0 |
| linux-arm64 | aarch64 | stable-2021.11-1 | aarch64-buildroot-linux-gnu | 10.3.0 |
| linux-arm32 | armv7-eabihf | stable-2021.11-1 | arm-buildroot-linux-gnueabihf | 10.3.0 |
| linux-riscv64 | riscv64-lp64d | stable-2021.11-1 | riscv64-buildroot-linux-gnu | 10.3.0 |
| linux-x86 | x86-i686 | stable-2021.11-1 | i686-buildroot-linux-gnu | 10.3.0 |
| linux-riscv32 | riscv32-ilp32d | bleeding-edge-2021.11-1 | riscv32-buildroot-linux-gnu | 11.2.0 |

(riscv32 has no stable series before 2024.05, which is glibc 2.39.) Older
ones exist for some targets only: aarch64 goes back to 2.27, x86-64 to
2.34. So a til binary built with these needs glibc 2.34 or newer: RHEL
9, Ubuntu 22.04, Debian 12 and later. The six archives were downloaded
here and their sha256 compared with the ~.sha256~ Bootlin publishes next
to each.

**** Step 1, done: bin/make fetches them

~bin/make linux_sysroots~ (all six) and ~bin/make vendor/linux/<target>~
(one): download, sha256 check, and unpack under ~vendor/linux/<target>~
(ignored; removed by ~bin/make clean_vendor~ like the other pinned downloads) only
what a compiler on any host reads: ~<tuple>/sysroot~ (headers, ~crt1.o~,
libc) and ~lib/gcc/<tuple>~ (~crtbegin.o~, ~libgcc~). 72 to 80 MB per
target unpacked, about 130 MB per download. Bootlin's own compiler, an
x86-64 Linux program, is not unpacked.

Tried by hand here, with the unpacked trees and clang 18 with lld:

: clang --target=<tuple> --sysroot=vendor/linux/<target>/<tuple>/sysroot --gcc-toolchain=vendor/linux/<target> -fuse-ld=lld

builds a C program for each of the six. The linux-x64 one runs here and
its only versioned symbols are GLIBC_2.2.5 and GLIBC_2.34; the other
five run under qemu-user with that sysroot.

**** Step 2, done: til and bin/make build a linux target against it

Where ~vendor/linux/<target>~ is unpacked (~targets.til~,
~linux_is_pinned~; named from the working directory, like ~vendor/macos~
and ~vendor/android~), til builds that target with

: clang --target=<tuple> --sysroot=vendor/linux/<target>/<tuple>/sysroot --gcc-toolchain=vendor/linux/<target> ... -fuse-ld=lld

on every host, the target's own included, and maps clang's own header
directory to ~clang-resource~ as for android (~clang_resource_map_args~,
the android function renamed). Where it is not unpacked nothing changes:
the host's gcc, or the distribution's cross gcc. ~bin/make~ builds the
target's libffi and nng the same way (clang, lld for the probe links,
llvm-ar), and does not reuse a build directory configured for the other
C library: cmake's cached "strlcpy found" from the host's glibc 2.39
failed the compile against 2.34, so a stamp in the directory says which
it was configured for. The gui and libsecp256k1 archives are not built
pinned yet: til itself links neither.

Measured here (Linux x64, Ubuntu's clang 18, not yet the pinned LLVM):
- ~hello_script~ for linux-x64: runs; versioned symbols up to
  GLIBC_2.34; every directory in ~.debug_line~ is relative (~.~,
  ~./src/self/codegen~, ~vendor/linux/linux-x64/.../sysroot/usr/include~,
  ~clang-resource/include~).
- ~hello_script~ for linux-arm64: runs under qemu-user.
- til itself for linux-x64, linked with the pinned libffi and nng: runs
  and interprets; GLIBC_2.34 at most (the gcc-built one needs 2.38).
- ~test/reproducible_build.til~ for linux-x64 and for linux-arm64: a
  program and a library built in two checkout roots are the same bytes.
  The test links ~vendor/linux~ into its second root; without that the
  second root built with the host's gcc.
- The collector lists both targets (280 lines), with llvm's objcopy and
  ar for a pinned linux target, as for the mac targets.

In CI: both Linux hosts list linux-x64 and linux-arm64 this way, after
their mac lists (the pinned LLVM is first on PATH there), on trial. The
lists made with each host's own gcc and glibc are removed. The tree is
deleted at the end of the step, so that nothing after it builds pinned.
