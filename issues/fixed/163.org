** FIXED #163 Per-file AST/import graph + Context.path (prep for removing Expr.path)

*** Post-mortem

    Most of this issue landed incrementally before its final re-analysis:
    ~Context.imported~ owns one canonical ~ImportUnit~ per file, each containing
    that file's AST and mode; init, typer,
    constfolder, scavenger, interpreter, and builders operate on per-file units;
    ~Context.path~ supplies current-file diagnostics; circular imports work; and
    ~Expr.path~ is gone.

    One duplicated source of truth remained: loader discovery
    extracted every explicit import into ~ImportUnit.imports~, while the same
    edge stayed in the AST. Init and typer walks then matched calls to paths by
    position, with separate offset arithmetic for mode auto-imports.

    Explicit dependency edges now live only in their AST calls. Each
    ~ImportUnit~ stores the base and optional library root needed to resolve
    those calls to canonical Context keys during every graph walk. Namespace
    import desugaring preserves the call as a bare statement, and the sole
    dependency without a source call -- a mode auto-import -- has one dedicated
    field. ~ProgramUnit.imports~, ~ImportUnit.imports~, ~extract_imports~, and
    all positional matching are removed.

    Regression: ~test_namespace_import_priv_siblings~ in ~test/imports.til~
    has no duplicate bare import, so it proves a rewritten namespace import
    remains the AST edge that loads and visits its dependency. The existing
    circular-import, mode, REPL, selective-import, and unused-import tests cover
    the other resolution paths.

*** Historical goals

Goals:

   - Store a canonical per-file AST and direct import list in Context
     (like ../rstil/), not in merged ASTs or ProgramUnit.ast.
   - Run phases per file (imports-first) so we can support circular deps.
   - Use Context.path (and per-file drivers) for diagnostics and phase behavior.

   Notes:

   - Expr.path is removed. Remaining work is to keep phases per-file so we do
     not re-introduce merged-AST-only assumptions.
   - This likely requires moving more phases (constfolder/scavenge/eval/build)
     to per-file drivers, or adding explicit file boundaries to merged views.
