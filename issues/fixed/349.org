** FIXED #349 Cmd's Windows argument quoting has never been executed

*** Post-mortem

The shape the issue asked for, built as two portable programs run on
both sides of the fence:

- test/echo_argv.til: the far end of the round trip -- prints argc,
  each argument bracketed on its own line, one env probe, one stderr
  line, and an --exit-7 mode for exact status propagation.
- test/win_quoting.til: the driver. Spawns the echo binary THROUGH Cmd
  with every shape from this issue's list -- spaces, tab, the empty
  argument, an embedded quote, literal backslashes, trailing single and
  doubled backslashes (bare and inside a quoted argument), a backslash
  run before an embedded quote, and %PATH%/$HOME staying literal -- and
  compares what the child's C runtime parsed against what was passed.
  Also: exact-case env override displaces on every host; stderr stays
  separate under capture(); stderr_to_stdout merges (content + total
  size, not byte order -- stream interleaving is buffering, not
  contract); exit 7 comes back as 7. Output is \r-normalized so the
  windows CRT's text mode cannot fail the comparison.

Two hosts, one driver, three legs:

- The suite's win_quoting single test builds and runs the pair on
  linux, pinning the driver itself and the execvp path.
- The windows-x64 host CI job cross-builds both to .exes beside
  til.exe; the windows runner job executes them -- the first-ever
  execution of win_quote_arg's CommandLineToArgvW rules, the
  CreateProcessA command line, win_env_block, and the GetTempPath
  capture spools, on real Windows rather than wine (the dual-CRT nng
  lesson: wine passes things Windows refuses).

One semantic split surfaced while writing it, now pinned per host: env
NAMES are case-insensitive on Windows and case-sensitive on POSIX, so
a lowercase override of an inherited uppercase variable must DISPLACE
it on Windows (win_env_block's _strnicmp) and must NOT touch it on
POSIX. The driver asserts each host's own contract; TIL_QUOTE_CASE=
parent in the runner's environment feeds the probe on both.

Verified here: the linux leg end to end (suite green), and both
programs emit windows-target C cleanly. The windows execution itself
happens on the CI runner at merge -- this container has neither mingw
nor wine, which is the whole reason this issue existed. If that leg
disagrees with the linux one, the quoting is wrong on the windows
side, and the driver's panic says which case.

The argv-based process API from #345 (~ccmd_*~ in ~src/c/ext.c~, the
~Cmd~ struct in ~src/std/sys.til~) has a Windows side: ~win_quote_arg~
implements CommandLineToArgvW's backslash rules (a backslash run is
literal unless a quote follows, in which case the run doubles and the
quote is escaped; an argument quotes when empty or holding space, tab
or quote), and ~cmd_start_impl~ builds the command line and environment
block for CreateProcessA. All of it compiles under mingw headers -- and
none of it has ever RUN. The container #345 was built in has neither
wine nor mingw, and no CI lane executes til-driven process spawning on
Windows.

#345's own acceptance list says the quoting needs a native or wine
regression test "before the API is called multiplatform", so until this
issue closes, Cmd is verified on POSIX only. Getting Windows quoting
wrong is not cosmetic: a trailing backslash in a path (~C:\path\~)
silently becomes ~C:\path"~ and swallows the next argument.

*** What the test needs to prove

test/process.til already pins the POSIX behavior: spaces, both quote
characters, empty arguments, no $VAR/glob expansion, exit codes,
stream separation/merging, redirection, cwd, environment overrides,
concurrent captures. The Windows test must cover the same claims plus
the quoting-specific corners:

- arguments containing spaces, tabs, embedded double quotes
- trailing single and doubled backslashes, backslash runs before quotes
- the empty argument
- case-insensitive environment override (an override of ~path~ must
  displace the inherited ~Path~ -- ~win_env_block~ uses ~_strnicmp~ for
  this and nothing has ever exercised it)
- capture spool files via GetTempPath/GetTempFileName, and
  stderr_to_stdout sharing one handle

The natural shape: an echo-argv til program (print each of its argv
elements on its own line) cross-compiled to windows-x64, driven by a
til test that spawns it THROUGH Cmd with the corner-case arguments and
compares the round trip. Self-contained -- the round trip through
CreateProcessA + the CRT's parser is exactly the property under test.

*** Where it can run

- The existing windows-native CI jobs already download and execute
  cross-built .exe artifacts on windows runners; a quoting fixture can
  join that flow (build in the linux mingw job, execute in the
  windows job).
- Or wine in the linux mingw job, which #345's acceptance text
  explicitly allows; wine's CRT startup uses the same argv parsing
  rules, and the repo already notes where wine was too permissive
  (the dual-CRT nng lesson), so a wine pass is necessary-not-yet-
  sufficient evidence -- prefer the real-runner variant when both are
  reachable.
- Local sessions and remote bot containers have neither, which is
  exactly why this cannot be a suite-only test and did not happen in
  #345.

*** Acceptance

- A windows execution (native runner or wine) of the quoting corner
  cases above, wired into CI so it runs on every master push, fails
  loudly on any quoting change, and does not reduce existing coverage.
- Until then, doc comments on Cmd keep saying the Windows side is
  untested rather than implying parity.
