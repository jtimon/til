** FIXED #400 Dynamic's width is written down twice, and only one copy follows the target

*** Post-mortem

Dynamic's core size, Tuple copies, and typer word limit were fixed at eight
bytes while the C runtime dispatcher used the target pointer size. The
typer also skipped primitive slot operands entirely and used host aggregate
layouts for target decisions.

Core now spells the width as ~UPtr.size()~ and Tuple uses ~Dynamic.size()~.
Initialization normalizes Dynamic's size method through the existing
generated-size mechanism: interpretation uses host pointer width, while
width-mismatched C emission uses ~sizeof(void *)~. This preserves actual
host pointers during compile-time execution instead of shrinking their
storage to the target width. Callable runtime sizes use host ~UPtr.size()~.

The typer derives its word width from ~ctx.target_uptr_pname~ and computes
target sizes/alignment directly from declarations, including nested
aggregates, pointer fields, and tagged/niche enums. It does not alter or
duplicate the interpreter's layout cache. The loader supplies the i386
SysV 64-bit scalar alignment exception. Both raw-slot overflow checks and
auto-shallow classification use these target sizes; scalar operands now
participate in overflow checks too.

Regression coverage: ~check_dynamic_widths~ in test/cpu_options.til checks
native interpreted/compiled Array/Vec/Tuple round-trips at both USize
widths; all five 32-bit C targets check the Dynamic size emission, nested
one-word acceptance, U64 literal/push and two-word aggregate rejection,
and auto-shallow parameter ABI. ~test_dyn_size_of~,
~test_func_ns_method_size~, and ~test_tuple_dynamic_word~ now assert/use
pointer width rather than an assumed eight-byte word. Linux x86 runtime
probes also passed for the container/Tuple round-trip and nested-word case.
~make clean && make test_two_pass~ passed all 507 tests, including the ASAN
suite and self-translation comparison. The two-pass build records the
normalized Dynamic size method in the self-applied bootstrap output.

*** Follow-up: checked byte counts and 32-bit runtime coverage

~usize_to_uptr~ no longer assumes a widening cast: it converts to the target
pointer integer and compares both values widened to U64, panicking if any
bits were lost. The round-trip check works during interpretation too, where
size() queries describe host storage rather than the target scalar width.
This enables ~--usize=64~ with 32-bit pointers for these programs.

~check_dynamic_widths~ now exercises both USize widths on all five 32-bit C
targets. Its CLI byte-count probe prevents constant folding and checks zero,
the U32 maximum, the first overflowing value, and the U64 maximum. The
existing linux-x86 CI job generates these same probes, cross-builds them at
both widths, and runs the Array/Vec/Tuple and nested-word cases under
~qemu-i386~. It also checks compiled byte-count success and overflow exits.
Follow-up verification: ~make clean && make test~ passed all 520 tests;
the linux-x86 QEMU probe commands passed locally at both USize widths.

*** Follow-up: avoid repeated compiler work in the probes

The added coverage made ~cpu_options~ the suite's critical path. Build the
byte-count executable once per width and batch successful runtime inputs;
overflow cases still run separately. One failing translation checks all
three distinct slot diagnostics, and one exported library per target/width
covers word acceptance, ABI, and the runtime probe bodies. Native and QEMU
wrappers call that same library. All five targets and both widths remain.

With the same compiler binaries, the isolated test fell from 106.72s to
65.73s (38%). All 520 suite tests and both QEMU widths passed. Concurrent
master/worktree builds affected the full-suite timing, so that run is not
a controlled wall-time comparison.

*** Follow-up: select the conversion body with a til macro

~make_usize_to_uptr(USize, UPtr)~ is now a ~macro~ returning ~FuncDef~.
The existing generator's compile-time type tests select a conversion-only
body for U32->U32, U32->U64 and U64->U64; only U64->U32 retains the overflow
check. Selection happens during initialization, before the generated body
is typed, with no runtime size test and no dependence on C optimization.

The generator's primitive-type condition evaluator now resolves aliases
through the target type scope. Previously it compared the preserved
~UPtr~ spelling against ~U64~ and chose the wrong branch. Instance names
and substituted signatures still preserve width-alias spellings.

~check_dynamic_widths~ additionally inspects emitted C: the overflow path
must be absent on non-narrowing builds and present on narrowing builds.
This reuses the existing compilations and target matrix. All 520 tests and
the linux-x86 QEMU checks at both USize widths passed.

*** Re-analysis (2026-10-07)

Source review on master ~dd23d262d~ confirms the mismatch remains. This is
an implementation plan, not a verified fix; no cross-target execution was
performed for this review.

~Dynamic~ means one pointer-sized raw word, but the codebase spells that
width differently. The hard-coded and target-aware answers agree on
8-byte-pointer targets:

- The til side says a literal 8. ~Dynamic.size()~ (src/core/dyn.til) returns
  ~8~; ~PTR_SIZE_BYTES : USize = 8~ in src/self/typer.til feeds every "is one
  8-byte word" diagnostic and the ~dynamic_slot_overflow~ threshold; the
  interpreter's ~h_dyn_size_of~ defaults ~sz~ to 8; and
  ~Tuple.push_all_dynamic~ (src/core/tuple.til) hard-codes ~malloc(8)~ /
  ~memcpy(.., 8)~ for a splatted raw word.
- The emitted C says ~sizeof(void *)~. #394 fixed the compiled
  ~dyn_size_of("Dynamic")~ arm to exactly that, on the argument that the C
  side "stays right if a pointer is ever not eight bytes" -- which is true,
  and is precisely how the two copies part ways.

On a target where a pointer is not 8 bytes the two answers diverge:
~Array(Dynamic)~ / ~Vec(Dynamic)~ size elements through ~T.size()~ (the til
literal, 8) while the runtime string-keyed ~dyn_size_of("Dynamic")~ answers
~sizeof(void *)~, so a Tuple element tagged "Dynamic" and a raw container
slot would disagree about element width -- the same class of split #394
closed, reopened one abstraction level up.

This does not depend on introducing a new target. ~target_is_32bit~ in
src/self/targets.til already covers Linux x86, Linux ARM32, Linux RISC-V32,
Windows x86, and Wasm32. ~target_uptr_name~ selects ~U32~ for all of them.
The original claim that every current target has 8-byte pointers was false.

#313 is a separate pointer-representation project, not a prerequisite for
this fix. The current C backend uses native pointers; changing a typedef
alone cannot implement pointer compression.

*** Existing authorities and host/target split

- ~ctx.target_uptr_pname~ already records the resolved target pointer
  integer type. Derive its width through ~unsigned_prim_width_for_name~;
  do not introduce another independent target-width setting. ~USize~ is
  independently selectable through ~--usize~ and is not the authority for
  Dynamic's width.
- ~UPtr.size()~ inside the running compiler describes the HOST pointer
  width. ~primitive_type_info~ in src/self/initer.til already uses it for
  Dynamic's interpreter layout. Those buffers contain real host pointers
  even when the compiler emits code for a narrower target.
- ~ctx_total_size~ reads ~ctx.struct_layouts~, the host-side layout data.
  Both ~dynamic_slot_overflow~ and ~is_shallow_struct~ compare that size
  against ~PTR_SIZE_BYTES~. Merely changing the threshold to the target
  width would compare two different layouts and can reject an aggregate
  that fits in one target word.
- #309 leaves auto-generated size methods unfolded on width-mismatched
  targets and emits C ~sizeof~ for them. Dynamic's hand-written ~size~
  method does not receive that auto-generated-method treatment.
- ~h_dyn_size_of~'s initial 8 is the callable-storage default. Other types,
  including Dynamic, go through its size-method/layout path. Its result
  buffer is written at target USize width; that is distinct from the
  pointer width whose size is being reported.

*** Fix direction

- Make core ~Dynamic.size()~ follow ~UPtr.size()~, checking alias resolution
  and folding on cross-target builds as well as native builds.
- Replace ~Tuple.push_all_dynamic~'s allocation/copy literals with
  ~Dynamic.size()~.
- Replace the typer's fixed word threshold and diagnostic width with the
  resolved target pointer width. Make the compared value size target-aware
  too, including aggregate layout; do not change the interpreter's shared
  host-layout tables to achieve this. Audit automatic shallow classification
  alongside raw Dynamic slot rejection, since both use the constant.
- Remove the interpreter's literal callable width while preserving its
  host-memory contract. Audit size evaluation during cross-compilation so
  host buffer sizes are not baked into emitted target code. Do not globally
  replace host pointer allocations with target-width allocations.
- Keep compiled ~dyn_size_of("Dynamic")~ consistent with native C pointer
  storage (~sizeof(void *)~). No new pointer-compression semantics belong
  in this fix.

*** Regression coverage

- Extend existing ~test_dyn_size_of~ / ~test_dyn_size_of_runtime_name~ in
  test/dynamic.til and the Dynamic Tuple coverage in test/tuples.til:
  runtime-name ~dyn_size_of("Dynamic")~, ~Dynamic.size()~, and ~UPtr.size()~
  must agree. Exercise raw Dynamic Array/Vec slots and Tuple splats.
- Replace test/macros.til's assumption that ~Dynamic.size() == 8~ with a
  pointer-width assertion, retaining its compile-time-folding coverage.
- Check that ~--usize=32~ versus ~--usize=64~ does not change Dynamic's
  width on the same pointer-width target.
- Add 32-bit-target checks for emitted size behavior and typer boundaries:
  a four-byte value fits, an eight-byte value does not, and an aggregate
  whose host layout is wider but whose target layout fits is accepted.
  Cover automatic shallow classification as well as Dynamic containers.
- Translation/type-checking regressions can run without a Wasm runtime.
  Execute the container/splat cases on an available 32-bit target to verify
  actual allocation, stride, and copy behavior; distinguish those runtime
  results from translation-only coverage.
