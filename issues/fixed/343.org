** FIXED #343 A view reaching a C string parameter reads past its end, unchecked

*** Post-mortem

  Route 1, with the discriminator the "Constraint" section below asked
  for: the terminator BYTE, not ~cap~.  ~c_str[count] == 0~ answers the
  actual question ("is this a C string?") and is immune to the CAP_LIT ->
  CAP_VIEW demotion that made a cap test fire on safe values, including
  ~get_env~'s own ~""~ return.  Reading that byte is always in bounds,
  which is what the NUL audit below had already established: every
  allocating Str path reserves count+1, and a view's end never passes its
  base's -- so the check trusts an invariant that was verified before it
  was written, not the other way round.

  Root cause: nothing connected the two halves of the mismatch.  til's
  ~Str~ is length-counted and C's string is terminator-counted, and the
  conversion between them -- ~.c_str~ in an ext argument -- was a bare
  member read that asserted nothing.  Every guarantee lived in prose
  (doc/ffi.org, per-binding ~///~ comments), so it held exactly as long
  as each caller remembered it.

  Changed:

  - ~src/self/builder.til~: ~emit_user_fcall_args~ wraps the argument in
    a new ~TIL_CSTR~ macro (emitted beside ~DEREF~, and panicking the
    same way) when the callee is an ext binding, the parameter is a plain
    ~name : I8~ -- exactly the shape ~emit_param_list~ gives
    ~const char *~ -- and the argument is ~<str>.c_str~.  ~shallow val :
    I8~ (a char by value) and ~mut text : I8~ (a buffer the callee writes
    or frees) are excluded because neither walks to a terminator.  A
    STRING LITERAL receiver is excluded too: it emits the C literal
    itself, so the check would be provably dead at most call sites (every
    ~InitWindow~ / ~DrawText~ in examples/) and they emit unchanged.
  - ~src/self/interpreter.til~: the mirror, so the backends cannot
    diverge.  ~ext_dispatch_ffi~ marks the arguments the builder wraps
    (~ctx.interp_cstr_arg~, a new one-shot Context flag) and
    ~eval_expr_field_raw~ consumes it at entry -- before the receiver is
    resolved, so a call in the receiver never inherits the mark -- then
    runs ~check_c_string_terminator~ on the base it already has.  A flag
    rather than a check inside ~.c_str~ itself, which was route 4 and is
    rejected: core/str.til reads ~c_str~ on views constantly and
    legitimately.
  - doc/ffi.org and std/sys.til's ~get_env~ record that the boundary now
    enforces what they used to only ask for.

  Regression test: ~cstr_view_interp~ / ~cstr_view_run~ (src/tests.til)
  over ~test/cstr_view.til~, one per backend, registered as ~count~
  entries on the panic text rather than expected-exit singles -- an exit
  1 could be any panic, while the message appearing exactly once says the
  terminator check is what stopped it.  The fixture spells the view with
  the ~Str~ constructor instead of ~substr~ because the two backends do
  not agree on what ~substr~ returns (compiled: a real CAP_VIEW into the
  base buffer; interpreted: an owned copy, hence terminated), so a
  substr-based fixture would have exercised one backend only -- which is
  how the first version of this test passed compiled and failed
  interpreted.  It also drives ~view.clone()~ through the same parameter
  FIRST, so a check that fired on anything view-SHAPED would fail there.
  The safe shapes stay pinned by ~test/ext_libc.til~ (a both entry).

  Still open, deliberately: route 2, the type-level guarantee.  The check
  is a runtime backstop under the rules, not a replacement for them, and
  it only sees the direct ~expr.c_str~ form.

  ~Str~ is pointer + count, and C strings are NUL-terminated, so the two
  worlds only line up for values that happen to carry a NUL one byte past
  their count.  Owned Strs do (the allocating paths reserve count+1) and
  C literals do.  A VIEW does not, by construction: ~substr~ returns a
  ~CAP_VIEW~ pointing into the middle of a bigger buffer, and the byte at
  ~c_str[count]~ is whatever the backing buffer holds next -- usually more
  of the original string, sometimes heap garbage.

  Nothing checks this.  Passing ~view.c_str~ to an ext binding's ~I8~
  parameter compiles clean and runs; the callee just keeps reading past
  the count.  ~setenv(name.substr(0, 19).c_str, ...)~ stores a longer name
  than asked for, and there is no diagnostic at any stage.

  What exists today is convention only:

  - doc/ffi.org ("Passing a Str to a C string parameter") says to
    ~clone()~ first, because an owned copy always carries the NUL.
  - Individual bindings repeat it per call site.  std/sys.til's
    ~get_env~ carries a ~///~ comment saying it is not view-compatible,
    which is exactly the band-aid this issue exists to replace: it puts
    the burden on every caller to know something the type system knows
    and does not say.

  The reason it bites harder than an ordinary documented footgun is that
  views are TRANSPARENT.  ~substr~ hands back a ~Str~, the same type an
  owned string has; nothing in the signature, the name, or the printed
  value says "this one has no NUL".  A caller cannot tell from reading
  til code whether the ~Str~ it holds is safe to pass to C, and a
  function taking ~name : Str~ cannot tell what its caller chose.  So the
  documented rule degenerates to "clone defensively at every boundary",
  which is what ~get_env~ did until the clone was removed as dead weight.

  Directions, none of them chosen -- this needs a decision before work:

  1. *Check at the ext-call boundary.*  The builder already knows the
     shape (a Str expression's ~c_str~ feeding an ext binding's ~I8~
     param), so it could emit a macro that panics when ~cap == CAP_VIEW~
     instead of a bare member read -- the same trick ~DEREF~ uses for
     null.  Loud at the real site, and wrappers stop cloning just in
     case.  Costs: the interpreter's FFI marshalling needs the mirror
     check or the backends diverge, and it only catches the direct
     ~expr.c_str~ form (a pointer laundered through an ~I8~ local first
     escapes it, which is fine -- that covers every real call site in
     the tree).
  2. *Make the NUL guarantee visible in the type.*  A distinct type (or
     qualifier) for "NUL-terminated Str" that ~clone~ produces and
     ~substr~ does not, checked at typecheck rather than runtime.  The
     honest fix, and much the largest: it touches every signature that
     currently says ~Str~ and means "C-ready".
  3. *Auto-clone views at the boundary.*  Rejected on sight, recorded so
     it is not re-proposed: it hides an allocation inside what reads as a
     field access, and it still dangles for a callee that RETAINS the
     pointer past the call (doc/ffi.org's actual hazard).
  4. *Panic inside ~.c_str~ itself.*  Also rejected: ~.c_str~ is how til
     code reaches the bytes, and core/str.til reads it on views
     constantly and legitimately -- ~eq~'s ~memcmp~, ~substr~ building
     the next view, indexing, ~hash~.  Those uses carry the count and
     never need the NUL; panicking there would kill the string library to
     catch the rare hostile case.

  Route 1 is the cheap one and route 2 is the correct one; they are not
  exclusive (1 can ship first and stay as a runtime backstop).

*** The NUL audit (done)

  A check that trusts a false invariant is worse than no check, so every
  allocating Str path was audited before choosing a route.  Result: the
  invariant holds everywhere EXCEPT one place, now fixed.

  Verified to terminate:

  - core/str.til: ~with_capacity~ (mallocs n+1, NUL at 0), ~push_str~
    (NUL at the new count), ~clone~, ~from_byte~.  ~format~, ~concat3~,
    ~join~, ~replace~ and ~split~ are all built out of those two, so they
    inherit it.
  - The interpreter's string-literal evaluation (~eval_expr_raw~), which
    NULs explicitly and carries a comment about the same bug class.
  - ext.c: ~F32_to_str~ / ~F32_to_repr~ / ~F64_to_str~ / ~F64_to_repr~ /
    ~U64_to_str_ext~ (memcpy len+1, terminator included),
    ~str_from_bytes~, ~doc_blob_lookup~, ~cfile_read_n~, ~in_read_line~,
    ~repl_str_assign~, ~til_str_left~, and everything routed through
    ~Str_clone~ (which is the compiled core/str.til ~clone~).

  The exception was ~cfile_read_all~ -- File.readfile, the single biggest
  Str producer in the tree.  It malloc'd exactly ~len~ bytes, wrote no
  terminator, and reported ~count = len~ rather than what ~fread~
  returned.  Reading its ~c_str~ as a C string ran off the end of the
  allocation (garbage past the file's last byte, heap-buffer-overflow
  under ASAN), and a short read published bytes that were never written.
  Fixed: malloc len+1, ~buf[got] = '\0'~, count from ~fread~'s return.
  Pinned by ~test_file_readfile_is_nul_terminated~ (test/files.til),
  which reads a file back through ~Str.from_c_str(content.c_str)~ and
  covers the empty-file edge.

  Note this was an OWNED Str breaking the invariant, not a view -- so the
  hazard this issue is about had a second source that no view-shaped
  check would have caught.

*** Constraint on route 1: CAP_VIEW does not imply "no NUL"

  Returning a literal from a til function emits
  ~if (_r->cap == TIL_CAP_LIT) { _r->cap = TIL_CAP_VIEW; }~ -- the Str
  struct is heap-boxed while ~c_str~ keeps pointing at the static C
  literal, and the cap is downgraded so ~delete~ frees the box but not
  the static.  Consequently every literal returned from a function, and
  every empty string (~clone~ of an empty returns ~""~ that way), carries
  ~cap == CAP_VIEW~ while being perfectly NUL-terminated.

  So the naive ext-boundary check -- panic when ~cap == CAP_VIEW~ --
  would fire on entirely safe values, starting with ~get_env~'s own ""
  return.  Route 1 needs a discriminator that separates "view into the
  middle of a til buffer" from "view onto a C literal", which the cap
  field alone does not provide.  Worth settling before any code.

  No known live bug on the view side: nothing in the tree passes a view
  to a C string parameter today, and test/ext_libc.til pins the safe
  shapes.  This is about the hole staying open for the next binding
  somebody writes.
