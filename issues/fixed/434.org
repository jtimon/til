** FIXED #434 Generic bounds: T implements A[, B, ...] for static, monomorphized polymorphism

*** Post-mortem

   Two commits. The first added the bound itself: `T: Type implements A, B`
   on a `(...)` type parameter (parse_type_param_bounds, Declaration.bounds),
   checked by generic_instantiate against the concrete type argument once
   per call site on both instantiation paths (check_generic_bounds; the
   errors are parked in Context.deferred_errors because the instantiation
   runs inside funcs, and the typer flushes them right after a late
   instantiation and at both ends of type_check_unit), a bound naming a
   non-interface or sitting on a runtime Type value rejected, the
   interface's own boxed value satisfying its bound, and the copies calling
   the concrete directly (static_draw__Circle calls Circle_draw).

   The second removed the last obstacle to a two-interface bound: a struct
   or enum now implements several interfaces (`Badge := struct implements
   Drawable, Named`; implements_name keeps them comma-joined,
   def_implements_names / type_def_implements_iface read them). Each is
   checked in full, each one's defaults are copied in, dispatchers and the
   scavenger include the type for every interface it implements, and a
   default two implemented interfaces both provide is copied from neither
   -- the implementer must override it, otherwise the conformance check
   reports "inherits default ... from more than one interface; override it".

   Decided and recorded on the way: the dynamic `d: Drawable` parameter and
   the static bound COEXIST, the bare spelling keeping its dynamic meaning.
   The `func<T>` sugar takes no bounds: `<T implements A, U>` cannot tell a
   second bound from a second parameter.

   Regression tests: test_interface_bound_static_dispatch and
   test_interface_multiple_implements in test/interfaces.til; terr_bound_*,
   TErrTwoMissing and TErrTwoAmbiguous in test/typer_errors.til.
   Documented in doc/concepts/functions.org "Bounded type parameters".

   `d: Drawable` (dynamic dispatch through a boxed value, #269/#432) and a
   bounded type parameter are different features. The second is a GENERIC
   BOUND: the function is instantiated per concrete type, calls are
   resolved statically, and there is no box, no heap copy and no runtime
   tag. It is Rust's `impl Trait` / `<T: Trait>`, Swift generics, C++
   concepts, Java generics -- and it composes for several interfaces where
   dynamic dispatch does not (Rust forbids `dyn A + B`; Go needs an ad-hoc
   `interface{ A; B }`). The #251 status (issues/fixed/251.org) records the
   gap: the parser keeps one implements_name per struct/enum, and multiple
   implemented interfaces, interface inheritance and interface bounds on
   generic parameters are not provided.

       // static: one specialization per concrete type, direct calls
       print_it := func(T: Type implements Drawable, d: T) {
           println(d.draw())
       }
       print_it(Circle(r = 1))      // print_it_Circle  -> Circle.draw
       print_it(Polygon.Tri)        // print_it_Polygon -> Polygon.draw

       // several bounds
       dump := func(T: Type implements Iterable, Printable, e: T) { ... }

       // dynamic, for contrast: one function, boxed value, runtime dispatch
       render := func(d: Drawable) returns Str { return d.draw() }

   til already has function-level type parameters with explicit and
   inferred instantiation (`generic_argument_holder := func(T: Type, tag: T,
   d: Drawable)` in test/interfaces.til, called both as
   `generic_argument_holder(I64, 7, x)` and `generic_argument_holder(7, x)`),
   so the bound attaches to an existing mechanism rather than a new one.

   Rust's rule of thumb applies: if the static form works, use it; the
   dynamic box is for a bag of mixed things dispatched at runtime (#433) or
   a type decided at runtime. Most `d: Drawable` parameters written so far
   are the static kind in disguise.

*** Semantics

   - Bound check = the #251 conformance check (interface_method_conforms):
     the concrete must provide every abstract method of every listed
     interface; a call with a non-conforming argument is a typer error at
     the call site naming the missing method. Since 0f13652c that check
     compares the complete FuncSig (ownership, mutability, effects, throws),
     so the bound inherits the full contract.
   - Instantiation = the #57 macro machinery (monomorphization by
     substitution, as #243 proposes for Vec(T)): one FuncDef per distinct
     concrete T reached from call sites.
   - Inside the body, `d.method()` resolves statically to T.method; the
     interface's concrete defaults (#268) are already copied into T's
     namespace, so a concrete override is honoured directly, with no
     dispatcher in between (through a box it is honoured too since e7551bac,
     via the virtual default dispatch).

*** Design questions

   - Syntax: `T: Type implements A, B` on the existing type parameter, vs an
     inline `d: T implements A` on the value parameter, vs both.
   - `returns T`, and `T` in fields (a struct generic over a bounded T --
     Vec(T) territory, #243).
   - Instantiation policy: per call site with dedup by concrete type; error
     on unbounded recursive instantiation.
   - DECIDED (2026-10-20): the two forms COEXIST. `d: Drawable` on a
     parameter stays the dynamic form (one function, dispatch on the box's
     tag, the only way to hold mixed concretes in one collection) and
     `T: Type implements Drawable, d: T` is the static one (one copy per
     T, direct calls, more generated code). Rust has both (`dyn Trait` /
     `impl Trait`), Go only the first; til keeps the dynamic one as the
     default so nothing already written changes meaning, and the static
     form is opt-in where the extra code is worth the speed. Each default
     and abstract call keeps the same meaning in both: #432's
     conformance check and virtual defaults apply to the box, direct
     resolution to the bound.

*** Progress

   - [X] `T: Type implements A, B` parses on a `(...)` type parameter
     (parse_type_param_bounds; Declaration.bounds). The `func<T>` sugar
     takes no bounds: `<T implements A, U>` cannot tell a second bound
     from a second parameter, while in a parameter list every parameter
     is `name:`.
   - [X] generic_instantiate checks every bound against the concrete type
     argument, once per call site, on both the init (explicit type
     argument) and the typer (inferred) instantiation paths
     (check_generic_bounds; errors parked in Context.deferred_errors since
     the instantiation runs inside funcs, and flushed by the typer right
     after a late instantiation and at both ends of type_check_unit).
     A bound naming a non-interface is reported at the same site; the
     interface's own boxed value satisfies its bound.
   - [X] A bound on a runtime `Type` value (a parameter the signature
     never uses as a type) is a typer error.
   - [X] Inside the copy, calls are static: static_draw__Circle calls
     Circle_draw directly in the generated C; a concrete override of a
     default is honoured (test_interface_bound_static_dispatch).
   - [X] Documented in doc/concepts/functions.org "Bounded type
     parameters"; the coexistence decision is recorded above.
   - [X] Two bounds are checked independently (terr_bound_two) and
     satisfied together by a type implementing both interfaces
     (test_interface_multiple_implements): `struct implements A, B` /
     `enum implements A, B`, each checked in full, ambiguous defaults
     rejected unless overridden.
