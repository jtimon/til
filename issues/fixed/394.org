# category: bugs
** FIXED #394 dyn_size_of("Dynamic") is 8 interpreted and 1 compiled

*** Post-mortem

Root cause: ~emit_dyn_size_of_body~ answered the name "Dynamic" with
~sizeof(Dynamic)~, and ~Dynamic~ in the emitted C is not the type -- it is
the placeholder ~emit_struct_typedef~ writes for a StructDef with no fields,
~char _;~, because ISO C has no empty struct. So the compiled dispatcher
reported 1 where the til declaration's ~size()~ namespace func, which the
interpreter resolves through, says a word. The arm's own comment explains why
~sizeof~ is the right oracle -- it makes the width right for the target
without the emitter knowing any width -- and that reasoning is sound
everywhere the emitted C type IS the layout. Dynamic is the one name where it
is not, and the branch was written as if it were.

Fix: one line. The Dynamic arm becomes
~emit_dyn_name_return_branch(f, "Dynamic", "sizeof(void *)")~ -- the same
shape the Fn and Body branches beside it already use, which is the existing
answer to "the emitted C type is a stand-in, so the branch names the width".
Nothing else changed: the interpreter was already right, and no other name
disagreed.

Blast radius checked, and it is smaller than the fix direction feared. A
field-less StructDef only reaches the dispatcher when it has a ~size()~
method AND survives the scavenger; a user-declared empty struct answers
"unknown type" on BOTH backends (verified for a bare ~struct { }~ and for one
carrying a ~size()~), so Dynamic was the only name with a wrong answer rather
than no answer. Bool and I64 are field-less StructDefs too, but they are
primitives: their arms resolve through ext.h's real typedefs, not a
placeholder.

Regression tests: ~test_dyn_size_of_runtime_name~ (test/dynamic.til) reads
the name out of an array at a loop index, the one spelling the constfolder
cannot reach -- every literal form in the neighbouring ~test_dyn_size_of~
folds through the interpreter, which is exactly why a nine-line test of
~dyn_size_of("Dynamic")~ sat beside this bug without seeing it, and why the
new test's emitted C was checked for a real call rather than assumed to have
one. ~test_tuple_dynamic_word~ (test/tuples.til) pins the unit behaviour: a
"Dynamic"-tagged element is a word wide and a second element lands after it,
not seven bytes early. ~test_dynamic_variadic_tuple~ (test/variadic.til) now
asserts what a splatted ~Array(Dynamic)~ element is WORTH beside what it is
tagged; it asserted only the tags before, which is how the values stayed
garbage. All three fail against the pre-fix compiler and pass on both
backends after.

A note for whoever revisits Dynamic's width: ~Dynamic.size()~ in
src/core/dyn.til returns a literal 8, while the emitted C now says
~sizeof(void *)~. They agree on every target the suite runs, and the C side
is the one that stays right if a pointer is ever not eight bytes -- but the
til literal would then be wrong, and ~Array(Dynamic)~ sizes its elements
through it. Out of scope here; the disagreement this issue is about is fixed.

A runtime ~dyn_size_of~ of the name "Dynamic" answers 8 in the interpreter
and 1 in the C backend. Every other type agrees; only Dynamic splits:

    ask := func(n: Str) returns USize { return dyn_size_of(n) }
    mut names := array(Str, "Dynamic", "I64", "Str")
    for i in 0..names.len() {
        ref n : Str = names.unsafe_get(i)
        println("dyn_size_of(", n, ") = ", ask(n).to_str())
    }

    | name    | interp | compiled |
    | Dynamic |      8 |        1 |
    | I64     |      8 |        8 |
    | Str     |     16 |       16 |

It has to be the RUNTIME dispatch. ~dyn_size_of("Dynamic")~ written with a
literal is const-folded through the interpreter and answers 8 on both, which
is why test/dynamic.til's test_dyn_size_of never saw this.

*** Root cause

~Dynamic~ is declared in src/core/dyn.til as a FIELD-LESS ~StructDef~ whose
namespace carries the real answer:

    Dynamic : StructDef = struct {
    namespace:
        size := func() returns USize { return 8 }

The interpreter's ~h_dyn_size_of~ resolves through that ~size()~ and gets 8.
The C backend does not: ~emit_dyn_size_of_body~ (src/self/c_codegen.til)
opens with a hardcoded arm

    if (name == "Dynamic") return sizeof(Dynamic);

and ~Dynamic~ in the emitted C is the placeholder a field-less struct gets --
~emit~ writes ~char _;~ into an otherwise empty struct body so the C is
legal -- so ~sizeof(Dynamic)~ is 1, not the word the til declaration means.

*** What it breaks

Every runtime consumer of ~dyn_size_of~ that can be handed "Dynamic":
~Tuple.push_type_name~ (src/core/tuple.til) and the ~src/std/dyn_*.til~
containers (dyn_array, dyn_set, dyn_vec). An element stored as "Dynamic"
occupies ONE byte compiled, so the word is truncated to its low byte and
every element pushed after it sits at the wrong offset.

Found through #392: a ~..~ splat of an ~Array(Dynamic)~ into a ~..Dynamic~
variadic pushes each element as "Dynamic", and reading them back disagrees.

    d := array(Dynamic, 11, 22)
    dump := func(xs: ..Dynamic) returns Str {
        mut out := ""
        for i in 0..xs.len() {
            ref n : I64 = xs.get(i)
            out = format(out, xs.type_at(i), "=", n.to_str(), " ")
        }
        return out
    }
    println(dump(..d))
    // interp:   Dynamic=11 Dynamic=22
    // compiled: Dynamic=94210673546763 Dynamic=368010443542

~size_at(0)~ reads 8 interpreted and 1 compiled, which is the whole story;
the garbage is the 8-byte read running off a 1-byte slot. Note the array
itself is fine -- ~d.unsafe_get(0)~ read as I64 gives 11 on both backends,
because ~Array(Dynamic)~ sizes its elements through ~T.size()~, which is
const-folded and correct. Only the string-keyed runtime path is wrong.

This predates #392: reproduced with ~bin/til_boot~ at master ~d68d078~.
#392's issue text claims an element pushed AS Dynamic "keeps raw-word
semantics" -- true interpreted, false compiled, because of this.

*** Fix direction

The hardcoded arm should report the width the til declaration promises --
~sizeof(void *)~ -- rather than the size of a placeholder struct that exists
only to make the C compile. Worth checking at the same time whether any
OTHER field-less StructDef reaches ~emit_dyn_size_of_arm~ and inherits the
same ~char _;~ answer, since the arm is generated for every struct decl.

*** Regression test

~dyn_size_of~ of a NON-literal "Dynamic" (behind a func, so the constfolder
cannot reach it), both backends -- the literal form already passes and hides
the bug. Plus the round trip through a Tuple element tagged "Dynamic": push
a known word, read it back, both backends.
