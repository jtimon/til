** FIXED #90 Til libraries: avoid symbol conflicts between independent libs

*** Post-mortem

Library output reused unqualified generated, generic, and runtime C names,
and its generated Til bindings repeated synthesized generic type names. Each
library now derives an injective C namespace from its artifact name and uses
the existing forward header as the namespace map for generated C, ~ext.c~,
declared ~link_c~ definitions, public headers, and language bindings. Library
output also uses its constructor initializer instead of emitting ~main~.

~test/library_namespace.til~ builds two libraries with the same ~Array(I64)~
and ~Vec(I64)~ instantiations, then compiles and runs combined-header static
and shared C consumers and a Til consumer importing both generated bindings.

When two til libraries are linked into the same C program, they both
define core, generated specialization, and C runtime symbols. This matters
when til is used as a library language by external C programs.

*** Re-analysis (2026-08-19)

The original description predates private path mangling (#179), library
scavenging and closed-world C linkage (#326), cross-target library output
(#25), installed libraries (#42), and the USize ABI switch (#309). Those
changes reduced each library, but did not isolate it:

- Library mode deliberately keeps its exported ABI non-static. Core and
  generated support declarations still become global definitions.
- ~compile_lib~ puts the complete hand-written ~ext.o~ in every shared and
  static library. Its runtime symbols are global too.
- The generated public header repeats core struct definitions and support
  prototypes, so composition fails before linking when two headers are
  included in one C translation unit.
- Library C currently emits ~main~ instead of the existing constructor
  path: ~is_script~ is initialized independently of ~is_lib~, making
  ~emit_lib_init~ unreachable for normal library modes.

Concrete reproduction with ~examples/lib/cell.til~ and
~examples/lib/alphabeta.til~:

- Their shared objects have 230 common exported symbol names.
- Linking both static archives fails on ~main~, ~CAP_LIT~, ~Str_clone~,
  ~Array__Str_*~, ~println~, and the rest of the common support surface.
- Linking both shared objects succeeds, but the second object's
  ~Str_clone~ and ~CAP_LIT~ relocations are interposable and bind by load
  order rather than to that library's own implementation.
- Including both generated headers fails with redefinitions of ~Str~,
  ~Array__Str~, ~Dynamic~, and their associated prototypes.

The two old proposals are insufficient:

- A common ~libcoretil.a~ does not own program-specific generic
  instantiations, generated helpers, or arbitrary ~link_c~ code. It also
  introduces a target/ASAN/USize/version ABI matrix and a new installed
  dependency.
- A fixed prefix such as ~_til_~ only moves the collision: every library
  would still export the same prefixed names. The namespace must include
  the library identity.

*** Required invariant

Two libraries whose own public declaration names do not conflict must be
usable together from one C program, through either their static or shared
artifacts, without special linker flags. Including both public headers must
compile. Each library must bind to its own generated/runtime implementation,
including when another library was built by a different til version with the
same public ABI settings. Different targets or USize settings are distinct
ABIs, not composable libraries. A genuine collision between the libraries'
own public APIs should remain a loud error.

*** Proposed implementation

Use a deterministic C namespace derived from the library artifact name,
for example ~til_cell__ca_step~ and ~til_cell__Str_clone~.

1. Prefix every symbol owned by a library: source definitions, globals,
   generated generic/lifecycle helpers, reflection helpers, initializer,
   and the bundled ~src/c/ext.c~ runtime. Do not rename unresolved external
   dependencies such as libc or symbols supplied by a separately linked C
   library.
2. Namespace generated C tags/typedefs as well as linker symbols, so two
   generated headers compose even when both libraries instantiate the same
   til type name.
3. Emit the real prefixed names in the C header. Generate til aliases or
   forwarding methods and Python lookups so those language bindings retain
   the original source-level API names.
4. Reuse the existing generated forward header as the compile-time symbol
   map for the generated C, ~ext.c~, and declared ~link_c~ definitions; do
   not add another generated artifact.
5. Emit the existing constructor-based library initializer, never ~main~.
6. Add one regression that builds two tiny libraries sharing core and the
   same generic instantiations, includes both headers, and links/calls both
   static archives. Run the equivalent shared-library program too, plus a
   til consumer of both generated bindings.

This intentionally changes the generated C ABI. Existing C consumers must
rebuild against the newly generated header; generated til/Python consumers
keep their source-level names. No compatibility aliases should be emitted,
because unprefixed aliases recreate the conflict this issue removes.

*** Follow-up: parallel build intermediates (2026-08-20)

The namespace fix made each library's bundled runtime implementation distinct,
but ~compile_lib~ still writes every build's runtime and declared ~link_c~
objects to the shared ~gen/lib/ext.o~ and ~gen/lib/user.o~ paths. A full-suite
run exposed the race when parallel ~pure_build~ and ~pura_build~ jobs produced:

#+begin_example
ar: gen/lib/ext.o: No such file or directory
error: static library creation failed
#+end_example

The collision is not merely temporary-file churn. Each ~ext.o~ is compiled
through that library's generated forward header, whose namespace map gives the
runtime different symbols. ~user.o~ also uses that header and can additionally
differ by declared C source and include flags. Target, ASAN, and USize settings
affect all three library objects. One build can therefore link or archive a
different library's complete but incompatible object, not just observe a
missing or partially written file.

The practical concurrency boundary is the library artifact name. Builds of
different names already have distinct generated C, primary objects, bindings,
and final libraries and should be safe in parallel. Concurrent builds of the
same name target the same canonical outputs throughout translation and remain
unsupported unless the entire build gains private staging and atomic
publication.

The fix keys every intermediate object by the existing library name:
~gen/lib/<name>.o~, ~gen/lib/<name>_ext.o~, and optional
~gen/lib/<name>_user.o~. ~compile_lib~ writes and consumes them; they stay under
the existing ignored ~gen/~ tree, ~make clean~ removes them, and install still
copies only the canonical public artifacts. The static archive is now created
at a fresh process-specific path and renamed into place: ~ar rcs~ updates an
existing archive and otherwise retains stale members, including the old generic
object names or an optional user object removed by a later source change.

The existing ~test/library_namespace.til~ fixture is the focused regression. It
starts its two library builds together with ~Cmd.start~, waits for both, then
keeps the current static, shared, and Til consumers. Their distinct namespaces
make cross-contaminated objects fail loudly without adding another fixture.
~make clean && make test~ passes 413/413.

Process-private staging under ~gen/lib~ is the stronger alternative. To support
same-name builds correctly it must cover generated C, forward/public headers,
bindings, all objects, both final libraries, and install copying, followed by a
coherent per-name publication step. Staging only ~ext.o~ and ~user.o~ would add
complexity without establishing that stronger contract.

*** Further follow-up assessment (2026-08-20)

The subsequent ~link_c~ namespace regression gives both concurrent fixture
libraries distinct declared C sources and consumes their exported helpers from
static, shared, and generated Til clients. It therefore covers the optional
~<name>_user.o~ path as well as ~<name>_ext.o~; no additional #90 regression is
missing there.

Supporting concurrent builds of the SAME artifact name is a separate contract,
not a remainder of the different-name fix. A correct implementation needs an
OS-released per-name lock held before translation touches any canonical path,
plus process-private staging for generated C, the forward/public headers, Til
and Python bindings, every object, and both libraries. Install needs a second
per-name lock under the destination prefix and must publish from that private
stage rather than reread the mutable build tree. Individual renames cannot make
this file set atomically visible to lock-free external C/Python readers; that
stronger guarantee would require an immutable-generation layout and one atomic
~current~ pointer, changing every consumer path.

A shared core remains incompatible with #90's chosen invariant. Nothing in the
current generated library can move unchanged: inline core operations have no
artifact, while ~ext.c~, generated lifecycle/generic/reflection/closure helpers,
runtime globals, and public layouts are library- or compiler-version-specific.
A reusable subset would first need a versioned ABI identity covering the exact
runtime/emitter revision, target, calling convention, pointer and USize widths,
ASAN, ownership/aggregate/enum/closure/error conventions, and toolchain. It
would also add versioned headers and static/shared artifacts, transitive dynamic
loading, installed dependency metadata, and extra static-link inputs. Bundling
those members back into each archive would preserve self-contained libraries
but would not reduce artifact duplication.

These are substantial new concurrency and distribution features. They should
not be implemented as implicit follow-ups to the completed #90 collision fix.
