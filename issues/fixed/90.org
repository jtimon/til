** FIXED #90 Til libraries: avoid symbol conflicts between independent libs

*** Post-mortem

Library output reused unqualified generated, generic, and runtime C names,
and its generated Til bindings repeated synthesized generic type names. Each
library now derives an injective C namespace from its artifact name and uses
the existing forward header as the namespace map for generated C, ~ext.c~,
declared ~link_c~ definitions, public headers, and language bindings. Library
output also uses its constructor initializer instead of emitting ~main~.

~test/library_namespace.til~ builds two libraries with the same ~Array(I64)~
and ~Vec(I64)~ instantiations, then compiles and runs combined-header static
and shared C consumers and a Til consumer importing both generated bindings.

When two til libraries are linked into the same C program, they both
define core, generated specialization, and C runtime symbols. This matters
when til is used as a library language by external C programs.

*** Re-analysis (2026-08-19)

The original description predates private path mangling (#179), library
scavenging and closed-world C linkage (#326), cross-target library output
(#25), installed libraries (#42), and the USize ABI switch (#309). Those
changes reduced each library, but did not isolate it:

- Library mode deliberately keeps its exported ABI non-static. Core and
  generated support declarations still become global definitions.
- ~compile_lib~ puts the complete hand-written ~ext.o~ in every shared and
  static library. Its runtime symbols are global too.
- The generated public header repeats core struct definitions and support
  prototypes, so composition fails before linking when two headers are
  included in one C translation unit.
- Library C currently emits ~main~ instead of the existing constructor
  path: ~is_script~ is initialized independently of ~is_lib~, making
  ~emit_lib_init~ unreachable for normal library modes.

Concrete reproduction with ~examples/lib/cell.til~ and
~examples/lib/alphabeta.til~:

- Their shared objects have 230 common exported symbol names.
- Linking both static archives fails on ~main~, ~CAP_LIT~, ~Str_clone~,
  ~Array__Str_*~, ~println~, and the rest of the common support surface.
- Linking both shared objects succeeds, but the second object's
  ~Str_clone~ and ~CAP_LIT~ relocations are interposable and bind by load
  order rather than to that library's own implementation.
- Including both generated headers fails with redefinitions of ~Str~,
  ~Array__Str~, ~Dynamic~, and their associated prototypes.

The two old proposals are insufficient:

- A common ~libcoretil.a~ does not own program-specific generic
  instantiations, generated helpers, or arbitrary ~link_c~ code. It also
  introduces a target/ASAN/USize/version ABI matrix and a new installed
  dependency.
- A fixed prefix such as ~_til_~ only moves the collision: every library
  would still export the same prefixed names. The namespace must include
  the library identity.

*** Required invariant

Two libraries whose own public declaration names do not conflict must be
usable together from one C program, through either their static or shared
artifacts, without special linker flags. Including both public headers must
compile. Each library must bind to its own generated/runtime implementation,
including when another library was built by a different til version with the
same public ABI settings. Different targets or USize settings are distinct
ABIs, not composable libraries. A genuine collision between the libraries'
own public APIs should remain a loud error.

*** Proposed implementation

Use a deterministic C namespace derived from the library artifact name,
for example ~til_cell__ca_step~ and ~til_cell__Str_clone~.

1. Prefix every symbol owned by a library: source definitions, globals,
   generated generic/lifecycle helpers, reflection helpers, initializer,
   and the bundled ~src/c/ext.c~ runtime. Do not rename unresolved external
   dependencies such as libc or symbols supplied by a separately linked C
   library.
2. Namespace generated C tags/typedefs as well as linker symbols, so two
   generated headers compose even when both libraries instantiate the same
   til type name.
3. Emit the real prefixed names in the C header. Generate til aliases or
   forwarding methods and Python lookups so those language bindings retain
   the original source-level API names.
4. Reuse the existing generated forward header as the compile-time symbol
   map for the generated C, ~ext.c~, and declared ~link_c~ definitions; do
   not add another generated artifact.
5. Emit the existing constructor-based library initializer, never ~main~.
6. Add one regression that builds two tiny libraries sharing core and the
   same generic instantiations, includes both headers, and links/calls both
   static archives. Run the equivalent shared-library program too, plus a
   til consumer of both generated bindings.

This intentionally changes the generated C ABI. Existing C consumers must
rebuild against the newly generated header; generated til/Python consumers
keep their source-level names. No compatibility aliases should be emitted,
because unprefixed aliases recreate the conflict this issue removes.

*** Follow-up: parallel build intermediates (2026-08-20)

The namespace fix made each library's bundled runtime implementation distinct,
but ~compile_lib~ still writes every build's runtime and declared ~link_c~
objects to the shared ~gen/lib/ext.o~ and ~gen/lib/user.o~ paths. A full-suite
run exposed the race when parallel ~pure_build~ and ~pura_build~ jobs produced:

#+begin_example
ar: gen/lib/ext.o: No such file or directory
error: static library creation failed
#+end_example

The collision is not merely temporary-file churn. Each ~ext.o~ is compiled
through that library's generated forward header, whose namespace map gives the
runtime different symbols. ~user.o~ also uses that header and can additionally
differ by declared C source and include flags. Target, ASAN, and USize settings
affect all three library objects. One build can therefore link or archive a
different library's complete but incompatible object, not just observe a
missing or partially written file.

The practical concurrency boundary is the library artifact name. Builds of
different names already have distinct generated C, primary objects, bindings,
and final libraries and should be safe in parallel. Concurrent builds of the
same name target the same canonical outputs throughout translation and remain
unsupported unless the entire build gains private staging and atomic
publication.

The fix keys every intermediate object by the existing library name:
~gen/lib/<name>.o~, ~gen/lib/<name>_ext.o~, and optional
~gen/lib/<name>_user.o~. ~compile_lib~ writes and consumes them; they stay under
the existing ignored ~gen/~ tree, ~make clean~ removes them, and install still
copies only the canonical public artifacts. The static archive is now created
at a fresh process-specific path and renamed into place: ~ar rcs~ updates an
existing archive and otherwise retains stale members, including the old generic
object names or an optional user object removed by a later source change.

The existing ~test/library_namespace.til~ fixture is the focused regression. It
starts its two library builds together with ~Cmd.start~, waits for both, then
keeps the current static, shared, and Til consumers. Their distinct namespaces
make cross-contaminated objects fail loudly without adding another fixture.
~make clean && make test~ passes 413/413.

Process-private staging under ~gen/lib~ is the stronger alternative. To support
same-name builds correctly it must cover generated C, forward/public headers,
bindings, all objects, both final libraries, and install copying, followed by a
coherent per-name publication step. Staging only ~ext.o~ and ~user.o~ would add
complexity without establishing that stronger contract.

*** Further follow-up assessment (2026-08-20)

The subsequent ~link_c~ namespace regression gives both concurrent fixture
libraries distinct declared C sources and consumes their exported helpers from
static, shared, and generated Til clients. It therefore covers the optional
~<name>_user.o~ path as well as ~<name>_ext.o~; no additional #90 regression is
missing there.

Supporting concurrent builds of the SAME artifact name is a separate contract,
not a remainder of the different-name fix. A correct implementation needs an
OS-released per-name lock held before translation touches any canonical path,
plus process-private staging for generated C, the forward/public headers, Til
and Python bindings, every object, and both libraries. Install needs a second
per-name lock under the destination prefix and must publish from that private
stage rather than reread the mutable build tree. Individual renames cannot make
this file set atomically visible to lock-free external C/Python readers; that
stronger guarantee would require an immutable-generation layout and one atomic
~current~ pointer, changing every consumer path.

A shared core remains incompatible with #90's chosen invariant. Nothing in the
current generated library can move unchanged: inline core operations have no
artifact, while ~ext.c~, generated lifecycle/generic/reflection/closure helpers,
runtime globals, and public layouts are library- or compiler-version-specific.
A reusable subset would first need a versioned ABI identity covering the exact
runtime/emitter revision, target, calling convention, pointer and USize widths,
ASAN, ownership/aggregate/enum/closure/error conventions, and toolchain. It
would also add versioned headers and static/shared artifacts, transitive dynamic
loading, installed dependency metadata, and extra static-link inputs. Bundling
those members back into each archive would preserve self-contained libraries
but would not reduce artifact duplication.

These are substantial new concurrency and distribution features. They should
not be implemented as implicit follow-ups to the completed #90 collision fix.

*** Follow-up: versioned shared runtime (2026-08-27)

The earlier shared-core assessment correctly rejected one unversioned runtime:
it would silently bind libraries built for incompatible compiler ABIs. The
missing boundary was an exact ABI identity, not a reason to duplicate the
entire hand-written runtime forever.

Each native library now maps ~ext.c~-owned symbols into a runtime namespace
containing the full compiler commit, target, resolved USize type, and ASAN
mode. ~compile_lib~ atomically publishes the matching
~gen/lib/libtilrt-<abi>~ shared object and links generated shared libraries to
it with a same-directory loader path. Different compiler ABIs coexist under
different filenames and symbols; libraries with the same ABI share one loaded
image and its code pages. Installation copies that runtime beside the library.

~ext.c~ formerly retained relocations to each generated library's ~CAP_LIT~
and ~CAP_VIEW~ globals. It now uses the same constant values locally, making
the runtime object independent of any one generated library. Static archives
embed the versioned runtime object, so they remain self-contained and the
static linker selects one copy when combining compatible libraries.

This does not pretend that all core code is already separately compilable.
Program-specific generic, lifecycle, reflection, and closure helpers remain in
the artifact namespace. Concrete core/std partitions can reuse this ABI and
loader model once the emitter has a real partition for them.

*** Follow-up: concrete shared core leaf (2026-08-27)

Generated dynamic libraries now also depend on ~libtilcore-<abi>~, using the
same revision/target/USize/ASAN identity and atomic publication as ~libtilrt~.
The initial fixed core ABI contains allocation-free Str query/comparison
operations plus primitive/Dynamic size and delete helpers. These are emitted
from their existing Til definitions: ~TIL_CORE_ONLY~ builds the shared image,
while ~TIL_SHARED_CORE~ removes the duplicate definitions from each generated
shared object.

The core image compiles hidden, function/data-sectioned code and exports only
the fixed core ABI; its generated library constructor is disabled, so building
it from a library's generated C cannot run or expose that library's globals.
Public C headers omit the internal shared-core prototypes, preserving header
composition despite each public library retaining its own C type namespace.
Static archives keep weak self-contained copies of the leaf functions, so they
still require no transitive static-link argument and compatible archives select
one definition.

Generic instantiations, aggregate lifecycle code, reflection, closure tables,
mutable core globals, and allocating/string-producing core functions remain
artifact-local. Moving any of those needs a canonical type/global/literal
partition rather than broadening this leaf ABI by name alone.

*** Follow-up: canonical Str ownership (2026-08-30)

The shared core now owns the versioned C ~Str~ layout and the immutable
~CAP_LIT~ / ~CAP_VIEW~ data symbols. Compatible public headers map ~Str~ to
the same core name and guard its definition with that versioned identity, so
two independent headers compose around one canonical layout. Shared library
objects declare the CAP globals from ~libtilcore~; core-only output exports
them, while static archives retain weak self-contained definitions.

Shared-core function bodies no longer resolve their literals through an
artifact's private ~_til_str_lits~ pool. Their literals stay inline with the
owning core function, making core-only output independent of the generating
library. This permits the concrete allocation/view family -- ~with_capacity~,
~from_c_str~, ~clone~, ~to_str~, ~delete~, ~borrowed_view~, ~substr~,
~trim_start~, ~trim~, ~get_char~, ~strip_prefix~, ~strip_suffix~,
~from_byte~, and ~c_str_len~ -- to join the existing query functions.
Panic/variadic/generic string operations remain artifact-local because their
emitted bodies depend on generated collection support.

~test/library_namespace.til~ verifies that both libraries use identical core
type, global, and allocating-function aliases. Its static/shared C and Til
consumers execute clone, trim, C-string view, suffix view, and byte-allocation
paths across the common core.

*** Follow-up: shared variadic panic dependency group (2026-09-24)

The existing panic implementation depended on artifact-local Array(Str)
construction, insertion, cloning, and deletion, plus format and println.
Even a single-message panic in Str.get or Str.push_str therefore prevented
those functions from moving into the shared core.

The fixed core partition now includes the canonical Array(Str) layout and
the required methods, adopt(Str), Str.size, format, panic, println, and its
print_single/print_flush output helpers. The latter are emitted directly by
c_codegen and now use the same definition partition as Til-source functions.
Str.get, Str.push_str, concat3, and Str.replace join this dependency group.
Definitions still come from the existing Til sources; other generic
specializations remain artifact-local. Static archives retain weak copies.
Panic keeps its current variadic allocation, output, location, and exit
behavior; the alternative borrowed C-array optimization is tracked in #405.

The library_namespace regression checks canonical aliases and composed
static/shared consumers, exercises formatting and replacement, and verifies
exit status 1 and stdout diagnostics for out-of-bounds Str.get, both
Str.push_str failures, and an explicit-location multipart panic. The install
regression exercises formatting and panic through an installed Python binding
from outside the repository.

*** Follow-up: shared numeric Str parsing (2026-09-25)

The versioned core now also owns the signed, unsigned, narrow integer, USize,
and floating-point Str conversion bodies. Their integer parsing dependencies
include digit_value, the immutable I64/U64 limit globals, and the existing
private parse_integer_magnitude function. The private helper's source C name
includes its file path, which differs between checkout and installed builds;
the library namespace map resolves that declaration to a stable versioned
core symbol. No duplicate parsing implementation or new generated artifact
is introduced.

Installed paths containing punctuation (for example the hyphen in a worktree
name) also exposed invalid C hoisted-temp identifiers inside that private
helper. The existing private-name encoder now sanitizes such paths when
naming their generated temporaries while normal source paths retain their
previous output and self-translation stability.

The library_namespace regression checks canonical symbols, signed and U64
boundaries, base prefixes, digit separators, narrow conversions, floating
parsing with views, and exact stdout diagnostics on invalid or out-of-range
values in both static and shared consumers. The install regression verifies
the canonical helper alias and parses U64.MAX through an installed Python
binding outside the checkout.

*** Follow-up: shared Vec(Str), split, and join (2026-09-25)

The versioned core now owns the concrete Vec(Str) layout and the methods
needed to construct, read, push, clone, and delete its contents. Str.split and
join use that same shared type and implementations; other Vec specializations
remain library-local. A folded empty Vec(Str) in Str.split formerly cloned an
artifact-private precomputed template. The emitter now materializes an empty
zero-capacity value within a shared-core body, without exporting or duplicating
any generated template; other precomputed templates remain artifact-local.

The Python binding derives the Vec(Str) ctypes layout from its existing
synthesized core StructDef, including when an exported function uses that type
but its declaration is absent from the library's own units. The interpreter
FFI must also convert the backing Str array when crossing USize widths, not
just the Vec header: the installed library uses 24-byte Str elements while
the USize32-built interpreter uses 16-byte elements. The conversion copies
each element at its own ABI stride and transfers only the element buffer's
ownership; the nested string data retains its existing ownership. Borrowed,
mutable, and owned FFI arguments release their respective converted buffers
or boxes after the call.

The library_namespace regression checks static and shared C consumers,
generated Python bindings, compiled and interpreted Til consumers passing a
Vec(Str) between two libraries, and mutable/owned vector arguments. The
install regression exercises split/join through the installed Python binding.
The interpreted consumer also runs under ASAN to verify no invalid frees or
leaked conversion buffers.

*** Follow-up: derive shared ownership from imported core (2026-09-25)

The previous shared-core name list in Context repeated individual methods,
types, and globals already defined by the always-imported core AST. The
scavenger now selects candidates from those typed, const-folded declarations:
stable Str/scalar and concrete core Array/Vec layouts, immutable literal
globals, and functions with signatures over those layouts. It drops bodies
with nonempty artifact-local precomputed templates, captured closures,
payload-carrying throws, user declarations, mutable/unselected core globals,
or program-specific reflection/dispatch dependencies. From the actual Str
definition it roots its explicitly declared methods and the helpers in the
same core unit, then follows the candidate dependency closure. Scalar
size/delete methods are shared by their lifecycle role. No new index or
source-of-truth file is written; the result reuses the existing core C-name
map and the existing versioned library/core artifacts. Private helper C
names derive from their source unit, not their checkout/install path.

The first attempt to export every eligible core declaration was counter to
the purpose of sharing: the two-library fixture's core grew from 83,600 to
179,240 bytes (97 to 251 exports). Limiting ownership to the Str entrypoints
and their dependencies leaves 90 exports and shrinks the core to 82,744
bytes. Across the core plus both shared libraries, measured ELF text drops
from 141,325 to 140,639 bytes; their two static archives together drop
from 569,194 to 565,350 bytes. These are code-size measurements, not a
measured CPU-cache or execution-speed improvement.

The library_namespace regression now compares the entire canonical alias
set between independently generated libraries: both builds publish the SAME
versioned core path, so one must never demand an export the other omitted.
It also checks that a FuncSig/closure layout remains library-local while
compiled, interpreted, installed, static and shared consumers still work.
