** FIXED #488 Restore pristine raylib and keep GUI adaptations in til

*** Post-mortem

Two downstream edits lived in raylib: til's browser presentation replaced
~src/shell.html~, and its Android backend carried polling/EGL shutdown fixes.
Both would be lost on an upstream update. Following the user's direction to
own GUI customizations in til, the complete tracked vendor tree now matches
the original upstream revision ~f9ea60738547fed4e9a2e16af6c5b83b08475281~
(subtree tree ~7bef6031f6093abc0d51408c0ac8b75080495efc~), byte for byte.

The browser shell moved verbatim to ~src/modes/gui.html~. The C builder
finds it through the compiler support root, and template edits invalidate
the linked browser output. The existing modes-tree installation includes it.
~test/build_outputs.til::check_browser_shell~ tests an independent support
tree with spaces in its path, unchanged-build reuse, and template-only relink.
A real Emscripten 6.0.0 Shootil build rendered in headless Chromium after a
canvas click, without JavaScript exceptions; the toolbar initialized too.

Android adaptation is in the existing first-party GUI boundary in
~src/self/codegen/ext.c~, enabled only for APK builds. Linker interposition
adds pbuffer capability during the owned window's EGL configuration and
ends polling once its activity is destroyed. The lifecycle callback binds
a tiny current pbuffer for GL cleanup, marking it for EGL's deferred
deletion on unbind. Thread-local phase/activity state leaves other threads'
EGL and looper calls alone. An already-closed window needs no cleanup surface.
Neither upstream source nor source copies are patched during builds.

The newer upstream polling fix (#6040) was identified, but that snapshot also
changes public APIs such as ChangeDirectory's return semantics. Restoring
the existing revision avoids that upgrade. The upstream EGL defect remains
upstream; this resolution follows the first-party GUI ownership direction,
not a claim that both bugs were merged upstream. The earlier plan below is
retained as investigation history.

Regression: ~examples/checkers.til~ on API 28/4 KB and API 35/16 KB passed
2P moves, Restart, Home/surface resume and four Back teardowns with repeated
same-process relaunch. Each teardown restored its GL cleanup context and
logs contain no contextless GL call or native crash. A bounded USize64 GUI
app also closed its window before activity destruction and relaunched twice.
The device driver was written in til (~tmp/raylib488_device.til~); all owned
SDK-managed devices were stopped. ARM64 and x64 APK root/time/signing checks
passed both layouts through ~test/reproducible_build.til~. No ARM execution
is claimed. ~make clean && make test~ passed 596/596.

The APK comparison exposed stale Android raylib archives after switching
clang 18 -> 23. ~make.til~ now checks the compiler producer string already
embedded in the ELF archive before reuse, without a new stamp/cache file.
Switching compilers rebuilds; an unchanged compiler remains a cache hit.
Local logs/screenshots are ~tmp/raylib488_*~.

*** Investigation (2026-11-17)

The imported upstream revision is ~f9ea60738547fed4e9a2e16af6c5b83b08475281~,
recorded by subtree import ~c988ff2c2~ and its squashed source tree
~7bef6031f6093abc0d51408c0ac8b75080495efc~. Comparing that complete tree with
the tracked ~vendor/raylib/~ tree identifies exactly two modified files:
~src/platforms/rcore_android.c~ and ~src/shell.html~. The latter is til's
custom browser UI from ~d7ab3d31c~, so restoring pristine vendor sources
also requires preserving that UI in a first-party source location.

The paused-destroy polling fix is already upstream:
[[https://github.com/raysan5/raylib/pull/6040][PR #6040]], commit
~7ee0b08647b9d11185b106614087eb68ef44c65a~ (2026-08-07). It adds the same
break after ~destroyRequested~ that the downstream fix added.

Current upstream master ~476557af33e3d01dbf03690298e3c2cd31cc0fa1~
(2026-11-17, header version ~6.5-dev~) still lacks the EGL cleanup fix.
Verified with an unmodified archive of that revision, the reference NDK
r30 clang, upstream native-app glue, and a minimal C-only NativeActivity
program calling InitWindow, a draw loop and CloseWindow. No til compiler,
runtime or patched raylib source participates in that reproducer.

*** Decision

Vendored libraries are upstream source downloaded and used as distributed.
Do not maintain a til-specific raylib fork, local source edits, or patches
applied to copied sources during the build. A raylib upgrade should not
require rediscovering and reapplying downstream fixes.

The Android lifecycle changes from [[../open/462.org][#462]] were merged as-is for
now. This issue tracks removing that exception through an upstream fix;
it is not an instruction to immediately revert the working demo.

*** Current downstream fixes

~vendor/raylib/src/platforms/rcore_android.c~ has two local fixes:

  - ~PollInputEvents~ now breaks after an Android destroy request. Before
    that change it set ~shouldClose~ and entered another infinite paused
    ~ALooper_pollOnce~ wait. The UI thread waited for native teardown and
    relaunch timed out instead of reopening the activity.
  - EGL configuration now requests window and pbuffer surfaces. On
    ~APP_CMD_DESTROY~, a 1x1 pbuffer keeps the preserved context current
    when the native window surface has already been destroyed. Without
    it, ~CloseWindow~ unloaded GL resources with no current context.

The exact downstream implementation is not a requirement on upstream;
equivalent upstream lifecycle handling is sufficient.
