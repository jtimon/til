** FIXED #420 Missing cross builds of the vendored libraries

*** Post-mortem

Root cause: each vendored library had an archive for the host (and
for windows-x64 at most), and the builder handed that host archive to
every cross linker -- or had no command at all that could build the
target's -- so most cross targets failed at the final link.

What changed, one commit per row, all on #235's libsecp256k1 template
(a make.til data table of per-target archives with bin/make path
goals, a targets.til per-target table keyed on ~target_is_host~, the
builder swapping the link token or reporting the missing archive with
the command that builds it):

- raylib + tinyfd for linux-arm64 / linux-riscv64 cross (~GuiTarget~).
- windows-host ~.dll~ twins for libsecp256k1, raylib and tinyfd, so
  til.exe interprets std/crypto and mode gui programs.
- libsecp256k1 for wasm32 (emcc), and for linux-x64 off a linux-x64
  host (~bin/make --linux-x64-cc=~ / ~LINUX_X64_CC~).
- libffi, configured out of tree, for linux-arm64, riscv64, x86, arm32,
  riscv32 and both mac arches (SDK-less off a mac).
- nng moved to #422 (custom modes declaring their own dependencies).

Bugs fixed on the way: the native-libffi lookups (Makefile and
make.til) would take a cross build directory that sorts first --
build-*, and i686-w64-mingw32, which the Makefile still picked until
the last commit; the interpreter had no riscv64 FFI ABI; the libffi
binding's ffi_cif reserved 4 trailing bytes where arm32 writes 24;
~target_ffi_lib~ named the host-arch mac archive for both mac arches;
a non-gui wasm32 program could not build at all (#424).

Regression tests: every archive is built and run in CI -- test/crypto.til
and test/ffi_prep.til (new, also in the suite on both backends) on
every cross target (qemu for linux, the windows and mac runners, node
for wasm32), the cross-built til's interpreter on arm64, riscv64 and
both macs, til.exe interpreting std/crypto and test/gui_interp.til on
windows. The 32-bit linux gui archives run under qemu+xvfb on
linux-x86; the arm64/riscv64/arm32/riscv32 ones are build-and-file-check
only, as no X11 userspace exists to run them against. Follow-ups found
on the way: #431 (til itself on 32-bit targets), #435, #436, #437.

The vendored libraries do not cover every target. #235 fixed this for
libsecp256k1 (std/crypto); the same gap remains for nng, raylib +
tinyfd and libffi, plus a few libsecp256k1 targets and the windows-host
interpreter twins. Most of these fail only at the final link, with the
host's x64 archive handed to a cross linker.

*** The pattern to reuse (from #235)

libsecp256k1's cross support is the template for every row below:

- ~make.til~: one data table of cross archives (~secp256k1_cross_targets~),
  each built with the target's compiler into its own directory
  (~vendor/<lib>/build-<target>/...~), one bin/make path goal per archive.
- ~src/self/targets.til~: a per-target archive table
  (~target_secp256k1_lib~) and ~target_is_host~.
- ~src/self/builder.til~: keep the canonical archive only when the
  target IS the host; otherwise swap the link() token for the target's
  archive, report a missing archive with its bin/make goal before the
  link, and refuse a target with no archive instead of linking the
  host's.
- CI: build the archive and run a test program for the target under
  qemu / wine / the mac and windows runners.
- Interpreter on a windows host: a ~.dll~ twin beside the canonical
  archive (~build_secp256k1_win_twin~), loaded by ~ffi_load_archive_twin~.

*** Missing builds

Observed on master d9976ce by cross-building examples/sender.til (nng,
~--extra-modes=examples/custom_modes.til~) and examples/hello_gui.til
(raylib + tinyfd); libffi from ~target_ffi_lib~.

| Library | Works today | Missing |
|---------+-------------+---------|
| nng | native host, windows-x64 | linux-arm64, linux-riscv64, linux-x86, linux-arm32, linux-riscv32, windows-x86, macos-x64, macos-arm64 (cross), wasm32 |
| raylib + tinyfd | native host, linux-x86, linux-arm32, linux-riscv32, windows-x64, windows-x86, wasm32, macos (cross via the mac CI archives) | linux-arm64 cross (only a native arm64 host works), linux-riscv64 (no ~target_gui_libs~ entry at all) |
| libffi (runtime ext_func dispatch only) | linux-x64, linux-arm64, linux-riscv64, linux-x86, linux-arm32, linux-riscv32, windows-x64, windows-x86, macos-x64, macos-arm64 | wasm32 |
| libsecp256k1 | every native target; every cross target (linux-x64 included, off a linux-x64 host with ~--linux-x64-cc~); til.exe interpreting | none (no TempleOS or JVM build) |
| windows-host twins (til.exe interpreting) | libsecp256k1, raylib, tinyfd (~.dll~ twins) | nng (moved to #422) |

How each fails today:

- nng, linux cross targets: the builder passes the host's
  ~vendor/nng/libnng.a~ through, and the cross ld rejects it:
  #+begin_example
  .../aarch64-linux-gnu/bin/ld: /home/user/til/vendor/nng/libnng.a: error adding symbols: file in wrong format
  #+end_example
  Same for linux-riscv64 and linux-arm32 (linux-x86 and linux-riscv32
  take the same path).
- nng, windows-x86: the linux archive is dropped by the windows
  rewrite but only a win64 nng exists:
  ~undefined reference to `nng_strerror'~.
- nng, macos cross: the archive token is dropped on the cross host:
  ~ld64.lld: error: undefined symbol: nng_close~.
- raylib, linux-arm64 / linux-riscv64 cross: the host's
  ~vendor/raylib/src/libraylib.a~ reaches the cross ld:
  ~error adding symbols: file in wrong format~.
- libffi: already reported before the link by compile_c (the generated
  C calls ~ffi_prep_cif~ and the target's archive does not exist), with
  ~target_ffi_build_hint~'s command -- but for the targets listed there
  is no command that builds one.
- libsecp256k1: refused before the link with
  ~std/crypto (libsecp256k1) has no cross build for this --target from this host~.
- windows-host twins: ~ffi_load_archive_twin~ panics naming the missing
  ~.dll~.

*** Plan

  - [-] nng: moved to #422. nng belongs to the user-defined custom
    server modes (~--extra-modes~), not a built-in mode, so per-target
    tables inside the compiler are the wrong fix; #422 is about letting a
    mode declare its supported targets and per-target dependencies.
  - [X] raylib + tinyfd: ~arm64~ and ~riscv64~ entries in make.til's
    ~GuiTarget~ table (distro cross gcc + the vendored X11 headers, like
    arm32), with path goals ~vendor/raylib/src/libraylib-{arm64,riscv64}.a~
    and ~vendor/tinyfiledialogs/libtinyfd-{arm64,riscv64}.a~.
    ~target_gui_libs~ keeps the canonical archives for a native
    arm64/riscv64 host (~target_is_host~) and names the cross ones
    otherwise (riscv64 had no entry at all), and the builder now drops the
    host's archive tokens for these two cross targets as it does for the
    32-bit ones. examples/hello_gui.til cross-links for both here; CI
    builds it in the linux-arm64 and linux-riscv64 jobs (build + file
    check, like arm32).
  - [X] libffi for the linux cross targets: make.til's
    ~libffi_cross_targets~ configures each OUT of tree, one
    ~vendor/libffi/build-linux-<name>~ per target (path goals
    ~vendor/libffi/build-linux-<name>/.libs/libffi.a~ for arm64,
    riscv64, x86, arm32 and riscv32 with ~--riscv32-cc~), so the path is
    fixed and the in-tree native build is untouched; ~target_ffi_lib~
    names them (a native arm64 host keeps the bootstrap's stable copy).
    Both native-libffi lookups (the Makefile's ~LIBFFI_LIBDIR~ wildcard
    and make.til's ~libffi_native_dir~) took the alphabetically first
    ~vendor/libffi/*/.libs~, which these directories would have become;
    both skip ~build-*~ now. Two bugs surfaced on the way: the
    interpreter's ~ffi_host_default_abi~ had no riscv64 entry (til
    cross-built for riscv64 panicked on its first ext_func; riscv's
    FFI_SYSV is 1), and the libffi binding's ~ffi_cif~ reserved 4
    trailing bytes for ~FFI_EXTRA_CIF_FIELDS~ where arm32's are 24
    (every ~ffi_prep_cif~ smashed the stack; now six U32 slots).
    test/ffi_prep.til (new, both backends in the suite) calls
    ~ffi_prep_cif~ with the running arch's default ABI; each linux
    cross CI job runs it under qemu, and the arm64 and riscv64 jobs also
    cross-build til and run its interpreter (hello_script,
    test/ext_libc.til) under qemu. til itself does not build for the
    32-bit targets (the interpreter casts U64 to UPtr), so those get
    test/ffi_prep.til only.
  - [X] libffi for macos from a non-mac host: two more
    ~libffi_cross_targets~ entries, ~build-macos-arm64~ and
    ~build-macos-x64~, configured with clang at til's mac deployment
    targets against the vendored SDK-less headers, with lld and the
    vendored libSystem.tbd for configure's probe links and llvm-ar /
    llvm-ranlib for the Mach-O archive (on a mac the real SDK, for the
    other arch). ~target_ffi_lib~ keeps ~libffi-macos.a~ only when the
    mac target IS the host -- it used to name it for both mac arches,
    the wrong arch for the other one -- and the cross archive otherwise.
    test/ffi_prep.til and til itself cross-link for both arches; the
    macos-cross-build CI job builds them, and the two cross-run jobs run
    ffi_prep and the cross-built til's interpreter (hello_script,
    test/ext_libc.til) on real macs.
  - [X] libsecp256k1 for wasm32: a ~build-wasm32~ entry in make.til's
    ~secp256k1_cross_targets~, configured through the vendored emsdk's
    Emscripten.cmake toolchain (path goal
    ~vendor/secp256k1/build-wasm32/lib/libsecp256k1.a~), and
    ~target_secp256k1_lib~'s wasm32 entry. The builder used to drop EVERY
    link() token for a wasm gui build; it now keeps libsecp256k1's, so a
    ~mode gui~ program importing std/crypto links for wasm32 with
    ~--cc=emcc~. test/crypto.til, translated for wasm32 and compiled with
    emcc against the archive, passes all vectors under node. Non-gui
    wasm32 programs link too since #424 (single-file ~.js~ run with
    node).
  - [X] libsecp256k1 for linux-x64 from a non-linux-x64 host: a
    ~build-linux-x64~ entry in ~secp256k1_cross_targets~ (path goal
    ~vendor/secp256k1/build-linux-x64/lib/libsecp256k1.a~) and
    ~target_secp256k1_lib~'s linux-x64 entry, which the builder consults
    only off a linux-x64 host. Its compiler is the new
    ~bin/make --linux-x64-cc=~ / ~LINUX_X64_CC~, defaulting to the
    distro cross gcc ~x86_64-linux-gnu-gcc~ (an arm64 linux host); the
    mac-host CI job passes messense's ~x86_64-unknown-linux-gnu-gcc~,
    builds test/crypto.til for linux-x64 and runs it on the linux
    runner. Locally the archive (default compiler, and both overrides)
    builds, and test/crypto.til linked against it passes 4/4.
  - [X] windows-host DLL twins for raylib and tinyfd: ~build_win_host~
    now also builds ~vendor/raylib/src/libraylib.dll~ and
    ~vendor/tinyfiledialogs/libtinyfd.dll~ from the win64 archives (one
    ~build_win_twin~ helper, shared with ~libsecp256k1.dll~, links each
    with the windows system libraries it calls; both import only system
    DLLs). ~til.exe interpret test/gui_interp.til~ passes under wine, with
    or without an X server, and panics naming the DLL when it is removed;
    CI's windows-host job runs it on the windows runner. nng's twin moves
    with nng to #422.
  - [X] CI: one build-and-run step per new archive, in the existing
    cross jobs. wasm32's libsecp256k1 is covered by the ~wasm32~ job
    (#424), which builds and runs test/crypto.til under node. The audit
    found the mingw libffi archives the only ones nothing ran directly
    (the win32 one not at all): windows-x64-build now builds
    test/ffi_prep.til for windows-x64 and windows-x86 and windows-x64-run
    runs both (x64 passes under wine here; this container has no 32-bit
    wine). Building the win32 libffi showed the Makefile's native-libffi
    lookup taking ~i686-w64-mingw32~ (it sorts before
    ~x86_64-pc-linux-gnu~), so the next bootstrap would link it; it now
    skips the mingw triples, as make.til's ~libffi_native_dir~ did.
