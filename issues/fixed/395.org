** FIXED #395 tutorial_file_doctests escapes its runner: 434/435 every run

*** Post-mortem

Root cause: the codebase already HAS a way to put a shell chain in a
registered command, and this one site did not use it. ~run_all_parallel~
splices a registered command into ~<cmd> > <outfile> 2>&1~ and hands the
result to a shell, so an ~&&~ written bare is the OUTER shell's operator: it
splits the chain before ~test_runner~ starts, leaving it wrapping only the
first command while the redirect lands on the last. Every other chained test
quotes the token -- ~'&&'~ -- so it survives as an argument and takes effect
inside ~test_runner~'s own shell, and ~self_translate~'s comment says exactly
that three lines above where it does it. The tutorial block, written later,
built its chain with bare ~&&~ and so ran outside the runner entirely.

Fix, in two parts.

The tutorial doctests now register ONE ~add_single~ per command -- interpret
and run, per file -- instead of one chain. That is the direction this issue
preferred over quoting, and the reason holds up: each doctest gets its own
result row, its own timing, and its own captured output when it fails. The
compiled rows pass explicit ~-o bin/c/<label> -c gen/c/<label>.c~ like
~add_cli_pair~ does, because these rows run in PARALLEL now and the default
artifact paths are keyed by source basename -- shared ground. Labels carry a
~tutorial_~ prefix: the label keys the result file, and ~namespaces~ alone
would collide with test/namespaces.til.

And the silence that let it last: a result file with no ~RESULT ~ line is now
a hard failure. ~test_runner~ prints that line on every path it takes, so its
absence means the runner never ran -- there is no benign reading. Before, the
missing line parsed as ~ok=0~ and the test simply stopped being counted,
which is why the only symptom was a "Passed: N-1/N" printed directly above
the words "all tests passed".

Verified both directions. With the fix the suite reports 459/459 -- the
twelve new rows replacing the one chained row, and, more to the point, no
legitimate test trips the new guard. To check it fires at all, a temporary
~add_single(tests, "guard_probe_395", "docs", 0, "", "true && true")~ was
registered and the suite run: it printed
~FAIL: guard_probe_395 produced no RESULT line~ and exited non-zero, with
"all tests passed" gone. That probe was removed; the guard is the regression
test, and it would have caught the original the day the tutorial chain was
added.

*** Follow-up: the two checks the fix above left out

Both come straight from this issue's own text and landed after it.

~one_command_only~ is "that assumption is worth making explicit or
enforcing", enforced: ~add_single~, ~add_count~ and ~add_counts~ refuse a
suffix containing a bare ~ && ~ and name the row. The missing-RESULT failure
catches the same mistake, but from the symptom and only once the suite has
run; this catches it at the call site, before anything is spawned. The
quoted ~'&&'~ form is not matched by the needle and stays legal -- it is how
~self_translate~ and the gui build rows chain, correctly.

And the count itself -- "after a run, ~total_passed == total_tests~" -- is
now asserted in the summary rather than printed and ignored. That line is
the one that reads as the original symptom: 434/435 sitting directly above
"all tests passed", for as long as the chained row existed.

Verified against deliberate breakage: a chained
~add_single(tests, "tmp395_chain_probe", "docs", 0, "", "true && true")~
panics at registration before a single row is spawned, and a row wired to a
command that writes no RESULT gives both failures at once --
~... wrote no RESULT line~ and
~FAIL: 444/445 -- a registered test was counted but never passed~ -- exit 1,
with "all tests passed" gone.

Every ~make test~ prints

    Passed:       434/435

    all tests passed

The missing one is ~tutorial_file_doctests~, and it is missing every run, not
intermittently. ~gen/out/results/tutorial_file_doctests.txt~ is 0 bytes, so
~run_all_parallel~'s ~rfind("RESULT ")~ finds nothing, ~t.ok~ parses as 0, and
the test counts toward ~total_tests~ but never toward ~total_passed~.
~fail~ stays 0, so the suite still says "all tests passed".

*** Root cause: the redirect binds to the wrong command

~add_single~ builds

    bin/test_runner single <label> <exit> -- <cmd_suffix>

and ~run_all_parallel~ appends ~" > ", t.outfile, " 2>&1"~ to that whole
string. For every other test ~cmd_suffix~ is ONE command, so the redirect
lands on ~bin/test_runner~. ~tutorial_file_doctests~ is the only test whose
suffix is a shell ~&&~ chain (src/tests.til builds one interpret + one run
per doctest file, six files today), so the spawned shell sees

    bin/test_runner single tutorial_file_doctests 0 -- bin/til interpret 'A'
      && bin/til run 'A' && ... && bin/til run 'F' > <outfile> 2>&1

The chain is split before ~test_runner~ ever starts. Two consequences:

- ~test_runner~ wraps only the FIRST doctest command. The other eleven run as
  ordinary top-level commands -- untimed, unmeasured, and outside the
  expected-exit check.
- ~> outfile 2>&1~ binds to the LAST command only. The runner's ~RESULT~ line
  goes to the SUITE's stdout instead of the result file, and the file gets
  whatever the last ~bin/til run~ printed, which is nothing.

The leak is visible in the suite log: the ~RESULT ms=... ok=1~ line lands
jammed onto the ~test/forward_refs.til~ row, followed by that doctest's own
~pass: test_safe_division~ / ~1/1 tests passed~.

*** What is and is not at risk

Nothing passes silently: ~&&~ still short-circuits, so a failing doctest
gives the spawned command a non-zero status, ~run_all_parallel~ sees
~status != 0~ and sets ~fail~. What is lost is the captured-output relay --
the block ~print_captured_err~ writes, which the comment on that same
~status != 0~ branch exists to guarantee ("a CI-only failure does not survive
that filter"). For this one test a failure would report an exit code with no
second line, which is exactly the twenty-red-runs problem that comment
describes. The pass count and the per-test timing are wrong too.

*** Fix direction

Either make the redirect cover the whole suffix (wrap it, so the shell binds
the redirect to the group rather than the last command) or -- probably better
-- register one ~add_single~ per tutorial doctest file instead of one ~&&~
chain, which also gives each file its own timing, its own result row and its
own captured output. Whichever way, the general hazard is that ~add_single~
silently assumes its ~cmd_suffix~ is a single command; that assumption is
worth making explicit or enforcing.

*** Regression test

The count itself: after a run, ~total_passed == total_tests~. Any test whose
result file has no ~RESULT~ line should be a hard failure rather than a
quietly uncounted pass -- that check would have caught this the day the
tutorial chain was added.
