# post-mortem: The for-in annotation slot predates the two-binding forms.
# When for-in had one binding its type was mandatory and the parser read
# `: Type` after that name only. The map form (#287) and the indexed form
# then gave the slot to the key/index, so the second binding could not be
# annotated: an indexed loop over Vec(Dynamic) was unwritable and the map
# form silently ignored even the key annotation. Preparation commit:
# ForInData.til_type2, parsed after the second name, used by the indexed
# and map lowerings, the comptime scope and the initer's priv rename and
# generic substitution. This commit restores the mandatory value type as
# ONE rule shared by the collection and map lowerings (it absorbs the old
# Dynamic-only "cannot infer element type" error): "for-in value 'x' needs
# a type annotation: 'x : T'", T spelled as the source writes it
# (source_type_spelling: Set(Str), not Set__Str; a priv type's own name).
# The index stays implicitly USize and a map key may stay bare; `_` binds
# nothing and is exempt. Annotating ~580 loops the rule flagged exposed a
# latent bug: in a generic body `for x : T` with T substituted by a
# primitive read as unannotated (expr_type_name_ref has no primitive arm),
# so the annotation was silently replaced by inference; the lowering now
# reads annotations with type_to_name_ref. Regression tests:
# test_for_index_value_typed (test/loops.til), test_hashmap_for_in_kv_typed
# (test/hashmaps.til), the terr514_* fixtures in test/typer_errors.til.
# category: features
** FIXED #514 for-in: require the value type; allow it on the second binding

  ~for x : T in v~ can annotate its element, but the two-binding forms
  cannot annotate their second binding: ~for i, x : T in v~ and
  ~for k, v : V in m~ fail to parse ("expected 'in', found ':'"). The
  annotation was mandatory when for-in had a single binding, and the
  index/key binding added later took over the only slot. Consequences:

  - an indexed loop over Vec(Dynamic) cannot be written, because the
    element type cannot be inferred from get() and cannot be declared
    either (two ~0..items.len()~ loops in src/self/codegen/c_codegen.til
    stay index loops for that reason);
  - ~for k : K, v in m~ parses but the typer ignores the ~K~.

  Accept ~for [mut] a [: A], [mut] b [: B] in xs~, using ~B~ as the
  element/value type and ~A~ as the index/key type.

  Then make the VALUE annotation mandatory for every collection and map
  for-in, the way it was before the two-binding forms existed: the
  index of a vec-like loop is implicitly USize and the map key stays
  optional, but the element/value binding must say its type. Range
  loops (~for i in a..b~) are not collection loops and are unaffected.
  The rule unifies with the existing "cannot infer element type, use
  explicit type" error, which today fires only for a Dynamic get().

  Staged (doc/self.org, preparation + use): the compiler sources cannot
  spell ~for i, x : T in v~ until the parser change is in boot/.

*** Progress
