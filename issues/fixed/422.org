** FIXED #422 Modes with C (and other) dependencies: declaring and building them per target

*** Post-mortem

Root cause: a ~link()~ path named ONE archive, the host's, so everything
per-target lived in the compiler as library-specific tables (the nng
swap, ~target_secp256k1_lib~, ~target_ffi_lib~, ~target_gui_libs~) that a
mode outside this repo could neither extend nor satisfy; a cross build of
such a mode failed at the final link.

What changed, across the series: ~Mode.targets~ (refuse unsupported
targets before compiling), ~link(path, "<targets>")~ (each target names
its own archive), ~Mode.build_hint~ and the missing-archive report
(~bin/make <path>~ for til's own vendored libraries), and every vendored
library moved onto it -- nng, libsecp256k1, libffi (staged) and, last,
raylib + tinyfd for mode gui. Each builds per target into
~vendor/<lib>/build-<target>~ from a make.til table, the host's included,
and the compiler's library tables are gone. The last step added
~link_macos("<Frameworks>")~ for what ~link()~ cannot spell: macOS
frameworks, linked as ~-framework~ on a mac host and as the generated
~.tbd~ stubs off one. src/til.til stopped linking raylib and tinyfd
altogether: the compiler calls neither (the interpreter loads their
twins), so the archives contributed nothing. The emscripten settings of
a wasm32 gui build stay in the builder (#437).

Regression tests: test/mode_loading.til (target refusal, per-target
links, the report and hint, a misspelled target, the wasm32 gui link),
test/link_macos.til (frameworks only on mac targets, -framework on a mac,
stubs or their report elsewhere, an empty list refused),
test/nng_pair.til, test/ffi_prep.til, test/install.til, plus the CI
cross jobs that build and run each target's archives.

Brainstorm, not a plan yet. Split out of #420: nng is a dependency of
the custom server modes in ~examples/custom_modes.til~ -- a user-defined
mode loaded with ~--extra-modes~, not a built-in one -- so cross-building
it the way #235 did for libsecp256k1 (tables inside the compiler) is the
wrong shape. A mode author outside this repo can neither edit those
tables nor ship the per-target archives the compiler would expect.

*** What exists today

- A mode is ~Mode(needs_main, decls_only, auto_import, is_library,
  is_pure, run_tests, debug_prints)~ (src/std/mode_type.til); its support
  file (~auto_import~) is ordinary til that may call ~link("<archive>")~,
  ~link("-lfoo")~ and ~link_c("<file.c>")~.
- A link() path names ONE archive, the host's. Everything per-target is
  knowledge baked into the compiler for specific libraries: the windows
  nng swap and libsecp256k1 table in src/self/builder.til,
  ~target_gui_libs~ / ~target_ffi_lib~ / ~target_secp256k1_lib~ in
  src/self/targets.til. Building the archives is make.til's job, per
  library (~build_nng_win~, ~secp256k1_cross_targets~, ~gui_targets~).
- The interpreter loads a twin beside each linked archive (~.so~, or
  ~.dll~ on a windows host), also built by make.til.

So a mode can declare a dependency only for the host, cannot say which
targets it supports, and cannot say how to obtain the dependency for a
target. A cross build of such a program fails at the final link with the
host archive in the wrong format, or with undefined symbols (#420 has
the observed errors for nng).

*** Questions

- Should a mode declare the targets it supports (allow-list), or the
  ones it does not (deny-list)? Either way the compiler can refuse an
  unsupported ~--target~ before compiling anything, naming the mode.
- How does a mode name the per-target artifact? Options: a target-keyed
  link (~link("...", target = "linux-arm64")~), a placeholder expanded by
  the compiler (~link("vendor/nng/build-{target}/libnng.a")~), or a
  function in the support file evaluated at compile time with the target
  as an argument (the constfolder already runs til at build time).
- Who BUILDS the artifact, and when? Keep it out of the compiler (the
  mode ships a build program, like make.til, and the compiler only
  reports "missing: <path>, build it with <command>"), or let the mode
  declare a build recipe the compiler runs on demand (a step in
  ~til build~, with its toolchain requirements checked up front)?
- Where do built artifacts live: beside the mode's sources, in a
  per-user cache keyed by target (and by til revision?), or in the
  program's tree? What does an installed til (~make install~) look in?
- Interpreter twins: the same declaration should say how to get the
  loadable form per HOST (~.so~ / ~.dll~ / ~.dylib~), or that the mode
  cannot be interpreted.
- Non-C dependencies: other til modules (already ~import~), external
  tools (cmake, emsdk, a cross gcc), system packages (pkg-config names),
  data files. Which belong in the declaration and which in the build
  recipe?
- Provenance: vendored source plus a recorded version and hash (what
  #235 did by hand), or fetched at build time? Fetching makes builds
  depend on the network; vendoring makes the mode heavy.
- Should the built-in vendored libraries (raylib/tinyfd for ~mode gui~,
  libsecp256k1 for std/crypto, libffi) move onto the same mechanism, so
  the compiler loses its library-specific tables? That is the test that
  the design is general enough.

*** Constraints from the rest of the repo

- New file formats, caches, manifests or CLI flags need explicit
  approval (CLAUDE.md); a design here should prefer plain til in the
  mode's support file over a new manifest format.
- Failure must be loud and early: a refused target or a missing artifact
  is reported before the C compile, with the command that fixes it (the
  shape #235 used for libsecp256k1).
- Cross-builds are verified in CI by RUNNING the result (qemu, wine, the
  windows and mac runners); a mechanism should make that easy for a mode
  author too.

*** Decisions (2026-10-27)

- ~Mode~ gets ~targets~: a space-separated list of ~--target~ names;
  empty (the default) means every target. Any other ~--target~ is
  refused before compiling, naming the mode.
- ~link()~ gets an optional second argument listing the targets it
  applies to; each target names its own archive on its own line. No
  placeholder in the path, and no manifest format: the declaration
  stays plain til in the mode's support file. (A compile-time switch
  around ~link()~ was considered: ~host_os()~ at compile time is the
  compiler's host, not the target, and the loader reads ~link()~ before
  any evaluation, so that would be a much larger change.)
- ~Mode~ gets ~build_hint~: the command printed with a missing
  target-restricted archive, ~{path}~ replaced by the path as written.
- Building stays outside the compiler (make.til in this repo).
- nng first, then the built-ins (libsecp256k1, raylib + tinyfd, libffi)
  move onto the same mechanism, staying built-in and installed: their
  per-target directories renamed to target names and each host's native
  archive built under ~build-<host target>~ too.

*** Progress

- [X] Mechanism + nng: ~Mode.targets~ / ~Mode.build_hint~
  (src/std/mode_type.til, parsed in src/self/loader.til), ~link(path,
  "<targets>")~ (loader's ~TargetLink~, resolved by
  ~link_flags_for_target~ / ~include_flags_for_target~ once ~lp.target~
  is known), the refusal in src/til.til, the missing-archive report in
  src/self/builder.til (~report_missing_target_archives~). nng builds
  per target into ~vendor/nng/build-<target>~ from make.til's
  ~NngTarget~ table (every linux target, both windows, both macs
  SDK-less off a mac; not wasm32), the host's included, so the old
  ~vendor/nng/libnng.a~ and the builder's windows nng swap are gone; the
  server modes and src/til.til list per-target links and the winsock
  libraries. Tests: test/mode_loading.til (refusal, per-target links,
  the report with the hint, a misspelled target), test/nng_pair.til (a
  one-process inproc:// round trip) on both backends in the suite and,
  cross-built, under qemu / wine / the windows and mac runners in CI.
  Not done: an nng ~.dll~ twin for til.exe interpreting server-mode
  programs on a windows host -- nng on msvcrt needs ~timespec_get~, which
  only ext.c's shim inside til.exe provides, and a DLL must resolve it
  at link time.
- [X] libsecp256k1 onto the mechanism: std/crypto lists one
  ~link("vendor/secp256k1/build-<target>/lib/libsecp256k1.a", "<target>")~
  per target (every linux target, both windows, both macs, wasm32), and
  make.til's ~SecpTarget~ table builds every one of them, the host's
  included (natively, position-independent for the interpreter's twin),
  so the plain-path ~vendor/secp256k1/libsecp256k1.a~ is gone and
  ~build-win64~ / ~build-win32~ are now ~build-windows-x64~ /
  ~build-windows-x86~. Deleted: targets.til's ~target_secp256k1_lib~ and
  ~target_secp256k1_build_hint~ and the builder's libsecp256k1 swap. The
  windows-host twin is ~build-windows-x64/lib/libsecp256k1.dll~, and an
  installed til carries ~build-<host>/lib~. The missing-archive report
  names ~bin/make <path>~ for a built-in library's archive (std/crypto
  is an import, so no mode build_hint applies). On jvm and templeos-x86,
  which have no archive, std/crypto now fails on the backends' own
  errors (the JVM names the unsupported secp256k1 calls) instead of the
  builder's refusal.
- [X] raylib + tinyfd (mode gui) onto the mechanism: src/modes/gui.til
  lists one raylib and one tinyfd ~link()~ per target (raylib only for
  wasm32), the windows system libraries for the windows targets, the
  linux ones for linux, and ~link_macos("OpenGL Cocoa IOKit CoreAudio
  CoreVideo")~. make.til's ~GuiTarget~ table builds every target's pair
  into ~vendor/{raylib,tinyfiledialogs}/build-<target>~ (the host's
  natively, the macs SDK-less off a mac, wasm32's raylib with emcc);
  the interpreter twins sit beside the host's, the windows-host DLLs
  beside the windows-x64 ones (CI no longer copies archives into
  place), and an installed til carries the host's. Gone: targets.til's
  ~target_gui_libs~ and ~target_is_host~ and the builder's raylib/tinyfd
  dropping, wasm32 link filter and per-target gui link tail.
- [X] libffi onto the mechanism. Staged (doc/self.org, "Staged
  migration across master merges"): the bootstrap's til_boot runs the
  OLD builder, which hard-requires libffi at its old native path when
  the generated C calls libffi (src/til.til always does), so moving the
  native archive under ~build-<host target>~ in one commit breaks pass 1.
  - [X] Transitional: the builder skips its ~target_ffi_lib~ table when
    a link() line already names a libffi archive (no line does yet).
  - [X] Migration: the Makefile builds the native libffi out of tree

    TilVm hosts) and test/ffi_prep.til carry per-target link() lines,
    and an interpreted program that links libffi loads a ~.so~ twin

    transitional rule included), the in-tree triple builds, the
    stable-path copies and ~libffi_native_dir~. An installed til
