** FIXED #183 Adding ~///~ comments to core lib files forces full rebuild+test

  POST-MORTEM:

  The report described the old REPL-help architecture: core ~///~ text was
  carried into the compiler's runtime documentation data, so changing prose
  changed the bootstrap artifact. Issue [[file:233.org][#233]] superseded that
  architecture. Core help data now comes from the generated
  ~doc/gen/*.org~ files and is loaded on demand; the documentation text is no
  longer embedded in ~boot/til.c~.

  Reproduction against current master confirmed the separation. Changing text
  within an existing ~///~ line and rebuilding changed no generated compiler
  code (the only ~boot/til.c~ difference was the independently embedded
  version). Splitting the same comment over one additional physical line
  changed only four source-location literals, plus the version. Those literals
  are the expected ~__LOC__~ line-number floor: inserting any source line must
  keep diagnostics aligned with the source. They are not documentation data
  and do not justify the stripping or separate-cache designs proposed below.

  Verification: ~make~ and ~make doc~ both completed successfully for the
  reproductions; searches of ~boot/~ found none of the tested documentation
  text.

Every ~///~ doc comment in a core library file (e.g. [[file:../../src/core/vec.til][src/core/vec.til]])
  gets embedded into ~boot/til.c~ during bootstrap, so the binary
  changes and a full ~make clean && make test~ cycle is required. For
  documentation-only changes this is unsustainable -- documenting a
  single function takes minutes of test suite time.

  Options:
  - Strip ~///~ comments during boot embed so they don't change the
    boot C output (doc registry is built at runtime from source, not
    from boot). Boot only needs the code, not the comments.
  - Cache the doc blob separately from the boot binary so doc-only
    changes don't invalidate the boot snapshot.
  - Add a ~make fast-test~ target that skips the full rebuild and only
    runs regression tests (the full suite is ~80% build tests that
    recompile examples irrelevant to a doc change).
  - In the merging procedure (~doc/bots/merging_from_remote.org~), skip
    the ~make test~ step when the only non-boot source change is
    ~///~ comments in core libs (risky: still need to ensure the
    parser embed didn't break).
