* Pipeline

This is the current high-level pipeline implemented in
[[file:../src/til.til][src/til.til]].
It is intentionally short and code-oriented.

* Orchestration and shared state

Two modules sit underneath every phase below:

- Load:
  - `prepare_program(...)` and friends
  - Implemented in til: [[file:../src/self/loader.til][src/self/loader.til]]
  - Drives the whole pipeline: discovers and reads source files by walking
    `import(...)` calls directly in each AST, picks the mode, then runs
    tokenize -> parse -> init -> type -> asap -> constfolder -> scavenge
    in order on the canonical per-file ASTs in `Context.imported` before
    handing the surviving units to a back end. The CLI
    (`src/til.til`) and the REPL both go through here.

- Context:
  - `Context`, `TypeScope`, `TypeBinding`, ...
  - Implemented in til: [[file:../src/self/context.til][src/self/context.til]]
  - The shared state threaded through the phases: imported units and their
    path-resolution roots, the active mode, the type scope and its name/type
    bindings, and the FFI map. Every phase reads and mutates the same `Context`.

1. Tokenize

- `tokenize(source, path)`
- Implemented in til: [[file:../src/self/lexer.til][src/self/lexer.til]]
- Turns source text into a stream of tokens.

2. Parse

- `parse(tokens, path, mode_out)`
- Implemented in til: [[file:../src/self/parser.til][src/self/parser.til]]
- The CLI loads:
  - `src/core/core.til`
  - user source
  - recursive `import(...)` files
  - optional mode auto-import file from `src/modes/*.til`
- Result: one `ImportUnit` AST per loaded file in `Context.imported`, plus
  `ProgramUnit` path/mode ordering metadata in `LoadedProgram`. Explicit
  dependency edges remain only as AST calls; the sole non-AST edge is a mode
  auto-import recorded on its owning `ImportUnit`.

3. Init declarations

- `init_seed_tree(...)`, then recursive `init_file(...)`
- Implemented in til: [[file:../src/self/initer.til][src/self/initer.til]]
- Responsibilities:
  - seed and register types, funcs, globals, aliases across the import graph
  - build initial `TypeScope`
  - recurse through explicit AST import calls and mode auto-import edges
  - prepare enough metadata for typing

4. Type check + desugar

- `type_file(path, context)`
- Implemented in til:
  [[file:../src/self/typer.til][src/self/typer.til]] (type errors + type
  inference) and
  [[file:../src/self/desugarer.til][src/self/desugarer.til]] (AST lowering /
  desugaring).
- The typer runs four coordinated graph-wide sweeps over the reachable
  `ImportUnit`s. The method-preparation sweep normalizes enum payload aliases
  and generates enum/interface methods needed by field defaults. The field
  sweep infers unannotated struct fields; ordinary generated method names
  expose only their fixed return signature on this disposable inference clone.
  The declaration sweep computes struct/enum layouts and generates struct
  clone/delete/hash/eq/cmp/to_str plus size/cmp/unity-derived methods. Only
  after those sweeps finish does the body sweep strictly resolve names and
  types, infer expression types, and reject invalid programs.
- The body sweep drives type-directed desugaring: interleaved with inference,
  the desugarer rewrites high-level constructs later phases do not handle into
  plain til. The desugars read inferred types, which is why they run
  interleaved rather than as a separate up-front pass.
- Typer responsibilities (src/self/typer.til):
  - resolve names and types
  - infer expression types
  - reject invalid programs (type errors)
- Desugarer responsibilities (src/self/desugarer.til), interleaved with typing
  and driven by the typer's walk:
  - lambda lifting (anonymous `func` literals -> top-level priv decls)
  - optional / named / default + variadic / kwargs args -> positional args
  - collection literals (array / vec / set / map) -> `new` + push/set/add
  - for-in loops -> while
  - switch / match -> if/elif chains (carrying the exhaustiveness and
    unreachable-case diagnostics computed during the lowering walk)
  - throw / catch / `?` / `!` -> plain til (mut `_err_kind` locals + if-guards)
    so downstream stages need no new node kinds; see
    [[file:./throws.org][doc/throws.org]] for the surface and recipes
  - argument hoisting into temps for the back ends
- Like the garbager (step 5), desugarer.til imports only `context`; it reaches
  typer helpers, and the typer reaches the desugar passes, through the shared
  program scope rather than an explicit import.

5. Asap destruction

- `insert_free_calls(body, scope, owns_scope)` (per body)
- Implemented in til: [[file:../src/self/garbager.til][src/self/garbager.til]]
- Responsibilities:
  - per-binding live-range analysis (~collect_scope_locals~,
    ~extend_ref_local_lifetimes~)
  - diagnose use-after-ownership-transfer
  - promote Decl ownership to Own where needed
  - insert ~Type.delete()~ / ~free()~ at the last use of every
    local, before reassignments, and on every early-exit edge
    (return / break / continue)
- After asap insertion, every owned local has an explicit cleanup
  call on every path that leaves its scope.
- The asap code now lives in its own ~mode lib~ module
  (src/self/garbager.til) and the program-body asap runs as its own
  phase, ~garbager_destroy(ctx)~, at the tail of
  ~init_and_type_program~ (see [[file:../issues/fixed/204.org][#204]]).
  The remaining per-body (function/if/while/block/catch) garbager
  calls are still invoked inline from the typer's scope-management
  sites because per-body scopes are stack-locals freed when
  ~infer_body~ returns; lifting them into the single
  ~garbager_destroy~ walk needs the per-body scope cache on ~Context~
  and is tracked under [[file:../issues/open/158.org][#158]].

6. Constfolder

- `constfolder(ast)`
- Implemented in til: [[file:../src/self/constfolder.til][src/self/constfolder.til]]
- Responsibilities:
  - fold macros
  - fold comptime-known pure calls recursively when possible
  - track known literal values
- After constfolder, macros should be gone from the AST.

7. Scavenge

- `scavenge_imported(lp)`
- Implemented in til: [[file:../src/self/scavenger.til][src/self/scavenger.til]]
- Removes declarations unreachable from the mode's roots, defined
  centrally per mode in ~scavenge_visited_imported~ (#326). Libraries
  are scavenged like every other mode, with their exported ABI as
  roots. The whole phase -- root policy, reachability BFS, sweep and
  body DCE -- lives in scavenger.til; the loader only calls
  ~scavenge_imported~ in phase order, like every other phase.
- BACKEND-AGNOSTIC, deliberately: it answers "is this declaration
  used" once, for whoever consumes the AST afterwards, and never asks
  which back end is coming. A reference made by RUNTIME NAME counts as
  a real edge -- ~get_elem_size~ builds ~T.size()~ from a name it only
  learns at runtime, so ~*.size~ is an unconditional root rather than
  something the interpreter opts into. See the back end below for the
  question this pass does NOT answer.
- Skipped where the open-world premise breaks static reachability:
  REPL sessions (the next turn can name anything;
  ~repl_finish_prepare_program~) and typed-AST-only paths like
  ~til doc~.

8. Back end

There are two main back ends.

- Interpret:
  - `interpret(ast, ...)`
  - [[file:../src/self/interpreter.til][src/self/interpreter.til]]
  - For calls into native C libraries the interpreter routes through
    its own FFI dispatcher, in the same
    [[file:../src/self/interpreter.til][src/self/interpreter.til]]
    (libffi-backed `ext_func`/`ext_proc` calls).

- Build:
  - [[file:../src/self/builder.til][src/self/builder.til]] owns output paths,
    toolchain invocation, install/run/test commands, and documentation.
  - [[file:../src/self/c_codegen.til][src/self/c_codegen.til]] owns the C ABI,
    C/header emission, C library bindings, and C-only emit reachability.
  - `c_codegen_translate_outputs(...)` is the boundary between them.
  - runs its own emit-reachability pass first
    (~builder_fill_emit_inventory~, #326). This is NOT a second
    scavenge: it answers a question only a C emitter can ask, because
    only the C emitter knows what it splices. `Color.Red` becomes a
    compound literal, `T.size()` was folded to a literal, a POD
    `p.clone()` becomes a struct copy -- each is a live reference the
    scavenger correctly kept, and none of them leaves a CALL in the C,
    so the out-of-line function must not be emitted. The pass builds
    the call-site inventory, iterates it to a fixpoint (a site inside a
    body that is itself omitted is not a call), and the emitters gate
    on the result.
  - a future back end needing the same cleanup writes its own version:
    the splicing rules are C's, not the language's. Only the
    reachability half above is shared.
  - the pass runs from `build`, after
    `build_register_func_symbols_lp`, not from `scavenge_imported` --
    its lowering queries read the C-symbol aliases that registration
    installs, and answering them earlier gives a different (wrong)
    result.
  - then `compile_c(...)` / `compile_lib(...)` compiles the emitted C
  - target/platform selection (the `Target` and `Lang` enums) lives in
    [[file:../src/self/targets.til][src/self/targets.til]]

9. Runtime/ext layer

- A small set of primitives is still implemented in handwritten C and linked
  into the self-hosted pipeline:
  - [[file:../src/c/ext.c][src/c/ext.c]]
- Til sees these through `ext_func` / `ext_proc` declarations imported through
  `modes.til`, and handwritten C sees til declarations through generated
  `boot/til_forward.h`.

* Bindings generator (separate tool)

- `generate_bindings(in_path, out_path)`
- Implemented in til: [[file:../src/self/binder.til][src/self/binder.til]]
- Not part of the translate/interpret pipeline above. Driven from
  `bin/til bindings <header> -o <out>`: reads one C header and emits a
  `mode lib` til file mirroring its typedefs, enums, function
  declarations and numeric `#define`s, so til can `import` the vendor
  binding files under `vendor/bindings/`.

* Notes

- Loader orchestrates the phases; Context carries the shared state.
- Lexer turns source into tokens.
- Parser builds the AST.
- Initer registers and synthesizes declarations.
- Typer resolves and validates.
- Desugarer lowers loops, switch/match, throw/catch, optional/variadic/kwargs
  args, collection literals, and lambdas into plain til the back ends handle;
  it runs interleaved with the typer.
- Garbager inserts the automatic destructor calls.
- Constfolder folds comptime work.
- Scavenger removes unused leftovers.
- C codegen/interpreter are the final execution back ends; builder orchestrates
  generated outputs and toolchains, the interpreter also handles its own FFI
  calls, and targets defines build targets.
- Binder is a standalone C-header -> til bindings generator, outside
  the main pipeline.

That is the current practical phase order to keep in mind when debugging:

- file loading / import resolution / mode selection: `src/self/loader.til`
- shared `Context` / `TypeScope` state: `src/self/context.til`
- tokenize problem: `src/self/lexer.til`
- parse problem: `src/self/parser.til`
- missing declaration / auto-generated helper: `src/self/initer.til`
- name/type resolution or enum switch behavior: `src/self/typer.til`
- loop / switch / match / throw-catch / optional-arg / collection-literal
  lowering: `src/self/desugarer.til`
- missing/extra `delete`/`free` call, use-after-move: `src/self/garbager.til`
- comptime folding issue: `src/self/constfolder.til`
- generated C issue: `src/self/c_codegen.til`
- generated-output path / compiler-link invocation issue: `src/self/builder.til`
- cross-compile target/lang issue: `src/self/targets.til`
- interpreter FFI call into native C: `src/self/interpreter.til`
- runtime behavior mismatch: `src/self/interpreter.til` or `src/c/ext.c`
- generated vendor bindings wrong: `src/self/binder.til`
