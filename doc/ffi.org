* FFI Bindings

How til talks to C, and the conventions that keep the boundary safe.

** Source imports and native links

~import("module")~ loads Til source and declarations. ~link("name")~
requests a native library; it does not declare that library's functions or
types. A generated Til library binding combines the two: importing the
binding brings in its ~link~ directive, native declarations and wrappers.
Importing the original implementation source into the interpreter instead
evaluates guest code and guest globals.

The interpreter uses the OS loader (~dlopen~ / ~LoadLibrary~) to load native
code, then libffi to call it. An explicit ~link("path/to/library.so")~ path
is resolved relative to the file containing the directive, not the process
working directory. Explicit paths are passed to the OS loader without a
shared-library suffix filter, so versioned filenames work too. A static
~.a~ path uses a loadable twin rather than loading the archive itself.
Missing or invalid explicit libraries stop preparation with a diagnostic
naming the library, before any guest statements execute. An optional second
argument restricts a link to the ~--target~ names it lists, so each target
can name its own build of a library (~link("vendor/nng/build-linux-arm64/libnng.a", "linux-arm64")~);
see [[file:tutorial/2_modes.org][the modes tutorial]] for the mode-level
~targets~ and ~build_hint~ that go with it.

A compiled host and an interpreter can share native globals by using the
same shared-library instance. ~TilVm.load_file~ accepts these prebuilt
libraries and imported bindings through the same ~import~ / ~link~ syntax.
It loads libraries and resolves native declarations in process, without
running a compiler. ~link_c~ is rejected: compile that code into a library
before loading the config.

In ~TilVm~, failure to load a named library, explicit path or archive twin
returns owned ~TilVmError~ diagnostics. A failed load can be retried on the
same VM. Missing native functions/globals also report through VM diagnostics
when used. Guest panic/exit remains recoverable, but native code executes
natively: its own panic, exit or fault can terminate the process. Use a
native error-return / throws contract for recoverable failures.

Loaded native libraries belong to the process lifetime. Destroying a VM
releases its guest state and FFI descriptors, not the shared library or its
globals; other VMs and the compiled host can continue using it. Native
initializers and earlier native calls are not rolled back on load/call
failure. Bindings retain their normal FFI ownership and ABI contracts.

*** Retained guest callbacks and typed values

~import("std/tilvm")~ provides ~TilVm.new(support_root)~. The root names the
installed ~lib/til~ SDK matching the host build. ~vm.load_file(path) throws
TilVmError~ loads one ~mode lib~ entry and evaluates its initializers in this
process. Failed loads can be retried; after a successful load, reload uses a
fresh VM. Serialize VM operations on one thread; independent VMs can coexist.

~vm.lookup(name, Signature) throws TilVmError~ retains a guest callable checked
against an ordinary named function-signature Type. Parameter/result types,
ownership/mutability and func/proc effects must match. Omitting Signature
retains the zero-argument, no-result func/proc contract. For a loaded guest
exporting ~transform := func(text: Str) returns Str~, a host can write:

#+begin_src til
Transform := func(Str) returns Str
mut transform := vm.lookup("transform", Transform)!
mut arguments := Tuple.new()
arguments.push(Str, own format("host", " input"))
result := transform.call(arguments)!
ref text : Str = result.get(0)
#+end_src

~callback.call(arguments) returns Tuple throws TilVmError~ accepts a mutable
Tuple of checked native values. Omitting arguments supplies an empty Tuple,
so existing ~callback.call()~ sites still work. A guest with no result returns
an empty Tuple; otherwise it returns one independently owned value.

This boundary uses snapshots:

- Each input is copied into guest storage. An ~own~ parameter consumes that
  guest snapshot, not the host Tuple element. An ~own mut~ parameter changes
  its transferred snapshot without writing back to the host input.
- A borrowed ~mut~ parameter copies changes back to the input Tuple, including
  when the guest later panics or exits. Earlier effects are not rolled back.
- Results copy strings even when the guest returned a borrow, literal or view.
  Host results remain valid after the inputs, callback and VM are destroyed.
- Signature, argument-count, type and width errors execute no guest code.
  Guest runtime errors preserve the loaded VM and callback for another call.

Lookup/call errors carry owned diagnostics, phase and optional exit status in
~TilVmError~. Hosts can catch them with ~?~ and ~catch~; the example's ~!~
instead converts an error into a host panic. Guest output uses host stdio.

The fixed call boundary supports core scalars and Str, with at most 63
arguments. Variadic, kwargs, throwing guest signatures and arbitrary record
arguments/results are unsupported. Native library functions can still use
their ordinary FFI throws contracts, and records can cross through the native
reference route described below.

A ~TilVmCallback~ owns its retained callable/captures and borrows the VM's
code/session. Cloning the handle clones captures independently while sharing
that VM's globals; calling it does not re-resolve the original global binding.
ASAP keeps the VM alive through its handles and destroys the handles first;
explicit teardown follows the same order. See
[[./concepts/ownership.org][Ownership: owning handles can borrow their resource owner]].
~test/install_tilvm.til~ builds and runs ~test/tilvm.til~ against the installed
API under ASAN with an empty PATH, exercising snapshot ownership and recovery.
~test/install_tilvm_errors.til~ independently checks private-member and lifetime
rejections, including ~test/tilvm_lifetime_error.til~. Each driver uses its own
copy-only installation and work directory.

*** Host-supplied prelude

A host can provide its API as an implicit module when loading configuration:

#+begin_src til
vm.load_file(init_path,
    prelude_source = "import(\"tiled_startup_api\")\n",
    prelude_name = "tiled-api",
    prelude_base = packaged_api_directory)?
#+end_src

All three arguments are optional together. Their defaults are empty strings;
empty source means no prelude. Supplying only some of the three is a structured
load error, including supplying a name/base with empty source. The base must
name an existing directory. The entry remains ~mode lib~, with the host calling
~init()~ through an ordinary retained callback. A successful load still seals
the VM; retry after failure and fresh-VM reload keep their existing contracts.

The source may import packaged generated bindings, or contain those generated
declarations, native links, types and wrappers directly. An omitted prelude mode
means ~lib~; any explicit mode other than ~lib~ is rejected. Source is parsed as
its own module, never concatenated with user code or written to a wrapper file.

~prelude_name~ is an exact logical module identity and diagnostic name. It is
neither opened nor canonicalized as a filesystem path, and does not introduce
an explicit-import alias. A collision with a loaded file module's diagnostic
identity is rejected, including collisions discovered in dependency traversal.
Distinct VMs may use the same name. Public declaration names supplied by the
prelude/dependency closure may not be redeclared by another module: types,
functions and values all produce a structured load error at the conflicting
declaration. Private declarations and file-local import aliases retain their
ordinary scope rules.

Relative prelude imports resolve from ~prelude_base~ using the ordinary import
resolver; relative native-library paths use that base too. Dependencies resolve
their own imports/links from their own files. User entry/helper paths, relative
imports, and line/column positions are unchanged. Prelude parse/type/evaluation
errors use its logical name; its link-loading errors also retain the directive's
logical origin and line, with the native library path in the message.

The entry and user helpers receive an implicit prelude dependency through the
same traversal used by mode auto-imports. SDK source/vendor modules, the prelude
itself, and its dependency closure do not receive that edge. Explicit imports
of an already-loaded dependency reuse its normal identity, including through
cycles. Exclusion concerns dependency edges: public declarations still use Til's
existing shared program scope, rather than a new module isolation system.

The loaded module owns the supplied source, logical identity and resolved base.
The host may release its input strings after loading; the VM retains the AST/code
through its callbacks' lifetime. Failures return owned diagnostics and allow
retry without invalidating another VM's callbacks. Native side effects are not
rolled back. The host remains responsible for packaging matching runtime assets
and for publishing staged configuration and callbacks.

~host_prelude_test~ in ~test/tilvm_native.til~ runs against an isolated installed
SDK under ASAN, private HOME and empty PATH. It covers generated bindings,
shared native state, implicit API use from cyclic relative helpers, deduplication,
excluded dependency edges, exact diagnostic locations, input-string release,
independent VMs, retry and teardown. The direct-declaration case also loads a
relative native library through a base directory containing spaces.

*** Editor buffer and reload example

~editor_buffer_test~ in ~test/tilvm_native.til~ is the concrete integration
example for Tiled. ~test/install_tilvm_native.til~ builds its native library and
host against an isolated installed SDK. From a built checkout, run
~bin/til run test/install_tilvm_native.til~; the driver runs the ASAN host with
an empty PATH, and the host writes/changes the config after compilation.

The native library owns the text buffer. ~native_buffer_set(text: Str)~
copies its borrowed input, ~native_buffer_insert(text: Str)~ borrows the
insertion text for the call, and ~native_buffer_snapshot() returns Str~
returns an independent owned copy. Both host and config import the generated
binding for this same shared library. The config exports an ~on_key~ closure
with owned text captures; the host retains it with ~vm.lookup("on_key")~
and invokes it later through ~callback.call()~.

Reload uses a separate candidate VM. Load and callback lookup must both
succeed before replacing the active pair, and the old callback is released
before its VM. The test replaces the same config file with syntax, type,
lookup-contract and evaluation failures, then repairs it. The old callback
continues to work after each rejected candidate is destroyed. The syntax/type
errors and side-effect-free lookup failure leave the buffer unchanged. Native
edits during initialization are not undone by a later lookup/evaluation error;
the runtime-panic case checks that an earlier insertion remains visible.
This is callback/VM replacement,
not a transaction over native side effects. Host snapshots and returned
diagnostics remain valid after all VMs and the native buffer contents are
released.

*** Mutable native configuration records

~native_config_test~ in the same fixture covers a library-owned ~NativeConfig~
with ~I32~, ~Bool~ and ~Str~ fields. The host keeps a reference obtained from
~native_config_ref() returns ref NativeConfig~. The guest imports the generated
record declaration, obtains that same reference, and calls its own
~init(mut config: NativeConfig)~. A no-argument ~run_init~ wrapper makes this
reachable through ~vm.lookup~; it does not require passing an arbitrary host
record through the callback argument API.

Field changes are visible through the host's original reference. Strings
stored in native-owned fields must survive VM teardown: VM literals live in
the VM's pool, and string views borrow their source storage, so neither can
become a lasting native value by copying its header alone. The interpreter
materializes owned character storage for those native stores/transfers,
including empty strings and inline string fields of a whole record. Native
provenance is tracked even when the native and interpreter layouts match.
Temporary borrowed FFI arguments retain their borrowing semantics.

The regression checks dynamic strings, literals, borrowed inputs, views,
whole-record replacement and an ~own Str~ native argument. It also checks
that a native function returning a reference to a borrowed guest record
preserves that record's identity and guest view semantics. Native records,
their contents and host string snapshots are exercised after VM teardown.

*** Native exceptions and generated bindings

Exception tags must agree between separately compiled libraries and callers.
They no longer depend on the order in which a compilation encounters error
types. The existing I64 error-kind slot uses fixed core tags (OutOfBounds = 1,
IntegerOverflow = 2, DivideByZero = 3, KeyNotFound = 4). Other nominal type names
use FNV-1a-64 of their name bytes, masked to 62 bits with bit 62 set. A collision
between distinct registered names is a compiler error. Zero still means success.
Rebuild libraries and their consumers together when upgrading from the old
registration-index ABI; old custom-error tags are not compatible.

Generated enum bindings declare variants once, rather than also exporting their
generated constructors/constants as duplicate namespace members. Typed nested
record defaults recover named constructor fields; automatically filled private
fields remain defaults rather than becoming illegal explicit arguments.

Native by-value enum marshalling covers tag-only enums (including wide tags),
tagged integer/float/string/record payloads, borrowed-pointer niches and owned
record-box niches. Descriptors match the emitted tag/union/pointer layout; only
the active payload is converted between interpreter and native widths. Mutable
copy-back preserves existing owned-box identity, and references returned into
converted arguments are rebased before the temporary carriers are released.
Owned native transfers materialize VM literals/views so stored strings survive
VM teardown. A native throw has no return value: the error slot is checked before
decoding its result, and zeroed error-only enum storage owns no payload.

This does not make native and interpreted closure carriers interchangeable.
Signatures containing callable enum payloads remain unavailable through FFI and
report an error when called; importing an unused declaration is allowed. Retain
guest commands through ~TilVmCallback~ or the command-table pattern below.
~test/library_namespace.til~ covers compiled/interpreted enum round trips and
cross-width boxed references; ~native_enum_test~ in the installed ASAN host
checks native-owned strings after VM destruction and unsupported callable enums.

*** Composing generated Til bindings

A library consuming another library's generated binding now retains that API
as an import rather than emitting a second copy of its types and globals. The
native API role is derived from checked external declarations/lifecycle wrappers
before folding, so a packaged binding can use ~mode lib~ or a different filename.
Ordinary implementation modules remain part of their owning library's export.

Generated imports use relative paths and the existing intentional-re-export
spelling (~_ := import("./dependency")~). Transitive imports retain normal module
identity and deduplication. An imported ~ext_global~ keeps its original native
linker symbol; a dependent library does not rename or recreate its storage.
Consumers can import both dependency and dependent APIs without duplicate type
declarations. They must use the generated model definition rather than also
importing the implementation source that defines that same model.

Regenerate affected bindings in dependency order and package the existing binding
files with their relative layout and native libraries. Installing one library
does not automatically bundle its dependency assets. No extra schema, manifest,
generated source copy or runtime compilation is involved. The composition test
builds two dependent layers, relocates their binding files together, and checks
both compiled and interpreted consumers against the same native global state.

*** Retaining commands in ordinary records and vectors

~test/stored_callbacks.til~ exercises a command table of ~Vec(Binding)~, where
~Binding~ contains an ordinary named proc-signature field. A registration helper
may borrow its callable parameter and construct ~Binding(action = action)~:
the field owns a copy of the callable environment. Releasing the caller's
callable box must not invalidate that stored copy. Both compiled and interpreted
field invocation use the retained environment, so private mutable captures
persist between invocations.

Copying a table clones its callable environments. Owned aggregate captures are
cloned through their actual clone methods, with independent mutable state.
Borrowed captures still borrow the same referents: copying the callable does
not extend those referents' lifetime or make them owned. Keep a borrowed adapter
alive until the table is destroyed, and its VM alive until the adapter and all
retained callbacks are destroyed. Alternatively, move the adapter into an
~[own mut adapter]~ capture; the table then owns that adapter's copied value,
while the adapter still borrows its VM. ~test/stored_callbacks_error.til~ rejects
escaping tables/records that carry a closure borrowing a dead local.

These ownership rules do not publish candidate editor state or undo native
effects. Reload still requires the host's explicit staging/publication policy.

*** Remaining embedding gaps and follow-up ownership

The #370 embedding contract is complete. Its current boundaries leave these
possible extensions:

- ~TilVmCallback.call(Tuple)~ does not marshal variadic or kwargs arguments,
  throwing guest signatures, or arbitrary record arguments/results. Extending
  it requires checked marshalling and ownership/error-path coverage in the
  installed host tests. Native-library record references and native throws
  already work; they do not provide these guest-callback contracts.
- Callable enum payloads cannot cross the native FFI boundary. Supporting them
  requires a defined native callable representation and capture/code lifetime
  contract, rather than treating interpreter closures as native function pointers.

These are unsupported extensions, not unfinished #370 acceptance checks. The
historical manual-registration proposal in that issue is not the current API.

** Why bindings need a human reviewer

The til-side qualifiers that govern call semantics --
~ext_proc~ vs ~ext_func~, ~own~ vs ~ref~ vs ~shallow~ on args,
and ~own~ vs ~ref~ vs ~shallow~ on returns -- carry information
that the C header simply does not encode.  C has no syntax for:

- *purity* / side effects.  ~int GetScreenWidth(void)~ and
  ~int CRC32(const char *)~ look identical to a header parser,
  but the first reads a process-global and the second is a pure
  function of its input.  til's constfolder pass folds pure calls at
  compile time; calling ~GetScreenWidth()~ at compile time
  silently returns 0 (no window) and bakes that 0 into the
  generated binary.  Folded vs not-folded is a til-side
  decision: ~ext_func~ means "pure, fold freely",
  ~ext_proc~ means "side effects, never fold".
- *pointer ownership on parameters*.  Does ~Foo *foo~ as an arg
  mean "callee borrows this pointer" or "callee takes ownership
  and will free it"?  Same C signature, opposite til-side
  contract.
- *pointer ownership on returns*.  Does the ~char *~ returned by
  ~GetClipboardText()~ point at memory the caller must free, or
  at raylib-internal scratch that mustn't be freed by anyone but
  raylib?
- *pointer nullability* (#321).  Every C pointer type admits NULL;
  whether a given field or result actually uses it ("never NULL",
  "will be NULL if not specified", "returns NULL on cancel") lives
  in header comments, not in the types.  The binder emits the safe
  shape for every pointer struct field --
  ~field : Option(ref T) = Option(ref T).None~ -- and cannot know
  which pointers the C library promises are non-null.  Tightening
  those to a mandatory ~ref field : T~ is a human call, made by
  reading the library's docs.

So the auto-generator (~src/self/binder.til~, run via
~make update_c_libs~) produces a starting point: structs spelled
correctly, primitive args mapped through, but every function
defaults to ~ext_func~ with ~shallow~ everywhere it could
guess.  A human then walks the output and tags the cases the
generator could not see.

** The audit checklist

When regenerating ~vendor/bindings/*.til~, scan each ~ext_func~
in the output and ask:

1. *Does the C function read or modify global state?*  Window
   metrics, input queues, time, allocator state, file system,
   GPU, audio device, PRNG seed -- anything that depends on or
   touches the world outside the call's arguments.  If yes:
   change ~ext_func~ to ~ext_proc~.  Return type stays
   (~ext_proc~ may return a value -- the proc/func distinction
   is purity only; whether the function returns a value has
   nothing to do with it).

2. *Does the C function take a pointer arg that it stores or
   frees?*  By default the binder emits ~shallow~ for primitives
   passed by value.  For a single-level pointer arg it follows the
   C ~const~ qualifier: a ~const T *p~ (read-only pointee) maps to
   the borrowed default ~p : T~, while a non-const ~T *p~ maps to
   ~mut p : T~ (a mutable borrow -- C args are mutable unless
   ~const~, til args are immutable unless ~mut~, so the generator
   bridges the two).  If the C side takes ownership of the buffer,
   change the arg to ~own~ -- til will then transfer the heap
   allocation across the call and not try to free it on this side.

3. *Does the C function return a pointer the caller does not
   own?*  raylib's ~GetMonitorName~, ~GetClipboardText~,
   ~GetWorkingDirectory~ return internal static buffers; the
   matching binding return type should be ~returns ref I8~ (not
   ~returns I8~, which would mean "caller owns and must free").
   The binder emits ~ref~ for raw-pointer returns by default,
   which is the safe choice -- audit the few cases where the C
   call actually hands ownership over.

4. *Does the C library document a pointer as never NULL?*  The
   binder emits every pointer struct field as
   ~field : Option(ref T) = Option(ref T).None~ -- nullable, the
   safe default, one word wide via the #320 niche, byte-identical
   to the C pointer it maps.  Where the header's comments promise
   the pointer is never NULL (nng_url's ~u_rawurl~: "never NULL"),
   or promise ~""~ rather than NULL when unset, tighten the field
   to a mandatory ~ref field : T~ (no default) so til code reads it
   without an unwrap.  Only that direction needs auditing: leaving
   a never-NULL pointer as Option is safe, just noisier for
   callers.  Two constraints come with the Option spelling:
   - at an ext SIGNATURE (param or return) a niche Option must be
     declared ~shallow~.  ~Option__ref_I8~ is
     ~struct { I8 *data; }~ and the SysV ABI passes it in a
     register exactly like the bare pointer -- but only by value;
     without ~shallow~ the ext boundary passes it by pointer and
     the call is ABI-wrong.  ~shallow~ is not inferred here.
   - #324 and #321 have both landed, so there is no
     "keep it as a nullable ref field" escape hatch left: the ~NULL~
     keyword is gone.  A typed nullable pointer field is
     ~field : Option(ref T) = Option(ref T).None~; a raw one stays in
     the quarantine as ~ref field : Dynamic = 0~ (integer zero is the
     null pointer there).  raylib.til shows both -- its typed arrays
     are Option fields, its ~Image.data~-style raw buffers are
     Dynamic.

If any of (1)-(4) flips, also walk the matching wrapper in
~src/modes/gui.til~ (or wherever the user-facing surface lives)
and propagate the same qualifier change.  A ~func~ wrapper
around an ~ext_proc~ has to itself become a ~proc~, or constfolder
will still try to fold the wrapper.  A ~ref~-returning ext call
threaded through a ~returns Str~ wrapper would leak the
caller's expectation that the wrapper owns the buffer.

** Quick reference

Mapping from "what the C function does" to the right binding
shape.  See [[file:concepts/qualifiers.org][doc/concepts/qualifiers.org]] for the
qualifier semantics themselves; this table is just the FFI
layer.

| C behaviour                                | til binding form                                            |
|--------------------------------------------+-------------------------------------------------------------|
| Pure function of args, returns a value     | ~ext_func(args) returns shallow T {}~                       |
| Reads/mutates global state, returns void   | ~ext_proc(args) {}~                                         |
| Reads/mutates global state, returns value  | ~ext_proc(args) returns shallow T {}~                       |
| Takes ownership of a heap pointer arg      | ~ext_proc(own buf : T)~ or ~ext_func(own buf : T) ...~      |
| Borrows a ~const T *~ pointer arg (read-only)| ~ext_*(buf : T)~ (default; ~ref~ keyword is redundant)    |
| Mutates a non-const ~T *~ pointer arg       | ~ext_*(mut buf : T)~ (the generator's default for non-const)|
| Returns an internal pointer (do not free)  | ~ext_*(...) returns ref T {}~                               |
| Returns a heap pointer the caller owns     | ~ext_*(...) returns T {}~ (default; ~own~ keyword redundant) |
| Nullable pointer struct field              | ~field : Option(ref T) = Option(ref T).None~ (generator default) |
| Pointer field documented never NULL        | ~ref field : T~ (mandatory, no default -- hand-tightened)   |
| Nullable pointer param / return            | ~shallow p : Option(ref T)~ / ~returns shallow Option(ref T) {}~ |

For passing scalars and small structs by value (the normal C
ABI shape), use ~shallow~ on the arg and ~returns shallow T~ on
the return -- those map to plain ~T arg~ / ~T return~ in the
generated C.

** External globals

An ~ext_global~ declaration binds a Til name directly to storage exported by
a C library:

#+begin_src til
COUNT := ext_global(I64, "library_count")
mut STATE := ext_global(State, "library_state")
#+end_src

The first argument is the Til object type; the second is the exact C symbol.
The declaration is an lvalue, not a function call: reads and writes access the
same storage from compiled and interpreted code. Only top-level and type
namespace declarations are allowed. Primitive, struct, and enum object types
are supported; pointer-like or source-only types fail at the declaration.

Generated library bindings use ~ext_global~ for public top-level globals and
namespace data, spelling the library-prefixed C symbol. Python bindings expose
the same storage through ~ctypes.in_dll~, so mutation is shared across C, Til,
and Python consumers. A non-~mut~ declaration is read-only to Til even when the
underlying C object itself is writable.

A ~ref~ declaration binds a C POINTER object. The Til name borrows the
pointee through that pointer, so whatever C points the variable at later is
what Til reads next:

#+begin_src til
ref cursor : I64 = ext_global(I64, "library_cursor")           // I64 *library_cursor
ref mut point : Point = ext_global(Point, "library_point")     // Point *library_point
#+end_src

Compiled code declares ~extern T *symbol;~ and reads through it on every use;
the interpreter keeps the variable's address and re-loads the pointer on every
lookup, so the two backends agree even when C re-points the variable after the
declaration. ~ref mut~ writes through the pointer. Generated library bindings
spell a library's own ~ref~ globals this way, and the Python binding exposes
them as ~ctypes.POINTER(T).in_dll~ views read through ~.contents~.

** Passing a Str to a C string parameter

A til ~Str~ is ~{c_str, count, cap}~ -- length-counted, like a Go
slice or a Rust ~&str~, not a C string.  C string APIs
(~fopen~, ~unlink~, ~dlsym~, raylib's ~DrawText~, ...) take a
~char *~ and read until they find a zero byte, so handing one a
~Str~'s buffer is only correct when a NUL actually sits at
~count~.

Whether it does depends on how the ~Str~ was made:

| Str origin                                  | NUL at count? |
|---------------------------------------------+---------------|
| ~Str.clone~, ~Str.with_capacity~, ~format~   | yes (they allocate count+1 and write it) |
| string literals                              | yes (C string constants when compiled; the interpreter terminates its interned copy) |
| ~Str.from_c_str~                             | yes (it wrapped a C string, and count stopped at the NUL) |
| ~substr~, ~trim~, ~trim_start~ -- any ~CAP_VIEW~ | *NO* -- the view points into the middle of another buffer |

So a view's ~.c_str~ hands C the view's bytes *plus whatever
follows them*.  This used to be silent: the C call operated on a
different string than the program meant, and usually just failed
(~ENOENT~ from ~unlink~, ~NULL~ from ~dlsym~) somewhere far from
the cause.  Both backends produce the same value here: the
interpreter used to materialise a returned view as an owned copy,
so a view bug could pass every interpreted test and still ship.
Issue #366 removed that copy -- a view is a view on both.

Issue #343 closed the silence: the ext-call boundary now CHECKS
the terminator.  A ~<str>.c_str~ argument feeding an ext
binding's plain ~name : I8~ parameter -- the shape that emits
~const char *~ -- is wrapped in the ~TIL_CSTR~ macro, which
panics when ~c_str[count]~ is not a NUL, the way ~DEREF~ panics
on a null.  The interpreter's FFI marshalling tests the same
byte, so both backends die identically.  Two things follow from
how it is spelled:

- The BYTE is the discriminator, not ~cap~.  Returning a literal
  from a til function demotes ~CAP_LIT~ to ~CAP_VIEW~ while
  leaving the string terminated, so a cap test would reject safe
  values; reading ~c_str[count]~ is always in bounds, because
  every allocating Str path reserves count+1 and a view's end
  never passes its base's.
- It catches the direct ~expr.c_str~ form only.  A pointer
  laundered through an ~I8~ local first, or handed to C by a
  binding's own C side, still escapes it -- which is why the two
  rules below remain the rules, with the check as a backstop
  under them rather than a replacement for them.

Two rules follow:

1. *Writing a binding's C side* (~src/c/ext.c~ and any
   ~link_c~ module): never cast ~s->c_str~ to a ~char *~.  Copy
   through ~dup_n(s->c_str, s->count)~ and ~free~ it, the way
   every path-taking function in ~ext.c~ does.  The callee cannot
   see whether its caller passed a view, so the copy is the only
   correct default.  ~test_file_c_boundary_takes_views~ in
   ~test/files.til~ pins this: it drives the File API over a
   ~substr~-backed path whose next byte is ~'Z'~.
2. *Writing til code that calls C directly* (~DrawText(s.c_str,
   ...)~ and friends): a bare ~.c_str~ is fine for a literal or an
   owned local, but not for anything that might be a view -- and a
   ~s : Str~ parameter might always be one, since the caller
   chooses.  ~clone()~ the string first: an owned copy always
   carries the NUL.  The boundary check turns getting this wrong
   into a panic naming the cause instead of a wrong string, but
   the panic is still a bug report, not a behaviour to rely on.

     c := s.clone()
     DrawText(c.c_str, 10, 10, 20, WHITE)

   A chained ~s.clone().c_str~ is a temporary, and the garbager
   frees it at the END of the statement -- the emitted C is
   ~clone; call; delete~, in that order.  So which form is safe
   depends on what the callee does with the pointer:

   - *Reads it during the call* (~DrawText~, ~unlink~, ~fopen~,
     ~strlen~ -- nearly every C string API): the chain is safe.
     The delete runs after the call returns.
   - *Retains it past the call*: the chain dangles.  ~Str.from_c_str~
     is the in-tree example -- it returns a ~CAP_VIEW~ over the
     buffer it was handed, so the view outlives the temporary and
     reads freed memory.  Storing the pointer C-side, or returning
     it, is the same shape.

   Binding the clone is the rule to teach because it is correct in
   both cases and costs nothing: the local lives to the end of its
   scope, so no callee can outlive it by accident.  ~c := s.clone()~
   then ~c.c_str~.

   Compiled code is again where this bites: the interpreter keeps
   the temporary alive, so a retaining chain prints the right
   string interpreted and garbage from the binary.
   ~test_clone_terminates_views~ in ~test/strings.til~ pins the
   bound form.

The same reasoning is why ~count~, not the terminator, is
authoritative on the til side: ~fwrite(s->c_str, 1, s->count,
...)~ and ~memcmp(a, b, count)~ are always correct, on views and
owned strings alike.  Prefer the count-bounded C API when the
function offers one.

** ext_struct vs struct: the field-layout contract

~ext_struct~ is not just "a struct whose methods live in C".  Its
reason to exist is field layout:

- ~struct~ reserves til's right to reorder fields (for packing,
  alignment, or any future layout optimization).  Source order is
  not a promise; two structs with the same fields in a different
  order may compile to the same layout.
- ~ext_struct~ guarantees declaration order == memory order.  The
  fields are laid out exactly as written, because the type has to
  match a C struct's ABI for FFI.  This holds even though the
  reordering optimization for ~struct~ is not implemented yet: it is
  a contract about what each form is *allowed* to do, not a snapshot
  of today's codegen.

Consequence: any type that crosses the C boundary by value (or whose
address is handed to C and read back field-by-field) must be an
~ext_struct~, never a plain ~struct~.  You cannot express "match this
exact C layout" with a form that is permitted to reorder.

~ext_struct~ takes an optional C struct tag for the cases where the C
library names the aggregate twice (the ~struct foo~ tag vs the
~typedef~ name):

- ~ext_struct {}~          -- anonymous (no C struct tag)
- ~ext_struct("foo") {}~   -- emits ~struct foo~

There is no ~ext_struct("")~ form: an empty tag is the same as no
tag, so the parser rejects it and points you at bare ~ext_struct {}~.

** noop_proc: forcing constfolder to skip a wrapper

Some user-level wrappers depend on runtime state but cannot
inherit a ~proc~ tag from their callees -- e.g. the wrapper
delegates to an ~ext_func~ that genuinely is pure on its
arguments, but the wrapper itself adds context (reads a global,
queries the current frame, etc) that constfolder must not evaluate
at compile time.  Drop a call to ~noop_proc~ anywhere in the
function body:

#+begin_src til
import("core/sys")  // for noop_proc

frame_relative_x := func(world_x: F32) returns F32 {
    noop_proc()  // mark this func impure; never fold
    return world_x.sub(camera_offset.x)  // camera_offset is a global
}
#+end_src

~noop_proc~ is a one-liner ~void noop_proc(void) {}~ in
~src/c/ext.c~, declared as ~ext_proc() {}~ in
~src/core/sys.til~ and listed in
~is_side_effecting_name~ inside ~src/self/constfolder.til~.  The
call has zero runtime cost (the C body is empty) and exists
purely as a flag for the constant folder.

This is the escape hatch for "the binding is correct but the
*wrapper* still depends on state."  When you find yourself
reaching for it, double-check that the underlying ~ext_func~
really is pure -- often the right fix is to flip *it* to
~ext_proc~ instead.

** Regenerating the bindings

~make update_c_libs~ runs ~bin/til bindings~ against
~vendor/raylib/src/raylib.h~, ~vendor/raylib/src/rcamera.h~,
~vendor/tinyfiledialogs/tinyfiledialogs.h~,
~vendor/nng/include/nng/nng.h~,
~vendor/secp256k1/include/secp256k1_schnorrsig.h~ (which pulls in
~secp256k1.h~ and ~secp256k1_extrakeys.h~ from the same directory,
so one pass covers the whole enabled API), and libffi's
~ffi.h~, and writes the output to
~vendor/bindings/{raylib,tinyfd,nng,secp256k1,libffi}.til~.

*The audit survives.*  The committed ~.til~ IS the audit record, so
the generator reads the file it is about to overwrite and keeps what
it finds there: every declaration whose name the header still
produces is re-emitted verbatim -- ~ext_proc~ tags, ~own~/~ref~
overrides, ~Option~ re-typings, struct FIELD qualifiers -- along with
the comment block above it.  Struct and alias lines are preserved
too, deliberately: ~nng_sockaddr_ipc~'s own C tag is a decision, not
a transcription.  A regen over an untouched checkout reproduces the
committed file byte for byte, which ~bindgen_preserves_audit~ pins
for tinyfd.

Two things it cannot preserve, both reported on stderr rather than
lost silently:

- *Declarations the header does not produce.*  Hand-ADDED bindings
  (the three below) name no generated line to attach to, and keeping
  unmatched declarations would resurrect symbols C deleted.  The
  generator lists them by name at the end of a run; re-add them.
- *A changed parameter count.*  An audit answers the signature it
  was written for.  When C's arity moves under a preserved name the
  line is still kept, but the run says which one to re-audit.

So the workflow below is now: regenerate, read the warnings,
re-add what they name, and diff to review the C-side changes -- not
re-derive 161 ~ext_proc~ flips for raylib and 354 for nng by hand.

*libffi is generated from a BUILD ARTIFACT, not from tracked
source.*  ~LIBFFI_BINDGEN_INCDIR~ points at
~vendor/libffi/x86_64-pc-linux-gnu/include~, which
~vendor/libffi/.gitignore~ ignores -- it appears only after
libffi is configured and built locally, and ~vendor/libffi/.built~
then short-circuits any rebuild.  A checkout whose build predates
a libffi upgrade therefore still has the OLD ~ffi.h~ while the
tracked source is already the new version, and regenerating there
silently rewrites ~vendor/bindings/libffi.til~ against the older
ABI: declarations that exist only in the newer release simply
vanish.  Nothing fails -- no test calls them -- so the file just
describes the wrong libffi until someone uses one of the missing
APIs and gets "not registered".

Before regenerating libffi, check that the header the regen will
read matches the source the repo ships:

#+begin_src sh
grep -m1 'libffi [0-9]' vendor/bindings/libffi.til                       # what the binding was built from
grep -m1 'libffi [0-9]' vendor/libffi/x86_64-pc-linux-gnu/include/ffi.h  # what the regen will read
grep -m1 AC_INIT vendor/libffi/configure.ac                              # what the repo ships
#+end_src

~make clean~ deletes that build directory, so the middle path is
simply missing on a freshly cleaned tree -- which is the safe
state: the next ~make~ rebuilds it from the tracked source.  The
dangerous state is a tree built BEFORE a libffi upgrade, where the
directory exists and holds the older ~ffi.h~ while ~.built~
suppresses the rebuild.

If the built header is behind (or you are unsure), either force a
rebuild first (~rm -rf vendor/libffi/x86_64-pc-linux-gnu
vendor/libffi/.built~, then ~make~) or keep
~vendor/bindings/libffi.til~ out of the regeneration -- restore it
with ~git checkout HEAD -- vendor/bindings/libffi.til~ and re-apply
the audit to the other three only.  This bit a real session: a
container built before the 3.4.6 -> 3.7.1 upgrade regenerated
against the old header and would have dropped ~ffi_call_plan~,
~ffi_get_version~, ~FFI_TYPE_UINT128~ and friends from the
committed binding, with a green test suite.

nng has four hand-edits the generator cannot produce, all of
which must be re-applied after regeneration:

0. *Every binding is ext_proc.*  The binder defaults to ext_func,
   but nng has no pure functions -- each call mutates or reads live
   socket/pipe/dialer/listener/ctx/aio/msg state, does I/O,
   allocates, or returns an internal pointer.  Folding any of them
   in constfolder (opening sockets at compile time, or baking a
   compiler-process pointer into the output) is wrong, so flip the
   whole file: ~sed -i 's/:= ext_func(/:= ext_proc(/g'~.

1. *~nng_logger~ alias.*  The binder leaves the ~nng_logger~
   function-pointer typedef undefined; add ~nng_logger := Dynamic~
   before the logging functions.
2. *Non-shallow logger param.*  ~nng_log_set_logger~ takes a
   ~nng_logger~ (now ~Dynamic~), so its parameter must NOT be
   ~shallow~ (shallow requires a scalar/struct type).
3. *Protocol constructors.*  ~nng_pair0_open~, ~nng_pub0_open~,
   ~nng_sub0_open~, etc. live in ~nng/protocol/*/*.h~, not in
   ~nng.h~, and reference ~NNG_DECL~/~nng_socket~ without including
   ~nng.h~ -- so they do not preprocess standalone.  Re-append the
   hand-written "Protocol constructors" block (each is
   ~ext_proc(mut sock : nng_socket) returns shallow I32 {}~, taking
   the socket out-parameter by address -- ~mut~ because the call
   writes the socket through that non-const pointer).
4. *nng_url nullability* (checklist item 4).  The generator emits
   every pointer field as ~Option(ref I8)~; re-tighten the six
   fields whose header comments promise non-null (~u_rawurl~,
   ~u_scheme~, ~u_hostname~, ~u_port~, ~u_path~, ~u_requri~) back
   to mandatory ~ref field : I8~.  The four genuinely nullable url
   fields and ~nng_iov.iov_buf~ stay exactly as generated.

libsecp256k1 (issue #235; vendored from the upstream v0.8.0 tag,
whose signing key matches the SECURITY.md maintainer list -- REM:
rerun upstream's own suite, ~cmake -DSECP256K1_BUILD_TESTS=ON~ +
~ctest~ in a scratch build, whenever the vendored tree is updated)
has these hand-edits beyond the ext_proc flips (every call reads or
mutates a run-time context, so none is foldable):

1. *Opaque caller-allocated structs.*  ~secp256k1_pubkey~,
   ~secp256k1_xonly_pubkey~, ~secp256k1_ecdsa_signature~ (64 bytes)
   and ~secp256k1_keypair~ (96 bytes) are ~unsigned char data[N]~
   upstream, which the binder cannot express, so it emits them
   field-less -- one byte on both backends.  But the CALLER
   allocates these and the library writes N bytes through the
   pointer, so their bodies are re-spelled as N/8 ~U64~ words.
   ~secp256k1_context~ stays field-less: it is only ever reached
   through the pointer ~secp256k1_context_create~ returns.
   ~secp256k1_schnorrsig_extraparams~ stays field-less too (its
   magic bytes cannot be initialised from til; use
   ~secp256k1_schnorrsig_sign32~).
2. *Function-pointer typedefs.*  ~secp256k1_nonce_function~ and
   ~secp256k1_sha256_compression_function~ are added as ~Dynamic~
   aliases, and the two parameters of those types lose their
   ~shallow~ (same as nng's logger).
3. *Flag constants.*  ~SECP256K1_CONTEXT_NONE~ / ~_VERIFY~ / ~_SIGN~
   / ~_DECLASSIFY~ and ~SECP256K1_EC_COMPRESSED~ / ~_UNCOMPRESSED~
   are ~#define~d as expressions over ~SECP256K1_FLAGS_*~, which the
   binder does not fold; their values are added by hand.
4. *Byte buffers are Dynamic.*  Every ~unsigned char *~ parameter
   (keys, messages, signatures, tweaks, hashes) is generated as ~U8~
   and retyped to ~Dynamic~, keeping ~mut~ where the C side writes.
   A ~U8~ parameter is a scalar passed by address, so only a raw
   ~malloc~ binding can reach it; ~Dynamic~ is what ~memcpy~ takes,
   and lets a ~U256~ or ~Signature~ value (src/std/crypto.til) go in
   directly, its bytes being the wire serialization.

The context is bound as ~ref mut ctx : secp256k1_context =
secp256k1_context_create(...)~ and released with
~secp256k1_context_destroy(ctx)~; a plain ~returns~ (owned) would
make the interpreter marshal the struct BY VALUE, which is what
~returns ref~ is for.  ~src/std/crypto.til~ is the worked example.

tinyfd has one hand-edit beyond the ext_proc flips: the file
dialogs pass NULL both ways (filter args in, "user cancelled"
out), so ~tinyfd_saveFileDialog~ / ~tinyfd_openFileDialog~ take
~shallow ... : Option(ref Dynamic)~ / ~Option(ref I8)~ filter args
and return ~shallow Option(ref I8)~ -- the generator still emits
plain ~Dynamic~ / ~I8~ params and ~returns ref I8~ there
(checklist item 4's ~shallow~ note applies: without it the ABI is
wrong).

raylib nullability (checklist item 4, marked "Hand-audited (#321)"
at the ~Font~ struct): every typed nullable pointer field in the
struct mirrors (~Font.recs~, the ~Mesh~ vertex arrays,
~Shader.locs~, the ~Model~/~ModelAnimation~ arrays,
~AudioStream.buffer~/~processor~,
~AutomationEventList.events~) is spelled
~field : Option(ref T) = Option(ref T).None~ -- ref fields cannot
default to nothing since #321 step 2 (and the NULL keyword is gone
entirely), while the niche keeps the struct layout byte-identical to
C's. The ~ref ... : Dynamic = 0~
fields (~Image.data~, ~AudioBuffer.data~, ~ctxData~, ~paths~)
stay as generated: the Dynamic quarantine keeps raw null legal.

libffi has four hand-edits, marked "Hand-audited" / "keep across
regens" in ~vendor/bindings/libffi.til~:

0. *The mutating calls are ext_proc.*  ~ffi_prep_cif(_var)~, the
   ~ffi_call~ family, every ~ffi_prep_*closure*~,
   ~ffi_closure_alloc~, ~ffi_call_plan_alloc~,
   ~ffi_raw_size~/~ffi_java_raw_size~ and ~ffi_get_struct_offsets~
   write through pointer args or touch allocator state; the binder
   emits ~ext_func~ for the value-returning ones and constfolding
   them would execute those writes at compile time.  Only the pure
   version/constant getters (~ffi_get_version(_number)~,
   ~ffi_get_default_abi~, ~ffi_get_closure_size~) stay ~ext_func~.
1. *~ffi_cif~ carries six trailing ~extra_cif_fields~ slots*
   (~extra_cif_fields~, ~extra_cif_fields_2~ .. ~_6~) mirroring the
   per-target ~FFI_EXTRA_CIF_FIELDS~ macro the binder cannot see
   through, sized for the largest one, arm32's 24 bytes (issue #25:
   without it every ~ffi_prep_cif~ on darwin-arm64 writes 4 bytes past
   the allocation; issue #420: 24 on linux-arm32).
2. *The ~ffi_abi~ constants carry a warning comment*: their values
   are x86-64-only; abi selection goes through
   ~ffi_host_default_abi()~ in ~src/self/interpreter.til~.
3. *~ffi_cif.rtype~ is a mandatory ~ref rtype : ffi_type~* (no
   default): non-null by C contract on every cif til reads
   (~ffi_prep_cif~ sets it before any use), and cifs are raw-built
   (malloc + prep), never ctor'd. ~ffi_type.elements~ stays ~own~
   (its own hand-audit note) and ~arg_types~ stays
   ~ref Dynamic = 0~ (quarantine).

Useful workflow:

1. Run ~make update_c_libs~ on a clean checkout, so the files it
   reads back are the committed audits.
2. Read the warnings.  Re-add every declaration it lists as not
   produced by the header (the ones below), and re-audit every
   name whose parameter count it reports as changed.  Exception:
   raylib.til is two headers in one file, so its two passes each
   list the OTHER half as "not produced" (the raylib pass names the
   rcamera tail, the rcamera pass names the whole raylib half) --
   that is the split talking, not a loss; the flow reunites them.
3. ~git diff vendor/bindings/~ is now the C-side change alone:
   new functions in their generated (unaudited) form, deleted ones
   gone.  Audit the new ones; everything else is already right.
4. Run ~make clean && make test~.  If a wrapper in
   ~src/modes/gui.til~ used a renamed-or-deleted C symbol,
   the build will tell you.
5. Verify the games (~bin/shootil~, ~bin/chess~, ~bin/go~) still
   render their HUDs and respond to mouse / keyboard.  The
   regressions that motivated this whole layer
   (issue #208 / commit ~3897ed9~) are interaction-shaped, so
   the test suite alone won't catch them.

Routine builds (~make~, ~make test~, ~make two_pass~) never
touch ~vendor/bindings/~ -- they consume the committed files.

** Ownership audit (raylib), 2026-05

A pass over every pointer-returning and free-style function in
~vendor/bindings/raylib.til~.  Conclusion: the binder's defaults are
correct for raylib's *manual* memory model, where the user pairs
each ~LoadX~ with an explicit ~UnloadX~ / ~MemFree~ and til stays
out of the lifecycle.  Specifically:

- *Pointer returns are all ~returns ref T~.*  ~GetClipboardText~,
  ~GetMonitorName~, ~Get*Name~, the whole ~Text*~ family, ...
  return raylib-internal/static buffers the caller must NOT free.
  The ~Load*~ family (~LoadFileData~, ~LoadImageColors~,
  ~LoadFontData~, ~LoadCodepoints~, ~LoadWaveSamples~,
  ~LoadMaterials~, ~LoadModelAnimations~, ~CompressData~, the
  ~Compute*~ hashes, ...) return heap the caller owns but frees via
  the matching ~UnloadX~ / ~MemFree~, NOT via ~free()~.  Either way
  til must not auto-free, so ~ref~ (til does not own) is correct.
  Promoting these to owned (~returns T~) would make til emit a
  generic ~free()~ at scope end -- a double-free against the user's
  ~UnloadX~, and wrong anyway for compound unloads
  (~UnloadModelAnimations~ frees nested arrays; ~free()~ wouldn't).

- *~Unload*~ / ~MemFree~ args are borrowed (or ~shallow~ for
  by-value structs).*  This is the correct mirror of the ~ref~
  returns: the value isn't til-owned, so there's no ownership to
  transfer with ~own~.  By-value resource structs (~Texture~,
  ~Image~, ~Sound~, ~Font~, ~Model~, ~Wave~, ~Music~, ...) pass
  ~shallow~; raylib frees their internal GPU/heap state.  No til
  pointer ownership is involved.

- *No arg needs ~own~.*  raylib copies or borrows every pointer arg
  (e.g. ~Load*FromMemory~ copies ~fileData~; ~UpdateTexture~ copies
  ~pixels~); none stores or frees a caller buffer in a way that maps
  to til's ownership-transfer.

*** Watch-list: ambiguous ~returns Dynamic~

A handful of functions return raw ~void *~ / ~void **~ as
~Dynamic~, which is til's *owned* raw-pointer type.  None has a til
caller today (no ~src/modes/gui.til~ wrapper), so there is no live
bug, but a wrapper author MUST pick the right shape per function
rather than letting til treat the result as owned:

- ~MemAlloc~, ~MemRealloc~: genuinely owned (caller frees via
  ~MemFree~).  ~Dynamic~ is right.
- ~GetWindowHandle~: returns the platform/GLFW window handle --
  *borrowed*, must never be freed.  A wrapper should treat it as a
  borrowed pointer, not an owned ~Dynamic~.
- ~TextSplit~: returns ~char **~ into raylib's internal static
  buffer -- *borrowed*, do not free.
- ~LoadTextLines~: allocates; freed via ~UnloadTextLines~ (compound,
  not a plain ~free()~), so a wrapper must route cleanup through
  ~UnloadTextLines~, not til's owned-Dynamic auto-free.

tinyfd (~tinyfd_*Dialog~ -> ~returns shallow Option(ref I8)~: a
static buffer, or None on cancel -- #321) and libffi
(~ffi_closure_alloc~ -> ~Dynamic~, freed via ~ffi_closure_free~)
follow the same rules and were spot-checked clean.
