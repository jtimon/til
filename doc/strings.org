* String Design in TIL

** Internal Representation

#+begin_src til
Str := struct {
    own c_str : I8 = 0   # pointer to buffer (C `char *`)
    count : USize = 0    # content length in bytes
    cap : USize = 0      # allocated capacity, or sentinel
}
#+end_src

The ~cap~ field encodes ownership. It is a ~USize~, so the sentinels are
the two largest values, not negatives, and "owned" is ~cap < CAP_VIEW~:

| cap                  | meaning                                  |
|----------------------+------------------------------------------|
| cap < CAP_VIEW       | owned buffer, cap = allocated size       |
| CAP_LIT ((USize)-1)  | static string literal wrapper and C data |
| CAP_VIEW ((USize)-2) | borrowed view into another Str's buffer  |

For owned strings, ~count <= cap~ and the byte at ~c_str[count]~ is a
NUL -- every allocating path reserves count+1 and writes it, which is
what lets an owned ~.c_str~ cross the C boundary (doc/ffi.org). For
literals and views, ~count~ is the content length and ~cap~ is the
sentinel; a literal is NUL-terminated (it is a C string constant), a
view is NOT -- its next byte is more of the base buffer.

Named constants ~CAP_LIT~ and ~CAP_VIEW~ are defined in str.til (globally
available via core import).

** String Creation Patterns

*** Literal Assignment
#+begin_src til
s := "hello"   # count=5, cap=CAP_LIT in codegen (points to static const)
#+end_src

In codegen, literal data lives in static const storage and the Str wrapper is
static too -- no malloc for either. In interpreter, data is strndup'd with
cap=CAP_LIT (also not freed by til delete).

*** Owned (from operations)
#+begin_src til
s := a.concat(b)   # count = a.count + b.count, cap = count (owned)
s := a.clone()      # owned copy
#+end_src

*** View (from substr)
#+begin_src til
view := s.substr(2, 3)   # count=3, cap=CAP_VIEW, points into s.c_str
owned := view.clone()     # materializes view into owned string
#+end_src

Zero-copy but can dangle if source is freed or realloced. No borrow
checker -- accepted risk. Call ~.clone()~ when you need ownership. Both
backends return the same view since #366; the interpreter used to hand
back an owned copy instead.

*** Pre-sized with Capacity
#+begin_src til
s := Str.with_capacity(100)   # count=0, cap=100
s.push_str("hello")           # count=5, cap=100 (in-place, no realloc)
#+end_src

** Deletion Semantics

#+begin_src til
delete := func(own self: Str, call_free: Bool = true) {
    if self.cap < CAP_VIEW { free(own self.c_str) }
    if call_free.and(self.cap.neq(CAP_LIT)) { free(own self) }
}
#+end_src

A sentinel cap (CAP_LIT or CAP_VIEW -- the two largest USize values, so
the test is ~cap < CAP_VIEW~, not a sign check) means the data is not
owned: skip the data free. CAP_LIT also means the wrapper is static, so
skip the wrapper free too.

** Clone

Clone always creates an owned copy regardless of source cap:

#+begin_src til
clone := func(val: Str) returns Str {
    if val.count == 0 { return "" }
    new_data : I8 = malloc(val.count + 1)
    memcpy(new_data, val.c_str, val.count)
    memset(ptr_add(new_data, val.count), 0, 1)
    return Str(c_str = new_data, count = val.count, cap = val.count)
}
#+end_src

The count+1 allocation and the NUL write are load-bearing, not
politeness: they are what makes ~view.clone().c_str~ safe to hand to a C
string parameter (doc/ffi.org, issue #343), and #343's ext-call boundary
check reads exactly that byte.

** push_str on views/literals

~push_str~ panics when ~cap >= CAP_VIEW~ (view or literal). Views and
literals are borrowed/static data -- mutating them is not allowed. Call
~.clone()~ first to get an owned copy, then push_str on that.

** Optimized Builders

The hot string builders now use ~Str.with_capacity(...)~ directly:

- ~format(parts...)~
- ~concat(a, b)~
- ~replace(self, from, to)~
- ~join(parts, sep)~

The intended pattern is:

#+begin_src til
out := Str.with_capacity(total_len)
out.push_str(part1)
out.push_str(part2)
return out
#+end_src

This keeps the API surface simple and avoids custom malloc/copy loops in the
individual helpers.
