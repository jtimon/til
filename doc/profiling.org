* Profiling the compiler and test suite

This is the workflow guide. Dated measurements, historical profiles, and
optimization decisions live in [[./optimizations.org][Optimization measurements]].

** Read the chart correctly

~doc/totals.csv~ is generated by successful suite runs. A rerun replaces the
row for the current HEAD. The local merge workflow may record a candidate's
result under its parent HEAD before committing the result.

~img/totals.svg~ shows only the last ten rows, without X-axis labels. Its time
series share an axis, so the larger summed times can hide small wall-time
changes. Read the CSV when comparing particular changes.

- ~wall~: elapsed suite time through the last non-self test. It excludes the
  self-translation benchmark and the build steps before ~bin/tests~ starts.
  It is not the elapsed time of the entire ~make test~ command.
- ~self~: the separately measured compiler self-translation benchmark. It
  runs alongside the other tests and can finish after ~wall~ stops.
- ~inte~, ~comp~, ~run~: summed interpretation, compilation, and execution
  times for the runner's ~both~ tests, not elapsed suite time or every build
  test. Reorganizing build-only rows need not lower these curves.
- ~mem-inte~, ~mem-comp~, ~mem-run~: sums of individual phase peaks, not
  simultaneous RAM usage. ~self-mem~ belongs to self-translation alone.
- ~peak-mem~: sampled maximum of summed RSS across active non-self test
  process trees, at 10 Hz. Concurrency affects this value.

** Compare changes under controlled conditions

- Use one source base, varying only the intended change. Record the revision,
  compiler paths and versions, dirty source changes, host, target, USize,
  optimization/CPU options, ASAN settings, and suite concurrency.
- Run with other builds and agent sessions stopped. One active session still
  leaves ordinary OS scheduling, frequency, and filesystem-cache variation.
- Decide warm-up policy before collecting results. Alternate baseline and
  candidate order, run each several times, and report all samples, medians,
  ranges, and paired differences. A small median difference within the run
  variation does not establish a win or regression.
- Keep test inputs fixed for a compiler A/B comparison. The suite invokes
  both ~bin/til~ and its selected ~--til-bin~ compiler; switching only the
  latter does not compare the complete build pipeline.
- Separate frontend, C compilation/linking, and program execution when finding
  the bottleneck. Faster individual jobs need not shorten the parallel tail.
- Verify correctness and output/diagnostic equivalence where applicable.
  Reduced coverage, different ASAN settings, and stale outputs are not speedups.

Create ~tmp/~ before capturing logs. Keep commands foreground and sequential.
For the normal clean verification run on the local machine:

  : systemd-run --user --scope -p MemoryMax=64G bash -c 'make clean && make test' > tmp/test.log 2>&1

The compiler macro-benchmark is ~time bin/til build src/til.til~. Keep its
time distinct from the suite's translation-only ~self~ measurement. See
[[./self.org][Self-hosting build]] for bootstrap and two-pass requirements.

** Function and allocation profiling

~--prof~ instruments the OUTPUT program with ~-finstrument-functions~. To
profile the compiler, build an instrumented compiler and run that binary:

  : bin/til build --prof -o bin/til_prof src/til.til
  : TIL_PROF_TOP=25 bin/til_prof translate test/maps.til > tmp/profile.log 2>&1

Use ~src/til.til~ for the full self-host frontend, or a smaller representative
fixture while iterating. ~TIL_PROF_TOP=0~ prints every row. The stderr tables
report function call counts, exclusive ~self_ms~, inclusive ~total_ms~, and
(without ASAN) allocation counts and bytes charged to the active function.

Call counts are the most useful exact signal. Timing tiny leaf functions is
distorted by the two clock reads per call; profiled time is not a normal-build
benchmark. Allocation bytes measure traffic, not peak/live heap. Allocation
wrapping is omitted when ~--prof~ and ~--asan~ are combined; CPU profiling
still works. Counters are not locked, so exact counts assume single-threaded
execution. ~--prof~ is ignored when cross-compiling to Windows.

On Linux, static generated names resolve through the executable's existing
ELF ~.symtab~; exported names use ~dladdr~ / ~-rdynamic~. No symbol sidecar is
needed. Some helpers are inlined in ordinary builds but still have conceptual
entries in instrumented profiles; use uninstrumented instruction counts to
assess those changes.

*** Existing convenience driver

  : bin/til run examples/profile.til [--prof|--massif] [target.til] [top_n]

Defaults are ~--prof~, ~test/maps.til~, and 25 rows. The driver rebuilds
~bin/til_prof~ when it is missing or older than ~bin/til~; rebuild ~bin/til~
after source edits before relying on that reuse.

  : bin/til run examples/profile.til src/til.til 40
  : bin/til run examples/profile.til --massif test/maps.til

Massif uses the existing ~bin/til~ and requires ~valgrind~ and ~ms_print~. It
reports peak/live heap and writes the full report to ~tmp/profile_massif.txt~.
Use the allocation table for churn; use Massif for memory retained at once.

** Sampling and instruction counts

Compiler C symbols retain recognizable til names, making C-level profiles
useful across source-file refactors. Default ~--opt=0~ builds retain debug
information; record any changed optimization flags with the measurement.

*** perf (Linux, when permitted)

  : perf record -F 997 -g --call-graph dwarf -o tmp/perf.data -- bin/til build -o tmp/prof_til src/til.til
  : perf report -i tmp/perf.data --stdio --sort=overhead -n

For a flamegraph, with Brendan Gregg's FlameGraph scripts installed:

  : perf script -i tmp/perf.data | stackcollapse-perf.pl | flamegraph.pl > tmp/selfhost.svg

Wide frames show where samples accumulate. If host permissions prohibit perf,
use the function profiler or callgrind rather than changing machine settings
as part of an optimization experiment.

*** callgrind

  : valgrind --tool=callgrind --callgrind-out-file=tmp/callgrind.out bin/til build -o tmp/prof_til examples/plot.til
  : callgrind_annotate tmp/callgrind.out

Instruction counts avoid sampling noise but runs can be 20-50 times slower;
start with a smaller fixture. Kcachegrind provides a call-graph view.
~callgrind_annotate --tree=caller~ has misattributed callers on the -O0
compiler (#397). Check the raw ~fn=~, ~cfn=~, and ~calls=~ records when caller
attribution matters.

Current direct ~translate~, ~build~, and ~run~ commands regenerate outputs
(#406). Older revisions with #170's timestamp shortcut require
~--force-rebuild~ when measuring compilation rather than cache hits.

Use these profiles to identify concrete Map/Vec/Str and AST call sites before
changing them. ~examples/bench_hashmap.til~ is the focused Map/HashMap
microbenchmark; the compiler profile determines whether that work matters to
the workload being optimized.
