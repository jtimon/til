* Profiling the self-host build (issue #237)

The canonical macro-bench is:

  : time bin/til build src/til.til

Is the compiler getting slower OVER TIME? That is already tracked without a
separate tool: every green ~make test~ on the merger's machine records the
~self_translate~ benchmark (~bin/til translate src/til.til~, the suite's
"self" row) into doc/totals.csv, one row per commit, plotted as the "self" /
"self-mem" series in img/totals.svg. (A separate best-of-3 harness --
~make profile~ writing doc/selfhost_build.csv -- used to duplicate that
per-commit series and was removed.)

This doc covers the other question: WHERE does the time actually go?

** Sample profile: where the time goes

~bin/til build~ compiles the generated C with ~-g~ and no ~-O~, so there is
no inlining and every til function shows up as a C symbol with the same
name (Map_set, Vec_push, Str_eq, the typer_* helpers, ...). A plain C-level
profile therefore reads back at the til source level and survives refactors
that move code between C translation units -- exactly what #237 asks for.

*** Option A: perf + flamegraph (Linux, when perf is available)

  : perf record -F 997 -g --call-graph dwarf -o tmp/perf.data -- \
  :     bin/til build -o tmp/prof_til src/til.til
  : perf script -i tmp/perf.data | stackcollapse-perf.pl | \
  :     flamegraph.pl > tmp/selfhost.svg

Open tmp/selfhost.svg in a browser; the widest frames are the hot functions.
stackcollapse-perf.pl / flamegraph.pl ship with Brendan Gregg's FlameGraph
repo. perf may need ~sysctl kernel.perf_event_paranoid=1~.

Quick text top-N without the flamegraph tooling:

  : perf record -F 997 -g -o tmp/perf.data -- bin/til build -o tmp/prof_til src/til.til
  : perf report -i tmp/perf.data --stdio --sort=overhead -n | head -40

*** Option B: callgrind (portable, no perf permissions needed)

  : valgrind --tool=callgrind --callgrind-out-file=tmp/callgrind.out \
  :     bin/til build -o tmp/prof_til src/til.til
  : callgrind_annotate tmp/callgrind.out | head -60

callgrind counts instructions (deterministic, no sampling noise) but runs
~20-50x slower than native, so prefer a smaller target while iterating, e.g.
examples/plot.til. Open tmp/callgrind.out in kcachegrind for a call-graph view.

** Picking hot Maps / alloc offenders

Use the flamegraph / callgrind top-N to find which Map / HashMap / Vec call
sites dominate, then point #234 / #235 / a HashMap-for-X swap at the concrete
callsite rather than guessing. examples/bench_hashmap.til remains the
microbench for Map vs HashMap in isolation; this profile tells you which of
those the compiler actually leans on.

** Per-function profile: ~til build --prof~

Builds the program with gcc's ~-finstrument-functions~ so the binary records,
per function, the exact call count and inclusive/self time, and dumps a top-N
table to stderr at exit. It mirrors ~--asan~: the flag instruments the OUTPUT
binary, so to profile the compiler you build the compiler with ~--prof~ and
then run it (just like bin/til_asan):

  : bin/til build --prof -o bin/til_prof src/til.til
  : bin/til_prof translate src/til.til         # profile the self-host front end
  : bin/til_prof translate test/maps.til        # ... or a smaller, faster input

At exit the run prints to stderr. For example, the compiler translating
test/maps.til (1413 functions instrumented; snapshot 2026-07, after
fieldless throw payloads #316, lazy Vec.new #291, the interpreter scope
pool, the redundant-expect removal, and single-compare eq for
payload-free enums), abridged:

inclusive total.

and prints a second table, ranked by bytes allocated -- same run, abridged:

Bytes are charged to whichever instrumented function is on top of the call
stack when malloc runs. Str_clone is the dominant allocator (string copies
-- interning again); the Vec__Expr entries are AST body rebuild/clone
traffic. Array__Str_new, previously #4 here at 586k calls / 20MB, is gone:
it was the variadic message array that every
~expect(x.is_null().not(), ...)~ built per call even on success (a
variadic FUNCTION argument is built eagerly at the call site; a panic
behind an ~if~ is not) -- those redundant null-guard expects were removed.
TokenType_eq, previously 4.3% of instructions (callgrind), is likewise
gone: eq for a payload-free enum now emits a single is_n tag compare
instead of a per-variant chain.

Set ~TIL_PROF_TOP=N~ for a different row count (0 = all). Names are the C
symbols, which are the til function names -- the build links ~-rdynamic~ and
the profiler resolves addresses with dladdr -- so the profile reads at the til
source level and survives refactors that move code between C files. That is
the point: it tells you which til functions and which Map/Vec/Str helpers the
compiler actually leans on.

Caveats: the call counts are exact and the most useful signal. ~self_ms~ of
tiny hot leaf functions (I64_add, Str_get) is inflated by the two
clock_gettime calls the instrumentation adds per call, so read self time as a
rough guide, not a microbenchmark. The instrumentation slows the run
substantially (every call hits a per-thread stack + the clock), so prefer a
representative input over the full ~translate src/til.til~ when iterating, and
expect a profiled self-host build to take noticeably longer than the bare one.
Linux only (the runtime in src/c/ext.c is ~#ifndef _WIN32~); ~--prof~ is
ignored when cross-compiling to Windows. The allocation table needs malloc
wrapping, which asan owns, so it is omitted when ~--asan~ and ~--prof~ are
combined (CPU profiling still works). The call stack is per-thread but the
counters are not locked, so the numbers are exact only for the single-threaded
self-host build.

** One-command driver: ~examples/profile.til~

The recipes above are a few steps each (build the instrumented compiler, set
TIL_PROF_TOP, run it; or run valgrind then ms_print). ~examples/profile.til~
wraps them so a profile is one command:

  : bin/til run examples/profile.til [--prof|--massif] [target.til] [top_n]

Defaults: method ~--prof~, target ~test/maps.til~, top_n 25.

~--prof~ (default) builds the instrumented compiler and runs it, printing the
per-function call/self-time and bytes-allocated tables -- the churn ranking that
found the Type_Primitive allocator. The instrument build is the slow step, so
~bin/til_prof~ is CACHED: it is rebuilt only when missing or older than
~bin/til~. Build it once, then profile many targets fast:

  : bin/til run examples/profile.til                # test/maps.til, top 25
  : bin/til run examples/profile.til src/til.til 40 # full self-host front end, top 40

~--massif~ runs valgrind massif on the EXISTING ~bin/til~ -- no instrumented
rebuild, so it is fast -- and prints the peak-heap snapshot's allocation tree
(the full ms_print report is saved to ~tmp/profile_massif.txt~):

  : bin/til run examples/profile.til --massif test/maps.til

Massif ranks PEAK/LIVE heap (what is held at once), not churn. Use it for "what
is held live"; use ~--prof~ for churny allocators that allocate and free fast
and so never dominate a peak snapshot -- the class Type_Primitive belonged to.
The ~--massif~ mode needs ~valgrind~ and ~ms_print~ on PATH.

** Status

All five #237 stretch goals shipped: the sample-profile recipe (perf /
callgrind), a build-time regression harness (~make profile~ -- since retired
as redundant with doc/totals.csv's per-commit "self" series), the
per-function ~--prof~ CPU/call profiler, the allocation profile (the second
~--prof~ table), and this hot-functions table. The table above is meant to be
refreshed each release and is where #234 / #235 / a HashMap-for-X swap can
point at a concrete callsite.
