* Modules and Imports

Each Til source file is a module. Imports load public declarations from another
file; ~priv~ keeps implementation details inside their declaring file.

** A library file

Put reusable declarations in a ~mode lib~ file. For example, ~math.til~ could
contain:

#+begin_src til :doctest-file modules/math.til
mode lib

priv square := func(n: I64) returns I64 {
    return n * n
}

sum_of_squares := func(a: I64, b: I64) returns I64 {
    return square(a) + square(b)
}
#+end_src

Declarations are public by default. Importers can call ~sum_of_squares~, while
~square~ remains available only inside ~math.til~.

** Bare imports

A bare import adds the selected file's public declarations to the importing
file's scope:

#+begin_src til :doctest-file modules/app.til :doctest-run
mode script
import("math")

assert_eq(I64, sum_of_squares(3, 4), 25)
#+end_src

Import paths omit the ~.til~ extension. Ordinary paths are relative to the
importing file, not the current working directory.

** Core and standard library

The prefixes ~core/~ and ~std/~ are reserved for the support tree belonging to
the compiler being run. For example, an application anywhere on disk can use:

#+begin_src til
mode cli
import("std/sys", process_id)

main := proc() {
    println(process_id().to_str())
}
#+end_src

This works with a checkout compiler and an installed compiler, including a
non-default installation prefix. It needs no neighboring checkout or copied
standard library. Nested project modules use the same spellings.

Local ~std/~ and ~core/~ directories cannot shadow these reserved imports.
Use ~import("./std/sys")~ or ~import("./core/str")~ to explicitly select a
project-local module. A missing reserved module is an import error; resolution
does not retry in the project or another compiler's support tree.

Core is loaded automatically: strings, numeric types, arrays, vectors, maps,
sets, options, ranges, tuples, memory helpers and basic I/O are available without
an import. Explicit core imports are useful for naming a dependency or a
namespace, for example ~strings := import("core/str")~ followed by
~strings.Str.clone("x")~. Explicit imports and automatic loading use the
same canonical file identity, so they do not duplicate types, definitions or
initialization. The usual unused-import checks still apply.

For existing applications, change ~import("../src/std/sys")~ to
~import("std/sys")~ (likewise for ~core/~). Legacy relative paths remain
supported: they first search relative to the importing file, then relative to
the compiler's ~lib/~ directory. Unlike reserved imports, that historical
spelling can still select a matching project-local file. On Unix, its
~lib/../src/~ fallback also requires the ~lib/~ directory to exist (for example,
after installing a library); a fresh compiler-only installation does not create it.
Natural imports work in either case.

** Namespace imports

Assign an import when its declarations should stay behind a local namespace:

#+begin_src til :doctest-file modules/namespace_app.til :doctest-run
math := import("math")
answer := math.sum_of_squares(3, 4)
assert_eq(I64, answer, 25)
#+end_src

This is useful when libraries expose similar names or when the module name
helps the call read clearly.

** Selective imports

Names after the path import only those public declarations:

#+begin_src til :doctest-file modules/selective_app.til :doctest-run
import("math", sum_of_squares)
answer := sum_of_squares(3, 4)
assert_eq(I64, answer, 25)
#+end_src

An import cannot expose a ~priv~ declaration. Top-level privacy is a cross-file
boundary; struct fields and namespace members use the stricter rules described
in chapter 7. The full visibility table is in
[[file:../concepts/qualifiers.org::*Visibility (priv keyword)][the qualifier reference]].

Modes remain per file. An application may therefore import several ~mode lib~
files while its entry file uses ~mode script~, ~mode cli~, or ~mode gui~.
