* Self-hosting build

  See the Makefile header comments and ~make help~ for the full
  reference.

** Where the build lives

  Build policy is a til program: ~make.til~, compiled to ~bin/make~
  (issue #345). Which artifact depends on what, which command produces
  it, and what differs per host are ordinary til code -- functions that
  call the steps they depend on, compare mtimes, and run commands.

  The Makefile owns only the part a til program cannot do for itself,
  produce the compiler that compiles it:

  1. build the vendored libffi that the checked-in compiler C links
  2. copy HEAD's ~boot/~ and C runtime (~src/self/codegen/~) out of git, compile ~bin/til_boot~
  3. compile ~make.til~ into ~bin/make~ with it
  4. run ~bin/make~ once with every requested goal

  So ~make test~ and ~bin/make test~ are the same build. Both entry
  points stay supported: ~bin/make~ is the direct one (real options,
  e.g. ~-j4~ or ~--riscv32-cc=<path>~), ~make~ is the compatibility and
  clean-checkout one, and it passes ~J~, ~RISCV32_CC~, ~EMCC~, ~EMAR~
  and ~EMRANLIB~ through unchanged.

  ~bin/make~ keeps itself current: if ~make.til~ (or the std/core/C
  sources it is built from) is newer, it renames the running program
  aside, compiles the replacement with ~bin/til_boot~, restores the old
  one if that fails, and otherwise re-runs it with the same arguments.
  ~bin/make~ is a generated artifact under ~bin/~ -- never committed,
  never installed.

  Note that ~bin/til_boot~ links libffi and nothing else vendored: no
  raylib, tinyfd or nng function appears in ~boot/til.c~ or the C runtime.
  Those libraries are built by ~make.til~, for ~bin/til~, which does
  link them.

** Key concepts

  - ~bin/til_boot~: built entirely from the last commit via git.
    Uses HEAD's boot/ AND HEAD's C runtime in src/self/codegen/. Completely isolated from
    any uncommitted changes. Always safe. Never fails.
  - ~bin/til~: built by til_boot from current sources. The resulting
    binary IS self-hosted (its compilation logic comes from the
    current .til sources), but the C it just emitted into boot/ was
    generated using HEAD's logic.
  - ~boot/~: generated C, committed for til_boot. Regenerated every
    build so the next commit's til_boot has current code.

** Command output paths and freshness

  ~translate~, ~build~ and ~run~ of a C-backend executable reuse existing
  outputs (#442). The emitted C and its forward header are current when
  newer than every loaded unit, mode file and the compiler binary, and the
  C ends with this invocation's translation stamp (compiler, source,
  output path, target, layout, CPU profile, loaded units); a current
  translation skips preparation and emission. The executable is current
  when newer than that C, the C runtime, link_c sources and the headers
  they include, linked archives and the compiler, and it carries this
  invocation's executable stamp (ext.c's ~til_build_stamp~: the
  translation stamp plus every compile option). A timestamp alone cannot
  establish which program or options produced a file (#406); the stamps
  do. ~file_mtime~ reports nanoseconds; an input as new as its output
  (one coarse kernel clock tick) counts as newer. Programs declaring a
  value macro, translations under ~TIL_GC_AUDIT~ (whose dump prints while
  translating), libraries, themes, other backends and ~test~ always
  regenerate, and ~--force-rebuild~ skips reuse. The build
  program's explicit dependency graph is separate from this CLI behavior
  and still decides which build steps need to run.

  Default executable and backend-source paths preserve source directories:
  ~foo/main.til~ produces ~bin/foo/main~ and ~gen/til/foo/main.c~ (plus its
  forward header); theme output uses ~gen/til/foo/main.el~. ~-o~ and ~-c~ override their
  respective paths. Library names, bindings and ~gen/lib/~ keep their
  existing naming contract.

  Source paths are canonicalized first. Absolute paths inside cwd use
  the same relative hierarchy; outside sources retain the absolute
  hierarchy below the output root, with the leading slash and Windows
  drive colon removed. Thus ~..~ never escapes ~bin/~ or ~gen/~.

  Bootstrap steps explicitly select ~bin/til~ and ~gen/til/til.c~ so the
  established boot regeneration paths work with old and new compilers.

** Shared program builder

  After CLI validation and the common ~prepare_program~ pass, C, HolyC, MLIR
  and FASM commands enter ~src/self/builder.til~'s ~build_program~ lifecycle:
  derive paths, create output directories, emit source, compile/assemble, then
  execute for ~run~. The compiled half of ~test~ uses the same lifecycle with
  executable output forced for library-mode test sources. CLI result handling
  and interpreter/lexer teardown are shared too.

  Backend differences are build hooks rather than separate command drivers:

  - ~derive_build_paths~ chooses the primary source path. MLIR also retains
    its existing ~gen/til/*.c~ / ~*_forward.h~ runtime-support paths.
  - ~translate_ast~ dispatches to the emitter: C or HolyC according to target
    language, or the selected MLIR/FASM backend. MLIR emits its C-core bridge
    before IR through the existing runtime emitter.
  - ~compile_ast~ dispatches to C/library compilation, ~compile_mlir~'s LLVM
    pipeline and library linking, or ~compile_fasm~'s assembler invocation.
    HolyC compilation still belongs inside TempleOS; theme is translation-only.
  - ~run_artifact~ executes the produced artifact and propagates its status,
    including the existing Node/wasm and ASAN child-environment handling.

  ~builder.til::fasm_prepare~ prepares the optional vendored assembler for the
  vendor/build/install workflows; there is no separate FASM build module.
  Source lowering and emitted instructions remain in the codegen modules.
  Existing CLI restrictions, output names and backend-specific library reporting
  are preserved. The backend options and ~test/build_outputs.til~ check source
  hierarchy, generated-file reporting, MLIR bridge files and early rejection;
  native integration drivers exercise the actual toolchains and execution.

** USize defaults and source-level configuration direction

  ~USize~ describes counts, lengths, capacities and indices; ~UPtr~ describes
  pointer-width arithmetic and always follows the target's pointer width.
  ~--usize~ selects the whole layout (one layout flag, below). On a 64-bit C
  target the default is ~--usize=32~, the compact layout: U32 container
  widths and own pointers in the #313 cage; ~--usize=64~ is the native
  layout. 32-bit targets are U32 either way. Mode theme and HolyC output
  (TempleOS) follow the target, the MLIR backend has the native layout only,
  and interpretation defaults to the running compiler's own layout (a
  compiler built ~--usize=64~ interprets at 64).

  The compiler's own build spells ~--usize=32~ in make.til although it is
  the default, so the compiler's layout does not depend on the default of
  whichever compiler runs that line.

  The agreed design direction is to express project configuration through
  source-level calls, analogous to ~link(...)~, rather than requiring users
  to repeat til-specific command-line options. Projects should be able to
  select such settings under their own compile-time options. Exact directive
  names, syntax and the project-option mechanism are not yet specified or
  implemented; this direction does not remove existing CLI flags.

  A USize-width directive cannot be an ordinary runtime call. It changes
  container layout and the program's ABI, so configuration must be resolved
  before type checking, layout calculation and constant evaluation that
  depends on those layouts. The early configuration evaluation must not
  depend on the width it is deciding: selecting USize using a condition
  that already depends on USize would be circular.

  Resolve one width for the compilation. An imported library cannot silently
  choose a different width within it; incompatible requirements must produce
  an error, and separately compiled libraries must satisfy the matching ABI.
  The precise resolution rules, including interaction with existing CLI
  overrides, need to be specified before implementing the directives.
  Native-width defaults should remain usable without configuration calls.

  History: the first attempt at a 32-bit USize (the ~wip_u32~ branch, when
  the compiler was still C) changed every container width atomically and
  could not bootstrap: the committed compiler folded ~Str.size()~ from its
  own U64 layout into literals that failed to typecheck against the U32
  sources, and no single commit could be self-consistent. What delivered it
  was making the width target-driven (#192), then overridable (#309), with
  the two devices this file describes: the preparation/use split (or the
  two-pass build) for emit-side changes, and the width pin in the generated
  headers, so a flag-less boot compile reproduces the layout its artifact
  was emitted at. The same two devices carried the cage (#313).

** Decided: one layout flag (~--usize~ selects the own-pointer storage too)

  Decision (2026-11-01): the two layout flags collapse into one. ~--usize=32~
  means the compact layout -- U32 container widths AND, on a 64-bit C
  target, own pointer fields stored as 32-bit cage offsets (#313);
  ~--usize=64~ means the fully native layout -- U64 widths and native
  pointers. Two layouts instead of four. The two combinations this drops
  are worthless: U64 widths with compressed pointers pads back to the
  native size, and U32 widths with native pointers was only ever the
  transition state before the cage became the default. 32-bit targets are
  untouched: their pointers are 32-bit already and the cage never applies
  there, so ~--usize~ keeps its current meaning for them. ~--usize=32~ is
  the default on 64-bit C targets -- for programs too, which had defaulted
  to U64 widths (only the compiler's own build was U32), so the cage stays
  their default. ~--cptr~ is gone (it was days old and the language is
  experimental); like any unknown flag, the driver now reads it as the
  source path and fails to open it.

  Implemented in one "Two-pass: " commit:

  - ext.h defines ~TIL_CPTR32~ from ~TIL_USIZE32~ on a 64-bit target, so
    the headers pin the USize width alone and the driver passes only the
    USize define (programs, libraries, the interpreter's FFI .so).
  - src/til.til resolves the width: an unset ~--usize~ on a 64-bit C
    target (not mode theme, not HolyC) is 32; ~lp.cptr32~ is a 32-bit
    width there under the C backend (FASM lays out its own native pointers
    at either width, without ext.c).
  - The MLIR backend emits U32 widths with native pointers and allocates
    with libc, so it cannot share a caged runtime: it has the native layout
    only. It defaults to ~--usize=64~ and refuses an explicit ~--usize=32~.
  - Interpretation defaults to the running compiler's layout: a library it
    loads shares its allocator, so ~ffi_check_lib_layout~ accepts only a
    library, and a program, at the binary's own layout.
  - ~abi_layout_id~ is the width alone (~U32~ / ~U64~), in runtime, core
    and library names and in the exported ~til_<lib>___til_abi_layout~.
  - make.til: ~check_cptr64~ and ~check_native64~ are gone. The width
    regressions (test/usize64*.til, test/usize32_sizes.til -- the old
    cptr32_sizes -- and the cross-width self-translate) run in every suite
    target as ~layout_regressions~; ~check_usize64~ adds the whole suite
    through a compiler built ~--usize=64 --asan~ (bin/til_usize64), every
    program built ~--usize=64~. CI keeps that one opt-out job.

** Pointer-compression cage (~--usize=32~)

  The compact layout (~--usize=32~, the default on 64-bit C targets; issue
  #313) stores every ~own~ pointer field as a 32-bit byte offset into one
  4GB allocation region, the cage. ~--usize=64~ is the native layout; a
  32-bit target, mode theme, HolyC output and the FASM backend are native
  at any width, and MLIR has the native layout only. ~ref~, ~Dynamic~ and
  callable fields stay native pointers. Str and Vec are 12 bytes instead of
  24. The 4GB is a hard per-process heap cap: a program that needs more
  builds ~--usize=64~. The language is experimental, so this default is
  chosen by measurement and can change again before a versioned release.

  The driver passes ~-DTIL_USIZE32~ or ~-DTIL_USIZE64~ on every C compile,
  and the generated headers carry the same pin as a default, so a flag-less
  compile of a checked-in artifact -- the boot compile of boot/til.c --
  builds ext.c for the layout it was emitted at. ext.h derives ~TIL_CPTR32~
  from ~TIL_USIZE32~ on a 64-bit target, and under it:

  - routes ~malloc~, ~calloc~, ~realloc~ and ~free~ -- the names generated
    code, ext.c and link_c code call -- to the cage allocator in ext.c.
    Exhausting the cage panics, and so does freeing a pointer the cage did
    not allocate; memory libc allocates for itself (~realpath(p, NULL)~) is
    released with ~(free)(p)~.
  - makes ~TIL_OWN_PTR(T)~, the spelling every generated struct uses for an
    own field, a ~{U32 off}~ struct instead of ~T *~. The offset counts bytes
    (a Str view points at any byte of its buffer), 0 is NULL. Loads and
    stores go through ~TIL_OWN_GET(T, field)~ / ~TIL_OWN_SET(field, p)~,
    which are plain accesses natively; a forgotten accessor is a C type
    error, never a silent truncation. User C (link_c, FFI libraries) that
    touches own fields uses the same macros.

  The generated C is otherwise the native one, except where a pointer had to
  be a link-time constant: string literals (pooled, __LOC__ and the rest) and
  precomputed sequence templates are copied into the cage, by constructors or
  on first use. ~Str.from_c_str~ copies the C string into an owned Str, since
  argv, getenv results and C library strings are not cage memory.

  One cage per process. A process can hold several copies of ext.c -- the
  program's own and the shared runtime of every mode-lib library it loads
  (a TilVm plugin, a library-namespaced .so) -- and they exchange values,
  so an offset must mean the same everywhere: the executable's plain
  ~til_cage_base~ is the slot every copy attaches to (dlsym(RTLD_DEFAULT),
  a module walk on Windows) when its image loads; a copy with no til
  executable around it (a .so Python loaded) uses its own. The allocator's
  bookkeeping lives inside the cage, at the base, so copies sharing a base
  share the allocator; a magic word rejects a cage laid out by another
  revision. Library copies keep their per-library symbol names, so a
  process holds one definition of the plain name. The ASAN shadow belongs
  to the cage too: a copy built without ASAN in an ASAN process (an ASAN
  interpreter loading a non-ASAN library) poisons and unpoisons through
  the sanitizer's entry points it finds in the process
  (test/ffi_cage_shadow.til).

  The layout is not negotiable across a library boundary: a library's
  values cross an interpreted call in the interpreter's layout, and the
  library shares the running binary's allocator, so a library loads only
  at the binary's own layout, into a program interpreted at it. Every
  library exports the layout it was built for (~til_<lib>___til_abi_layout~,
  ~U32~ or ~U64~, the same ~abi_layout_id~ that names its shared runtime),
  and the interpreter refuses another one when it loads the library, naming
  the ~--usize~ to rebuild it with (test/ffi_lib_layout.til). A library
  without the symbol is a C library, or one from a compiler before the
  check.

  Leaks. LeakSanitizer knows only libc's chunks, so it cannot see a leaked
  til object any more. The cage keeps its own live count (block bytes handed
  out and not freed, the literal copies apart), and in an ASAN build the copy
  that owns the cage reports at exit the live blocks nothing reaches: on
  Linux it scans every loaded image's writable segments, the exiting
  thread's stack and registers, and the reached blocks, for native pointers
  and 4-byte offsets, interior ones included -- the conservative
  reachability LeakSanitizer applies, so a global's storage or a template
  built on first use is not a leak but a lost allocation is. The report
  exits 1 like LeakSanitizer under ASAN and is silenced by the same
  ~detect_leaks=0~ (test/leak_report.til). ASAN's use-after-return
  detection stays on: the locals of a program that exits from deep inside
  sit in ASAN's fake frames, which the scan reaches through the frame
  addresses the real stack holds (~__asan_addr_is_in_fake_stack~ confirms
  each and gives the frame's bounds). ~TIL_LEAK_PROBE~'s never-freed total
  adds the cage's live bytes to the sanitizer's.

  The compiler itself is a cage build: make.til spells ~--usize=32~ on
  every build of src/til.til, so the compiler's own layout is pinned
  whatever compiler runs that line (the commit that made the cage the
  default needed exactly that: pass 1 of its two-pass build ran under a
  native boot compiler whose default was still native). Its interpreter's
  value memory uses the running binary's own layout (initer marks compressed
  own fields ~FieldLayout.is_cptr~, 4 bytes), and reads/writes a
  pointer-field slot with ~own_slot_load~ / ~own_slot_store~, size-aware
  twins of ~deref~ / ~write_ptr~ that the typer's raw-store rules name
  alongside ~write_ptr~. ~ext_struct~ fields mirror C library structs and
  always stay native. Like #309's width split, sizes fold only when host and
  target agree; a native (~--usize=64~) compiler building a compact program
  (or the reverse) emits ~X.size()~ as C ~sizeof~, so that translation is
  not byte-identical to a same-layout one.

  ~make check_usize64~ (and its CI job) keeps the native layout alive: the
  whole suite through an ASAN compiler built ~--usize=64~, with every
  compiled program built ~--usize=64~ too, after the struct sizes of both
  layouts (test/usize32_sizes.til, test/usize64_sizes.til). Measured on the
  self-translate before the cage became the default (-O0, U32 widths):
  -4.8% peak RSS, -3.9% time for the cage.

** CPU profiles and C optimization

  ~--cpu=baseline|x86-64-v3|x86-64-v4~ selects a target CPU profile,
  independently of ~--target~'s OS/architecture. The default is baseline.
  These are x86-64 instruction-set levels, not compiler versions: v3
  includes AVX2; v4 includes AVX-512F/BW/CD/DQ/VL. The executable requires
  the selected feature set. No host CPUID, native tuning or runtime dispatch
  participates in selection.

  One resolved ~TargetCpu~ supplies both C compiler flags and the frontend's
  SIMD width fact. Baseline x86-64/AArch64 recommends 128 bits; x86-64 v3
  recommends 256 and v4 recommends 512. Thus ~simd_width(F32)~ is 4/8/16
  on those x86-64 profiles, in interpretation and translation alike. Explicit
  ~Simd(T, N)~ widths remain legal independently of that recommendation.
  Other targets retain their existing baseline width; v3/v4 require an
  x86-64 C target. Wider recommendations are not universal speed guarantees.

  ~--cpu~ applies to file-based interpret/translate/build/run/test/install/doc.
  ~--opt=0|2|3~ applies to C build/run/test/install only, with default 0.
  AST printing, bindings generation and the REPL reject these controls;
  non-C backends and theme mode reject explicit CPU/optimization options.
  Interpretation emulates the selected SIMD shape; its native FFI bridge
  remains host code rather than a cross-compiled target program.

  Every builder-owned C compilation, including ~link_c~, runtime/core and
  library objects, receives the selected flags. They follow options embedded
  in ~--cc~, so til's ~-march~ and ~-O~ selections (including defaults) win
  over those options. Use ~--opt=2~, rather than ~--cc='gcc -O2'~, to request
  optimization. Floating-point contraction is explicitly disabled; these
  controls enable neither fast-math nor implicit FMA/reassociation.
  ~-fexcess-precision=standard~ makes declared-format casts and assignments
  round on x87 too, rather than retaining extended intermediates. Vendor
  archives and already-built external libraries are not rebuilt by the flags.

  Non-baseline shared runtime/core names and their C symbol namespaces add
  the CPU profile to the existing revision/target/USize identity, before the
  optional ASAN suffix. This prevents an AVX2/AVX-512 build from overwriting
  a baseline dependency. The normal build/install paths generate and copy
  those variants, and generated bindings/linker references name the matching
  dependencies. Optimization levels share an identity; baseline names retain
  their previous spelling. There is no additional manifest or cache.

  Explicit ~a.fma(b, c)~ is available on ~F32~, ~F64~, and floating-point
  ~Simd(T, N)~ in the interpreter and C backend. It computes ~a*b+c~ with
  one final rounding per scalar/lane; ordinary ~a*b+c~ keeps separate
  rounding. Arguments have matching types/widths and are evaluated once in
  source order. IEEE infinities, signed zero and NaN results are supported;
  NaN payload/sign are unspecified and no til exception is thrown. C uses
  fused builtins/libm, including on targets without hardware FMA. There is
  no separate CPU flag or fast-math requirement for explicit fusion.

** Experimental MLIR backend

  ~--backend=mlir~ selects the initial CPU MLIR implementation for
  ~translate~, ~build~ and ~run~. ~--backend=c~ explicitly selects the
  existing default. Backend selection is separate from ~--target~; the
  initial MLIR ABI supports Linux x86-64 hosts and targets only.

  This is a restricted value/control-flow backend, not GPU execution or a
  replacement for the general C backend. It supports F32/F64, ~Simd(F32,4)~,
  ~Simd(I32,4)~, ~Simd(U32,4)~,
  ~Simd(Bool,4)~ masks,
  Bool and all I8/U8, I16/U16, I32/U32 and I64/U64 scalar values, including USize/UPtr aliases resolved
  through the existing target configuration. Scalar/nested POD structs support
  construction, field access/update and value returns as described below.
  Value parameters are immutable;
  locals may be mutable. Borrowed ~Array(F32)~, ~Array(I32)~ and ~Array(U32)~ parameters support read-only
  inputs and ~mut~ outputs. Arithmetic includes addition, subtraction and
  multiplication (integer operations wrap), integer increment/decrement,
  integer bitwise operations, scalar comparisons/cmp, Boolean logic, cloning, literals, cross-unit direct
  calls and returns. Scalar integer division, shifts and other unsupported
  operations still produce diagnostics. SIMD ~new~,
  ~splat~, ~zero~, fixed-order ~reduce_add~ and checked lane
  access/update (~v[i]~, ~v.get(i)?~, ~v.set(i,own x)!~) are supported. Unsupported arithmetic,
  ownership, globals, runtime calls and types produce
  source-located errors. Generated compile-time core helpers are not treated
  as exported source functions. A runnable program needs a no-argument,
  void ~main~; its native entry returns zero. CLI arguments are unsupported.

  ~if~/~else~ and ~while~, including nested loops, ~break~, ~continue~ and
  early returns, lower to explicit LLVM-dialect blocks and branches. Lazy
  Boolean operands remain conditional. Mutable locals have storage allocated
  once in the function's entry block, not once per loop iteration; their
  initializers still execute at the source declaration. Lexical bindings
  are restored after each block, while stores to an outer local persist.
  LLVM/Clang may promote these non-escaping slots to SSA values when optimizing.

  Direct calls resolve the actual prepared FunctionDef across user/imported
  units, including functions and procedures declared inside a namespace.
  Namespace membership does not add a receiver ABI: static calls and UFCS use
  the same formal parameter list after the shared frontend rewrites the call.
  A namespace can contain scalar-only callables without constructing an owner
  value. Functions named main inside namespaces are ordinary callables, not
  executable entrypoints. Source-defined namespace bodies take precedence over
  intrinsic-name shortcuts, including user add and clone implementations.

  Executables emit main and its transitive direct-call dependencies. Libraries
  root public source callables in all user units and public type namespaces,
  matching the shared library export policy. Private helpers stay internal;
  concrete generics use the frontend's registered identities and declaring
  source paths. Emission follows unit/declaration order, not pointer ordering.
  Source contexts are restored per body for diagnostics and runtime literals.

  Public namespace symbols use the C spelling Owner_member; collisions with
  another source callable are diagnosed. Imported unsupported bodies that are
  not reachable in an executable need not be emitted. Retained namespace values
  and indirect callable values remain unsupported; a FuncSig declaration alone
  is type metadata, not an executable body. Existing core/runtime entries still
  use the temporary C-core bridge where they are not emitted as concrete bodies.

  Scalar-aligned four-F32 storage retains the C backend's Linux SysV ABI:
  each value argument is split into two ~vector<2xf32>~ arguments, and the
  return is a two-member LLVM struct. Inside a function, values use
  ~vector<4xf32>~, ~arith.addf~ and ~arith.mulf~, without fast-math flags.
  ~reduce_add~ emits exactly ~(lane0+lane2)+(lane1+lane3)~, not a reassociating
  vector reduction or an extra initial addition of positive zero. Multiply
  followed by add remains unfused. Arguments beyond the register budget use
  the SysV stack ABI described below.
  Mutable scalar parameters and ownership-transferring numeric-buffer parameters remain
  outside the subset; strings, borrowed buffers and the error-out parameter are
  described below.

  F32, F64 and F32x4 division use IEEE floating-point semantics, including zero
  divisors, signed zeros, infinities and NaNs, through ~arith.divf~. Explicit
  ~a.fma(b,c)~ uses ~llvm.intr.fma~ with one fused rounding; ordinary ~a*b+c~
  remains separate. Operands are evaluated once in source order. Executables
  and shared libraries link libm so baseline CPUs can use LLVM's ~fmaf~/~fma~
  lowering; native callers of static archives must also link ~-lm~ when needed.
  Integration tests compare finite/zero results bit-for-bit and NaNs by
  classification against C division/~fmaf~, at O0/O2/O3 and both USize widths.
  Integer parameters/results use their resolved bit width. Bool uses i1
  internally and normalized byte values at the C ABI boundary. Integer
  arguments do not consume the SSE argument budget. Native-width USize
  remains the default; the existing explicit width override is unchanged.
  Accepted integer widening uses sign or zero extension as appropriate,
  including widened locals, assignments and return values. Narrow signed
  parameters/results carry signext, unsigned ones carry zeroext, and Bool's
  normalized-byte ABI uses zeroext. The LLVM export adapter restores these
  call-site attributes as well as the aggregate ABI attributes.

  I8/U8 and I16/U16 locals and fields retain their declared widths: arithmetic
  wraps without LLVM overflow flags, comparisons preserve signedness, and
  integer constants retain their width-specific bit patterns. F64 constants
  preserve all 64 bits, including negative zero. Floating comparisons use
  ordered predicates except inequality; cmp returns zero for unordered inputs,
  matching core's existing scalar cmp. F32/F64 share the SSE argument budget.
  The existing numeric to_x/from_i64 conversions are lowered using their actual
  declared return type, including narrowing and cross-signedness conversion;
  legacy float-to-integer to_x remains unchecked. Checked cast retains its
  range/NaN/infinity panic contract. Float-width conversions preserve numeric
  rounding, and formatting/to_repr still uses the ordinary C-core bridge.

  I32x4/U32x4 use ~vector<4xi32>~ internally. Their four scalar fields cross
  the SysV ABI as two i64 INTEGER chunks for arguments and returns, independent
  of the SSE budget. Sign-sensitive comparisons and division use the source
  lane type; arithmetic and reduce_add wrap modulo 2^32 without LLVM overflow
  promises. Division returns zero for a zero divisor, and signed MIN/-1 returns
  MIN, matching til's SIMD div_lane. Exceptional lanes receive a safe divisor
  before LLVM division, rather than selecting away a poison result afterwards.
  Construction, splat, zero, band/bor/bxor/bnot, comparisons, mask selection,
  checked lanes and checked load/store are supported for both types.

  Arguments use the six INTEGER and eight SSE registers in source order,
  accounting for a leading sret pointer and trailing lowered error parameters.
  A four-lane numeric vector needs two registers of its bank. If both are not
  available, the WHOLE scalar-layout aggregate is passed on the stack; it does
  not consume the remaining register, which a later scalar/mask can still use.
  The two banks are independent. This removes the old SIMD argument-count
  limits without changing register-passed values or return conventions.

  Definitions and direct calls share one allocation calculation. Stack
  aggregates use LLVM byval pointers to four-scalar structs with alignment 8,
  not native-vector parameter types. Each call site's source snapshot has an
  aligned entry-block slot, so repeated loop calls do not grow local storage.
  LLVM 18 exports byval/sret and integer extension attributes on declarations
  but drops the corresponding call-site attributes.
  The export adapter described below restores those attributes BEFORE any
  optimization. Instruction selection consulting the callee is not sufficient:
  padded POD forwarding passed O0 but failed O2 until the call was annotated.
  Indirect calls remain unsupported.

  Tests exercise register exhaustion and rollback, subsequent scalar/mask
  arguments, mixed-bank spills, stack scalars, sret and error-out pointers,
  incoming C calls, MLIR-to-MLIR forwarding and ASAN til/C consumers at O0/O2/O3
  with the supported native USize64 layout. Raw F32 bits survive stack copies,
  earlier operands remain snapshots across mutation, and a million-iteration
  caller checks bounded stack storage. Other integer SIMD tests cover
  mixed scalar/vector/SSE arguments, direct calls,
  signed/unsigned boundary values, wraparound, zero/overflow division, all
  selection masks, and C/til consumers at both USize widths and O0/O2/O3.

  ~cast(value,T)~ and ~value.cast(T)~ convert between I32x4, U32x4 and F32x4,
  retaining lane count and evaluating the operand once. Integer sign casts
  preserve bits; integer/float casts convert numeric values. Floating results
  use the normal rounding mode (nearest-even by default), possibly losing
  precision. Float-to-integer truncates toward zero and panics if that truncated
  value is out of range, or the input is NaN/infinite. Checks precede LLVM
  fptosi/fptoui so invalid inputs cannot produce poison. Any invalid lane
  panics through ordinary core with the original cast's source location.
  Scalar casts follow the same rules for the types supported by this backend;
  the interpreter/C backend additionally supports all integer widths and F64.
  Parsing and formatting retain named to_x methods. Existing numeric to_x
  methods are retained for compatibility. Tests cover all six vector directions,
  boundary/fractional values, rounding, single evaluation, discarded-result
  panics and exact diagnostics from imported functions at O0/O2/O3.

  F32x4, I32x4 and U32x4 support ~reduce_min~ and ~reduce_max~. The operand
  is evaluated once, then the existing halving tree combines lanes (0,2),
  (1,3), and those two results. Integer comparisons retain signedness. Floating
  pairs propagate NaNs, selecting the right-hand NaN when both are NaNs;
  selection preserves its original bits, including signaling state and payload.
  Zero ties prefer -0 for min and +0 for max when present. Explicit comparisons
  and selects preserve these rules rather than an unspecified/reassociated
  LLVM reduction. Tests cover every four-lane combination of 14 boundary bit
  patterns, all zero-sign combinations, multiple NaN payloads, single evaluation
  and throwing operands, at both widths and O0/O2/O3.

  F32x4 comparisons return elementwise Bool masks. Equality and ordered
  comparisons are false for NaNs; inequality is true for unordered operands,
  matching the interpreter/C backend. Masks use ~vector<4xi1>~ internally and
  four normalized Bool bytes at the public ABI (one SysV INTEGER/i32 chunk),
  not packed predicate bits. They support construction, splat, zero, checked
  lane reads, equality/inequality, band/bor/bxor/bnot and all/any reductions.
  ~select~ accepts masks and F32x4, I32x4, U32x4 or Boolx4 values and preserves the
  selected lane's bits, including signed zero and NaN payloads. Mask operands
  are values; these operations do not introduce scalar short-circuiting or
  masked memory access. Mutable mask locals and direct calls retain the
  same representation conversions as exported functions.

  F32x4, I32x4, U32x4 and Boolx4 lane reads and local updates accept runtime indices.
  Unsigned USize comparison against 4 precedes extraction/insertion, with no
  truncation that could turn an invalid wide index into a valid one. Failure
  writes OutOfBounds tag 1 and leaves the vector unchanged; preceding writes
  remain visible. The shared lowered guards handle propagation, catch and !.
  Successful access leaves the error slot untouched. Proven in-range constant
  indices omit the check and preserve error-state knowledge; ordinary mutable
  locals are not treated as constants. Mutable vector parameters remain outside
  the supported ABI. Both USize widths are tested at O0/O2/O3, including all
  four lanes, out-of-range/maximal indices, raw F32 bits and all 16 masks.

  Borrowed buffers retain the existing C Array ABI: a pointer to a descriptor
  containing a data pointer followed by a USize capacity. The capacity field
  uses the selected USize width; the data pointer stays pointer-sized.
  ~len~, checked scalar ~get/set~ and four-lane ~load/store~ are supported for
  F32, I32 and U32 buffers. Borrowed integer element reads retain signedness
  when widened to I64.
  Element references may be read or, when declared mutable, written through.
  Buffer aliases borrow the same descriptor. Allocation, cloning, destruction,
  array returns and descriptor replacement stay in the host; passing an array
  as ~own~ or ~shallow~ is rejected rather than changing its ABI.

  Checked memory operations support ~?~ propagation, local ~OutOfBounds~
  catches and ~!~ panic handling. Propagation uses the existing trailing
  ~I64 *~ error-kind ABI for functions declaring ~throws OutOfBounds~:
  the caller initializes the slot to zero; success leaves it unchanged and
  failure writes tag 1. Failure results are unused ABI placeholders, not
  substitute data. The shared lowered success guards and loop exits control
  propagation. Local catches reset the error slot before recovery, including
  repeated loop failures and rethrowing. Generated ~!~ failures preserve the
  source location, stdout diagnostic and exit status 1 through ordinary core
  ~panic~ calls, just like explicit user panics. The old generated-bang pattern
  recognizer and special diagnostic emitter have been removed. Other exception
  types remain unsupported. A proven-clear error branch also permits existing constant
  SIMD lane reads after a successful load; possibly throwing calls invalidate
  that proof, including at loop exits.

  Vector bounds checks test ~start <= count~ before ~count-start >= 4~.
  The emitter forms the data address only in the successful block, uses
  scalar alignment (4 bytes), and zero-extends 32-bit indices to the 64-bit
  pointer domain. It does not attach ~inbounds~ or ~noalias~ assumptions.
  Failed stores write no elements; earlier successful stores remain visible.

*** Scalar and nested POD structs

  POD structs may contain Bool, all scalar integer widths, F32/F64 and nested structs from
  that same set. Constructors use the shared frontend's positional/default
  field lowering. Mutable locals, whole-value assignment, field reads/writes,
  nested field aliases, auto-generated clone and size are supported. These
  values have no owning/reference/raw-pointer fields or nontrivial destructor;
  SIMD fields and empty runtime structs are not yet supported in this increment.
  Source-defined clone functions can be emitted through the normal namespace
  callable path when their bodies use the supported subset. Heap-outer owning parameters and borrowed user
  returns remain outside this slice.

  The existing typer decides whether an ordinary parameter borrows or is an
  auto-shallowed small value. Borrowed/mut parameters use pointers, and explicit
  shallow parameters use the native value ABI. Struct layout preserves native
  field offsets and padding, with Bool stored as a normalized byte. Borrowed
  whole-struct loads make no stronger alignment promise than their source;
  compiler-owned slots remain aligned and live in the entry block.

  For values up to 16 bytes, recursive SysV eightbyte classification merges
  nested fields: INTEGER dominates SSE within an eightbyte. Parameters and
  returns use the corresponding integer/SSE register chunks. Larger returns
  use sret; larger shallow arguments, or small arguments whose required banks
  do not all fit, use whole-aggregate byval stack copies. A spill rolls back
  both banks. ABI coercion storage covers the full chunks, even when the source
  struct is smaller, so return padding never causes an out-of-bounds load.

  Tests compare 14 scalar/mixed/nested layouts with native C and til/C callers
  at O0/O2/O3, including small-value auto-shallowing, pointer borrows, mutable
  nested fields, Bool aliases, default construction, reassignment and snapshots.
  Cases cover mixed-class register rollback, hidden returns, raw NaN/zero bits,
  scalar-aligned array elements and a million-iteration bounded-stack copy loop.
  User POD bodies are emitted as MLIR, not additional C wrappers.

*** Temporary C-core runtime bridge

  MLIR now emits Str literals, locals, borrowed/mutable/own parameters and
  value returns, plus the Array(Str) packing used by variadic core calls.
  ~println~, ~print~, ~format~, ~panic~, string methods and numeric formatting
  call the existing C-compiled core/runtime implementations. This is a
  temporary implementation bridge, not the intended final backend architecture.
  The goal is to emit til core bodies directly as MLIR, depending on libc and
  platform libraries at the low-level boundary as ext.c does today, without
  depending on C-generated til core code.

  Str retains its data-pointer/count/cap layout. At USize32 its 16-byte value
  return uses two SysV INTEGER chunks; at USize64 its 24-byte return uses an
  sret pointer. Record parameters use the existing pointer ABI; shallow record
  parameters and borrowed record returns from user functions remain unsupported.
  AST ownership/keep-outer/save-old-delete decisions govern transfers and
  cleanup. Moving a stack record boxes its wrapper; forwarding an already-owned
  wrapper does not box again. Returned values release a moved parameter wrapper
  while retaining its payload. Copied literal wrappers become CAP_VIEW so
  their storage is releasable without freeing literal bytes.

  MLIR translation also writes the normal ~gen/til/<source>.c~ and
  ~<source>_forward.h~ support files. Builds compile their ~TIL_CORE_ONLY~
  partition and ~src/self/codegen/ext.c~ into the existing revision/target/USize-qualified
  core/runtime object paths in ~gen/lib/~. Only user bodies are compiled from
  MLIR; they are not compiled again from the C support file. The linker includes
  both support objects in executables/shared libraries/static archives. Native
  static-archive callers must link libm (~-lm~). Public C/til/Python binding
  files are not generated by this bridge.

  This adds a second generated representation and C compilation to MLIR builds.
  It does not add a persistent cache or alternate source of truth: each
  invocation regenerates support from the same prepared program, compiler
  revision, target width and source tree. The LLVM 18 toolchain's Clang compiles
  the C support. These files and the bridge dependency should disappear when
  the core bodies and low-level runtime boundary can be emitted directly.

  Runtime integration compares interpreter/C output with MLIR stdout/stderr,
  including embedded NULs, escaping, formatting and explicit panic diagnostics.
  Native C and ASAN til/C consumers check both record-return ABIs. Repeated
  ownership transfers, returned owned parameters, mutation and replacement
  exercise cleanup under LeakSanitizer at both USize widths and O0/O2/O3.

*** Generated outputs and toolchain

  til writes ~gen/mlir/<source>.mlir~, preserving the same normalized source
  hierarchy as C output. ~mlir-opt-18~ lowers vector/arith operations to the
  LLVM dialect; ~mlir-translate-18~ produces LLVM IR; ~clang-18~ compiles it.
  Lowered MLIR flows through a pipe. LLVM 18's exporter omits call-site byval,
  sret and narrow-integer extension attributes, so builds stage its LLVM IR in caller-local
  ~tmp/mlir-<pid>.ll~. Til reads that file, restores the required call attributes
  from the exported function declarations (arguments and results), and rewrites it; Clang then reads
  it, and til removes it after compilation (including a Clang failure).
  Balanced type parsing handles named/quoted types and nested aggregate
  signatures; inconsistent argument counts/attributes fail loudly.

  This temporary LLVM 18 adapter replaces fully streamed LLVM IR with scratch
  file I/O and an in-memory rewrite. It adds no installed artifact or dependency.
  The file is regenerated on every build, never reused as a cache, and can be
  removed when the selected exporter preserves call-site ABI attributes. On
  Linux lowering still uses Bash ~pipefail~ so a failing stage is not hidden.
  Translation-only output remains the .mlir and approved C-support files.

  Executables retain ~bin/<source>~ or the existing ~-o~ override. Library
  builds use ~gen/lib/<name>.o~, ~gen/lib/lib<name>.so~ and
  ~gen/lib/lib<name>.a~. C headers and til/Python binding generation are not
  yet implemented for MLIR libraries. C callers can declare the four-float
  struct by value; til ~ext_func~ bindings must explicitly use ~shallow~ on
  those value parameters and returns, as for other by-value C aggregates.

  ~--cpu~ and ~--opt~ retain their existing meanings. ~-c~, ~--cc~, ~--asan~,
  ~--prof~, ~link_c~ and link flags are rejected for this initial backend.
  ~interpret~, ~test~, ~install~, ~ast~, ~doc~, ~bindings~ and REPL do not
  accept ~--backend~. Normal C/bootstrap builds never invoke the MLIR tools.
  Optional package/version instructions are in [[../README.org::*Optional LLVM/MLIR development tools][README]].

  Minimal library source:

  #+begin_src til
  mode pure
  F4 := Simd(F32, 4)
  add4 := func(a: F4, b: F4) returns F4 { return a + b }
  dot4 := func(a: F4, b: F4) returns F32 { return (a * b).reduce_add() }
  sum_to := func(limit: USize) returns USize {
      mut i : USize = 0
      mut total : USize = 0
      while i < limit { total = total + i; i++ }
      return total
  }
  add_first4 := func(a: Array(F32), b: Array(F32), mut out: Array(F32)) throws OutOfBounds {
      x := F4.load(a, 0)?
      y := F4.load(b, 0)?
      sum := x + y
      sum.store(out, 0)?
  }
  #+end_src

  #+begin_src sh
  bin/til translate --backend=mlir path/to/library.til
  bin/til build --backend=mlir --opt=2 path/to/library.til
  # Optional LLVM 18 integration checks, including C and til/C callers:
  bin/til run test/mlir.til bin/til
  #+end_src

  ~test/mlir_options.til~ is part of ~make test~ and checks emission and
  diagnostics without requiring LLVM tools. The opt-in ~test/mlir.til~
  checks ABI calls, private helpers, construction, lane reordering, arithmetic,
  dot products, argument register limits, cancellation, signed zeros,
  subnormals, infinities and NaNs at O0/O2/O3. The same dot-product checks
  run against interpreted til, the C backend and a til/C caller of the MLIR
  library. Finite results and zeros are compared bit-for-bit; arithmetic NaN
  results are checked by classification. Construction, splatting and lane
  reordering preserve raw bits, including signaling-NaN payloads, and are
  checked byte-for-byte. A multiply/add case distinguishes separate rounding
  from FMA (zero versus one).

  Control-flow tests compare the interpreter/C reference with native C and
  til/C callers of the MLIR library at O0/O2/O3, with USize32 and USize64.
  Cases cover zero iterations, condition re-evaluation, nested loop-local
  initialization, break/continue, early returns, lexical branch locals,
  mutable-value snapshots, signed/unsigned comparisons, integer wraparound,
  integer widening, Boolean ABI calls and a mutable SIMD accumulator. A million-iteration
  nested loop also checks that loop-local storage does not grow the stack.

  Buffer integration tests run array addition and four-lane dot products with
  scalar tails, using interpreter/C references and C/til callers of MLIR
  libraries at both USize widths and O0/O2/O3. They cover empty buffers,
  scalar-aligned vector starts, short inputs/outputs, maximum indices, error
  forwarding, partial writes, in-place/overlapping buffers, cancellation,
  reference writes and bit-preserving loads/stores of NaN payloads.

  Exception checks cover local recovery, repeated catches, rethrowing, nested
  ~?~ inside ~!~, partial writes and scalar/vector bang success. Failure
  subprocesses compare stdout byte-for-byte with interpreter/C diagnostics,
  require empty stderr and exit status 1, at both widths and O0/O2/O3.

** Experimental FASM backend

  ~--backend=fasm~ selects native assembly for ~translate~, ~build~ and ~run~
  on Linux x86-64 hosts and targets. The subset accepts ~mode script~ and
  ~mode cli~ with a no-argument, void ~main~, ordinary functions with supported
  lowered bodies, up to six runtime arguments (including lowered error slots),
  scalar/struct parameters, value locals, local assignments, calls, returns, if/else and
  while loops. Range for loops use the shared frontend lowering; nested
  break/continue and lexical blocks preserve their normal control flow.
  Bool and/or, including &&/|| and their n-ary forms, short-circuit.

  Integer add/subtract/multiply/inc/dec wrap at the declared width. Division
  and remainder use the existing zero-divisor result of zero and native C
  integer promotions; bitwise operations, shifts, signed/unsigned comparisons,
  cmp, casts and Bool negation are supported. This does not define new behavior
  for C's undefined signed division overflow or out-of-range shift counts.
  Narrow cells are reloaded at their declared width after mut/ref writes.
  Arithmetic retains its method width before any caller-parameter widening.
  Unsupported constructs receive source-located errors.

  Til writes ~gen/fasm/<source>.fasm~, preserving the normal source hierarchy.
  The vendored FASM writes a standalone ELF64 executable to ~bin/<source>~
  or the existing ~-o~ override. There is no C compiler, libc or linker in
  that path. Internal calls use SysV integer registers and aligned frames;
  this does not yet expose a library ABI. Libraries, program arguments,
  other modes, ~-c~, ~--cc~, ~--asan~, ~--prof~, ~--cpu~, ~--opt~, ~link_c~
  and link flags are rejected. See README for the assembler bootstrap.

  After bootstrap, the vendor build and FASM build/run paths refresh a stale
  ~vendor/fasm/fasm~ from its assembly/includes, using the existing executable.
  The replacement is built in checkout-local ~tmp/~ and renamed into place
  after success. Installed compilers carry the prebuilt assembler/license at
  ~<prefix>/lib/til/vendor/fasm/~ and the runtime at ~<prefix>/lib/til/src/self/codegen/~.
  The install phase is copy-only; it never rebuilds under sudo. If FASM has
  not been bootstrapped, installation reports runtime-sources-only support.

*** Native runtime and ABI

  Generated assembly includes ~src/self/codegen/ext.fasm~ at its absolute support-tree
  path. That file remains hand-written source, read directly by FASM on each
  assembly; it is not copied into generated files. Linux syscalls supply the
  external boundary. ~src/self/codegen/ext.c~ is the behavioral reference, with
  ~src/core/str.til~, ~io.til~ and ~exit.til~ defining the language helpers.

  The ABI uses SysV integer argument registers, a 16-byte-aligned call stack
  and RAX for scalar/pointer results. Str uses native pointer storage: an eight-byte data pointer,
  then USize count and capacity (16 bytes total for USize32, 24 for USize64).
  CAP_VIEW/CAP_LIT retain their width-specific -2/-1 meanings. Array(Str)
  uses inline Str elements and a {data pointer, USize capacity} header.
  Aggregate-producing runtime entries receive caller-provided descriptor
  storage, just like generated functions. Character/element buffers retain
  their own allocation lifetimes. Borrowed references retain pointer identity.

  User structs, nested inline/own/ref fields, arrays of supported values,
  aggregate returns and reassignment use the prepared declarations and
  ownership decisions. Field offsets and sizes come from the shared
  target-size/alignment query, NOT ctx.struct_layouts: that cache describes
  host interpreter storage and can differ from the generated program's USize.
  No second persistent layout cache is introduced.

  The internal aggregate calling convention passes addresses in the integer
  registers. Shallow value parameters get independent outer slots; borrowed
  and mut parameters preserve their addresses. A non-ref aggregate return
  receives its caller's result address in RAX, saves it on entry, writes the
  result there and returns that address. Direct/indirect calls, constructors,
  enum values, clone methods and native runtime producers all use this rule.
  The result buffer is distinct from borrowed inputs. Ref returns still return
  the borrowed address rather than a copy.

  Ordinary own aggregate parameters consume contents while borrowing the
  caller's outer storage. If an argument already owns a heap outer, the caller
  releases it after the call, preserving the result across cleanup. Lifecycle
  methods retain the source call_free argument and receive outer-ownership
  information in R11; frame storage is never passed to the allocator's free,
  including through indirect calls and forwarding destructors. Moving such a
  parameter into a result releases an actual heap outer after copying it.
  RAX/R10/R11 are private ABI inputs, leaving all six integer argument registers
  available.

  Frame slots hold ordinary locals, constructed values and results. Heap
  storage still supplies actual own fields, owned-niche payloads, escaping
  private captures, raw allocations and opaque ownership transfers that may
  outlive a call. Stack copies can still be needed for value semantics or
  replacement ordering; there is no allocate/copy/free result-wrapper cycle.
  This is an internal til convention, not a public C aggregate ABI.

  The emitter indexes canonical imported AST definitions and emits reachable
  methods, including generated and user-defined clone/delete functions.
  Array/Vec operations and File wrappers backed by the implemented cfile_*
  primitives therefore use the existing core/std bodies. Shared lowered
  bounds-error paths, catches and bang panics carry their existing error slots.
  save_old_delete, move and swap_replace decisions retain their frontend
  meanings: evaluate the new value before destroying the old, consume moved
  storage, and run custom cleanup once. Discarded owned results are destroyed.

  PrecomputedSequence values become read-only templates in the existing
  assembly output. The ordinary til clone method creates each runtime value,
  so nested owned buffers are not shared with the template.

  Enums use the shared variant/tag definitions and target-size queries. Plain
  tags retain their declared integer width and explicit discriminant values.
  Tagged payloads use the shared union alignment; borrowed payloads contain
  pointers, while value payloads are inline. Niche enums, including borrowed
  and owned forms of Option, contain a single native pointer: null selects
  the empty variant, and a non-null pointer selects the payload variant,
  regardless of declaration order or explicit tag values.

  Constructors, tag tests, switch dispatch and get_payload/deref bindings lower
  to native operations. Nested patterns and guards use the shared lowered
  control flow; switch arms do not fall through, and lowered loop transfers
  retain their enclosing loop targets. Payload-alias assignments write through
  the payload storage instead of retargeting a local reference. Enum values use
  the internal address/caller-result convention above, including small tag-only
  and niche values; this is not an exported C enum ABI.

  Generated/user enum clone, delete, comparison and formatting methods are
  emitted from their prepared til bodies. Tagged and owned-niche payloads
  therefore run their actual lifecycle methods; borrowed payloads are not
  destroyed by the carrier. Precomputed arrays can contain tagged or owned-niche
  enums and are cloned through the same methods, keeping templates immutable.

  Callable values are native pointers to four-word descriptors
  ~{code, environment, drop, clone}~. Static named functions share read-only
  descriptors with no environment/drop/clone; reference bindings can name
  stable descriptor cells. Capturing functions and Body values allocate one
  block containing the descriptor, environment pointer table and eight-byte-
  aligned private capture storage. The environment starts after the four-word
  descriptor. Ref entries retain borrowed addresses; private value entries point
  inside the block. Moving an existing heap owner retains its pointee address,
  and owned opaque pointers keep their independent storage. Typed private space
  is reserved even when such a moved heap owner leaves that space unused.

  The clone callback receives the source environment and returns a complete
  cloned descriptor/block. It retains Ref targets, deep-clones aggregates into
  the provided private storage and clones nested callables directly into inline
  descriptor cells. Character/element buffers and nested closure blocks retain
  their own lifetimes. Drop destroys private contents without freeing interior
  addresses, releases independently owned captures through their lifecycle
  methods, then the runtime frees the whole closure block once. Custom delete
  methods retain their call_free flag behavior; R11 selects actual outer
  ownership independently. Raw escaping callable-slot APIs still allocate the
  independent pointer-sized cells their contracts return.

  Indirect calls evaluate the callable before its arguments, save intermediate
  values in the existing frames, then call its code pointer. R10 carries the
  hidden environment and is saved on entry before other calls; the six existing
  integer argument registers remain available for explicit runtime arguments.
  This is a private invocation convention, not the C closure-call ABI. Aggregate
  results use caller-provided result storage; callable values return descriptor
  pointers, and ref-callable results return addresses of descriptor cells.
  Mutable callable parameters likewise receive cells for write-back.

  Prepared closure bodies are indexed by routes into the canonical imported
  AST. Signature metadata for locals/captures supplies the indirect ABI after
  typer scopes have gone. The shared ownership pass supplies replacement/drop
  decisions; native closure slot clone/take/pop/delete operations execute them.
  Supported bodyless runtime operations can be materialized through native
  thunks. Precomputed callable fields contain static descriptors; serializing a
  capturing environment into a precomputed template remains unsupported.

  Shared preparation also preserves borrowed factory inputs when the result
  can be a capturing callable: auto-shallow must not leave an environment
  pointing into a dead by-value input. Capture provenance is included in return
  summaries. An owned callable factory result used immediately as a callee is
  hoisted before its arguments, so ordinary cleanup destroys it after invocation;
  an immediate cast still borrows its callable instead of resetting private state.

  Supported module and namespace globals have stable, zero-filled storage in
  the executable's writable segment. Scalars use addressable slots; aggregates
  use target-sized inline storage or pointer slots according to their prepared
  ownership/storage metadata. Ref globals retain pointer identity. Function
  parameters and nested locals shadow global bindings without inheriting their
  address, reference or ownership flags.

  Literal globals are initialized before namespace runtime values; namespace
  members follow the shared dependency order. Ordinary module initializers then
  run in canonical import order, once per unit, before main (or the root script's
  statements). Hoisted expression/error/varargs temporaries remain local to the
  initializer frame. Initializer calls can read or mutate globals without
  capturing those temporary frames. The shared frontend still determines which
  namespace defaults can be prepared; this does not defer its eager namespace
  evaluation or broaden the supported value types.

  Global replacement follows the existing save_old_delete/move decisions,
  including custom destructors. Merely returning from an initializer does not
  destroy a global; no new implicit process-exit destruction is added.
  Unsupported global types and external-symbol globals remain diagnostics.

  Implemented services:

  - Counted-byte stdout/stderr writes, including embedded NULs; print_flush
    adds the same newline as the C implementation. Writes retry EINTR and
    complete short writes. print/println/format use compiler-generated
    variadic string arrays, not a separate variadic source representation.
  - panic/assert/expect preserve stdout, source-location/message formatting
    and exit status 1. Native Str mutation errors use a "FASM runtime" location;
    syscall failures report a native operation diagnostic on stderr, without
    libc's strerror text. They never turn into successful/truncated results.
  - malloc/calloc/realloc/free use anonymous mappings with private size headers.
    Allocation failure returns NULL; failed realloc leaves the old block intact.
    This is a simple allocator, not a speed-optimized replacement for libc.
    memcpy/memmove/memset/memcmp, pointer arithmetic, scalar pointer reads/writes
    and C-string length support the typed raw-allocation boundary.
  - Str capacity, clone, delete, borrowed views, substr, from_c_str, length,
    equality, append and integer-to-string conversion follow the core contracts.
    Owned buffers have a terminator beyond count; views need not. File paths
    are copied by count and terminated before entering the kernel.
  - cfile_open/read/write/close, update/append, exists/remove, tell and seek
    primitives follow ext.c. Handles encode fd+1, reserving zero for closed.
    read_n clamps negative counts and handles EOF; read_all attempts rewind,
    then grows to EOF, including streams and /proc files with no useful size.
    Removal follows ext.c's unlink contract: a missing path is harmless, but
    directories and other failures are errors.

  Interfaces, floating-point operations, dynamic method/reflection lookup,
  unsupported external runtime services and mode test remain outside this
  subset. Array methods are no longer restricted to compiler-generated
  variadic collectors.

  The shared ~test/aggregate_control.til~ corpus runs through interpretation,
  C and FASM at both USize widths. It exercises nested and owned fields,
  custom clone/delete, returned borrows, reassignment, mut-parameter replacement,
  discarded results, precomputed arrays, checked indexing and ordinary File
  wrappers. The existing imported-call and bang-panic fixtures run unchanged.
  Aggregate translation also runs in the assembler-free options test.

  The same corpus covers enum tags (including U64 values above 32 bits),
  narrow/Bool/USize payloads, mutable payload bindings, nested patterns,
  multi-pattern arms, scalar ranges and loop transfers. It checks enum fields,
  returned values, tagged/ref/owned-niche cloning, custom destructor counts,
  immutable precomputed templates, Option(ref I64)/Option(ref Record), and
  taking an owned Record from Option. Resource-bearing cases execute with a
  runtime seed rather than relying solely on folded enum literals.

  Callable coverage includes static/inferred values, parameters/fields/globals,
  returned closures, six-argument captures, scalar/aggregate/ref results, mutable
  callable cells, borrowed/private/moved captures, Body values with owned nested
  captures, static templates, independent clones and custom destructor counts.
  It pins factory-before-argument evaluation and immediate-result destruction.
  A captured six-argument function returning a resource-owning record checks
  result storage and the hidden environment simultaneously. The runtime driver
  checks direct/indirect lifecycle forwarding with a computed call_free flag.
  Its allocation probes count native allocator calls in a temporary instrumented
  runtime: value-only aggregate/enum calls and views need zero heap blocks,
  numeric-to-string conversion needs only its character buffer, and returning
  an explicitly heap-allocated aggregate frees its original outer once. See
  [[file:./optimizations.org][Optimization measurements]] for the baseline and counts.
  Raw slot take/pop/clone/delete and immediate Dynamic casts are additionally
  compared between native C and FASM; the interpreter's owning Dynamic path
  requires its typed-container bookkeeping for these raw cells. The options test
  checks materializing a supported native runtime entry as a callable.

  ~test/reference_rebinding.til~ now runs unchanged through the interpreter,
  C and FASM at both USize widths. Reference rebinding retargets the borrow
  without cloning or destroying either pointee. Its coverage includes snapshots,
  repeated/nested rebindings, shadowing, fields, ref-returning calls and keeping
  the new owner alive through later uses. Scalar value assignments and mutable
  parameters retain write-through behavior. Separate negative fixtures reject
  inner-scope escapes and writes through a rebound read-only borrow.

  ~test/fasm_runtime.til~ compares identical runtime programs through the
  interpreter, C and FASM at USize32 and USize64. It reuses the existing
  ~examples/hello_script.til~ source unchanged. Frontier snippets live only
  in ~tmp/fasm_runtime/~ during the test. Coverage includes counted bytes,
  panic text/streams/status, ownership cleanup, raw memory, file update/append,
  growing reads, counted path views, /proc and failed writes to /dev/full.
  Global coverage includes CLI/script entry, diamond imports and once-only
  initialization, recursion, narrow mut-parameter writes, USize storage,
  heap strings, aggregate replacement/custom deletes, ref-returning accessors,
  reference and raw-allocation globals, namespace data/dependencies and local
  shadowing. All those fixtures use the same source for interpretation, C and
  FASM at both USize widths; the options test also translates globals without
  requiring an assembler and checks unsupported global diagnostics.
  A separate lexical-global lookup through a shadowing caller is compared
  between C and FASM only: the interpreter currently reads the caller's shadow.
  Nullable allocation failures compare native C/USize64 and FASM; C/USize32's
  allocation cage instead must reject an oversized allocation with its diagnostic
  (ASAN intentionally intercepts huge allocations). A small assembly ABI check
  verifies that a failed realloc preserves the old allocation. ASAN runs cover the compiler
  and test driver, not the generated syscall-only executable.

  Independent execution is useful for differential testing. This backend
  also supplies groundwork for selective future JIT execution of expensive
  functions, not a replacement for all interpretation. In-process executable
  memory, relocations, interpreter/native calls and code lifetimes remain
  separate future work, outside the initial backend's completion criteria.

** Single-pass build

  The Makefile builds til in one pass:

  1. ~til_boot~ (from HEAD) translates current .til sources to C,
     regenerates boot/, builds ~bin/til~

  In most cases this is enough: the C in ~boot/~ is the output of
  HEAD's compiler applied to the current source, and that compiles
  into a working ~bin/til~. ~make clean && make test~ on every
  commit confirms that the next commit's ~til_boot~ will build.

** When a preparation commit is needed

  Because boot/ is generated by HEAD's logic (not the current
  source's logic), changes that alter how the compiler EMITS code
  cannot take effect in the same commit that uses them. The most
  common case is auto-generated methods -- e.g. a new rule that
  synthesises ~clone~ or ~delete~ on structs/enums that lack them.
  HEAD's compiler doesn't know about the new rule, so it won't
  emit those methods into boot/ for the commit that introduces it.

  When that happens, split the work into two commits:

  1. Preparation commit: introduce the new auto-gen logic (or other
     emit-side change). After this commit lands, ~til_boot~ on the
     NEXT build will have the new logic baked in.
  2. Use commit: rely on the new behaviour. til_boot now emits the
     expected output, so boot/ and bin/til are consistent.

  This is uncommon -- most changes (new syntax desugaring that
  reuses existing emit paths, type-checker changes, runtime fixes,
  C runtime tweaks, library code) take effect in a single commit.
  Only changes that the BOOTSTRAP compiler must already understand
  in order to emit them need the two-commit dance.

  If in doubt, run ~make clean && make test~. If it passes, the
  commit stands on its own.

** Two-pass build (single commit alternative)

  When you would otherwise need a preparation commit, running the
  build twice locally is an alternative: pass 1 compiles current
  sources with HEAD's til_boot (old emit), pass 2 recompiles using
  the freshly-built bin/til (new emit). The boot/til.c committed at
  the end is the result of the new compiler self-applied, exactly
  the state that two separate commits would have converged to.

  Use ~make two_pass~ for the build, ~make test_two_pass~ for the
  full test suite. Commits depending on this MUST be prefixed
  "Two-pass: " so the local merger reproduces the same regen
  procedure (the merging procedure in
  ~doc/bots/merging_from_remote.org~ runs ~make test~ by default and
  needs to switch to ~make test_two_pass~ for these).

  Choosing between the two approaches:

  - Preparation + use commits: each commit verifies independently
    with ~make test~. Bisect-friendly. Preferred when the change
    is large or the emit-side logic might want a second look on
    its own.
  - Two-pass single commit: more compact history, the change ships
    atomically. Useful for small self-applied tweaks where the
    intermediate "logic without users" state is uninteresting.

** Staged migration across master merges

  Some changes are NOT a single emit-side step but a change to the
  source-level contract that the loader/parser enforces. Example:
  switching ~import("loader.til")~ to ~import("loader")~ requires
  the loader to start appending ~.til~ internally AND the call
  sites to drop the suffix. HEAD's til_boot has the old loader
  baked in; if a single commit ships both the new loader source
  and the new bare call sites, HEAD's til_boot rejects the new
  call sites at parse/resolve time and the build never reaches
  pass 2 -- ~two_pass~ does not help here because pass 1 itself
  fails.

  These migrations need a sequence of commits, each one merged to
  master before the next is authored:

  1. Transitional commit: extend the loader/parser to accept BOTH
     the old and new forms (e.g. loader strips trailing ~.til~ if
     present, then appends ~.til~). Call sites stay in the old
     form so HEAD's til_boot still parses them. ~make clean &&
     make test~ passes. Merge to master.
  2. Migration commit: now that master's til_boot understands the
     new form, update call sites to the new form and (optionally)
     reject the old form with a clear error. ~make clean && make
     test~ passes against the master from step 1. Merge to master.

  The remote agent can author commit 2 only after commit 1 has
  landed on origin/master, because til_boot is built from the last
  commit on the agent's base. A reviewer rebasing a feature branch
  that contains BOTH commits at once cannot use the soft-reset +
  regen recipe -- the intermediate til_boot they need is the one
  baked into commit 1's boot/til.c, which only exists once commit
  1 has been merged.

** Staged interface migration with a temporary alias

  Some bootstrap-safe source interface changes need THREE commits, not
  two. This happens when existing source call sites must keep working
  for HEAD's til_boot, but you still want the final public name to
  change.

  Example pattern: changing ~Set.new("Str")~ into ~Set.new(Str)~.
  If commit 1 changed ~Set.new~ directly, old bootstrapped code that
  still emits string-arg calls could break before the source tree is
  fully migrated.

  Use this sequence instead:

  1. Add a temporary alias with the NEW interface, under a NEW name
     (for example ~Set.new_newi(T: Type)~), while keeping the old
     ~Set.new(elem_type: Str)~ interface intact. Rewrite all source
     call sites and desugars to use the temporary alias. ~make clean &&
     make test~ passes. Merge to master.
  2. Flip the original public name to the NEW interface (for example
     ~Set.new(T: Type)~), and rewrite all source call sites back to
     the original name. Keep the temporary alias as a forwarding
     wrapper so bootstrapped/generated callers from commit 1 still
     work. ~make clean && make test~ passes. Merge to master.
  3. Remove the temporary alias once nothing in source or generated
     output still calls it. ~make clean && make test~ passes. Merge to
     master.

  This is the right pattern when the final interface name must stay the
  same, but the argument contract changes in a way that old boot output
  cannot consume immediately.

** Breaking changes in standalone scripts (~examples/~, ~tools/~)

  ~make test~ exercises the compiler, the test suite, and every example
  the suite knows how to build. But standalone scripts that are NOT
  hooked into the suite (the merge helper at ~examples/merge_commit.til~,
  ad-hoc scripts under ~examples/~ that nobody runs as part of CI) won't
  be caught when a commit makes a previously non-throwing function newly
  throw -- e.g. ~Vec.get throws OutOfBounds~. Bare ~vec.get(i)~ in such a
  script compiles fine before the change lands, fails after with
  "missing argument for parameter '_err_kind'".

  The breaking-change commit's ~make test~ passes regardless: every
  caller the suite covers gets a ~!~ or a ~?~ (or a ~v[i]~ subscript) in
  the same commit. The standalone script isn't in the suite, so it falls
  outside that proof.

  *** The merge helper has a special constraint ***

  The local merger runs ~examples/merge_commit.til~ using ~master's
  bin/til~, but compiles the helper source taken from ~the candidate
  commit's tree~. So at merge time the helper file from the candidate
  is being compiled by the OLD compiler:

  - Naively bundle the script adaptation INTO the breaking commit
    (e.g. switch ~vec.get(i)~ to ~vec[i]~) -> at merge time, master's
    ~bin/til~ sees the candidate's adapted script. The subscript
    desugars to ~vec.get(i)!~ and the bang triggers "function does not
    throw, remove the '!'" because master's Vec.get isn't throwing
    yet. The merge can't even start.
  - Keep the candidate's helper at master's form (untouched) -> the
    merger proceeds and lands the commit, but AFTER it lands, the
    next merge's ~bin/til~ rebuilds from the new source and the
    helper's bare ~vec.get(i)~ now fails to compile. The human has to
    hand-fix it before the next merge.
  - Write the candidate's helper in a form that compiles under BOTH
    typers, then bundle that into the breaking commit. The merge
    works, and so does every subsequent merge. THIS is what to aim
    for; the follow-up commit then cleans the workaround up to the
    natural post-merge form.

  *** Cross-typer-compatible patterns ***

  ~for x : T in vec~ desugars in the parser to a loop that calls
  Vec.get. Master's typer emits a bare call (Vec.get non-throwing);
  the new typer inline-lowers the call to a panic-on-OOB shape.
  Source-identical, accepted by both. Use this for sequential
  iteration.

  For random indexed access there is no for-in shape, but the same
  effect is reachable via an iteration counter:

    mut idx : USize = 0
    mut c2 := ""
    mut c3 := ""
    for c : Str in cells {
        if idx.eq(2) { c2 = c.clone() }
        if idx.eq(3) { c3 = c.clone() }
        idx = idx.add(1)
    }

  Ugly, but it compiles under both typers. Bundle this shape into
  the breaking commit. The very next commit (a hand-applied follow-up
  on master) can simplify to ~ref c2 : Str = cells[2]~, which only
  compiles under the new typer.

  *** Other standalone scripts ***

  For scripts that aren't part of the merge workflow, follow-up is
  fine: bundling means a same-commit fix, follow-up keeps the diff
  narrow. Either way the patterns are:

  - Bare ~.get(i)~ becomes ~v[i]~ for panic-on-OOB (the parser
    desugars subscript into ~.get(i)!~), or stay with ~.get(i)?~
    when you want to catch instead of panic.
  - Nested ~v[i]~ inside another call (e.g.
    ~trim_spaces(cells[i]).to_i64()~) hits the Dynamic-hoist limit on
    the bang temp and needs an explicit ref binding first:
      ref c : Str = cells[i]
      trim_spaces(c).to_i64()

  *** Always test the merger end-to-end ***

  Before pushing a breaking commit that touches the merge helper,
  build the candidate commit in a master-state worktree and run the
  helper there:

    git worktree add /tmp/pre-merge origin/master
    cd /tmp/pre-merge && make
    cp bin/til /tmp/master-til
    cd /path/to/your/branch
    /tmp/master-til build examples/merge_commit.til

  If that exits non-zero, the merger will reject the candidate. The
  in-suite ~make test~ won't catch this because the helper isn't part
  of the suite.

** Test-mode files

  Keep test files in ~mode test~ rather than changing them to ~mode lib~.
  ~til test file.til~ discovers and runs test declarations regardless of
  the file's mode, so under that command ~mode test~ has no behavioral
  difference from ~mode lib~. The modes still describe different kinds of
  files, though: ~mode lib~ marks a file as a compilable library, while
  ~mode test~ marks a test program and makes plain ~til interpret~ and
  ~til build~ run its tests automatically.

** Commands

  Every one of these also works as ~bin/make <goal>~, which is the same
  build without the Make frontend. ~make help~ (i.e. ~bin/make help~)
  lists all of them, the artifact paths that can be named directly, and
  the options.

  - ~make test~ builds + runs the full test suite (uses xvfb-run). Commit
    includes boot/. TEMPORARY (issue #464): without ASAN until #313 is
    settled; ~make test_asan~ is the ASAN suite (~bin/til_asan~, ASAN
    programs, the cage's leak report), which CI's native linux jobs run.
    Layout checks and nested VM, qualifier, numeric-cast and JNI drivers
    follow this selection too; the default performs no sanitizer builds.
    Restoration steps are in [[../issues/open/464.org][#464]].
  - ~make two_pass~ builds, then rebuilds with the freshly-built ~bin/til~
    so ~boot/til.c~ reflects the new compiler self-applied. Use for
    "Two-pass: "-prefixed commits.
  - ~make test_two_pass~ ~two_pass~ + run the full test suite.
  - ~make doc~ uses ~imports_for_docs.til~ as the single compiler/std entry
    point and regenerates API pages, one shared index/search and UML. Add new
    std entry modules to that file; ~test/doc_sdk.til~ checks every std source
    has a generated page, including dependencies. This file is documentation
    input, not an installed module or directory-import language feature (#459).
    Signatures render retained default expressions, including map/set literals
    and match expressions. Callable/body defaults show their signatures/captures with
    an explicit ~{ ... }~ marker for the omitted implementation; the reference
    is not a source-code serialization. The same formatting is used by help().
  - ~make test_asan_full~ is an alias for ~make test_asan~.
  - ~make test_nogui~ skips GUI build tests (no xvfb needed).
  - ~make test_regen~ rewrites the ~test/*.expected~ goldens from what the
    tests actually print. They are reviewed artifacts, not a cache: a
    missing golden is a test FAILURE, never a silent first-run
    expectation. Run this only for an INTENDED output change, then read
    the git diff -- that diff is the review.
  - ~make bin/til_asan~ ASAN build for memory debugging.
  - ~make bin/til_debug~ debug build for gdb.
  - ~make clean && make test~ always works.
  - ~git checkout HEAD boot/~ for recovery.

** Self-translation measurements

  The default suite translates once through ~bin/til~, compares the C and
  forward header with ~boot/~, and records ~self_ms~ / ~self_mem~. A different
  ~--til-bin~ adds its own self-application check (two-process repeatability
  instead of a boot comparison for the native-layout opt-out). Both stay
  outside suite wall/peak; only the normal compiler supplies benchmark data.

  The ~self-asan~ curve is retired. Historical ~self_asan_ms~ / ~self_asan_mem~
  cells remain verbatim in ~doc/totals.csv~; new rows leave those cells empty,
  even during explicit ASAN runs. They must never contain native timings or
  fabricated zeroes. ~examples/plot.til~ treats empty cells as absent data.
