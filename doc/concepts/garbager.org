* The Garbager: ASAP destruction and ownership cleanup

Companion to [[file:./ownership.org][doc/concepts/ownership.org]] (the lifetime model)
and [[file:./qualifiers.org][doc/concepts/qualifiers.org]] (the C shapes). Those two
describe the LANGUAGE contract; this file documents the PASS that implements
it -- ~src/self/garbager.til~, pipeline step 5 -- and, explicitly, the exact
OUTPUT CONTRACT the pass has today. Issue #302 is the rework that makes this
contract complete and explicit; this document is its stage 0 snapshot, kept
current as the stages land.

** Names and metaphors

The two compiler passes have different jobs:

| Pass      | Descriptive name                       | What it handles                         |
|-----------+----------------------------------------+-----------------------------------------|
| Garbager  | ASAP destruction / ownership cleanup   | Lifetimes and destruction of owned values |
| Scavenger | Reachability / dead-code elimination   | Code and declarations that are not needed |

The scavenger "eats dead code". The garbager "takes out the garbage" by
placing cleanup where ownership ends. The metaphors are useful mnemonics;
pair them with the descriptive names when introducing a pass. In particular,
"compile-time GC" here means statically inserted ownership cleanup, not a
runtime tracing collector or reference-counting scheme. See
[[file:../pipeline.org][the pipeline]] and
[[file:../../src/self/scavenger.til][src/self/scavenger.til]].

Passing ~own x~ transfers responsibility for that value to the callee, which
destroys it or transfers it onward. The caller no longer owns that value.
The ownership contract requires reassignment cleanup to distinguish the old
value consumed by an ~own~ RHS from the new value returned into the slot:
the caller must not delete the consumed value again.

*** Terms in other languages

These are terminology/model comparisons, not claims that the other compilers
have passes with til's internal names. Checked against the sources below on
2026-10-05:

- Mojo calls its policy *automatic destruction* and *as-soon-as-possible
  (ASAP) destruction*. It determines last use at compile time and invokes
  ~__deinit__()~; ownership transfer ends the source's ownership. This is the
  closest comparison to til's garbager, though Mojo can destroy values after
  subexpressions while til's cleanup is statement-oriented.
- Roc describes *automatic memory management*. Its runtime uses *reference
  counting* (~incref~ / ~decref~), with allocation/deallocation supplied by the
  platform. This manages shared allocations without exposing til's explicit
  ~own~ argument contract to application code.
- Odin uses *explicit memory management*: allocators, ~free~ / ~delete~, and
  explicit ~defer~ for scope-exit cleanup. Its FAQ explicitly distinguishes
  this from ownership semantics and automatic C++-style destructors. A
  scope-exit defer is a different policy from last-use destruction.

Sources:
- [[https://docs.modular.com/mojo/manual/lifecycle/death/][Mojo: Automatic destruction]]
  and [[https://docs.modular.com/mojo/manual/values/ownership/][Mojo: Ownership]].
- [[https://www.roc-lang.org/fast][Roc: automatic memory management and platforms]]
  and [[https://github.com/roc-lang/roc/blob/main/src/builtins/utils.zig][Roc runtime: reference-count operations]].
- [[https://odin-lang.org/docs/faq/#does-odin-have-c-style-destructors][Odin FAQ: destructors]]
  and [[https://odin-lang.org/docs/overview/#defer-statement][Odin: defer]].

** What the pass is

ASAP destruction (Mojo-style): every owned value has exactly one owner, and
the compiler inserts the destructor at the owner's last use, before
reassignment, and on every early-exit edge. One run per body:

  - File-based programs: one ~garbager_destroy(ctx)~ phase after typing
    (loader.til). It walks each imported unit and its nested bodies
    post-order, rebuilding short-lived per-body TypeScopes from the typed
    AST, parameters and capture metadata. The typer no longer inserts
    cleanup inline, and this walk retains no per-body scope cache (#158).
  - REPL deltas: ~garbager_destroy_body~ per delta (loader.til), using the
    populated program scope.

The orchestrator is ~insert_free_calls~: collect per-binding facts
(~collect_scope_locals~ -> ~LocalInfo~ with ~decl_index~ / ~last_use~ /
~own_transfer~ statement indexes), run the analysis fixups
(~extend_ref_local_lifetimes~, ~check_use_after_own_transfer~,
~promote_own_transferred_locals~, ~sink_conditional_transfer_deletes~,
~extend_hoist_view_lifetimes~), then rewrite the body statement list.

** Borrow-lifetime policy inventory (#461)

Source review at ~bac208501~ (2026-10-31). This records the current
implementation and concrete compatibility dependencies, not a decision to
change the language. The tests below were read, not rerun with protection
disabled: several mechanisms overlap, so a listed test is not a claim that
removing any single helper would necessarily make that test fail.

*** Baseline and what an extension means

~collect_scope_locals~ starts with a declaration index and the last
non-directive statement whose ~BodyFacts.uses~ mentions the binding. Its
~last_use~ is a statement position within this body, not a dynamic timestamp.
Ordinary owned locals are candidates for automatic destruction there.
~insert_free_calls~ then applies reference edges, transfer checks and view
escape checks; later it applies hoist/view taint before scheduling cleanup.
CFG liveness handles paths and exit cleanup, but does not make every borrow
edge path-sensitive or erase all conservative lifetime extensions.

~propagate_borrow_edges~ computes a monotone maximum: an owner's reach must
cover the edge's fixed statement position and the borrower's propagated
reach. Synthetic nodes represent nested reference declarations. This can
retain several possible owners; it does not dynamically select one owner,
count live references, or transfer ownership to a reference.

~ref~ bindings themselves skip destruction. That is an ownership rule,
separate from retaining the owner. Likewise, ~mut~ grants mutation and does
not establish ownership. Neither rule should be changed merely because a
different owner-lifetime policy is chosen.

*** Extension mechanisms and their dependencies

- *Direct references, fields and ref-returning calls.*
  ~collect_borrow_edges~ rule 3 retains the root of ~ref x = src~ or
  ~ref x = src.field~ through the reference's last textual/propagated use.
  For a ref-initializing call it conservatively considers each argument's
  identifier/field root, excluding transferred own arguments unless
  ~keep_outer~ retains their storage. This is broader than proving which
  single argument a call returns.
  ~test/gc_audit.til::borrow_local~ pins the owner's extended last use and
  the reference's ~skip=1~ in ~test/gc_audit.expected~. The field/getter cases
  in ~test/ref.til~ exercise the addressing forms, but many are POD or use
  string literals; their successful output alone is weaker evidence than
  an owned-buffer test or the audit golden.

- *Reference rebinding and nested scopes.*
  ~collect_reference_loans~ resolves storage identity, tracks reference
  sources and records loans acquired by subsequent assignments. Nested
  names have synthetic identities and are restored on scope exit; loan
  updates to outer references survive. Source sets accumulate: rebinding
  does not remove the earlier owner's edge. The analysis may therefore keep
  both old and new owners alive longer than the actual selected pointer
  needs. Callable storage, Dynamic, payload aliases and borrowed interface
  boxing are excluded from this walk's ordinary reference classification;
  this is not the only retention mechanism for those values.
  ~test/reference_rebinding.til::late_borrow~ reads the new owner's heap
  string after its final direct use; ~scoped_borrow~ adds nested shadowing
  and loans acquired inside a block. These are resource-bearing examples,
  not just checks that an integer pointer retargets correctly.

- *Ref fields and enum payloads.*
  The direct ref-field assignment rule adds a body-end edge for a named
  source. Its current syntactic gate is a ~FieldAssign~ with Ref field
  ownership, an identifiable holder root and an Ident RHS. It is not a
  universal field-sensitive alias solver. ~collect_enum_ref_payload_edges~
  recursively finds ref-payload constructors and retains the Ident or
  field-chain root to the end of the containing body. These conservative
  bounds account for pointer-preserving copies of carriers.
  ~test/option.til::test_safe_ref_extends_source_lifetime~ stores a heap-backed
  ~SafeRefHeap~ in ~Option(ref SafeRefHeap)~ and later reads its text.
  ~test/ref.til::test_ref_struct_field~ and
  ~test/enums.til::test_ref_payload_field_chain_borrow~ cover pointer-copy
  and field-root behavior; both also use the source later, so do not by
  themselves isolate a lifetime extension.

- *Borrows returned inside owned values, interfaces and callbacks.*
  ~collect_call_ref_return_edges~ consumes the typer's ~ref_return_params~,
  ~ref_return_into_params~ and ~ref_return_carried_params~ summaries for
  borrow-carrying declarations/assignments/field assignments. A direct or
  into-borrow retains argument storage; copying a carrier retains its
  borrowed owners rather than automatically retaining the original carrier.
  ~gc_ref_container~ identifies ref-qualified generic containers.
  ~test/tilvm.til::callback_owner_lifetime~ is a concrete API dependency:
  ~retain_callback(vm)~ returns a holder containing a callback; the VM has
  no further direct use, but must survive two callback calls and cleanup.
  This remains an owner-lifetime dependency even though the callback/holder
  is an owned value rather than a local spelled ~ref~.
  ~test/interfaces.til~ covers borrowed boxes and owned copies separately;
  ~iface_payload_borrowed~ also prevents destroying a borrowed payload.

- *Calls depositing borrows into other storage.*
  ~gc_collect_deposits~ rebuilds call deposits after hoisting from
  ~deposit_matrix~ and ~deposit_borrow_matrix~. It distinguishes borrowed
  argument storage from references carried inside a copied value, then adds
  source-to-sink edges. ~gc_carried_loan_start~ distinguishes stable ordinary
  variable storage from an interface's replaceable payload allocation.
  ~test/ref.til~'s ~bp393_*~ and ~bp398_*~ cases cover Vec/Map stores, field
  stores and helper-to-helper propagation. Most assert mutability credit on
  caller-owned POD values; they are essential provenance coverage, not
  independent demonstrations of premature heap destruction.

- *Closures and Body values.*
  Ref captures in a declaration's FuncDef/BodyValue initializer add an edge
  from the captured source to the callable binding's reach. Owned captures
  instead transfer ownership into the environment. In addition, nested-use
  facts can suppress owner cleanup altogether (below). ~test/closures.til~
  covers Ref, mut-Ref, shallow and own capture modes; the
  ~capture_*_escape_error.til~ fixtures cover escaping borrowed captures.
  Removing just capture edges is not equivalent to making all captured
  sources die at their last direct use.

- *String views and compiler-generated temporaries.*
  ~str_view_source_name~ contributes source-to-view edges. Separately,
  ~extend_hoist_view_lifetimes~ follows initializer dependencies and closes
  taint over statements using a tainted value, including transfers through
  synthesized varargs arrays. It deliberately over-approximates dependencies
  (even through some clones) and runs after use-after-transfer checking.
  This protection is not limited to explicit Ref declarations.
  ~test/strings.til::make_holder250~ evaluates
  ~h.s = arg.substr(5, arg.len().sub(5)).clone()~ using a grown buffer;
  ~test/bug350.til~ passes ~s.trim()~ / ~s.substr(...)~ through ~format~.
  Their source-level expressions still use the owner, but hoisting splits
  each expression into several statements. Destroying the owner between
  those synthesized statements breaks evaluation of the expression itself.
  ~test/bug258.til~ additionally covers retaining required clones for named
  views; ~rhs_depends_on_var~ and assignment cleanup protect the old buffer
  until the RHS has finished reading it.

*** Cleanup suppression is different from a later last use

~collect_scope_locals~ sets ~skip_scope_delete~ for several reasons:

- Non-hoisted program-scope bindings are not automatically destroyed here;
  a body must not destroy globals belonging to another import or REPL delta.
- A nested closure use or a ~write_ptr~ escape suppresses automatic cleanup
  because the value remains reachable beyond its textual use. This is not
  merely a promise to insert a destructor at scope end.
- Ref bindings and borrowed interface payloads own no data to destroy.
- ~aliased_by_returned_ref~ suppresses cleanup for a local handed out through
  a returned Ref alias, including the raw-allocator/~to_ptr~ bridge.
  This is not blanket permission to return references to ordinary locals;
  typer escape checks reject many such returns before cleanup insertion.

~test/gc_audit.til::raw_alloc_escapes~ pins ~write_ptr~ suppression and
explicitly documents the resulting deliberate leak. Turning suppression
into ordinary cleanup would introduce dangling pointers in such shapes;
keeping suppression while removing edge propagation would not implement
a uniform "direct-use-only" policy either.

*** Diagnostics and operation semantics that share the analysis

- ~reference_assignment_rebinds~ distinguishes pointer retargeting from
  write-through assignment. ~insert_assign_delete~ and
  ~flag_outer_assign_rebinds~ avoid deleting a non-owning reference's old
  pointee. Parameters/captured places are not ordinary retargetable locals.
  These operation semantics must survive any retention-policy change.
- ~check_reference_rebind_lifetime~ rejects borrowing a shorter-lived inner
  owner into an outer reference (~reference_rebinding_escape_error.til~).
  Read-only-source rejection (~reference_rebinding_readonly_error.til~) is a
  separate mutability constraint, not owner retention.
- ~report_local_return_roots~ / ~check_carried_borrow_of_local_return~ reject
  escaping local-owned storage inside results. ~check_interface_deposit_lifetimes~
  checks destinations outside the owner's lexical scope, and
  ~ref_container_source_stable~ rejects unsuitable temporary storage.
  These checks have explicit exemptions and are not a universal lifetime proof.
- ~extend_ref_local_lifetimes~ also diagnoses replacement of storage while a
  known later borrower remains live, using ~created_at~ and propagated reach.
  Removing that function removes this diagnostic as well as retention.
  ~test/tilvm_lifetime_error.til::replace_borrowed_vm~ and
  ~test/view_escape_error.til::reassign_then_use~ exercise this boundary.
  The latter file's loop/container cases also exercise ~check_view_escapes~,
  which is a separate check. Explicit ~own vm.delete()~ with later callback
  use is covered by ownership-transfer checks, not just reassignment checks.
- Borrow roots and call/deposit summaries also credit writes through aliases
  to the original mutable parameter. The ~bp344_*~, ~bp351_*~, ~bp393_*~ and
  ~bp398_*~ tests in ~test/ref.til~ require this independently of when owners
  are destroyed. Removing those summaries wholesale would change mutability
  checking and return/deposit provenance, not merely shorten lifetimes.

Dynamic, raw pointers, external calls and explicit cleanup remain boundaries
of the proof. Known raw escape suppression is not general tracking of every
pointer consumer; allocation lifetime and pointer validity must not be
inferred solely from passing these checks.

*** Consequences for the policy decision

The proposed simplification needs a precise definition of "last use":
last direct source use, last lowered statement use, or transitive borrower
use. Today the last is approximated with the mechanisms above. Hoisting must
not invalidate an otherwise valid source expression under any chosen rule.

Under direct-source-use responsibility, ~borrow_local~'s owner could die
after ~ref view = s~, and ~late_borrow~'s new owner could die before the later
alias read. ~Option(ref T)~, borrowed interface boxes and retained VM callbacks
need the same decision; restricting the change to locals spelled ~ref~ leaves
most of the policy and analysis intact. Compiler-created borrows also occur
in ordinary chained calls, field reads and varargs expressions.

Keeping the current policy preserves those usages but also its conservative
destructor timing: old rebinding sources can stay live, body-end edges can
outlast a carrier, and taint can retain an owner past a deep clone. Destructors
can release files/VM sessions or execute user logic, so timing differences
are observable even when output strings and ASAN remain correct.

Rejecting provably unsafe uses instead of extending owners still needs
provenance, statement/path ordering and escape analysis; deleting an
extension is not an implementation of that rejection policy. Transferring
responsibility to programmers must specify how long owners must remain live
and how that requirement is expressed. Lexical scope alone is not enough
under ASAP destruction, and there is no keep-alive primitive introduced by
this inventory. Independent owned copies can remove a dependency only when
the copy is made while the source remains valid.

Before a semantic change, select the affected mechanisms explicitly, preserve
rebinding/non-owning deletion rules and source-expression evaluation, then
review destructor-site diffs with the existing GC audit alongside resource
and negative fixtures. Do not silently update golden output or remove failing
diagnostics to make a new policy appear equivalent. Interpreter/C agreement
alone is insufficient: constant evaluation can hide a lifetime defect, and
POD/literal tests can pass despite an incorrect destruction boundary.

The policy choice and an isolated historical timing comparison remain open
in [[file:../../issues/open/461.org][#461]]. The measured implementation-only reductions are in
[[file:../optimizations.org][Optimization measurements]].

** The output contract (today)

Everything the pass produces, and who consumes it. This is the interface
the builder and the interpreter must execute; #302's point is that today
parts of it are re-derived or bypassed instead.

  1. Inserted destructor statements: ~Type.delete(x, call_free)~ /
     ~free(own x)~ / ~til_closure_delete(x)~ FCall nodes (built by
     typer.til's ~make_delete_call~ / ~make_free_call~ /
     ~make_closure_delete_call~) at last use, at scope end, before the
     statement that reassigns, and on exit edges (break / continue / return
     paths, including edges inside nested if/while/switch bodies).
  2. Deletes attached as EXTRA CHILDREN of ~Return~ nodes: children[1..]
     of a Return are cleanup calls to run AFTER evaluating children[0] and
     before returning. Every return-emission shape in builder.til unpacks
     this, and ~body_diverges~ must know cleanup can follow a terminator.
  3. ~save_old_delete~ flags on Assign / FieldAssign: the builder emits the
     old value's delete inline (stack and heap variants). Set from TWO
     places today: typer's ~infer_assign_stmt~ and garbager's
     ~insert_assign_delete~.
  4. ~own_type~ promotion on Decl (~promote_own_transferred_locals~):
     owned aggregate locals flip Shallow -> Own so codegen heap-boxes them.
     Deliberate exceptions stay stack: LiteralStr RHS, ~returns shallow~
     FCall RHS, POD-enum clone wrap.
  5. Clone-elision rewrites (~insert_post_stmt_deletes~): at a dying
     local's last use, ~lhs = local.clone()~ / ~holder.f =
     T.clone(local)~ is rewritten back to bare ~local~ so codegen emits a
     move; the local's own delete is skipped (Assign) or reduced to a
     wrapper ~free~ (value-field FieldAssign; an Own field consumes the
     wrapper instead, #256).
  6. Wrapper frees after a Shallow-field value-copy transfer
     (~transfer_is_shallow_field_value_copy~ + ~make_free_call~): the
     "half a transfer" shape -- the field's destructor owns the inner
     data, the orphaned heap wrapper still needs a bare ~free~.

Known consumers that RE-DERIVE parts of this contract instead of reading
it (the #302 inventory has the full list): builder.til's ~stack_locals~ /
~stack_local_types~ (its own copy of decision 4's stack-vs-heap
classification), ~is_noop_delete_stmt~, ~emit_as_ptr~'s ~_oa~ malloc-copy
wrap, ~delete_call_free_lit~; interpreter.til's delete-interception layer
(~delete_body_has_custom_logic~ + ~struct_deep_free~ family), manual arg-
temp and scope teardown (~free_temp_arg_value~, ~free_non_own_temp_args~,
deep ~scope_free~).

** The decision-audit dump (stage 0 tooling)

~TIL_GC_AUDIT=<path-substring>~ makes ~insert_free_calls~ print, for every
body whose unit path contains the substring, the pass's settled decisions
and the resulting destructor sites:

  : GC-AUDIT body <path>:<line>:<col> locals=<n>
  : GC-AUDIT local <name> type=<T> decl=<i> last_use=<i> own_transfer=<i> heap=<0|1> skip=<0|1>
  : GC-AUDIT site <stmt-path> delete <T>.delete(<arg>) call_free=<0|1> [own=1]
  : GC-AUDIT site <stmt-path> free(<arg>) [own=1]
  : GC-AUDIT site <stmt-path> closure-delete(<arg>)
  : GC-AUDIT site <stmt-path> return-attached <destructor>
  : GC-AUDIT site <stmt-path> assign-old-delete <name>
  : GC-AUDIT site <stmt-path> fieldassign-old-delete <name>

~<stmt-path>~ is a dotted statement path ("2.if0.1" = statement 1 of the
then-branch of the if at statement 2). ~local~ lines are the LocalInfo
table AFTER the analysis phases (so ~last_use~ includes borrow extensions,
~heap~ includes promotion); ~site~ lines are found by walking the body
AFTER insertion, so they include pre-existing user-written cleanup of the
same shapes -- the dump is a body snapshot, not an insertion log. Nested
if/while/block bodies appear twice: once from their own per-body run,
once inside the enclosing body's walk (which is where the enclosing
body's exit deletes land). Synthesized names (the ~hoisted__~ /
leading-underscore population) print with their digit runs replaced by a
per-body first-appearance ordinal (~hoisted__U64_#0~): the raw counters
are global across every previously typed unit, so printing them would
shift the whole golden on any unrelated core/std change.

The golden test ~gc_audit~ (src/tests.til) pins
~TIL_GC_AUDIT=test/gc_audit.til bin/til translate test/gc_audit.til~
against ~test/gc_audit.expected~, so every #302 stage shows its decision
diffs in review. Regeneration recipe in test/gc_audit.til's header. The
env read is ~std/sys~'s ~get_env~ ("" when unset); unset means disabled
and the pass does no extra work beyond one env read per body.

** The target contract (#302)

Where the rework is taking this interface -- see issue #302 for the full
design and staging:

  - One ownership dataflow on a real per-body CFG (states Uninit / Owned /
    Moved / Borrowed-from), replacing the three statement indexes and the
    path special cases (sinking, pre-transfer exit rules, taint machinery,
    borrow-lifetime extensions). The same dataflow reports the
    obviously-leaking shapes as compile errors: path-sensitive
    use-after-move (including transfer inside a loop), and the
    Dynamic-never-owns pair -- binding an allocator result to Dynamic
    is a type error (Dynamic is for type-erased borrows: to_ptr /
    ptr_add results, dyn features), while allocator-rooted TYPED
    locals (own U8 buffers, Vec.pop's `out : T = malloc(...)`) become
    ordinary garbager-owned values, freed automatically -- deleting
    the manual `free(own buf)` call class instead of policing it
    (#302's census, class d).
  - Decisions recorded once, explicitly: storage class on Declaration
    (builder's ~stack_locals~ re-derivation dies), full contracts on
    destructor statements (no-op deletes simply not inserted), explicit
    move markers instead of clone-elision rewrites, ~save_old_delete~ set
    only by the garbager.
  - Returns normalized to ~return <ident>~ with cleanup as ordinary
    preceding statements (decision 2 disappears).
  - The hoisting contract enforced: an owned temp the hoister missed is an
    ICE, not a silent leak.
  - Backends execute the recorded decisions; compensation code in
    builder.til and (via #286) interpreter.til is deleted stage by stage.

** Ownership-flow fact reuse

Forward ownership effects read the same name-indexed ~BodyFacts~ rows used
by local collection, rather than calling declaration, reassignment and
ownership-transfer subtree predicates separately for every binding. The
precedence remains declaration/reassignment -> Owned, then transfer -> Moved,
otherwise identity. The reassignment row follows ~expr_reassigns_var~ exactly,
including assignments inside nested FuncDefs; declaration and transfer rows
retain their existing function-body cuts and capture rules.

CFG queries share fact rows for the expressions actually evaluated by each
block. Ordinary root statements reuse their existing rows. A compound tail
uses only its condition or switch subject, and a bare Body tail has no effect;
branch bodies occupy their own blocks. Selected nested/head expressions are
collected once across all binding queries. The existing no-transfer and
straight-line fast paths remain in place.

Facts are refreshed after wrapper-free or non-transfer-path grafts, before
later ownership queries inspect the changed AST. This also keeps transfer rows
available after sinking, rather than rebuilding only the liveness rows.

On identical self-translation inputs, ~expr_transfers_own~ visits fell from
21,948,856 to 15,634 and struct lookups from 30,328,465 to 17,915,645. Generated
C and forward headers were byte-identical, as was ~test/gc_audit.expected~.
These are work counts, not an isolated elapsed-time comparison while other
sessions are running. ~test/ownership_shapes.til~ also covers an owned argument
consumed in an If condition and a reassignment whose RHS consumes a distinct
binding, with interpreted and ASAN-compiled execution.
