* UFCS

  UFCS is usually short for Uniform Function Call Syntax. Some D material
  expands it as Universal Function Call Syntax. The idea is the same: a call
  whose first argument is the receiver can be written with method-call syntax.

  In the usual examples, these are equivalent:

  #+begin_src til
  add(a, b)
  a.add(b)
  #+end_src

  This is useful when the returned value feeds the next call, because the code
  reads left-to-right:

  #+begin_src til
  a.add(b).add(c)
  #+end_src

** Til Shape

  Til has no methods in the OO sense: nothing is attached to an object. There
  is one rule -- ~recv.f(args)~ means ~f(recv, args)~ -- and it applies to
  every function whose first parameter fits the receiver, wherever that
  function is written.

  Two places count as "wherever":

  1. *Standalone top-level functions.* Ordinary functions, members of nothing.
     Dot syntax works on them:

     #+begin_src til
     join(parts, "-")          parts.join("-")          // the same call
     format("x", "y", "z")     "x".format("y", "z")
     #+end_src

  2. *Namespace members.* A ~struct~/~enum~ ~namespace:~ block groups
     functions under a type name. The namespace is a naming scope, not an
     object:

     #+begin_src til
     Str.substr(s, 1, 3)       s.substr(1, 3)
     File.write(f, "a")        f.write("a")
     #+end_src

  So the namespace decides how a function is NAMED and found; UFCS decides how
  a call may be SPELLED. Having both is what makes til's shape slightly
  unusual -- most languages offering this syntax pick one mechanism (see the
  comparison below).

  Practical consequence, and the main reason this file exists: *do not write a
  wrapper just to get dot syntax.* If a function already takes the value as
  its first parameter, ~x.f()~ already works. A forwarder like

  #+begin_src til
  // pointless: doc_blob_lookup(blob, name) already works, and so does
  // blob.doc_blob_lookup(name)
  __doc_lookup__ := func(blob: Str, name: Str) returns Str {
      return doc_blob_lookup(blob, name)
  }
  #+end_src

  is pure bloat: a second name for one operation, another entry in the docs
  and the REPL, one more thing to keep in sync. If the name is wrong, rename
  the function; do not add an alias. The same goes for a wrapper that renames
  a core operation for one use case -- ~Str.to_c_str~ returning ~self.clone()~
  was exactly this, and was removed.

  A wrapper earns its place when it DOES something: a different default, a
  check, an assembled argument (~File.fwrite~ is ~write(format(..parts))~), or
  a public API name over a raw C primitive (~File.remove~ over
  ~cfile_remove~).

** How other languages do it

  | Language                 | Mechanism                                                                                          |
  |--------------------------+----------------------------------------------------------------------------------------------------|
  | D                        | True UFCS: any free function callable as ~x.f(y)~. The feature this file's name comes from.         |
  | Nim                      | True UFCS both ways: ~f(x, y)~ and ~x.f(y)~ are interchangeable throughout.                         |
  | til                      | True UFCS over BOTH free functions and namespace members.                                          |
  | C++                      | No. "Unified call syntax" was proposed repeatedly (Sutter's P0251, Stroustrup's N4174) and dropped. |
  | Rust                     | No. ~x.f()~ needs an ~impl~; traits extend types, but a free ~fn~ never gets dot syntax.            |
  | Kotlin, C#, Swift        | Extension functions: dot syntax works, but only for functions DECLARED as extensions of that type.  |
  | Go                       | No. Methods must be declared on a type in the same package.                                        |
  | Python, Java             | No. Methods live in the class.                                                                     |
  | F#, Elixir, OCaml, Julia | No UFCS, but a pipe (~|>~, Clojure's ~->~ macro) buys the same left-to-right reading.               |

  The two clusters are worth keeping apart. D, Nim and til make the CALL SITE
  free: any function can be spelled either way and the function's author does
  nothing. Kotlin/C#/Swift extensions make the DECLARATION special: a function
  opts in, and only then does dot syntax work -- which is why "extension
  method" bloat is a real pattern there and a mistake here. Pipes solve only
  the chaining-readability half and leave call syntax alone.

  til's own twist is that its namespaces are not classes: ~Str.len(s)~ is a
  qualified free function, not a method on an object, so both spellings are
  the same call with the same resolution and neither is privileged.

** Builder Output

  ~File.write~ writes one string and returns ~ref File~, so chains like this
  work:

  #+begin_src til
  f.write("a").write(b).write("c")
  #+end_src

  Prefer ~fwrite~ when the pieces are plain strings:

  #+begin_src til
  f.fwrite("a", b, "c")
  #+end_src

  ~File.fwrite~ is just ~write(format(...))~ with the noisy wrapper removed.
  Do not force it across procedural emitters such as ~emit_expr~,
  ~emit_deref~, or ~emit_as_ptr~; those calls are output logic, not just string
  pieces.

  In short: use UFCS where it expresses a real pipeline, and use ~fwrite~ for
  adjacent string assembly.
