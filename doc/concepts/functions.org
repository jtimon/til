* Function kinds

til has three kinds of named callable, plus three specialized forms.
They sort along two axes: does the declaration carry a BODY, and does a
call EMIT AS A REAL CALL or get inlined.

| keyword               | body | compiled C          | interpreter          |
|-----------------------+------+---------------------+----------------------|
| ~func~ / ~proc~       | yes  | function + call     | runs the body        |
| ~ext_func~/~ext_proc~ | no   | call to src/c/ sym  | FFI call             |
| ~core_func~/~core_proc~ | no | inlined natively    | registered handler   |
| ~core_lazy_func~      | no   | inlined (lazy)      | lazy handler         |
| ~lazy_func~/~lazy_proc~ | yes | inlined, lazy args | lazy body eval       |
| ~macro~               | yes  | (gone by codegen)   | executed at comptime |
| ~test~                | yes  | test-runner entry   | runs the body        |

** func / proc

The ordinary kind: a body in til, compiled to a real C function and
called normally; the interpreter runs the body.

~proc~ declares an EFFECT THE SIGNATURE CANNOT SHOW: I/O, and anything
else that reaches outside the call. ~func~ declares the absence of one.
A func may still mutate through a ~mut~ parameter and consume an ~own~
one -- that is declared, right there in the signature, and it is not
what proc is for. ~Vec.push := func(mut self: Vec(T), own val: T)~ does
both and is a func; so is ~Str.push_str~, and so is ~memcpy~. Reading
those as procs would make ~new~, ~delete~, ~clone~ and every container
method a proc, and procs are not constfolded -- the classification
would cost exactly the code it exists to describe.

The roots are the ext_procs, and in core they are I/O and nothing else:
~print_single~, ~eprint_single~, ~print_flush~ (plus ~println~ / ~print~
/ the ~*_error~ procs, which call them). Everything else is a proc only
by CONTAGION, and the typer enforces that contagion both ways: a func
calling a proc is an error ("func cannot call proc"), and a proc that
calls none is an error ("proc has no proc/ext_proc calls; should be a
func"). So classifying the base ext declarations correctly is the whole
job -- the call graph propagates it from there.

Outside the debug-print exception below, two things follow. A pass may skip
evaluating a call only when it is a func AND takes no ~mut~ or ~own~
parameter: the typer guarantees no proc
effect hides inside a func, and the qualifiers say nothing is written
through a parameter. And a bodyless ext declaration owes the truth about
what it writes -- an FFI symbol that writes through a pointer declares
that pointer ~mut~, or the signature lies and every reader of it is
wrong.

~pura~ and ~liba~ make an explicit exception for ~print~ / ~println~ in
funcs. When the constfolder runs a func or macro, printing happens directly
as the body executes. It is not queued or conditional on replacing the call.
Output already printed remains visible even if evaluation later aborts or
cannot reconstruct a constant result. Other macro effects likewise execute
normally; constant evaluation does not roll them back.

This does not make proc calls foldable. The constfolder walks proc and test
definitions to optimize eligible expressions inside them, without executing
the enclosing proc or test at compile time.

** ext_func / ext_proc

No body (~{}~). The implementation is a hand-written C symbol in
src/c/ (ext.c and friends) with the C signature the til qualifiers
describe (see doc/concepts/qualifiers.org). The backend emits an ordinary call
to that symbol; the interpreter reaches it through libffi
(~ffi_register~ registers every ExtFunc/ExtProc it loads).

** core_func / core_proc

An ext_func OPTIMIZED TO BE INLINED: same shape (no body, qualifiers
describe a fixed C signature), but instead of expecting a linkable
symbol from ext.o, every backend (C today; any future codegen) lowers a
call to native code at the call site -- ~a + b~, ~!(a)~, ~(UPtr)p == 0~,
~((E*)a)->tag == ((E*)b)->tag~, pointer arithmetic. No call, no symbol.

core_func is THE inlining mechanism, and it is reserved for core
primitives (src/core). There is deliberately NO keyword for user code
to be inlined: inlining a func that has a body is an optimizer's job,
not a language surface. A core_func the backend does not recognize is a
hard error (~core_func backend lowering: unknown op~), not a fallback
call.

Current core ops:

- the scalar numeric ops on U8..U64, I8..I64, F32: ~add sub mul div
  mod eq neq lt gt lte gte band bor bxor bnot shl shr~ (the generic
  scalar lowering in builder.til, ~core_binop_to_c~)
- ~inc~ / ~dec~ on the integer types (the range-loop counter step every
  ~for x in a..b~ desugars to) -- the first MUTATING core ops
  (~mut self~): they lower to native pre-increment ~(++x)~ / ~(--x)~ in
  place, no call
- ~Bool.eq~ (same generic scalar lowering: native ~==~)
- ~not~ (native ~!~)
- ~is_n~ (width-aware enum-tag compare, ~((E*)a)->tag == ((E*)b)->tag~)
- the auto-generated enum ~is~ method (initer generates it per enum as a
  bodyless core_func; same typed tag-compare lowering as is_n, and the
  interpreter dispatches it by its flat "<Enum>_is" name via
  ~enum_core_is_eval~ -- per-enum names cannot be reg_dispatch'd
  statically)
- ~is_null~ (native null test, ~(UPtr)p == 0~)
- ~ptr_add~ (native pointer arithmetic, ~(void*)((U8*)buf + off)~)

The interpreter cannot FFI a core_func (there is no registered symbol
contract) and has no body to run, so each core op has a native
evaluation path: the scalar ops go through ~scalar_core_op_eval~
(parses the flat ~U32_eq~-style dispatch name) -- including inc/dec,
whose arms step the receiver's scope cell in place via
~scalar_step_cell~ (a mutating op writes its result back into the
variable's cell instead of returning it) -- the rest through
registered ~reg_dispatch~ handlers (~h_Bool_eq~, ~h_Bool_not~,
~h_is_n~, ~h_is_null~, ~h_ptr_add~, ~h_get_payload~). Handlers extract C-level arg
pointers with ~value_c_arg_ptr~, which mirrors the FFI marshalling, so
interp and compile modes agree.

Bootstrap note: src/c/ may KEEP a symbol for an op that becomes a
core_func -- transiently. That is what lets the conversion land as a
single "Two-pass: " commit: pass-1 til_boot predates the inline and
emits real calls, which link against the kept symbol; pass 2 inlines
them. Once the conversion is in master nothing emits the call anymore
and the dead symbol is dropped one commit later (~Bool_eq~, ~not~,
~is_n~, ~ptr_add~ and ~get_payload~ are all gone now) -- the lag is structural: the
commit that makes a symbol unnecessary is itself compiled by a
til_boot that still emits calls to it. When there is no
symbol to keep AND comptime code exercises the op under pass-1's
interpreter (inc/dec: the old symbols were generated from the very
func bodies the flip deletes, and every comptime range loop steps a
counter), the conversion instead needs its lowering and its interp arm
landed as dormant preparation commits first. See doc/self.org.

** lazy_func / lazy_proc

A body, but calls are inlined WITH LAZY ARGUMENT EVALUATION: an
argument expression is only evaluated where the body actually uses it.
This is how ~and~ / ~or~ short-circuit without being language builtins.

** core_lazy_func

A bodyless lazy core primitive -- core_func's discipline (no body, no
symbol, never indirected, reserved for the core) plus lazy_func's
call-by-name arguments. Its expansion is compiler-known (there is
nothing to splice a body from): the loader replaces parse-time calls
with the hardcoded short-circuit ~match~ (arms are statement contexts,
so complex second operands keep full ownership/cleanup lowering), the C
backend lowers residual calls (the desugarer's post-typer synthesized
chains) to the natively short-circuiting ~&&~ / ~||~, and the
interpreter's handlers evaluate the second operand only when the first
does not decide the result. ~and~ / ~or~ (the ~&&~ / ~||~ operators'
canonical forms) are the only core lazy ops; an unknown one is a hard
error in both the loader and the backend. Variadic ~vand~ / ~vor~ stay
ordinary lazy_funcs -- their unrolling derives from their loop bodies.

** macro

A body that is EXECUTED AT COMPILE TIME (not expanded): the call site
is replaced by the AST node the macro returns. By codegen time no
macro calls remain. A macro returning ~FuncDef~ generates functions;
see "Function generators" below.

** test

A named test block; ~make test~ collects and runs them in both interp
and compile modes.

* Function types

A bodyless ~func~ declaration names a function TYPE (a FuncSig):

#+begin_src til
IntOp := func(I64) returns I64
VecLen := func(Vec(I64)) returns USize

apply := func(f: IntOp, x: I64) returns I64 { return f(x) }
inc := func(x: I64) returns I64 { return x + 1 }

apply(inc, 1)                    // 2
#+end_src

Its params are bare types (no names); parametric types such as
~Vec(I64)~ are allowed there like anywhere else a type is expected. A
param can also spell the type inline with ~Fn~:

#+begin_src til
twice := func(f: Fn(I64) returns I64, x: I64) returns I64 { return f(f(x)) }
#+end_src

* Interface method contracts

An interface declares required methods with bodyless ~func~/~proc~ signatures:

#+begin_src til
Drawable := interface {
    draw := func(self: Drawable) returns Str
    label := func(_self: Drawable) returns Str { return "shape" }
    describe := func(self: Drawable) returns Str { return self.draw() }
}
#+end_src

~draw~ is a requirement; ~label~ and ~describe~ supply defaults. A body,
even an empty ~{}~, makes an ordinary ~func~/~proc~ a default. The legacy
~ext_func(...) returns T {}~ / ~ext_proc(...) {}~ spellings remain supported
as requirements.

A struct or enum must implement every requirement with a matching signature,
including ownership, mutability, effects and throws. A compatible default
from another implemented interface can satisfy a requirement; two interfaces
requiring the same method do not create a default conflict. The rules apply
to both boxed dynamic calls and bounded generic calls. Interfaces cannot
declare ~clone~ or ~delete~: those belong to the generated box lifecycle.

Outside an interface, a bodyless function signature remains a function type.

* Generic functions

A ~Type~ parameter that the rest of the signature uses as a type makes a
function generic:

#+begin_src til
first := func(T: Type, v: Vec(T)) returns T { return v.get(0)!.clone() }
gid := func<T>(x: T) returns T { return x }
#+end_src

~func<T>(...)~ is sugar for a function generator (below) taking ~T: Type~.
Each distinct set of type arguments compiles to one concrete function
(~gid__I64~), shared across modules.

The type arguments can be passed explicitly, ~gid(I64, 1)~, or omitted
and inferred:

  - from an argument whose param type IS the parameter: ~gid(x)~ with
    ~x: I64~. Untyped numeric literals default to ~I64~ (~F64~ if any is
    fractional);
  - from the destination's declared type: ~y : U8 = gid(3)~;
  - from inside another type, by lining up the instance names: a
    ~Vec(I64)~ argument for ~v: Vec(T)~ gives ~T = I64~;
  - from a function argument's signature, when the param is a function
    type built by a generator (below): a function returning ~U64~ passed
    for ~f: FnOf(G)~ gives ~G = U64~.

When nothing fixes a parameter (it only appears in the return type and
the destination is undeclared, or only ~Dynamic~ / ~null~ arguments
mention it), the call is an error that says which way out applies:
pass the type explicitly or declare the destination.

** Bounded type parameters (#434)

~T: Type implements A, B~ restricts a type parameter to structs and enums
that implement every listed interface. The check runs at the call site,
once per instantiation, and names the missing interface. Inside the
copy, ~d.draw()~ on a ~d: T~ is an ordinary static call on the concrete
type -- no box, no runtime dispatch -- and the interface's concrete
defaults (copied into the implementer) are honoured exactly as when
called on the concrete directly.

#+begin_src til
static_draw := func(T: Type implements Drawable, d: T) returns Str {
    return format(d.label(), ":", d.draw())
}
static_draw(Circle(r = 1))        // static_draw__Circle  -> Circle.draw
static_draw(Polygon.Tri)          // static_draw__Polygon -> Polygon.draw
static_draw(Circle, c)            // explicit type argument works too

render := func(d: Drawable) returns Str { return d.draw() }   // dynamic: one copy
#+end_src

The two forms coexist and the user picks per function: ~d: Drawable~ is
the DYNAMIC form (one copy, dispatch on the box's type tag, the only way
to keep mixed concretes in one collection; see doc/concepts/ownership.org
"Interface-typed locals"); the bound is the STATIC form (one copy per
concrete type, direct calls, more generated code), like Rust's ~impl
Trait~ against ~dyn Trait~. The interface's own boxed value satisfies its
bound, so a ~view: Drawable~ can be passed to the static form; that copy
dispatches on the box. A struct or enum may implement several interfaces
(~Badge := struct implements Drawable, Named~): each is checked in full,
each one's defaults are copied in, and a default that two of them provide
is copied from neither -- the implementer must override it. A
two-interface bound is satisfied by such a type (the dynamic box, by
contrast, is always of ONE interface). The bound belongs on a parameter the signature uses as a type;
on a runtime ~Type~ value it is an error. The ~func<T>~ sugar does not
take bounds (a bound list and the next ~<T, U>~ parameter would be
ambiguous there); spell the parameter out.

* Function generators

A macro returning ~FuncDef~ runs at compile time and produces a
function. Its params may be values, baked into the generated body, or
types:

#+begin_src til
make_adder := macro(N: I64) returns FuncDef {
    return func(x: I64) returns I64 { return x + N }
}
add5 := make_adder(5)            // add5(1) == 6

make_vec_len := macro(T: Type) returns FuncDef {
    return func(v: Vec(T)) returns USize { return v.len() }
}
make_vec_len(I64)(v)             // inline instantiation
#+end_src

A generator may also return a bodyless ~func~, i.e. build a function
TYPE from type arguments. Generic functions can take such a type
applied to their own parameter:

#+begin_src til
FnOf := macro(H: Type) returns FuncDef {
    return func(Dynamic, USize) returns H
}
apply_bytes := func(G: Type, s: Str, f: FnOf(G)) returns G { return f(s.c_str, s.count) }
count_bytes := func(_data: Dynamic, n: USize) returns U64 { return n.to_u64() }

apply_bytes("abcd", count_bytes) // G inferred as U64 from count_bytes
#+end_src

** Conditional definitions

A generator can choose its returned definition with ~if~ / ~else if~ /
~else~. Selection happens during initialization, after argument substitution
and before typing the generated body; it does not leave a runtime branch.
Alongside ~T.is(Type.Primitive(...))~ tests, conditions use ordinary typed
expressions evaluated by the shared compile-time interpreter. Dependencies
are prepared on demand, including aggregate size methods and user-defined
functions, their helpers, loops, and immutable file-level and namespace
constants. Constant initializers use the same evaluator in dependency order,
including references to later namespace members and through type aliases.
Combine conditions with ~or~ / ~and~, in method or plain-call form. ~||~ /
~&&~ are sugar for these operations and retain their left-to-right
short-circuit behavior: an operand skipped by ~or~ or ~and~ is not evaluated.

#+begin_src til
make_width_check := macro(T: Type, limit: U64) returns FuncDef {
    if T.size() <= limit {
        return func() returns Bool { return true }
    } else {
        return func() returns Bool { return false }
    }
}
fits_word := make_width_check(USize, 4)
#+end_src

These size conditions describe the compilation TARGET. ~USize~, ~UPtr~ and
type aliases resolve through the target type scope, including
~--usize~ overrides. Ordinary interpreter storage-size queries remain
host-sized; they are not used to make this decision. Two size queries can
also be compared directly, for example ~USize.size() <= UPtr.size()~.

Generated struct and enum size methods describe target layout too;
user-defined ~size~ methods execute their ordinary bodies. Interpreter
storage remains host-sized. Layout-dependent raw-memory calls are rejected
when their size dependencies differ between host and target storage.
Unavailable runtime values and calls that cannot be evaluated produce an
expansion error, not a false condition. The same selection rules apply to
generators returning ~StructDef~ or ~EnumDef~.

Known gap: an alias of a generated function (~add5~ above) can be
called but not yet used as a function VALUE (#425); the inline form
(~f : IntOp = make_adder(5)~) works.

* Inlining the compiler does on its own

Two backend optimizations inline calls to ordinary funcs. They are not
keywords and not name-lists a user can extend; they key on properties
of the callee:

- Accessor inline (#300): a method named ~len~ / ~unsafe_get~ whose
  callee is a plain func with a single ~return EXPR~ body is spliced
  inline (param-substituted) at the call site, for any type. ~for x in
  c~ desugars to ~c.len()~ / ~c.unsafe_get(i)~ per iteration, so these
  accessors must not cost a call.
- Primitive clone fold: a ~clone~ call whose result is a value
  primitive emits as the value itself. The ownership pass inserts
  ~.clone()~ nodes on value-copy assignments (loop indices,
  capacities, line/col fields); they must stay in the AST for
  ownership/liveness analysis, so the fold happens at emit time. Calls
  through a pointer (an ~own U8~ heap-buffer field) and the reflective
  dispatch path keep the real ~<Prim>_clone~ call.
