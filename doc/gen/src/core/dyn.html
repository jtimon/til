    dyn_call

    Group
    Core

    Dispatch <type_name>.<method> at runtime, by name.

    DECLARED ext_func, BUT THE CONTRACT IS THE CALLER'S. Which method this runs is a Str decided at runtime, so the declaration cannot say what the call does -- the same dispatcher reaches a pure accessor and an I/O proc. ext_func here means only "the runtime cannot know", not "this has no effect".

    So the caller carries it. A func that dispatches a PROC through these must call noop_proc() in its own body: that is what makes it a proc, and from there the typer propagates proc-ness the ordinary way (a func calling a proc is an error; see doc/concepts/functions.org). Dispatch a func and there is nothing to do.

    Mutation is the other half and travels separately, as mut does everywhere: dyn_call(tn, "delete", 2, ptr, false) writes through ptr. That one is not expressible here either -- the same parameter is written by a "delete" and only read by a "clone".

    ext_func (type_name: Str, method: Str, arity: I64, a: Dynamic, b: Dynamic)

    dyn_call_ret

    Group
    Core

    Same contract as dyn_call, for a method that returns a value: the caller says noop_proc() when what it dispatches is a proc. This is the general interface-dispatch path (~dyn_call_ret(iface_type_name, "method", arity, iface_val, ...)~), so it reaches any user method.
