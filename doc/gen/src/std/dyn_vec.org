* DynVec.move_from
:PROPERTIES:
:CUSTOM_ID: til.src.std.dyn_vec.DynVec.move_from
:group: Standard library
:END:

Replace self's contents with other's via memcpy (no per-elem clone).
Avoids the Vec_clone + extra Vec_delete that plain ~self = other~ emits.
Takes ~mut~ (not ~own~) so caller retains ownership of other; its
natural scope-end auto-delete frees other.data. Setting other.count = 0
prevents that auto-delete from re-running elem_delete on items whose
bytes were moved into self.

#+begin_src til
func DynVec.move_from(mut self: DynVec, mut other: DynVec)
#+end_src

:END:

Give self's contents to ~dest~, which drops whatever it held.
Vec.move_to's counterpart, and the argument-flipped spelling of
~dest.move_from(self)~. Both sides are ~mut~ here rather than one
of them ~own~, because the values these moves exist for are struct
FIELDS, and a field cannot be an owned argument or receiver.

* DynVec.take
:PROPERTIES:
:CUSTOM_ID: til.src.std.dyn_vec.DynVec.take
:group: Standard library
:END:

Take the contents out: the returned DynVec holds self's elements
and self is left empty. Vec.take hands its BUFFER over and blanks
itself; a DynVec cannot, because elem_size/elem_kind/elem_clone/
elem_delete are runtime values rather than type parameters, and a
blanked DynVec would no longer know how to grow or free itself.
The elements move as bytes into a fresh buffer instead -- which is
take_prefix of the whole vec.

#+begin_src til
func DynVec.take(mut self: DynVec) returns DynVec
#+end_src
