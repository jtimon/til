    Group
    Compiler backend

    Create an empty Set. T must implement cmp. Allocates nothing: like Vec.new, an empty Set is lazy (cap 0) and add seeds the first slot. Short-lived empty Sets are common -- the garbager builds four per statement for its per-statement name facts, most of them never added to.

    Set__USize.with_capacity

    Group

    Create an empty Set pre-sized for n elements, so adding up to n reallocs zero times (Vec.with_capacity's counterpart). Use it where the final size is known or well predicted; new() grows 0->1->2->4, which is the right default but costs a realloc per doubling. n=0 behaves like new(): lazy-empty, no allocation.

    Vec__priv___src_self_c_codegen_til__CollectionInfo.take

    Group
    Compiler backend

    Take the contents out: the returned Vec owns self's buffer and self is left lazy-empty. No element is copied or cloned.

    This is how a struct FIELD hands its contents over (mut old := body.children.take()): a field cannot be an own argument or receiver, because the callee would then free the ADDRESS OF THE FIELD -- the compiler dies with "free(): invalid pointer" compiling itself. Everything the caller can give away uses the two move forms below instead.

    Vec__priv___src_self_c_codegen_til__CollectionInfo.move_to

    Group
    Compiler backend

    Give self's contents to dest, which drops whatever it held. SELF is consumed, so the receiver is the owned one and the call spells the type out: Vec(T).move_to(own src, dest).

    The three fields move as BYTES on purpose: dest.data = self.data drops dest's old pointer (right) and then self.data = 0 drops the pointer dest just adopted -- a double free, which is what the emitted C does with field assignment. Blanking the source leaves a genuinely valid lazy-empty Vec, so a later push on it allocates afresh instead of reallocating a buffer that now belongs to someone else.
